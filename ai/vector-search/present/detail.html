Detail — the deep dive

◑ ~12 min read ✎ What · Where · When · How · Why

What it is

Given a set X of N vectors in ℝd, a dissimilarity function δ, a query vector q, and an integer k:

  • k-nearest-neighbour (k-NN) search returns the k points of X with the smallest δ(q, x). A flat scan solves it exactly in O(N·d) per query.
  • Approximate nearest-neighbour (ANN) search returns a set S of size k. It is judged by recall@k = |S ∩ true top-k| / k, under a latency and memory budget.
  • Graph and partition indexes give no worst-case recall guarantee.
  • Only LSH offers a probabilistic (1+ε)-approximation bound, and it pays for that bound in memory.

How the three metrics relate

  • On unit-normalized vectors, ‖q − x‖² = 2 − 2·(q·x). So L2, cosine, and inner product produce the same ranking.
  • On unnormalized vectors, inner product is not a metric: it breaks the triangle inequality.
  • Ranking by it is called maximum inner product search (MIPS) find the stored vectors with the largest dot product with q. Some indexes need a transform or special handling to support it.

On this page, "vector search" means an ANN index plus the query execution around it: metric, filters, top-k merge, and optional re-ranking.

The core building blocks

Vectors + a metric
Dense float vectors, usually 384–3072 dimensions, from an embedding model. The metric must match the one the model was trained with.
Partition indexes (IVF family)
k-means splits the space into nlist cells; a query scans only the nprobe nearest cells. SPANN and SPFresh are disk- and update-oriented variants.
Graph indexes
Each vector is a node linked to nearby nodes; a query walks the graph greedily. HNSW (Malkov & Yashunin), Vamana/DiskANN, NVIDIA's GPU-built CAGRA.
Hash and tree indexes
LSH and random-projection trees such as Spotify's Annoy. Largely displaced by graphs at high recall.
Quantization
Compresses stored vectors. int8 scalar = 4× smaller than float32. PQ = typically 16–64× smaller. Binary (1 bit per dim, e.g. RaBitQ, Elastic's BBQ) = 32× smaller.
Re-ranking (refinement)
Over-fetch candidates using compressed vectors, then re-score them with full-precision vectors to win back recall.
Filter integration
Pre-filter, post-filter, or filter-aware traversal. Decides whether WHERE tenant_id = 42 still returns k rows.
Query-time knobs
ef_search for graphs, nprobe/probes for IVF. They move each query along the recall/latency curve.
Evaluation setup
Brute-force ground truth on a query sample plus recall@k. ANN-Benchmarks is the public reference.

Its neighbours

  • Vector search is the dense, high-dimensional branch of similarity search.
  • Lexical retrieval is its closest sibling: BM25 over an inverted index, matching exact terms in sparse, very high-dimensional space.
  • Learned sparse retrieval (SPLADE) sits in between: model-produced weights stored in an inverted index.
  • Spatial indexes (R-trees, kd-trees) solve the same problem well in 2–10 dimensions (geo, CAD) and collapse beyond that.

Where it lives

It runs in the retrieval layer of the data tier, on the hot path of every semantic query. The app embeds the query by calling a model, sends the vector to the index, and gets back IDs, scores, and payloads. Four deployment shapes:

1 · In-process library

FAISS, hnswlib, USearch. Your service owns the index's memory, persistence, and replication.

2 · Feature of a general DB

pgvector, Lucene-based Elasticsearch/OpenSearch, MongoDB Atlas, SQL Server 2025. Vectors live next to relational or document data.

3 · Dedicated vector DB

Milvus, Qdrant, Weaviate, Pinecone. Sharding, filtering, and hybrid search are built in.

4 · Object-storage-native

turbopuffer, LanceDB, Amazon S3 Vectors. Data lives in S3-class storage with an NVMe/RAM cache in front.

Where you typically meet it

  • The retrieval step of RAG systems and coding assistants that search a codebase or document corpus.
  • Candidate generation in recommenders: a two-tower model embeds users and items, ANN fetches the top few hundred items, then a heavier ranker scores them.
  • E-commerce "similar products" and visual search.
  • Near-duplicate detection for images, support tickets, or scraped pages.
  • Hybrid site search in Elasticsearch/OpenSearch, where kNN results are fused with BM25.

When it emerged

  1. 1975–1998 · Trees hit the dimensionality wall. kd-trees work well in low dimensions. Weber, Schek & Blott (VLDB 1998) showed tree and partitioning methods lose to a sequential scan above roughly 10 dimensions. That pushed the field toward approximation.
  2. 1998 · LSH. Indyk & Motwani introduced locality-sensitive hashing, the first sublinear approximate scheme with guarantees. High recall needed many hash tables, so memory grew fast.
  3. 2011 · Product quantization. Jégou, Douze & Schmid (TPAMI) compressed vectors to a few bytes each and computed distances through lookup tables. IVFADC (IVF + PQ) made billion-scale search fit in RAM.
  4. 2014–2016 · Navigable small-world graphs. NSW, then HNSW (arXiv 2016, TPAMI 2018), gave logarithmic-scaling search with high recall. HNSW became the default in-memory index.
  5. 2017–2020 · Industrial libraries. FAISS open-sourced in 2017. DiskANN (NeurIPS 2019) served 1B SIFT vectors from a 64 GB RAM machine plus an SSD at >5,000 QPS, <3 ms mean latency, and 95%+ 1-recall@1. ScaNN followed in 2020.
  6. 2023 onward · The LLM wave. RAG turned ANN from a recommender/IR specialty into general app infrastructure. pgvector added HNSW in 0.5.0 (August 2023).

When to use it

✓ Reach for it when

  • Queries describe intent in natural language or by example ("like this image"), and exact-term matching misses relevant results.
  • The corpus is big enough that a flat scan breaks your latency budget.
  • A recall of about 0.95 is fine, because a downstream step (an LLM, a reranker, or a human) tolerates a few misses.
  • You already embed content for other reasons, so an index costs little extra.

✕ Skip it when

  • The corpus has fewer than about 10⁴–10⁵ vectors. A flat scan is exact, simple, and fast enough; an index adds build cost and tuning for no gain.
  • Lookups are exact: IDs, SKUs, error codes, emails. Use B-tree or inverted indexes.
  • Recall must be complete and auditable (e-discovery, compliance holds).
  • Structured predicates already narrow the set to a few thousand rows. Filter first, then rank exactly.
  • The team can't run an embedding pipeline. Re-embedding on every model change is a real operational cost.
◆

Rule of thumb

A flat scan of 1M × 768-dim float32 vectors touches about 3 GB per query. If that blows your latency budget, you need an index.

How it works

HNSW: build and query

  1. Level assignment. Each new vector draws a top layer from an exponentially decaying distribution, with normalization factor mL = 1/ln(M). Most nodes live only on layer 0. The result is a probabilistic skip list over a proximity graph.
  2. Insert. From the global entry point, greedily descend the layers above the node's top layer. On each layer from there down, run a beam search a search that keeps the best N candidates at each step instead of only the single best of width ef_construction. Then pick up to M neighbours (2·M on layer 0) with a diversity rule: drop a candidate if it is closer to an already-chosen neighbour than to the new node. This keeps long-range edges and prevents isolated clusters.
  3. Query. Greedy descent with beam width 1 through the upper layers. On layer 0, run a best-first search that keeps the ef_search best candidates. Stop when the nearest unexplored candidate is farther than the worst kept result. Return the top k.
  4. Cost. Search cost grows roughly as log N × node degree. Memory = raw vectors + about 2·M × 4 bytes of neighbour IDs per node. For 1M × 1536-dim float32: about 6.1 GB of vectors vs about 0.13 GB of graph at M=16. Vectors dominate, which is why quantization matters more than M.

IVF (and IVF-PQ): build and query

  1. Train. Run k-means on a representative sample to get nlist centroids. pgvector recommends lists = rows/1000 up to 1M rows and sqrt(rows) beyond.
  2. Assign. Put each vector in its nearest centroid's inverted list.
  3. Optional PQ. Split each residual vector into m sub-vectors and quantize each to one of 256 sub-centroids, so each vector costs m bytes. Example: 1536 dims with m=192 gives 192 bytes vs 6,144 bytes as float32.
  4. Query. Compute distances to all centroids and pick the nprobe nearest. For PQ, precompute an m × 256 distance lookup table per query ( asymmetric distance computation the query stays full precision; only stored vectors are compressed, so distances come from table lookups). Scan the chosen lists via table lookups, keep a top-k heap, and optionally re-rank with full vectors.

Filtering strategies

Post-filter

Run ANN, then drop non-matching rows. With a selective filter, this returns fewer than k rows.

Pre-filter

Compute the matching set first, then scan it exactly. Ideal when the filter is selective; cost grows with the size of the matching set.

Filter-aware traversal

The graph walk skips or bridges non-matching nodes. Qdrant adds per-payload-value edges ("filterable HNSW") and a cardinality-based query planner. ACORN (SIGMOD 2024) expands neighbour lists so predicate subgraphs stay navigable; Weaviate added it in v1.27 and made it the default in v1.34.

Iterative scan

pgvector 0.8.0 (October 2024) keeps fetching from the index until k rows pass the filter, capped by hnsw.max_scan_tuples (default 20,000).

Common failure modes

✕

A filtered query returns 3 rows instead of 10

Cause: post-filtering an ef_search=40 candidate list. A 10%-selective filter leaves about 4 matches.

⚠

Recall quietly drops weeks after launch

Cause: update/delete churn leaves tombstones deleted entries that are only marked dead, not removed from the graph and unreachable nodes in the graph. The index needs periodic rebuilds.

⚠

IVF recall falls after a data shift

Cause: centroids were trained on old or tiny data, so the lists become unbalanced. pgvector warns to build IVFFlat only after the table has data.

✕

The Postgres index is never used

Cause: the query operator doesn't match the opclass the operator class an index was built for, which fixes which distance operator it can serve (for example <-> against vector_cosine_ops), or the planner costs a high ef_search above a sequential scan.

✕

p99 jumps from milliseconds to hundreds of milliseconds

Cause: the HNSW index outgrew RAM, so every hop became a page fault.

✕

Scores look reasonable but results are garbage

Cause: vectors from two embedding models, or two model versions, were mixed in one index. Their spaces are not comparable.

⚠

Ranking is subtly wrong

Cause: the metric doesn't match the model's training (L2 on unnormalized vectors from a dot-product model).

⚠

Searches for "ERR_4012" or a SKU miss

Cause: dense embeddings blur rare exact tokens. Add BM25 and fuse the results with RRF (k=60 by convention, per Cormack et al. 2009).

⚠

A fixed similarity threshold behaves inconsistently

Cause: cosine scores are not calibrated across queries or models.

Why it exists

  • Exact nearest-neighbour search in high dimensions has no known algorithm that is both sublinear and free of exponential dependence on d.
  • At N = 10⁸ and d = 1024, a flat scan reads hundreds of gigabytes per query. That is a memory-bandwidth problem no CPU solves at interactive QPS.
  • ANN trades a measured, tunable amount of correctness (recall) for orders of magnitude less data touched per query.
  • It works because real embeddings have a much lower intrinsic dimension the number of directions the data really varies along, versus the nominal d than their nominal d. Locality survives in a navigable structure even where trees fail.

Why it looks the way it does

Why graphs beat LSH and trees
LSH gives guarantees but needs many hash tables for high recall, which multiplies memory. Trees degrade toward a scan above about 10 dimensions. Graphs adapt to the data's intrinsic dimension and reach 0.95+ recall while visiting a tiny fraction of nodes.
Why HNSW has layers
A flat NSW graph mixes long and short links, so searches waste hops and complexity scales polylogarithmically. HNSW separates links by length scale, like a skip list: coarse layers cover distance fast, layer 0 refines. That gives log-scaling hop counts.
Why DiskANN goes back to one flat layer
On SSD each hop is a random 4 KB read, so hop count matters more than CPU. Vamana's α-pruning keeps long edges in a single graph to cut hops. Compressed PQ codes stay in RAM to steer the search; full vectors come from disk only for re-ranking.
Why object-storage engines use IVF-style partitions
A graph walk on S3 would cost one ~100 ms round trip per hop. Centroid indexes need about 3–4 round trips total, and a partition is a natural unit for batch writes. turbopuffer reports about 400–500 ms cold and about 16 ms p50 warm.

Why it matters now

As of 2026, vector search is turning into a feature of existing databases rather than a product category of its own:

  • pgvector is the default answer in Postgres shops.
  • SQL Server 2025 ships a VECTOR type.
  • Elasticsearch 9.1+ quantizes by default with bbq_hnsw.
  • Amazon S3 Vectors went GA on 2 December 2025: up to 2 billion vectors per index, sub-second infrequent queries, about 100 ms for frequent ones.

The open problems have moved from "which index" to four narrower areas:

  • Filtered recall (ACORN-style traversal).
  • Aggressive quantization with re-ranking (RaBitQ, BBQ).
  • Tiered RAM/SSD/object storage for cost.
  • GPU index builds. cuVS CAGRA builds up to about 12× faster than CPU HNSW in Meta's FAISS benchmarks.

The core is stable. Storage tiering and filtering are where it is still changing.
