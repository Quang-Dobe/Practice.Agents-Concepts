Detail — the deep dive

◑ ~10 min read ✎ What · Where · When · How · Why

What it is

Precisely: an embedding is a learned function that maps an input — a token, a sentence, an image patch, an audio clip — to a dense vector, such that a distance measure between two vectors tracks how related the two inputs actually are. A neural network's weights are trained until the shape of the output space encodes meaning.

  • Core idea. Similar inputs land near each other; unrelated inputs land far apart. That's the one mechanism everything else hangs off.
  • Not portable. Two embeddings from different models live in different spaces and cannot be compared — even at the same dimension. The space is defined by how the model was trained, not by how long the vector is.
  • Family. Embeddings are the dense end of a spectrum that also holds sparse representations (one-hot, TF-IDF, BM25) and structured ones (knowledge-graph entities).

The building blocks, named once each:

Encoder
The network that produces the vector — almost always a transformer for text.
Pooling head
Turns a sequence of token vectors into one fixed-length vector — [CLS], mean-pool, last-token, or attention-weighted.
Projection & normalization
A final linear layer plus L2 normalization, so the vector lands on the unit hypersphere. Most modern text embeddings ship pre-normalized.
Vector space
Typically 384, 768, 1024, 1536, or 3072 numbers wide. More width buys more capacity, more storage, and a slower similarity check.
Similarity metric
Cosine, dot product, or Euclidean distance. On normalized vectors, all three rank results in the same order.
Loss / training signal
Contrastive (InfoNCE), triplet, or masked-language-modeling objectives.

Inside the embedding family, the axes that separate one model from another: static vs. contextual, single-vector vs. multi-vector (ColBERT), text-only vs. multimodal (CLIP, SigLIP, Gemini Embedding 2), and fixed-dimension vs. Matryoshka-truncatable.

Where it lives

Embedding generation is a model call — local GPU/CPU inference or a hosted API. The resulting vectors live in a storage layer built for nearest-neighbor search. Query-time similarity search runs inside that storage layer; a RAG pipeline, a classifier, or a prompt builder sits on top.

Inference layer

OpenAI, Cohere, Voyage, Google, or a self-hosted model turns text into vectors.

Storage layer

Pinecone, Qdrant, Weaviate, Milvus, pgvector, SQL Server's vector type, OpenSearch k-NN, Elasticsearch dense_vector.

Consumer layer

RAG pipelines, classifiers, recommenders, and dedup jobs read the search results.

Where you'll actually run into it:

  • RAG pipelines: chunk → embed → store → retrieve → prompt an LLM.
  • Semantic search: product catalogs, support knowledge bases, code search (Copilot, Sourcegraph).
  • Recommendations: two-tower / dual-encoder models at YouTube, Spotify, Pinterest.
  • Clustering & deduplication: feedback grouping, near-duplicate document detection.
  • Anomaly detection: flag records that sit far from any cluster center.
  • Multimodal retrieval: CLIP / SigLIP for "find images matching this caption."

Ecosystem, at a glance: hosted models include OpenAI text-embedding-3, Cohere embed-v4, Voyage voyage-3-large, Google gemini-embedding-001. Open-weight models include bge-*, nomic-embed-text-v1.5, nv-embed-v2, Qwen3-Embedding-8B, e5-mistral-7b-instruct. MTEB (Massive Text Embedding Benchmark) is the de-facto leaderboard; BEIR covers retrieval only.

When it emerged

  1. 2003. Bengio's neural language model produces the first dense word vectors, as a side effect of predicting the next word.
  2. 2013. word2vec (Mikolov) makes dense word vectors cheap to train, and gives the famous king - man + woman ≈ queen analogy.
  3. 2014. GloVe factors a global co-occurrence matrix instead of predicting from a local window.
  4. 2018. ELMo, then BERT, bring contextual embeddings — the vector for "bank" now depends on the sentence around it.
  5. 2019. Sentence-BERT adds a siamese training scheme so the pooled vector actually works for sentence similarity. Raw BERT vectors were notoriously bad at this before.
  6. 2020. DPR (Dense Passage Retrieval) sets the contrastive + in-batch-negatives + hard-negatives recipe every modern dense retriever still uses.
  7. 2022–2024. OpenAI ships text-embedding-ada-002, then text-embedding-3-* with Matryoshka Representation Learning.
  8. 2025–2026. Open-weight models (NV-Embed-v2 at 72.31 on MTEB, Qwen3-Embedding) catch and overtake closed APIs; multimodal embeddings go mainstream.

When to use it — and when not

◆

Rule of thumb

Reach for embeddings when the signal is semantic (paraphrase, synonym, cross-language) rather than lexical, when you're past a few thousand items, when you need one shared space across modalities or languages, or when you're clustering / deduplicating / classifying by nearest example. Skip them for exact-match or boolean filters, corpora dominated by rare entity names (BM25 still wins there), decisions that need an audit trail, or data that mutates faster than re-embedding pays for.

How it works

Four stages, from training a model to answering one query:

  1. Train. Modern text embedders are trained as dual encoders — also called a bi-encoder two independent encoder passes, one for the query and one for the document, compared only at the end — with a contrastive push matching pairs together, push everything else in the batch apart objective called InfoNCE. For a batch of N query/document pairs, every off-diagonal pair is a free "in-batch negative"; hard negatives (near-misses mined by BM25 or a weaker retriever) and large batches (1024–32768 pairs) sharpen the signal further.
  2. Infer. Tokenize → run through the transformer → pool the token states into one vector → L2-normalize → return. A sentence-BERT-class model does a few thousand sentences per second on a modern GPU; a 7B-parameter embedder like e5-mistral drops to tens per second per GPU.
  3. Store & index. Vectors go into an ANN index — HNSW or IVF.
  4. Search. For normalized vectors, cosine similarity is just a dot product — one multiply-add per dimension, vectorized on SIMD or GPU.

HNSW answers in roughly 1–10 ms per query at billion scale, but the whole graph has to fit in RAM — 1–4 KB per vector at full precision. IVF runs 5–50 ms, uses 16–64x less memory, and plays nicer with pre-filters; it's often paired with Product Quantization (PQ) to compress vectors 8–32x for a modest recall loss.

The standard production pattern is bi-encoder retrieval + cross-encoder rerank on the top 50: cheap recall first, expensive precision second.

Common failure modes

✕

Anisotropy / hubness

Raw BERT [CLS] vectors cluster in a narrow cone; some vectors turn into "hubs" that look close to everything. Fix: contrastive fine-tuning, whitening, or a sentence-BERT-class model.

⚠

Chunking mismatch

Chunks too long bury the relevant sentence; chunks too short lose context. Symptom: recall drops on multi-sentence questions.

⚠

Domain drift

A general-web embedder underperforms on legal, biomedical, or code corpora. Fix: a domain-adapted or fine-tuned model.

✕

Asymmetric query/doc lengths

Queries run 10 tokens, documents run 500. Most modern models expect a query: / passage: prefix for this — get it wrong and recall silently drops by half.

✕

Mixing model versions

Re-embedding half the corpus with a new model and searching across both. The two spaces are unrelated; results are noise.

⚠

Forgotten normalization

Un-normalized vectors work fine with cosine, but querying them with dot product silently ranks by magnitude instead of meaning.

⚠

Filtered HNSW collapse

High-selectivity filters (over 90% rejected) fragment the graph and tail latency explodes. Switch to IVF, or pre-filter before the vector search.

Why it exists

Comparing discrete symbols is brittle: "automobile" and "car" share zero characters but mean the same thing; "bank" can mean two different things in an identical string. Embeddings exist because geometry generalizes where exact matching cannot. Once meaning is a coordinate, similarity is arithmetic, indexable, and scalable — an exponential, sparse symbol space becomes a tractable, dense, continuous one where ordinary tools (k-NN, clustering, linear classifiers) just work.

Why it looks the way it does

Why one dense vector instead of, say, a graph of token relationships? Because a single vector is a fixed-size, GPU-friendly object any downstream consumer can handle the same way. Multi-vector approaches like ColBERT score higher on retrieval benchmarks, but multiply storage and search cost by 30–200x for a 1–3 point NDCG gain — not worth it for most production systems.

Why contrastive training and not just masked-language-modeling? MLM optimizes for guessing hidden words, not for pushing unrelated sentences apart in vector space. Models trained only with MLM produce vectors that sit at similar cosine regardless of meaning — the anisotropy problem above. Contrastive training with hard negatives explicitly pushes unrelated content apart, which is exactly the geometry retrieval needs.

Why Matryoshka? Committing to one width at training time forces a trade-off between quality (big d) and cost (small d). Matryoshka Representation Learning trains nested objectives so the first k numbers of the vector are themselves a valid embedding for any k. OpenAI's text-embedding-3-large at d=256 beats text-embedding-ada-002 at d=1536 on MTEB — same model family, one-sixth the storage.

Why it matters now: RAG made embeddings load-bearing infrastructure. The 2026 MTEB leaderboard is dominated by open-weight models (NV-Embed-v2, Qwen3-Embedding-8B, BGE-en-ICL), so teams can self-host top-tier retrieval without an API bill. Multimodal embeddings (Gemini Embedding 2, March 2026) are collapsing separate text-search and image-search pipelines into one index. Vector databases have crossed into mainstream relational territory via pgvector and SQL Server's vector type. Anyone shipping an AI feature in 2026 is, transitively, shipping an embedding pipeline.
