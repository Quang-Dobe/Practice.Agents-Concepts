Detail — the deep dive

◑ ~10 min read ✎ What · Where · When · How · Why

What it is

A harness is the deterministic software system that wraps a non-deterministic model and turns it into an agent. Formally: given a model M that maps a prompt to a completion, the harness is the program H such that Agent(task) = H(M, task).

  • Core idea. H owns the control loop, tool invocation, context building, persistence, validation, and observability. The model is one stateless function call inside it.
  • The role. A harness engineer designs, builds, and runs H. It reads as platform engineering applied to LLM runtimes — same posture as SRE/platform work (budgets, traces, retries, idempotency), a different, probabilistic component in the hot path.
  • Family. Sits inside AI engineering as the runtime-systems specialization, distinct from prompt engineering (input design), model engineering (training/fine-tuning), and RAG engineering (a retrieval component, not a runtime).

The seven building blocks

Every non-trivial harness contains roughly seven subsystems. Most production failures trace back to one that's missing or weak.

Orchestration / control loop
The Thought → Action → Observation cycle, often a ReAct variant or a Plan-Execute-Verify phase gate. Owns step counting, stopping conditions, and whether to call the model again, call a tool, hand off, or stop.
Tool registry and invocation
A typed catalog of capabilities exposed to the model as JSON schema. Owns schema validation, argument coercion, timeouts, sandbox boundaries, and result formatting. Increasingly federated through the Model Context Protocol (MCP).
Context window management
Decides what tokens go into each call: a short-term scratchpad, a long-term store (vector index, KV store, or files), and a compaction a summarization step that runs near the token budget to shrink the scratchpad policy. Anthropic and Cursor both report compaction cutting context by 60–80% on long sessions.
State persistence and resumption
Durable checkpoints saved snapshots of thread state between turns — thread state, intermediate results, pending tool calls. Enables crash recovery, human-in-the-loop pauses, and resuming a multi-hour run on another worker. LangGraph's Checkpointer and Anthropic's git-backed claude-progress.txt are two reference implementations.
Validation and guardrails
Pre-call (input policy, PII redaction, prompt-injection screening) and post-call (schema validation on tool args, output classifiers, refusal detection). Layered as preventive (block before execution) plus corrective (detect and self-correct in the loop).
Observability and tracing
Structured spans for every model call, tool call, and decision, exported via OpenTelemetry GenAI semantic conventions (stabilized 2025) to Langfuse, Arize Phoenix, Braintrust, or LangSmith. Without this, evals are guesswork.
Safety and permissions
Capability scoping per tool, per user, per environment. Approvals for state-mutating actions, rate limits, and budget enforcement (tokens / dollars / wall-clock). Anything that touches money or production state lives behind this layer.

Sibling disciplines outside AI: backend platform engineering (it borrows control planes, idempotency, traces), workflow orchestration (Temporal, Airflow — same lifecycle problems, deterministic workers), and OS kernels — the "model is a CPU, harness is the OS" analogy is structural, not just a turn of phrase.

Where it lives

The harness sits between the API gateway and the model provider. A typical request: client → gateway/auth → harness process → (model API, tool calls, vector DB, state store) → response. Two deployment shapes dominate:

In-process library

Runs inside a backend service — fine for low-concurrency, single-tenant agents. LangChain and LlamaIndex apps usually start here.

Harness-as-a-service

A dedicated control plane — its own deploy, queue, worker pool, durable checkpointer — that other services call. This is what Claude Code, Cursor, Devin, and Replit Agent run internally, and what LangGraph Platform, OpenAI's AgentKit, and CrewAI Enterprise sell.

Where you'll typically encounter it: Claude Code and Codex (shell, file IO, and git tools), Cursor and Windsurf (IDE-embedded, heavy on speculative tool calls and KV-cache reuse), Devin, Factory, and Cognition (long-running autonomous coding agents), GitHub Copilot Workspace (issue-to-PR planning and verification), and customer-support or ops agents at most SaaS vendors, typically on LangGraph or a homegrown loop.

The ecosystem splits by concern: orchestration (LangGraph, CrewAI, Microsoft AutoGen/AG2, OpenAI Agents SDK, Pydantic AI), tools (MCP, OpenAI function calling, Anthropic tool use, Gemini function calling), memory (pgvector, Qdrant, Weaviate, LanceDB, Mem0, Zep), observability (Langfuse, Arize Phoenix, LangSmith, Braintrust, Helicone, OpenLLMetry), state and durability (LangGraph Checkpointer, Temporal, Inngest, Redis streams), and safety (NeMo Guardrails, Llama Guard, Lakera Guard, Pillar).

When to use it

✓ Reach for it when

  • The task is multi-turn and the model needs more than one tool call to finish.
  • Tools mutate state — writes to a database, sending email, calling a payment API — so you now need idempotency, approvals, and traces.
  • You have a cost or latency SLO (a per-task token budget, a p95 wall-clock target) you must enforce, not just measure.
  • Sessions are long-running or resumable — minutes to hours, with humans approving midway.
  • You want eval-driven iteration — you can't improve what you can't replay.
  • You expect to swap models without rewriting application logic.

✕ Skip it when

  • A single-turn prompt with no tools solves the task — one chat completion call is enough.
  • The workload is batch classification or embedding — no loop, no agency, nothing to wrap.
  • You're still figuring out whether the task is feasible — prototype in a notebook first.
  • The team is one engineer on an internal use case — a thin script is the right level for weeks, maybe months.

A little history

"Harness engineering" entered common usage in 2025, after OpenAI's "Harness engineering: leveraging Codex in an agent-first world" post, and crystallized in early 2026 with Anthropic's "Effective harnesses for long-running agents" and Martin Fowler's writeup citing Birgitta Böckeler's Agent = Model + Harness framing. The motivating observation: as frontier models converged on raw capability (GPT-5 class, Claude 4.x, Gemini 2.5), the variance in agent quality stopped tracking model choice and started tracking the surrounding system. Before 2024, "agent" mostly meant a single ReAct loop in a notebook — AutoGPT and BabyAGI both famously failed in production for harness reasons: no stop conditions, no state, no eval. The name became necessary once teams started hiring people specifically to build that surrounding system.

How it works

One full turn, end to end, in a production harness:

  1. Ingress. The gateway checks auth, applies rate limits, attaches a trace ID, and enqueues the task. A worker picks it up and loads any prior checkpoint for the thread.
  2. Context assembly. The context builder pulls the system prompt, tool schemas filtered by permission, retrieved long-term memory, the recent scratchpad, and the current message. It checks the token count against the model's window minus a reserved output budget, and triggers compaction if over the threshold.
  3. Model call. The harness calls the model with its tool list, streaming tokens for the UI but only committing the result once the full message arrives. Transient 5xx/429 errors retry with backoff and jitter; persistent failures fall through to a fallback model or fail the turn cleanly.
  4. Decision. Parse the response. A final answer gets validated (schema, refusal classifier) and returned. Tool calls get routed to the registry.
  5. Tool invocation. Each call is schema-validated, scoped to the caller's permissions, run inside a timeout and sandbox, and logged as its own span. Tools are built idempotent — a request ID an identifier the harness attaches to a call so a retried call coalesces instead of duplicating its side effect from the harness lets a retried call coalesce instead of duplicating its side effect.
  6. State update. Append the tool results to the scratchpad, save the new checkpoint, and subtract from the token/step/dollar budget. If any budget is spent, move to a graceful-stop branch.
  7. Loop or terminate. If a stopping condition holds — final answer, budget exhausted, human approval required, max steps — exit. Otherwise, go back to step 2.

A minimal sketch of the loop — illustrative only, the runnable version lives in the code folder:

def run_turn(thread_id, user_msg, budget):
    state = checkpointer.load(thread_id)
    state.append({"role": "user", "content": user_msg})

    for step in range(budget.max_steps):
        ctx = context_builder.assemble(state, budget.tokens_left)
        resp = call_model_with_retry(ctx, tools=registry.schemas())
        state.append(resp.message)

        if not resp.tool_calls:
            guardrails.validate_output(resp.message)
            checkpointer.save(thread_id, state)
            return resp.message

        for call in resp.tool_calls:
            guardrails.validate_call(call)
            result = registry.invoke(
                call.name, call.args,
                request_id=f"{thread_id}:{step}:{call.id}",
                timeout=budget.tool_timeout,
            )
            state.append({"role": "tool", "id": call.id, "content": result})

        budget.spend(resp.usage)
        checkpointer.save(thread_id, state)
        if budget.exhausted():
            return graceful_stop(state)

    return graceful_stop(state)

Evals close the loop. Every trace is replayable. A regression suite of "golden traces" reruns nightly against the current model and harness; the metrics are task success, step count, token spend, and tool-call validity. Prompt or tool changes ship only when the eval deltas are positive.

Common failure modes

✕

Infinite loop

The model keeps calling the same tool. Cause: no step cap, or no check that observations are actually making progress.

⚠

Context overflow

The token limit is hit mid-run. Cause: an unbounded scratchpad with no compaction policy.

⚠

Sycophantic confirmation

The model claims "done" before the work is done. Cause: no verification phase or external success criterion.

⚠

Tool sprawl

50+ tools confuse the model. Cause: no progressive disclosure — everything sits in the system prompt at once.

✕

Silent fact destruction during compaction

The summary drops a critical constraint. Cause: an unstructured "summarize this" instead of templated state.

✕

Double-execution

A retry sends two payments. Cause: non-idempotent tools with no request-ID deduplication.

✕

Prompt injection via tool output

A fetched web page contains "ignore previous instructions." Cause: tool results treated as trusted text instead of untrusted input.

⚠

Trace blindness

A bug can't be reproduced. Cause: logs without span IDs or input/output payloads.

Why it exists

Models are stateless probability distributions over tokens. Production software needs state, retries, transactions, audits, budgets, and approvals. The harness is the boundary that turns a probabilistic component into a system you can run, debug, bill, and trust — it exists for the same reason an operating system exists around a CPU: the compute element is not where most of the engineering lives.

Why it looks the way it does

Two design choices recur across every serious harness:

  • Why a loop and not a graph? A pure DAG (Airflow-style) can't express "the agent decides what to do next." A pure free-form loop (AutoGPT-style) can't be debugged. The industry settled on constrained graphs with loops (LangGraph) or typed phase machines (Plan-Execute-Verify) because they keep agent autonomy inside a structure a human can read and bound.
  • Why standardize tools with MCP instead of each app defining its own? Tool sprawl is the dominant ongoing cost, and every team was reinventing the same shell, filesystem, and HTTP tool. A shared protocol makes tools a market rather than something every team rebuilds — the same logic as LSP for editors. The trade-off, judged worth it, is one extra network hop and a schema-versioning problem.

Why it matters now

As of 2026, the strongest empirical claim in the field is that harness quality dominates model choice for most agent tasks. Anthropic's three-agent harness post, Cursor's published architecture, and Augment Code's coding-agent guides all make this case with numbers. The major labs now agree the harness is the product — they only disagree on pricing. For a working engineer that means most of the payoff sits in the harness: the role commands a 10–20% premium over an equivalent backend role, and the discipline maps cleanly onto skills any solid platform engineer already has.

Questions worth verifying before you ship

  • What is the actual step-count distribution of your task? If p95 is 3 steps, you don't need durable checkpoints; if it's 50, you do.
  • Where does compaction lose information on your real traces? Run a "constraint recall" eval before and after.
  • Are your tools genuinely idempotent? Force a duplicate request ID and confirm there's no double side-effect.
  • Does your stopping condition fire on "the model believes it's done" or on "an external verifier says it's done"? Only the second is safe.
  • What's the cost per successful task, not per call? Token cost without a success rate is meaningless.
  • Can a new engineer replay any production trace locally in under five minutes? If not, the observability is for show.
