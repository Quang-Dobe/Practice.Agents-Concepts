Practice — how it plays out for real

● ~10 min read ✎ best practices · anti-patterns · checklist

Where you'll meet it

This is the layer you end up writing once a notebook prototype graduates to a service real users hit. The pattern is consistent everywhere it shows up: one process per agent run, the model call is a small slice of a turn, and 70–80% of the code is everything else — retries, schemas, traces, budgets, checkpoints. If you're reasoning about "why did the agent loop forever last Tuesday at 3am," you're a harness engineer whether your title says so or not.

Coding-agent product

Claude Code, Cursor, Codex CLI, Devin. Owns the shell, file IO, diff application, and the long-running session that survives a crashed worker.

Customer-support / ops agent

Sits between the chat gateway and the ticket, Slack, or Stripe tools inside a SaaS backend. Owns permissions and audit trails.

Internal data agent

Decides whether the model is allowed to run a DELETE against the warehouse — the harness is the permission boundary.

Best practices

1

Own the control loop explicitly

Do

Write the loop and its stopping conditions in your own code. Even on LangGraph or the Agents SDK, the routing of "tool call vs. final answer vs. hand-off" should be your code, not framework magic.

Why

When a run misbehaves at 2am, you need to read one function and know exactly what happened. Frameworks change minor versions and quietly shift loop semantics; your on-call shift doesn't have that luxury.

Avoid

agent.run(task) as a black box, with step counts, retries, and budgets configured only through YAML.

2

Treat tools as a versioned API surface

Do

Give each tool a stable name, a JSON schema, a docstring written for the model, a typed return shape, and a version. Add new tools; never silently change an argument shape.

Why

Tool-call schema drift is one of the most-cited production failure modes — an n8n February 2026 post-mortem traces a whole outage to it. Once the model has cached behavior around a tool, a shape change produces malformed-but-plausible calls, not clean errors.

Avoid

Renaming search_docs(query) to search_docs(q, top_k) in place because "the model will figure it out."

3

Assemble context in named, replaceable slices

Do

Build the prompt from explicit slots — system, tool catalog, memory slice, scratchpad, user message — each produced by its own function and testable on its own. Reserve a fixed output budget; compact once the input crosses a threshold.

Why

When recall drops, you need to A/B one slice — swap the retrieval, say — without rebuilding the whole prompt. MemU's 2026 measurement of roughly 2% context retention loss per step makes the slice that owns compaction the highest-impact thing to tune.

Avoid

A single 600-line f-string nobody dares refactor.

4

Deterministic where possible, model where necessary

Do

If a step can be a regex, a SQL query, or a typed function, make it that. Reserve the model for steps that genuinely need judgment.

Why

Every model call costs latency, money, and a chance of hallucination. Production coding-agent harnesses push parsing, file globbing, and diff application out of the model entirely.

Avoid

Asking the model to "extract the JSON" from a string you already control.

5

Checkpoint every state transition

Do

Persist (thread_id, step, state) after every tool call and every model response, in a real store — Postgres, Redis Streams, a LangGraph checkpointer, Temporal — not in-process memory.

Why

Worker pods get rescheduled. A 40-step run that loses state on minute 12 costs more than the entire day's infrastructure bill. Checkpointing also enables human-in-the-loop pauses for free.

Avoid

Keeping the conversation in a Python list on a single worker.

6

Small reversible tools beat big "do anything" tools

Do

Prefer read_file, write_file, run_tests, apply_patch over a single do_engineering_task(description). Favor reversible side effects, with idempotency keys, over irreversible ones.

Why

The Replit July 2025 incident — an agent ran DROP DATABASE against production despite a freeze — is the canonical case for narrow tools with an explicit blast radius how much damage one tool call can do if it goes wrong. Big tools also confuse the model: it picks the broad one "to be safe."

Avoid

A single execute(command) tool with shell access and no allowlist.

7

Validate tool arguments before invocation

Do

JSON-schema-validate every tool call, coerce types, and reject a mismatch with a structured error the model can read. Do the same for outputs that claim to be JSON.

Why

Individual tool calls fail 3–15% of the time in production (per Atlan's 2026 anti-pattern report), and most failures are malformed arguments, not bad logic. A validator turns silent corruption into a recoverable loop step.

Avoid

json.loads(model_output) wrapped in a bare try/except.

8

Idempotency keys on every state-mutating tool

Do

Pass request_id = f"{thread_id}:{step}:{call_id}" to every write tool, and have tools dedupe on it.

Why

Retries aren't optional in distributed systems. Without idempotency, an exponential backoff sends two payments. This is the single most common money-losing bug in agent products.

Avoid

"We'll add idempotency later" — by the time you need it, you have a customer-facing incident.

9

Budgets are hard caps, not metrics

Do

Enforce max_steps, max_tokens, max_wall_clock, and max_dollars_per_task inside the loop. On breach, transition to a graceful-stop branch that returns a partial answer plus a trace link.

Why

AutoGPT-style runaway loops still happen in 2026 — they just look like a Stripe bill instead of a news story. Budgets bound the worst case.

Avoid

Logging token spend to a dashboard and trusting yourself to notice.

10

Evals are the harness's regression suite, not the model's

Do

Maintain a corpus of golden traces — input, expected tool-call sequence, final state — and replay it nightly. Gate prompt and tool changes on the diff against this corpus, not on vibes.

Why

The model is a moving target you don't control; your harness is yours. Most regressions you'll ship are tool-schema changes and prompt edits — both eval-catchable.

Avoid

"It worked on the demo task" as a release criterion.

11

Trace everything with span IDs the model never sees

Do

One OTEL span per model call, per tool call, per decision. Persist inputs and outputs. Generate a trace ID at ingress and propagate it — but never paste trace data into the model's context.

Why

A new engineer should be able to open a trace and replay any production run locally in under five minutes. Mixing observability data into the conversation pollutes context and burns tokens.

Avoid

print() statements and hoping for the best.

12

Adopt MCP instead of inventing a tool protocol

Do

Expose tools over MCP so the same tool server works across Claude, GPT, and Gemini harnesses, and across your own products.

Why

Tool sprawl is the dominant ongoing cost in a maturing agent codebase. MCP standardizes the contract the same way LSP did for editors. Rebuilding a worse version internally pays nothing back.

Avoid

A bespoke tools.yaml format that only your harness can read.

Anti-patterns to recognize

✕

Framework owns the loop

Code reads crew.kickoff() and the actual control flow lives inside a vendor's decorator stack. Failures become unsearchable. Better: keep the loop and stopping conditions in your repo; let the framework own state and traces if you want, not the routing.

✕

Unbounded scratchpad

Every turn appends, nothing compacts, and eventually a 200k-token context costs several dollars a turn while the model forgets the original task. Better: a compaction policy triggered at a fraction of the window, using templated state — decisions, open questions, facts — rather than free-form summarization.

✕

Tool sprawl in one registry

50 tools advertised on every call. Token bloat plus model confusion — accuracy drops sharply past roughly 15 tools in published benchmarks. Better: progressive disclosure — subagents or phase-specific tool subsets, as in Claude Code's per-subagent tool lists.

✕

Mutating tools without idempotency

A retry sends two emails, double-charges a card, opens two tickets. Better: request IDs flowed by the harness, deduped at the tool boundary.

✕

"It worked once" as a test

No replayable trace, no golden corpus, no regression suite. The next prompt edit silently breaks production. Better: a trace replayer plus 20–100 golden cases gated in CI.

✕

Observability inside the conversation

Stack traces and span IDs pasted into tool results. The model latches onto the noise, cost balloons, and the prompt-injection surface grows. Better: structured logs out-of-band; the model sees only what it needs to reason with.

✕

Trusting model JSON

json.loads with no schema validation and no repair loop. Better: validate against a JSON schema; on failure, return a structured error and let the model self-correct once before failing the turn.

✕

Reinventing MCP

A custom tool-discovery protocol because "ours is simpler." Six months later there are three half-built versions and no shared tools across products. Better: adopt MCP and contribute upstream.

Real-world usage patterns

Coding agent at IDE scale (Cursor, Windsurf)

An editor plugin plus a cloud harness. Codebase indexing sits behind a tool — semantic search, symbol lookup — instead of being stuffed into context. Speculative tool calls are pre-warmed against the KV cache so an applied edit feels instant. Lesson: treat the index as a service, not as context — context is the most expensive memory tier you own.

Long-running autonomous coder (Devin, SWE-agent variants)

Explicit Plan → Execute → Verify phases. A strong model plans with a small tool set; a cheaper model executes with a wide tool set; a verifier runs the test suite and gates progress. Lesson: splitting planning from execution keeps a 200-step run from drifting — the verifier is the only honest stopping condition.

Agentic coding CLI (Claude Code, Codex CLI)

Subagents each get their own context window and tool allowlist — Read, Grep, Glob for a reviewer, full write access for an implementer. A /compact command surfaces compaction as a user-visible action instead of hiding it. Lesson: tool permissioning belongs at the subagent boundary, enforced in code, not in the system prompt — prompts are advisory, allowlists aren't.

Customer-support agent in a B2B SaaS backend

A LangGraph state machine with about 8 tools — search the knowledge base, look up a user, create a ticket, refund within a set limit — plus human-in-the-loop approval above that limit, and full OTEL tracing to Langfuse. Lesson: the moment a tool spends money, the harness needs an approval queue and an audit log — that's what turns a demo into a regulated workflow.

Internal data analyst agent

A SQL tool against a read-replica only, with a query allowlist and a row-count cap. The harness rewrites generated SQL through a validator before running it. Lesson: the safest write tool is no write tool — if the read-only version solves the task, ship that and stop.

Operational checklist

✓

Before you call it done

  • Monitoring: are you emitting per-turn metrics — success rate, p95 step count, p95 tokens, p95 wall-clock, tool-call failure rate per tool, and cost per successful task?
  • Tracing: can a new engineer pull any production trace ID and replay it locally in under five minutes?
  • Failure handling: is there a tested path for "the model provider returns 503 for 90 seconds" and for "a tool times out mid-turn"? Does the agent resume, or fail cleanly?
  • Idempotency: have you forced a duplicate request ID against every state-mutating tool and confirmed there's no double side-effect?
  • Loop safety: are max_steps, max_tokens, max_wall_clock, and max_dollars_per_task enforced inside the loop, not just logged?
  • Security: does each tool have a capability scope tied to the caller's identity? Is tool output treated as untrusted, prompt-injection-screened text?
  • Cost: what's the cost-per-success on your top 5 task types? Which tool's tokens dominate?
  • Evals: is the golden-trace suite wired into CI and blocking on regression?
  • Onboarding: can a new engineer point at one file and say "this is the control loop"? Can they add a tool without editing more than two files?
  • Documentation: is the tool catalog auto-generated from schemas, so it can't drift from the code?

How it evolves in a codebase

  1. Single file. One model call, a while loop, two tools, an in-memory message list. This is the right starting point — building a platform too early is its own anti-pattern.
  2. Survive a deploy. Sessions need to outlive a redeploy. In-memory state becomes a Redis or Postgres checkpoint, and the worker becomes a queue consumer instead of an HTTP handler. OTEL tracing usually gets adopted right around here, because without it the first production bug is unsolvable.
  3. Tool federation. The tool registry, once a Python dict, becomes an MCP server — often several — the moment a second product or team wants the same tool.
  4. Split into subagents. The monolithic agent splits into subagents with scoped tool allowlists, not because anyone wanted multi-agent architecture but because the tool catalog hit around 20 items and accuracy started dropping. At this point the harness looks less like a script and more like a small distributed system — a control plane, durable workers, a tool plane, an eval plane, an observability plane — with its own SLO.

The lesson worth internalizing early: every harness that reaches production ends up here. Build the first version simply, but pick abstractions — named context slices, idempotent tools, explicit budgets, schema-validated calls — that hold up as the system grows.
