Detail — the deep dive

◑ ~10 min read ✎ What · Where · When · How · Why

What it is

A tokenizer is a deterministic, lossless mapping from a Unicode string to a sequence of integer IDs drawn from a fixed vocabulary, and back. It runs in two stages:

  • Pre-tokenizer. A pre-tokenizer the regex pass that splits raw text into word-like chunks before subword merging starts splits the raw string into "word-like" chunks using a regex over Unicode categories.
  • Subword model. Segments each chunk into vocabulary entries — by merging (BPE, WordPiece) or by picking the most likely split (Unigram).
  • Frozen vocabulary. Learned once on a training corpus, then frozen. At inference time, encoding is a pure function of the input bytes.

Formally, a subword tokenizer is a tuple (V, M, P): V is the vocabulary, M is either an ordered merge table an ordered list of character-pair merges — replaying it out of order changes the output (BPE/WordPiece) or a probability distribution over V (Unigram), and P is the pre-tokenization regex.

The core building blocks

Vocabulary V
32k (Llama 2), 100k (GPT-4 / cl100k_base), 128k (Llama 3), or 200k (GPT-4o / o200k_base) entries, each with a unique ID.
Base alphabet
The smallest units that can never run out. Byte-level BPE uses the 256 UTF-8 byte values, so every input is representable.
Merge table
An ordered list of pairs (a, b) → ab for BPE/WordPiece. Order is part of the model.
Unigram probability table
Unigram stores log p(t) per token and runs Viterbi to find the most likely split.
Pre-tokenization regex
Guarantees merges never span a space-to-letter or letter-to-digit boundary.
Special tokens
Reserved IDs added after training (<|endoftext|>, <|im_start|>) — never produced by merging, only inserted by a chat template.
Decoder
The inverse map. For byte-level tokenizers: concatenate token byte strings, then re-decode as UTF-8.

Subword tokenizers sit between two extremes: word-level (huge vocabulary, terrible behavior on unseen words, effectively dead) and character/byte-level (tiny vocabulary, very long sequences, expensive attention). Inside the subword family there are three sibling algorithms — BPE (Sennrich et al., 2016), WordPiece (Schuster & Nakajima, 2012; revived by BERT), and Unigram LM (Kudo, 2018) — plus the SentencePiece library, which is a packaging of BPE or Unigram that treats whitespace as a regular character. Newer research (Boundless BPE, BlockBPE) is pushing on the pre-tokenizer step itself, but as of 2026 every production LLM still uses one of those three algorithms.

When to use it

✓ Reach for an existing tokenizer when

  • You're calling any hosted LLM API — you must match what the model was trained on; there's no choice here.
  • You're fine-tuning a foundation model — extending the vocabulary is possible but rare; reuse the base tokenizer.
  • You're building a RAG pipeline — measure chunk size in tokens, not characters, because the context budget is in tokens.

✕ Skip it — or don't reuse one — when

  • You only need word counts for a UI — str.split() is correct and cheaper.
  • You want semantic similarity — that's sentence embeddings, a separate model.
  • You're reusing another model's tokenizer with a different model's weights — "tokenizer recycling" reliably produces garbage.
◆

Train your own only when

  • You're pre-training from scratch on a domain (code, biomedical text, a low-resource language) where public tokenizers give bad fertilitytokens produced per word — higher fertility means more tokens, more cost, and less usable context for the same text — typically more than 2 tokens per word on your evaluation set.
  • You need a custom alphabet — protein sequences, MIDI events — where Unicode-based pre-tokenization is the wrong tool.

How it works

Encoding a string with byte-level BPE (the cl100k_base recipe):

  1. Normalize. Pass the input through Unicode NFC. Most modern tokenizers don't normalize aggressively — they want to round-trip exactly.
  2. Pre-tokenize. Apply the regex. " the cat sat" becomes the chunks [" the", " cat", " sat"] — note the leading space stays attached, so " cat" and "cat" are different tokens.
  3. Encode to bytes. Each chunk becomes a UTF-8 byte sequence, remapped through a reversible byte-to-printable-character table so the merge table can be written in plain text.
  4. Greedy merge. For every adjacent pair of current tokens, apply the lowest-rank (earliest-learned) merge in the table first. Repeat until no merge applies.
  5. Look up IDs. Map each final piece to its integer ID.
  6. Concatenate. Emit the flat list of IDs across all chunks.

The complexity is O(n log n) per chunk with a priority queue keyed on merge rank, or O(n) with the linked-list trick tiktoken uses. A 4k-token prompt encodes in single-digit milliseconds on a laptop CPU.

Training a vocabulary

Training builds the merge table the encode loop replays. Starting from the 256 base bytes, count every adjacent token-pair across the corpus, merge the most frequent pair into a new vocabulary entry, record it as the next merge, and repeat until the vocabulary hits its target size. The three algorithms differ in how they pick and apply merges:

BPE

Picks the most frequent pair at each step. Deterministic, fast, easy to cache. Used by GPT-4/4o's tiktoken and Llama 3.

WordPiece

Picks the pair that maximizes a likelihood ratio, count(a,b) / (count(a)·count(b)), not raw frequency. Marks continuation pieces with ## and matches greedily at encode time. Used by BERT.

Unigram

Works top-down: seed a huge candidate set, estimate probabilities with EM, drop the lowest-scoring ~10%, repeat. Encoding runs Viterbi to find the most likely split, which also enables sampling alternate splits for data augmentation. Used by SentencePiece and Gemma.

Common failure modes

✕

Digit-grouping arithmetic errors

cl100k_base and Llama 3 chunk runs of digits into up-to-3-digit tokens. 1,000,001 may split into 1, 000, 001 while 999 is one token — the model learns inconsistent representations of the same digit position.

⚠

Leading-space artifacts

"Hello" and " Hello" are different IDs. A model fine-tuned on "Hello" after a newline can quietly underperform when the prompt template inserts a space.

⚠

Glitch tokens

Tokens like SolidGoldMagikarp made it into the vocabulary from corpus quirks but were stripped from later training data. Their embeddings stay near their random initialization and produce nonsense output.

⚠

Multilingual fertility tax

English averages ~1.2 tokens/word; Ukrainian ~2.7; Burmese, Telugu, and Khmer are often above 3. Same API call, different cost; same 8k context window, roughly half the usable text.

✕

Chat-template injection

A user message that contains literal <|im_end|> text can be tokenized straight into the special ID if the tokenizer is configured to recognize specials in input — a real prompt-injection surface.

✕

Tokenizer recycling

Porting another model's tokenizer onto new weights (say, using Llama's tokenizer for a French model) causes fertility to blow up and perplexity to degrade.

⚠

Trailing-whitespace traps

A chat template that ends the prompt with a trailing space makes the model score the wrong continuation tokens, because the leading-space variant is already "consumed".

Why it exists

  • Lossless integer encoding is required. Transformers compute on integer-indexed embeddings, so the string-to-int step has to be reversible and identical at training and inference time.
  • Sequence length costs O(n²) attention. Compressing 4 characters into 1 token quarters the cost of attention. Tokenization is a learned compressor trying to shrink the sequence without losing the ability to express anything.
  • No-OOV guarantee. A byte-level alphabet makes the encoder a total function — every Unicode string round-trips, with nothing ever "unknown".

Why it looks the way it does

The obvious alternative is pure character-level tokenization: a vocabulary of every Unicode code point, no merging, no pre-tokenizer. It's simpler, fairer across languages, and sidesteps glitch tokens entirely. It isn't used because:

  • Sequences become 3–5× longer, blowing the attention budget.
  • The model spends most of its capacity learning spelling instead of meaning.
  • Subword models match or beat character models on downstream tasks at a fraction of the compute (Kudo & Richardson, 2018, and many follow-ups).

Byte-level — not character-level — BPE is the synthesis: it keeps the no-OOV property of character models and the compression of subword models, at the cost that one Han character may run 3 bytes. The BPE-vs-Unigram choice is mostly about training convenience: Unigram supports sampled splits during training, BPE is deterministic and faster to encode. Most production tokenizers picked BPE because encode-time determinism made the engineering simpler, not because it's mathematically better.

Why it matters now

  • Context windows keep growing — 1M tokens for Gemini, 200k+ for Claude and GPT. Fertility is now a first-class scaling-cost question: a 10% better tokenizer is a 10% larger effective context.
  • Multilingual deployment is the norm. The fertility tax lands hardest on the regions with the fastest LLM adoption growth.
  • Code-acting agents parse, edit, and re-emit source code, where numeric and whitespace tokenization now have real correctness effects on diff fidelity, not just cost.
