Detail — the deep dive

◑ ~10 min read ✎ What · Where · When · How · Why

What it is

"Web Components" is not one spec. It is a suite of three W3C/WHATWG specifications that together let you define, isolate, and stamp out reusable custom HTML elements.

  • Custom Elements v1 — WHATWG HTML Standard §4.13. Defines customElements.define(), the reaction queue the internal FIFO queue that runs each lifecycle callback in the order its triggering event happened, and the four lifecycle callbacks.
  • Shadow DOM v1 — WHATWG DOM Standard §4.8, wired into the HTML parser. Defines attachShadow(), ShadowRoot, event retargeting, and the composed tree.
  • HTML template — WHATWG HTML Standard §4.12.3. Parses to an inert DocumentFragment that never renders and whose scripts never run.

The core building blocks

HTMLElement subclass
Every element is a class extending HTMLElement. Its constructor runs at creation time; mutating the DOM inside the constructor is illegal — the spec throws NotSupportedError.
CustomElementRegistry
The global window.customElements object. Owns define(name, ctor, options?), get(), whenDefined(), and upgrade(). A tag registers once; its name must contain a hyphen.
Shadow root
A DocumentFragment-like node from element.attachShadow({ mode }). Its subtree is the shadow tree; the element's own children are the light tree. The composed tree is what the browser paints.
<slot>
A placeholder in the shadow tree that projects light-DOM children into a spot. Default (<slot>) or named (<slot name="header">).
<template>
Inert markup container; template.content is a DocumentFragment you cloneNode(true) to stamp instances cheaply.
ElementInternals
From this.attachInternals(). Exposes form association, ARIA reflection, and custom validity (WebKit shipped this in Safari 16.4).

Web Components sit in the family of encapsulated UI primitives. The closest relatives are framework components (React, Vue, Svelte, Solid) — compile-time abstractions the browser never sees — and iframes, which are process-level isolation with their own document. The niche Web Components own is runtime, standards-based, cross-framework encapsulation: the browser itself understands the tag, so the same my-widget renders identical DOM inside React, Vue, or a static .html file.

Where it lives

Purely client-side, at the DOM layer — one rung above the parser, one rung below any framework's virtual DOM. A custom element is a real Node in the document tree: the browser dispatches events to it, applies CSS to its host box, and calls its lifecycle callbacks synchronously as part of the DOM mutation algorithm. A server-rendered variant exists too: Declarative Shadow DOM lets the parser build a shadow root straight from a template shadowrootmode="open" child, moving first paint into the HTML byte stream — no JavaScript required.

Where you'll actually see the tags running:

Vendor design systems

Adobe Spectrum, Microsoft Fluent UI, SAP UI5, and GitHub's ongoing Primer migration ship components as tag libraries.

Cross-framework platforms

Salesforce Lightning Web Components (LWC) — a whole enterprise app framework built on literal custom elements. Ionic's ion-button renders the same in Angular, React, and Vue.

Progressive enhancement

GitHub.com uses tags like relative-time, clipboard-copy, and details-menu layered on top of server-rendered HTML.

General UI kits

Shoelace / Web Awesome work with any framework or none. YouTube desktop, built on the Polymer library, still ships hundreds of yt-* tags.

Tooling around the specs: Lit (~5 KB, the most common authoring library), Stencil (compiles TSX to custom elements), and FAST for authoring; @lit-labs/ssr, Enhance, WebC, and Astro's built-in support for SSR; @open-wc/testing, Web Test Runner, and Playwright for testing; @lit/react, Angular's CUSTOM_ELEMENTS_SCHEMA, and Vue's compilerOptions.isCustomElement for framework interop.

When to use it

✓ Reach for it when

  • The same widget must ship into multiple framework contexts or unknown host pages — embeds, checkouts, chat widgets.
  • You're building a design system with a 3+ year lifespan across teams that won't agree on one framework.
  • You need hard style isolation — third-party CSS on the page must not touch your widget.
  • You want a framework-free island on an otherwise static page and refuse to add a bundler.
  • The team is comfortable with DOM APIs and doesn't need JSX-level ergonomics for internal state.

✕ Skip it when

  • The app is single-framework and staying that way — you'll fight the framework's own idioms at every boundary.
  • You need rich SSR with streaming and fine-grained hydration — Next.js, Remix, and SvelteKit are still ahead here.
  • You need to pass complex objects as attributes — attributes are strings; that's exactly where framework interop breaks.
  • The team is small, junior, and moving fast — vanilla Web Components mean hand-building change detection, templating, and state.

A little history

Web Components began around 2011 as a Google project. The original v0 specs shipped only in Chrome with awkward ergonomics (document.registerElement, a createdCallback naming style). Custom Elements v1 and Shadow DOM v1 were redesigned in 2016 through cross-vendor agreement — Safari shipped v1 that year, Firefox followed in 2018 (release 63), and Edge inherited support in 2020 when it switched to Chromium.

How it works

The life of a custom element, from source HTML to torn-down node:

  1. Registration. customElements.define('x-foo', XFoo) checks the name — must contain a hyphen, be lowercase, and not be a reserved name — then schedules an upgrade for every matching tag already parsed anywhere in the document.
  2. Parsing. If the tag is undefined when the parser meets it, the parser creates a plain placeholder element with the right tag but no behavior. It matches the :not(:defined) CSS pseudo-class.
  3. Upgrade. Once define() runs — now or later — the browser walks the placeholder, runs the constructor with new.target === XFoo, and swaps in the real prototype.
  4. connectedCallback. Fires when the element lands in a document with a browsing context. It fires every time it's (re)inserted, including on an appendChild move — not idempotent, so check this.isConnected.
  5. attributeChangedCallback. Fires only for names listed in the static observedAttributes getter — the browser skips everything else as a performance optimization. Runs synchronously inside the mutation algorithm.
  6. adoptedCallback. Fires on document.adoptNode() — moving an element between, say, an iframe and the main document. Rare in practice.
  7. disconnectedCallback. Fires on removal from the tree. Not called on page unload — use it to tear down listeners, timers, and observers.
  8. Shadow attachment and paint. Usually inside the constructor: this.attachShadow({ mode: 'open' }) — mode is permanent for the element's life. The browser flattens light DOM into slots to build the composed tree the flattened tree of light-DOM nodes projected into shadow slots — what the browser actually paints, then paints. Events dispatched inside the shadow tree are retargeted to the host as they cross the boundary, unless dispatched with composed: true.

Waiting for a definition without racing the parser:

await customElements.whenDefined('x-foo');
// The class is registered globally now.
// Any existing <x-foo> in the DOM has been (or is being) upgraded.

Common failure modes

✕

Touching this before super()

Throws ReferenceError immediately — a direct consequence of extending HTMLElement.

✕

DOM work in the constructor

Adding children before connectedCallback throws NotSupportedError — the spec forbids DOM mutation that early.

⚠

connectedCallback fires more than once

Moving the element with appendChild runs disconnect then reconnect. It is not idempotent — check this.isConnected.

⚠

attributeChangedCallback never fires

You forgot the static observedAttributes getter — the browser skips callbacks for anything not listed there.

⚠

Attribute vs. property drift

The outside sets el.checked = true, the reflected attribute never updates, and a framework re-render clobbers the state. Cause: no reflection wiring.

⚠

Style leaks through the slot

Slotted content lives in the light DOM, so the page's global CSS still styles it. Not a bug — but often surprising the first time.

⚠

Closed roots and accessibility tools

Some screen readers have historically failed to reach into closed shadow roots. Use open unless you have an actual threat model to defend against.

⚠

FOUC before upgrade

Undefined elements render as unstyled inline boxes. Fix with a :not(:defined) { visibility: hidden } rule in a global stylesheet.

✕

Global registry collision

Two copies of the same library both call define('x-foo', ...) — the second call throws. Scoped Custom Element Registries, still in progress, will fix this.

Why it exists

Because the browser is the only durable runtime on the web, and every earlier attempt at reusable UI — Backbone views, Dojo widgets, Angular 1 directives, React 15 mixins — died along with its framework. The specs answer three first-principles concerns:

  • Encapsulation — isolate styles and DOM so composition scales past a handful of components.
  • Interoperability — a plain HTML tag is understood everywhere, by definition.
  • Longevity — standards outlive frameworks; a tag defined today still works after the next framework generation turns over.

Why it looks the way it does

Two choices look strange until you see the alternative.

Hyphen-required tag names. The obvious alternative was a registry of reserved words. The committee picked the hyphen rule instead, so the HTML parser can decide at parse time — with zero lookup — whether a tag might be custom, and keep the un-hyphenated space free for future built-in elements forever. Cheap, forward-compatible, no ambiguity.

Shadow DOM instead of CSS-only scoping. A CSS-only system (like Vue's style scoped) would have shipped faster and stayed simpler. It was rejected because it doesn't scope DOM queries — document.querySelector('button') would still reach inside the widget. Shadow DOM gives a real tree boundary, at the cost of one extra concept: composed tree vs. flat tree.

Why it matters now

In 2026 the ecosystem crossed two lines that used to be blockers. React 19 finally assigns matching properties instead of stringifying every prop to an attribute, closing the biggest framework-interop complaint. Declarative Shadow DOM reached Baseline "newly available" on 2024-02-20 and is expected at Baseline "widely available" by mid-2026, closing the SSR gap that once made Web Components a poor fit for content-first sites. Meanwhile design-system consolidation — Adobe Spectrum, Fluent, SAP UI5, GitHub Primer's ongoing migration — has quietly made custom elements the default currency of cross-framework UI at large companies.
