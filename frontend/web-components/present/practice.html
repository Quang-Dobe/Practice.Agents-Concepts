Practice — how it plays out for real

● ~11 min read ✎ best practices · anti-patterns · checklist

Where you'll meet it

The most common production home is a cross-framework design system: a platform team ships acme-button, acme-modal, acme-datepicker once, and a React app, an Angular admin, a Vue site, and a legacy Rails partial all consume the same tag. You'll rarely reach for a Web Component to build a whole single-page app — the sweet spot is leaf-level, high-reuse UI, not routing or global state.

Cross-framework design system

Adobe Spectrum, Microsoft Fluent, SAP UI5, GitHub Primer, Shoelace, and Ionic all follow this shape.

Embeddable widget

Chat bubbles, checkout drop-ins, consent banners living inside an unknown host page's CSS. Shadow DOM protects them without paying for an iframe.

Micro-frontends

Salesforce LWC is the enterprise poster child — each team ships a bundle exposing tags; the shell composes them by tag name and CustomEvent, not shared framework state.

Best practices

1

Do DOM work in connectedCallback, not the constructor

Do

Reserve the constructor for super(), class-field init, and attachShadow. Stamp the template, wire listeners, and read attributes in connectedCallback.

Why

The spec forbids child mutation in the constructor and browsers throw NotSupportedError. It also keeps SSR and Declarative Shadow DOM parsing clean, and lets elements be document.createElement'd without side effects.

Avoid

Calling innerHTML =, appendChild, or fetch in the constructor because "it works in Chrome."

2

Reflect properties to attributes for anything that belongs in HTML

Do

For state a user might set in markup (disabled, open, variant="primary"), pair a getter/setter with attributeChangedCallback and mirror the value both ways. Attribute presence should mean boolean true, matching built-in HTML.

Why

Server-rendered pages, view-source debugging, framework attribute binding, and CSS selectors like [disabled] all rely on the attribute being real. Without reflection you get silent drift between DOM and JS state.

Avoid

Storing state only on the class instance and expecting outside observers or CSS to see it.

3

Declare observedAttributes explicitly and keep the list small

Do

List only the attributes that are part of your public API. Reach for a MutationObserver only if you truly need dynamic keys.

Why

The browser skips attributeChangedCallback for anything not observed, as a performance optimization. A missing entry is the top reason "my attribute update does nothing." A bloated list turns every class="…" toggle into a callback.

Avoid

Listing every attribute blindly, or forgetting to add a new one when the API grows.

4

Dispatch typed, composed CustomEvents — never call parent methods

Do

this.dispatchEvent(new CustomEvent('acme-change', { detail: { value }, bubbles: true, composed: true })). Prefix event names, use detail for payload, and document them.

Why

composed: true is what lets the event cross the shadow boundary — without it the host page sees nothing. Prefixing avoids collisions with future native events. Calling parent methods ties a component to one specific parent and breaks reuse.

Avoid

Un-prefixed generic names like change — it collides with native form events — or forgetting composed.

5

Clean up everything in disconnectedCallback

Do

Remove listeners added to window/document, disconnect any ResizeObserver / MutationObserver / IntersectionObserver, cancel AbortControllers, clear timers. Pass one shared AbortSignal to every addEventListener for one-line teardown.

Why

Custom elements are re-inserted during framework re-renders and route changes. Leaked listeners survive across navigations in SPA hosts, causing a slow memory leak and duplicated handlers.

Avoid

Assuming garbage collection handles it because "the element is gone" — a listener on window still holds a hard reference.

6

Share stylesheets with adopted stylesheets

Do

Build one CSSStyleSheet per component class, reuse it across every instance via adopted stylesheets one parsed CSSStyleSheet object attached to many shadow roots via shadowRoot.adoptedStyleSheets, instead of cloning a style tag into each one (shadowRoot.adoptedStyleSheets = [sheet]). Lit does this for you already.

Why

Cloning a style tag into 500 shadow roots costs 500 parses and 500 style engines. Adopted sheets share one parsed rule set — a measurable render-time win on component-heavy pages.

Avoid

Setting shadowRoot.innerHTML with a large inline stylesheet on high-count components.

7

Theme through custom properties and ::part, never through piercing selectors

Do

Expose design tokens as --acme-color-primary; expose stylable internals via part="trigger". Document both as a public API.

Why

Custom properties inherit through shadow boundaries by spec; ::part gives consumers an explicit hook. Anything else — deep selectors, !important hacks — breaks the moment internals get refactored, and they will.

Avoid

Encouraging consumers to reach into shadowRoot with piercing-combinator shims. That's a public-API breach waiting for a bug report.

8

Use ElementInternals for form-associated a custom element that participates in an ancestor form element the same way a native input does components

Do

Add static formAssociated = true and call this.attachInternals(). Use setFormValue(), setValidity(), and the ARIA reflection setters (ariaLabel, role).

Why

Without form association your input is invisible to form submission, FormData, native validation, and reset. ARIA reflection avoids the classic "custom element with no accessible name" bug (WebKit shipped this in Safari 16.4, Firefox in 126).

Avoid

Faking form participation with a hidden proxy input — it duplicates state and breaks with server-rendered forms.

9

Guard first paint against FOUC and upgrade flashes

Do

Ship :not(:defined) { visibility: hidden } in a global stylesheet, or use Declarative Shadow DOM so first paint is already encapsulated. Gate JS that assumes upgrade with customElements.whenDefined('acme-button').

Why

Undefined elements render as inline boxes of unstyled content — a jarring flash on cold loads and layout thrash on hydration.

Avoid

Blocking rendering behind a top-of-body script — that costs more time-to-first-byte than the flash ever cost you.

10

Ship as ESM, side-effect free per import, with a guarded define()

Do

Export the class and provide a separate define.js, or wrap the call in if (!customElements.get(...)) customElements.define(...). Publish "type": "module", mark "sideEffects": false, and version the tag name (acme-button-v2) for breaking changes.

Why

Two copies of your library on one page — a half-rolled-out upgrade, a micro-frontend collision — throw on the second define() and crash the host. Tag names are one global namespace; treat them like it.

Avoid

UMD bundles that eagerly define() on import, or unconditional define() calls with no guard.

11

Test with a runner that understands Shadow DOM

Do

Use @web/test-runner plus @open-wc/testing for unit tests, Playwright for end-to-end. Playwright's locators pierce open shadow roots automatically — use getByRole / getByText.

Why

Jest with jsdom has historically had broken or partial custom-element support — you'll chase phantom failures. Real-browser runners exercise the actual upgrade and reaction queue.

Avoid

Chaining querySelector through nested shadowRoot.shadowRoot lookups in tests — it encodes implementation details and breaks on refactor.

12

Match the framework interop story to your consumer list

Do

For React below version 19, ship a wrapper generated by @lit/react. For Vue, document the .prop modifier and set compilerOptions.isCustomElement. For Angular, add CUSTOM_ELEMENTS_SCHEMA and rely on [prop] / (event) bindings.

Why

React 18 stringifies unknown props into attributes, silently mangling booleans and objects. React 19 fixed most of it, but object-typed properties without an existing setter can still coerce. Angular's schema is required or the compiler throws.

Avoid

Assuming "it's just a tag" — every framework has at least one edge case, and your users will find it before you do.

Anti-patterns to recognize

✕

Shadow DOM as a security boundary

Assuming a closed root protects secrets. It only hides from same-page JS with a reference — anyone can intercept attachShadow before your script runs, and the shadow tree shares the same JS realm. Use an iframe with sandbox for real isolation.

✕

Constructor-heavy elements

Template stamping, network calls, or observer setup in the constructor. Every document.createElement call — including speculative ones from framework diffing — pays that cost. Move it to connectedCallback.

✕

Slot-blind global CSS

Forgetting slotted content stays in the light DOM. A rule like slot > * written inside the shadow tree loses to host-page styles, and everyone blames Shadow DOM. Use design tokens plus ::slotted(*) instead.

✕

Attribute-only APIs for complex data

Serializing a JSON object into an attribute so an older React can pass it in. Every re-render re-parses it. Use properties, wrap for React, and reserve attributes for HTML-native primitives.

✕

Nested shadow root fractals

Ten-deep shadow trees to "componentize everything." Event retargeting becomes untraceable, ::part doesn't forward past one level without explicit exportparts, and DevTools inspection turns miserable. Flat is better.

✕

Global define() in a shared library entry point

A design system whose single import calls define() for 40 tags on first load. A second copy of the library throws; consumers pay for all 40 tags whether they use one or all. Ship per-component entry points with a guarded define().

✕

Framework re-render blast radius

React remounting a chart component on every parent render because a prop identity changed. Each cycle runs disconnect, reconnect, and re-init — visible flashing. Memoize props at the boundary or wrap with @lit/react.

✕

Custom element as the whole SPA root

Turning one element into a mini-framework with routing and stores inside a shadow root. You lose SSR and DevTools ergonomics and re-invent a framework badly. Use a real framework for the app shell; custom elements for reusable widgets.

Real-world usage patterns

Enterprise design system, polyglot teams

A financial services company runs React, Angular, and legacy JSP portals. The platform team ships ~60 Lit-based custom elements plus per-framework wrappers. Lesson: the wrappers are as much of the product as the elements — dropping @lit/react too early broke tabular-data props for pre-React-19 consumers for six months.

Embeddable checkout widget

A payments provider replaces an iframe drop-in with a Shadow DOM widget for better accessibility and first paint. Lesson: customers still demanded visual matching, so --pay-radius and --pay-font custom properties became the actual theming product surface.

CMS island architecture

A marketing site is 95% static HTML with a handful of interactive islands — a price calculator, a video hero, a map locator — each a single ESM file. Lesson: standardizing on Declarative Shadow DOM for the hero let Lighthouse measure the real painted content instead of a post-hydration flash, recovering 8 points.

Salesforce LWC-style platform

An internal app platform composes line-of-business "apps" as bundles of custom elements. Lesson: they version tag names (acme-grid-v3) rather than assume semver, because two versions of the same tag can't coexist under one global registry.

GitHub-style progressive enhancement

Server-rendered pages sprinkle in tiny, dependency-free tags like clipboard-copy and relative-time. Lesson: "works before JS loads, better after" keeps the site usable on slow connections and inside search-engine renderers that time out on heavy hydration.

Operational checklist

✓

Before you call it done

  • Monitoring: is time-to-whenDefined for critical tags tracked in real-user monitoring? A regression here shows up as a subtle LCP drop before anyone sees FOUC.
  • Failure handling: if customElements.define() throws on a duplicate registration, does the app degrade or crash? Has loading two library versions on one page been tested?
  • Framework interop: is there a snapshot test per supported framework version exercising boolean, object, and event bindings?
  • Accessibility: for every form-associated element, is ElementInternals wired for role, ariaLabel, and validity? Has a real screen reader gone through the shadow tree?
  • Security: does anything render untrusted content via innerHTML? Shadow DOM is not XSS protection — sanitize the same way you would in light DOM.
  • Cost / performance: are adopted stylesheets used for high-count components? Has upgrade cost been measured at the realistic max element count?
  • Bundling: is the package "type": "module", marked "sideEffects": false, with an independent entry per component?
  • Distribution: is the tag namespaced (acme-*), with the major version in the tag name if breaking changes are expected?
  • Onboarding: can a new engineer find the "define once, guard the double-define" convention in under five minutes?
  • SSR: if Declarative Shadow DOM ships, is there a fallback for older Firefox still in the analytics tail, and is hydration mismatch detected somehow?

How it evolves in a codebase

  1. One component. A widget has to work in two framework contexts, or survive an unknown host page. Someone writes it in vanilla HTMLElement in an afternoon and it goes live. It works.
  2. Proliferation, then Lit. Six months later there are five such components in five different styles. Pure vanilla scales badly past roughly ten components — change detection, templating, and typed props get re-implemented in each one — so the team standardizes on Lit.
  3. Framework interop debt. React attribute-stringification bugs pile up; the team wraps everything with @lit/react or pins to React 19. SSR becomes a requirement around the same time, forcing state to be serializable into attributes and an API redesign for older components.
  4. v1 → v2 migration. Because tag names are global, two majors can't ship under the same name. Teams version the tag (acme-button-v2), rename the package, or wait for scoped Custom Element Registries — still not universally shipped in 2026. Whichever path is chosen, planning for it before the first customElements.define('acme-button', ...) ships saves months later.
