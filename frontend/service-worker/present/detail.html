Detail — the deep dive

◑ ~9 min read ✎ What · Where · When · How · Why

What it is

A Service Worker is an event-driven script, standardized by the W3C, that the browser runs in its own worker context — a ServiceWorkerGlobalScope the worker's global object; there is no DOM, no window, no document — separate from any document, scoped to an origin and a URL prefix. It intercepts HTTP requests from clients in its scope and can answer on their behalf. The spec models it as a state machine attached to a registration record stored per origin in the browser's storage.

  • Core idea. One script, one registration per origin, that gets a first look at every in-scope request.
  • Runtime environment. self is the global; self.registration, self.clients, and self.caches give it control over updates, controlled pages, and the Cache API. There is no window, no synchronous XMLHttpRequest, no localStorage.
  • State is not durable. The browser can end the worker between events. On the next event it spins up fresh, and any plain JavaScript variables are gone — anything that must last goes to caches or indexedDB.
  • Family. It belongs to the Web Workers family (Dedicated, Shared, Service). Only Service Workers persist past the page's lifetime and intercept network traffic. The closest cross-platform cousin is an edge worker — Cloudflare Workers, Deno Deploy, Vercel Edge — which shares the same fetch-event model on the server side. Its deprecated predecessor was Application Cache (AppCache), removed from browsers around 2021.

Where it lives

A Service Worker is a programmable proxy that sits on the client, between the page's fetch/resource-loading code and the network stack:

Process boundary

Chromium runs it out-of-process in its own service worker process with its own event loop. Firefox and Safari use a separate worker thread. Either way: no shared memory with any page, message-passing only.

Script location & scope

The script must be same-origin. Its URL's directory caps the scope: /sw.js can claim up to /; /static/sw.js can only claim /static/. Breaking out of that requires the server to send a Service-Worker-Allowed header naming a broader path — why tutorials insist the worker live at the site root.

Security model

HTTPS-only, with localhost/127.0.0.1 exempted for development. Same-origin everything. The browser also clamps the worker script's own cache lifetime to 86400 seconds (24 hours) and refetches it if the last fetch is older than that — so a buggy worker can't pin itself forever.

You'll meet it in the wild inside Workbox (Google's library that compiles caching strategies into a worker), framework wrappers built on it (Next.js's next-pwa, Nuxt's PWA module, the Vite PWA plugin), web push delivery (FCM, OneSignal — the push handler must live in a worker), Mock Service Worker (MSW) for browser-side test mocking, and production sites like Google Docs, Twitter/X, YouTube Music, and Pinterest.

When things happen

When each event fires

  • install — once per worker version, right after the script is parsed and accepted.
  • activate — once, when the worker leaves the waiting state, either because every controlled client is gone or because skipWaiting() was called.
  • fetch — for every in-scope request from a controlled client, including the page's own HTML navigation, every subresource, and explicit fetch() calls.
  • message, push, sync / periodicsync, notificationclick / notificationclose — client messages, push-service deliveries, background-sync runs, and notification interactions.

When updates happen

On every in-scope navigation, and after roughly 24 hours idle, the browser refetches the script and does a byte-for-byte comparison an exact comparison of the script's bytes against the stored copy to detect changes against the stored copy. Since Chrome 78 that comparison also covers any scripts pulled in via importScripts() — change one of those and the parent worker counts as updated even with identical top-level bytes (see w3c/ServiceWorker PR #1023). The updateViaCache setting defaults to imports — cache the imports, but always revalidate the top-level script. If any byte differs, a new worker enters installing while the old one keeps serving traffic.

When skipWaiting / clients.claim take effect

  • skipWaiting() only matters while the new worker is installing or waiting. Called from install, it lets the new worker activate the moment install finishes, regardless of open tabs.
  • clients.claim() is called from activate (or later). It sets controller on every same-origin in-scope client that currently has none, or that the previous worker controlled. Without it, clients keep their original controller until they reload — the first load after registration is always uncontrolled.

When the browser kills the worker

After about 30 seconds with no events (the figure Chromium's extension docs cite; timing elsewhere is similar but unspecified), under memory pressure, or when a single handler runs past a hard ceiling (5 minutes in Chromium). It spins back up on the next event.

How it works

Walk a request through a typical cache-first worker:

  1. Register. The page calls navigator.serviceWorker.register('/sw.js', { scope: '/' }) once.
  2. Install. The install handler wraps its cache-population promise in event.waitUntil extends an event's lifetime until the given promise settles, so the worker stays installing until the shell is cached.
  3. Activate. The activate handler sweeps caches whose name isn't the current version, also inside event.waitUntil. No fetch events arrive yet.
  4. Intercept. On fetch, the handler must call event.respondWith(promise) synchronously — the async work happens inside that promise, not before the call.
  5. Answer. Check cache.match(request); return it on a hit. On a miss, fetch the network, clone the response into the cache, and return it.

The named caching strategies

  • Cache-first — check cache, fall back to network. Best for immutable, fingerprinted assets.
  • Network-first — try network with a timeout, fall back to cache. Best for HTML and API responses that change often.
  • Stale-while-revalidate — return the cache immediately, refresh it in the background for next time. Best for content that can be a little stale.
  • Cache-only — return cache or fail. Used for precached app-shell assets.
  • Network-only — never touch the cache. Used for POSTs, analytics, anything mutating.

None of these are browser primitives — they're conventions. Workbox ships them as ready-made classes; hand-rolled, each is roughly 10 lines.

Cache versioning is the entire migration story — bump one constant and the old cache is swept on the next activation. Illustrative only; the runnable version lives in the code folder:

const CACHE = 'app-shell-v7';

self.addEventListener('install', (event) => {
  event.waitUntil(caches.open(CACHE).then((c) => c.addAll(SHELL_URLS)));
});

self.addEventListener('activate', (event) => {
  event.waitUntil(
    caches.keys().then((keys) =>
      Promise.all(keys.filter((k) => k !== CACHE).map((k) => caches.delete(k)))
    )
  );
});

Common failure modes

✕

The worker pins a stale index.html

Cause: cache-first applied to the navigation request. The user can never see the new HTML.

⚠

A new worker never activates

Cause: a long-lived tab is still controlled by the old one, and skipWaiting() is missing.

⚠

First load after install is uncontrolled

Working as designed — but surprising if you wanted immediate control and forgot clients.claim().

✕

event.respondWith() rejects, browser shows a network error

Cause: an unhandled exception in the async handler. Always catch and return a fallback Response.

⚠

Worker dies mid-request

Cause: long-running work happening outside event.waitUntil() — the browser doesn't know the worker is still busy.

✕

Quota exceeded

Cause: unbounded cache growth. Nothing evicts the Cache API for you — use LRU or explicit max-entry caps.

⚠

CORS / opaque responses fill the cache with 0-byte holes

Cause: storing responses where response.type === 'opaque'. They count against quota at a padded size and can't be inspected.

Why it exists

No DOM access. The worker runs in parallel with any number of pages. If it could read or write the DOM, every property access would need cross-thread synchronization, and JavaScript's single-threaded determinism would fall apart. Message-passing forces an explicit, serializable interface instead:

HTTPS-only. A Service Worker is a network man-in-the-middle running with the page's authority. If a coffee-shop Wi-Fi could install one over plain HTTP, every site visited from that network could be rewritten silently on future visits. TLS is the prerequisite for trusting the script came from the claimed origin.

Staged install/activate. At deploy time, pages already loaded against the previous worker hold references to old asset URLs. If the new worker activated instantly and wiped the old cache, those tabs would break the moment they next requested a resource. The waiting state is the version-skew guard.

Allowed to be killed and resurrected. Keeping a JS context alive per origin, across dozens of installed sites, would burn battery and memory on mobile. The spec's answer: assume cold start, store anything that must last in quota the storage limit the browser enforces per origin for caches and IndexedDB-bound storage, and treat in-memory state as scratch space.

Why it looks the way it does

The obvious alternative — a declarative cache manifest, which is exactly what AppCache tried — was abandoned. Real caching policy is conditional: different strategies per route, version negotiation, fallback chains, none of which a static manifest can express. The Service Worker design replaces the manifest with a full event handler written in JavaScript. That is a sharper foot-gun — a broken worker can brick the site for returning visitors — mitigated by the 24-hour script-cache cap, the byte-diff update check, and clients.claim() only ever firing when a developer opts in.

Why it matters now

As of 2026, Service Workers are the foundation of the entire PWA story — install prompts, offline behavior, push, background sync — and table stakes for any site that wants to feel fast on flaky connections. They are also what makes browser-side request mocking (MSW) and edge-worker portability possible, since edge platforms share the same fetch-event signature. The API itself is past its churn phase; every evergreen browser ships it, and the interesting movement is in the surrounding APIs — Background Fetch, Periodic Sync, Web Push — not the core.
