Practice — how it plays out for real

● ~10 min read ✎ best practices · anti-patterns · checklist

Where you'll meet it

The worker is invisible until the day it decides whether your app loads instantly on the second visit or hangs waiting on a request that will never land. It's rarely hand-written — a Workbox-based bundler plugin generates it, and your job is picking a strategy per route and owning the update UX.

SaaS frontend

Makes the app load instantly on repeat visits and degrade sanely on a bad connection. Generated by a Workbox plugin; the engineer picks strategies per route.

E-commerce storefront

Caches product images and the storefront shell; checkout and payment calls stay network-only.

Docs site / admin panel

Owns the offline-ready app shell — a precached skeleton that renders even with no network.

Installable PWA

Home for push notifications and background sync — retrying a failed request once the user is back online.

Outside the "PWA" framing: Mock Service Worker (MSW) uses one as a request-interception layer for browser-side test mocks, and sites that want control over fetch for analytics scrubbing, header rewriting, or A/B-test routing eventually write one too.

Best practices

1

Pick a caching strategy per route, not per file extension

Do

Match the strategy to how often the content changes: cache-first for hashed, fingerprinted assets; network-first for HTML and freshness-sensitive APIs; stale-while-revalidate for content the user tolerates a few seconds stale; network-only for anything mutating.

Why

Wrong strategy per route breaks something specific: cache-first on HTML pins users to an old build; network-first on hashed JS pays a pointless round trip every load; anything but network-only on a POST risks replaying a mutation.

Avoid

One blanket strategy applied to every request regardless of what it is.

2

Gate skipWaiting() behind a user action

Do

Let a new worker sit waiting; postMessage the page to show an "update available" toast, and call skipWaiting() only when the user clicks it.

Why

Automatic skipWaiting() can hand a tab new assets mid-session while its DOM was rendered by the previous build — a runtime-loaded chunk can throw from that version skew, and a long-lived dashboard tab or an in-progress checkout is the worst place for it to happen.

Avoid

Calling skipWaiting() unconditionally from install because a tutorial showed it that way.

3

Serve sw.js itself with Cache-Control: no-cache

Do

Keep the worker's own URL stable (always /sw.js, never /sw.abc123.js) and uncached, and keep a "kill switch" branch ready — a no-op worker that calls self.registration.unregister() and clears every cache.

Why

The browser's 24-hour refetch and 86400-second max-age clamp on the script are your cheap, automatic rollback path for a buggy deploy — but only if sw.js isn't itself long-cached or versioned in its URL, which would hide the fix from the browser.

Avoid

A hashed or long-cached sw.js URL. There is no way for the page to discover the next version, and no kill switch ready when you need one.

4

Call event.respondWith() synchronously

Do

Call event.respondWith(handle(event.request)) as the first line of the fetch handler; put all awaits inside handle().

Why

respondWith has to run before the microtask queue drains. Await anything first and the browser has already sent the request to the network — your eventual Response is discarded and interception silently stops.

Avoid

const r = await something(); event.respondWith(r) — the classic way interception quietly breaks.

5

Use Workbox instead of hand-rolling, unless you need something it doesn't model

Do

Reach for Workbox or a framework wrapper (vite-plugin-pwa, next-pwa, Nuxt's PWA module) for the build-time precache manifest, registerRoute(), and strategy plugins (ExpirationPlugin, CacheableResponsePlugin, BroadcastUpdatePlugin).

Why

Almost no one hand-writes a Service Worker in 2026. Workbox already solved precaching, route matching, and expiration correctly; re-deriving it by hand mostly reproduces known bugs.

Avoid

Hand-rolling a full worker when the only reason is unfamiliarity with Workbox. Save raw worker code for push handling, custom analytics interception, or MSW-style mocking — things Workbox doesn't model.

6

Precache an app shell plus an offline fallback page

Do

Precache the minimal HTML/CSS/JS that renders a skeleton, and register a navigation fallback (Workbox's setCatchHandler, or a catch in your own fetch handler) that returns /offline.html when the network fails on navigation.

Why

That one precached file is what the user actually sees the moment their train enters a tunnel.

Avoid

Shipping offline caching for assets with no offline navigation fallback — the user gets a bare browser error page instead of your shell.

7

Version cache names and sweep them in activate

Do

Name caches with a version suffix (app-shell-v7, runtime-images-v3); in activate, enumerate caches.keys() and delete anything not on the current allow-list.

Why

Bumping the version constant is the entire migration story — old caches are deleted only after the new worker has fully installed, so tabs on the old version keep working.

Avoid

Hand-rolling the caching logic and forgetting the sweep. Workbox does this for you automatically.

8

Build an explicit "update available" flow

Do

On the page, listen for updatefound, watch the new worker's statechange to installed, show a toast, postMessage({type:'SKIP_WAITING'}) on click, and reload on controllerchange.

Why

This keeps the deploy under the user's control instead of yanking the carpet mid-action — the same reasoning behind gating skipWaiting() in practice 2.

Avoid

Silent, automatic reloads that interrupt a form fill or a checkout in progress.

9

Treat the worker as a route table a set of matcher-to-strategy rules instead of one large handler, not a pile of ifs

Do

Use registerRoute(matcher, strategy) per route, each with its own cache name, expiration policy, and quota, instead of branching on url.pathname inside one mega-handler.

Why

A route table is auditable — you can point at one line and say what it does. A pile of nested conditionals is not.

Avoid

One fetch handler with a growing chain of if (url.pathname.startsWith(...)) checks.

Anti-patterns to recognize

✕

Cache everything by default

Storage quota fills up, opaque cross-origin responses count at their padded size (often around 7 MB each), and stale 404s or CORS preflight responses come back to haunt you. Cache by allow-list, not deny-list, and gate on response.ok.

✕

Unconditional skipWaiting()

Looks tidy in a tutorial, breaks in-flight tabs mid-checkout. Gate it behind a user action (practice 2).

✕

Forgetting event.waitUntil() in install

The worker transitions to installed before cache.addAll() finishes, leaving a half-populated cache. Wrap every async install task.

✕

Per-user data in shared caches

A logged-out user can be served a logged-in user's cached /api/me. Partition the cache key by user ID, or don't cache authenticated responses at all.

✕

In-memory state in the worker

The browser can kill the worker after roughly 30 seconds idle. A plain let counter = 0 resets silently. Persist to IndexedDB or the Cache API.

✕

Debugging without DevTools' lifecycle controls

Trying to reproduce a stuck worker by hard-refreshing wastes an afternoon. Use the Application panel's lifecycle controls instead.

Real-world usage patterns

Framework-generated PWA

A team ships a Vite/Next app with a PWA plugin generating the worker at build time. Engineers pick strategies per route in config and own the update-toast UX; nobody hand-writes fetch handlers. Lesson: the value-add work is strategy choice and update UX, not writing the worker itself.

Rollback after a bad deploy

A buggy sw.js ships. Because the script is served with Cache-Control: no-cache at a stable URL, the fix ships within the browser's 24-hour refetch window, and the team keeps a no-op "kill switch" worker ready to unregister and clear caches. Lesson: the rollback path only works if the script itself was never long-cached.

Browser-side test mocking

A frontend team uses Mock Service Worker (MSW) so component and integration tests intercept real fetch calls in the browser instead of stubbing the client library. Lesson: the same interception model that powers offline apps also powers test infrastructure.

Consent-driven update toast

A dashboard app with long-lived tabs shows "New version available — Reload" instead of auto-updating. skipWaiting() fires only on click, then the page reloads on controllerchange. Lesson: for session-heavy apps, an ignored update is safer than a silent one.

Operational checklist

✓

Before you call it done

  • Script caching: is sw.js served with Cache-Control: no-cache at a stable, non-versioned URL?
  • Update UX: is the update flow consent-driven (toast + postMessage + controllerchange reload) rather than an unconditional skipWaiting()?
  • Cache sweep: does activate delete every cache key not on the current version's allow-list?
  • Error handling: are self.addEventListener('error', …) and unhandledrejection handlers attached, since silent failures inside respondWith show up only as user-visible network errors?
  • CI smoke test: does it load the page, wait for activated, assert the precache contains the expected entries, then confirm offline navigation works?
  • Kill switch ready: is a no-op unregister-and-clear-caches worker written and ready to ship if a bad deploy needs a fast rollback?
  • Browser quirks checked: have you accounted for Safari's 7-day storage eviction for uninteracted-with sites, and Firefox disabling workers entirely in Private Browsing?

How it evolves in a codebase

  1. Hand-rolled first pass. A cache-first worker for everything ships fine for a demo — no route-specific strategy yet.
  2. First deploy pain. Returning users are stuck on the old worker; the fix is an unconditional skipWaiting()/clients.claim(), which then breaks a long-lived tab mid-session and forces a move to the consent-driven toast flow.
  3. Adopt Workbox. Hand-rolled if chains are replaced by a precache manifest and registerRoute() strategies; expiration and quota move into plugins instead of custom code.
  4. Maturity. The update UX, a tested kill-switch rollback, a CI smoke test for offline navigation, and the Safari/Firefox edge cases are all documented and owned by one team.
