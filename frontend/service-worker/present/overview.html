Overview

◔ ~3 min read ✎ intuition-first

A Service Worker is a small script the browser runs in the background, separate from any tab, that watches every network request your page makes and decides how to answer it.

ⓘ

In 30 seconds

You register it once. After that it sits between your page and the network: it can serve a request from a cache, change it, or just let it pass through untouched. That one power is what makes web apps feel "app-like" — instant loads, working offline, push notifications, and background sync — without shipping a native app. It is the official, standards-track way to control the network layer in the browser.

The mental model

Picture every request your page makes — an image, a script, a JSON call — as a letter dropped in a mailbox. Without a Service Worker the letter goes straight to the network. With one installed, you have a personal mail clerk who reads the address first and picks one of three answers:

  • "I already have a copy in the filing cabinet — here you go." (cache hit)
  • "Let me run to the post office and bring back the reply." (network pass-through)
  • "The post office is closed today; here is last week's copy with a note." (offline fallback)

The clerk only ever looks at the envelope. It cannot read what is inside your house — no DOM, no window, no document — and it never blocks the page while it works. Its authority is limited to the scope the URL prefix the worker is allowed to answer requests for: a worker registered at the site root can see every request; one tucked into a subfolder only sees requests under that subfolder.

What it is not

⚠

Common mix-ups

  • Not a Web Worker. A Web Worker also runs off the main thread, but it belongs to a single page and exists to offload CPU work. A Service Worker outlives any page and exists to intercept network traffic.
  • Not the Cache API. The Cache API is a key/value store of request/response pairs. Service Workers use it heavily, but the cache works fine without a Service Worker, and a worker can ignore the cache entirely.
  • Not Application Cache (AppCache). AppCache was the previous attempt at offline web. It is deprecated and removed. Service Workers replaced it.
  • Not a server. It runs on the user's own device, inside their browser, scoped to one origin.

When to reach for it — and when not to

✓ Reach for it when

  • You want the app to open and render something useful with no network connection.
  • You need fine-grained caching that HTTP cache headers can't express — stale-while-revalidate, cache-first for shells, network-first for APIs.
  • You need to receive push notifications when the site isn't open.
  • You want background sync — retrying a failed POST once the user is back online.
  • You are building a Progressive Web App and need an installable, offline-capable shell.

✕ Skip it when

  • The site is a single static landing page with no offline needs — HTTP caching is enough.
  • You need to touch the DOM in the background. Workers can't; use a Web Worker plus postMessage instead.
  • You have no HTTPS and can't get a certificate. Workers only run over HTTPS, except on localhost for development.
  • You need synchronous access to page state. The worker is event-driven and decoupled by design.

Key vocabulary

Registration
The one-time call from a page — navigator.serviceWorker.register('/sw.js') — that tells the browser to install this script.
Scope
The URL prefix the worker controls. A worker at /sw.js controls everything under /; one at /app/sw.js controls only /app/.
Lifecycle states
parsed, installing, installed (waiting), activating, activated, redundant.
install event
Fires once per worker version; the place to pre-populate caches.
activate event
Fires when this worker is about to take control; the place to clean up old caches.
fetch event
Fires for every network request inside scope; where the "mail clerk" makes its decision.
Controlled client
A page (tab, iframe) currently governed by an active worker.
Cache API
The caches global — a request/response key-value store the worker reads and writes.
skipWaiting / clients.claim
Opt-in calls that let a new worker take over immediately instead of waiting for every tab to close.
