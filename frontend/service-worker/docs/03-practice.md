# Service Worker — In Practice

> Builds on `01-overview.md` and `02-deep-dive.md`. Read those first.

## Where you'll actually meet this topic

In a typical SaaS frontend, the Service Worker is the thing that makes the app load instantly on the second visit and degrade sanely when the user's train enters a tunnel. It is rarely written by hand — it is generated by a Workbox-based plugin wired into the bundler, and the engineer's job is to pick strategies per route and own the update UX. In an e-commerce frontend, it caches product images and the storefront shell; in a docs site or admin panel, it owns the offline-ready app shell; in a mobile-web product targeting installable PWAs, it is the home for push notifications and background sync.

You also meet Service Workers outside the "PWA" framing: Mock Service Worker (MSW) uses one as the interception layer for browser-side test mocks, and any site that wants control over `fetch` for analytics scrubbing, header rewriting, or AB-test routing eventually ends up writing one.

## Caching strategies, applied

Pick a strategy per route, not per file extension. The named strategies from `02-deep-dive.md § How` map to production use as follows:

- **Cache-first** — immutable, fingerprinted assets (`app.8a1f.js`, hashed CSS, woff2 fonts, versioned image bundles). If you pick this for HTML, the user gets pinned to an old build and you cannot ship.
- **Network-first** — the HTML document and any "freshness matters" API (account balance, inventory count). If you pick this for hashed JS, you pay a network round-trip on every load for no reason.
- **Stale-while-revalidate** — avatars, list endpoints, search suggestions, anything the user tolerates being a few seconds stale. If you pick this for the HTML shell, two consecutive deploys produce a visible flash of old chrome.
- **Network-only** — `POST` / `PUT` / `DELETE`, payments, anything mutating, analytics beacons. If you pick anything else, you risk replaying mutations or returning a cached `200 OK` for a write that never happened.
- **Cache-only** — the precached app-shell HTML used as the offline fallback, and only that. If you pick this for runtime requests, the first miss is a hard failure and you spend an hour wondering why the offline page renders fine but nothing else loads.

## Lifecycle gotchas teams actually hit

**"The old worker still controls the page."** After a deploy, returning users keep the old worker until every controlled tab closes. Long-lived dashboard tabs make this effectively forever. `self.skipWaiting()` in `install` plus `self.clients.claim()` in `activate` cuts through the wait, but only do that if your new assets are still safe to serve to a DOM rendered by the previous build — version-skew on a runtime-loaded chunk will throw at runtime. The conservative pattern is: do not call `skipWaiting()` automatically; instead `postMessage` the page when a new worker is `waiting`, let the user click "Reload to update," and call `skipWaiting()` only in response to that message.

**"I shipped a bug in `sw.js` and now no users can update."** The browser refetches the worker script on navigations and at most every 24 hours, and silently clamps `max-age` on the script to 86400 seconds (see [Chrome's Fresher service workers notes](https://developer.chrome.com/blog/fresher-sw)). So a buggy worker is recoverable within a day in the worst case — but only if your `sw.js` itself is **not** served with a long `Cache-Control`, **not** versioned in its URL, and **not** itself cached by the worker. Always serve `sw.js` with `Cache-Control: no-cache` (or `max-age=0`). Keep a "kill switch" branch ready that publishes a no-op worker that calls `self.registration.unregister()` and clears `caches`. That is your rollback.

**"Navigation requests stop hitting my fetch handler."** Scope is determined by the script's URL path. A worker at `/static/sw.js` controls only `/static/*` — your HTML at `/` is uncontrolled, no `fetch` event fires for navigations. Either move the script to the site root, or have the static origin return the [`Service-Worker-Allowed`](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Service-Worker-Allowed) header.

**"I `await`ed before calling `event.respondWith`."** `respondWith` must be called synchronously, inside the `fetch` handler's invocation, before the microtask queue drains. The pattern is:

```js
self.addEventListener('fetch', (event) => {
  event.respondWith(handle(event.request)); // sync call; async work inside
});
```

If you `await` first, the browser has already moved on, the request goes to the network, and your handler's eventual `Response` is discarded.

## Production patterns mature teams use

**Almost no one writes raw Service Workers in 2026.** They use [Workbox](https://developer.chrome.com/docs/workbox) or its framework wrappers (`vite-plugin-pwa`, `next-pwa`, Nuxt's PWA module). What Workbox gives you, concretely: a build-time precaching manifest (a list of `{url, revision}` for every hashed asset, injected into the worker), runtime route registration (`registerRoute(matcher, strategy)`), strategy classes with plug-in slots for `ExpirationPlugin`, `CacheableResponsePlugin`, `BroadcastUpdatePlugin`, and a `Workbox` class on the page side that exposes `waiting`/`controlling` events. Reach for raw worker code only when you are doing something Workbox does not model — push handling, custom analytics interception, MSW-style mocking.

**App shell plus offline page.** Precache the minimal HTML/CSS/JS that renders a skeleton, and register a navigation fallback (`setCatchHandler` in Workbox, or a `catch` inside your fetch handler) that returns `/offline.html` when the network fails on a navigation request. That single file is what users see in the tunnel.

**Versioned cache names with an activate-time sweep.** Name caches `app-shell-v7`, `runtime-images-v3`, etc. In `activate`, enumerate `caches.keys()` and delete anything not in your current allow-list (see `02-deep-dive.md § How`). Workbox does this for you; if you hand-roll, do not forget it.

**The "update available" UX flow.** Page-side:

```js
const reg = await navigator.serviceWorker.register('/sw.js');
reg.addEventListener('updatefound', () => {
  const next = reg.installing;
  next.addEventListener('statechange', () => {
    if (next.state === 'installed' && navigator.serviceWorker.controller) {
      showUpdateToast(() => next.postMessage({ type: 'SKIP_WAITING' }));
    }
  });
});
```

Worker-side: `self.addEventListener('message', (e) => { if (e.data?.type === 'SKIP_WAITING') self.skipWaiting(); })`. Reload the page on `controllerchange`. This pattern keeps the deploy under the user's control instead of yanking the carpet mid-action.

**Treat the worker as a route table, not a pile of `if`s.** Instead of branching on `url.pathname.startsWith('/api/')` inside one mega-handler, use `registerRoute(({ url }) => url.pathname.startsWith('/api/'), new NetworkFirst({...}))`. Each route gets its own strategy instance with its own cache name, expiration policy, and quota. This is the difference between a worker you can audit and one you cannot.

## Anti-patterns to avoid

- **Cache everything by default.** Storage quota fills up, opaque cross-origin responses count as their padded size (often ~7 MB each), and stale 404s or stale CORS preflight responses come back to haunt you. Cache by allow-list, not deny-list, and gate on `response.ok` plus `CacheableResponsePlugin({ statuses: [0, 200] })` only where opaque is genuinely intended.
- **Unconditional `skipWaiting()`.** Looks tidy in tutorials, breaks in-flight tabs that are mid-checkout. Gate it behind a user action.
- **Forgetting `event.waitUntil()` in `install`.** The worker transitions to `installed` before your `cache.addAll` finishes, leaving a half-populated cache. Wrap every async install task in `event.waitUntil()`.
- **Per-user data in shared caches.** A logged-out user can be served a logged-in user's cached `/api/me`. Partition by including the user ID in the cache key, or do not cache authenticated responses at all.
- **In-memory state in the worker.** The browser kills the worker after ~30 seconds idle (see `02-deep-dive.md § When`). A `let counter = 0` resets silently. Persist to `IndexedDB` or `caches`.
- **Debugging without DevTools' lifecycle controls.** Trying to repro a stuck worker by hard-refreshing is a waste of an afternoon. Use the Application panel.

## Testing, debugging, observability

**DevTools.** The Application > Service Workers panel exposes the lifecycle: "Update on reload" forces a refetch and skip-wait on every reload (use during development, never in production reasoning), "Bypass for network" disables the worker entirely for the tab, and "Unregister" plus "Clear storage" is your nuclear reset. The Cache Storage tree below it lets you inspect every entry. Chromium also exposes `chrome://serviceworker-internals` for cross-origin debugging and forced starts.

**Instrumentation.** Worker code cannot reach `window.Sentry` or your usual frontend logger. Two patterns: `postMessage` log lines from the worker to all controlled clients, which forward to your normal pipeline; or import a worker-aware SDK (Sentry, Datadog RUM both ship worker builds). Always attach `self.addEventListener('error', ...)` and `self.addEventListener('unhandledrejection', ...)` — silent failures inside `event.respondWith` show up as user-visible network errors with no stack.

**CI / update strategy.** Bundlers emit hashed asset filenames; your `sw.js` should reference them via a generated precache manifest so a new asset implies a new worker. Serve `sw.js` with `Cache-Control: no-cache` and a stable URL (`/sw.js`, never `/sw.abc123.js` — there would be no way for the page to find the next version). Run a smoke test that loads the page, waits for `activated`, asserts the precache cache contains the expected revisions, and reloads to confirm offline navigation works.

## Browser support and sharp edges in 2026

Universally supported across evergreen Chrome, Edge, Firefox, and Safari. Safari is still the strictest on storage eviction (the [7-day cap on script-writable storage](https://webkit.org/blog/10218/full-third-party-cookie-blocking-and-more/) for sites the user has not interacted with applies to the Cache API and IndexedDB) and was the last to ship Web Push for installed PWAs — iOS got it in 16.4 (early 2023) and parity with desktop is still imperfect. Private-browsing modes vary: Firefox disables Service Workers entirely in Private windows; Chrome allows them but storage is wiped on session end. Plan for the cache disappearing, not for the cache lasting forever.
