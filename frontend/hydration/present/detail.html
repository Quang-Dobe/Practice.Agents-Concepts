Detail — the deep dive

◑ ~10 min read ✎ What · Where · When · How · Why

What it is

Hydration is the process by which a client-side UI framework adopts a pre-existing DOM subtree produced by a server (SSR) or a build step (SSG), walks its own component tree against that DOM in lockstep, attaches event listeners, restores state from a serialized payload, and runs mount-time effects — without recreating the DOM nodes already on the page.

  • It's a proof, not just a render. Given a server-rendered subtree and a client component tree, hydration is a walk that checks the two agree, while populating the framework's own runtime structures (React's Fiber tree, Vue's vnode tree, Svelte's component instances).
  • Every node ends up owned by one component. The walk finishes with each DOM node claimed by exactly one component instance.
  • Mismatches force a choice. If the check fails — wrong node, wrong attribute, wrong text — the framework either throws that piece away and re-renders it from scratch (Vue, older React), or logs an error and patches what it can (React 18+).

The core building blocks

Server renderer
renderToString / renderToPipeableStream (React), renderToString (Vue), Svelte's render, SolidJS's renderToStringAsync. Produces HTML plus a separate serialized state payload.
Serialized state envelope
The JSON blob shipped alongside the HTML so the client doesn't refetch: __NEXT_DATA__ in Next.js, __NUXT__ in Nuxt, a <script> tag SvelteKit's runtime reads on boot.
Client hydration entry point
hydrateRoot(domNode, <App/>) (React 18+), createSSRApp(App).mount('#app') (Vue 3), hydrate(App, { target }) (Svelte), hydrate(() => <App/>, root) (SolidJS).
Reconciler
The framework's tree-walking diff engine in hydration mode — the Fiber reconciler for React, the hydrate function in Vue's runtime core, generated index-walking code for Svelte.
Event delegation system
A small number of root-level listeners dispatching synthetic events down to the matched component, instead of one DOM listener per handler.

Hydration sits inside the family of isomorphic / universal rendering strategies. Its siblings differ in how much work the client repeats:

Hydration is the default for SSR-capable JS frameworks; islands and resumability both exist as answers to its cost.

Where it lives

Hydration is a browser-runtime concern, but it depends on three other layers cooperating:

1 · Server / build pipeline

Runs the SSR renderer, emits HTML and the state envelope.

2 · Bundler

Produces the client JS bundle with the same component code the server ran, plus the runtime in hydration mode. Code-splitting here decides hydration granularity.

3 · Framework runtime

The Fiber / vnode / instance machinery that performs reconciliation in the browser.

Where you typically encounter it

  • Next.js App Router — React Server Components by default; 'use client' components hydrate via hydrateRoot, streamed by renderToPipeableStream.
  • Nuxt 3 — Vue 3's createSSRApp under the hood, with <ClientOnly> as the standard mismatch escape hatch.
  • SvelteKit — hydration per route, controllable via the csr page option.
  • Remix — React, hydrates the full route tree.
  • SolidStart — SolidJS hydrate, fine-grained reactivity instead of a virtual-DOM diff.
  • Astro — explicit client:load, client:visible, client:idle, client:media directives per island.
  • Qwik / QwikCity — does not hydrate; it resumes instead.

Ecosystem and tooling

  • Diagnosing mismatches: the React DevTools Components tab, browser-extension detection scripts, the Next.js dev overlay, why-did-you-render.
  • Deferring hydration: react-lazy-hydration, Astro's client:* directives, Nuxt lazy-hydration helpers.
  • Replacing hydration: Qwik (resumability), Marko (server-driven streaming with auto-islands), HTMX (no hydration — it re-renders fragments from the server).
  • State serialization: superjson, devalue (used internally by SvelteKit), Next's built-in JSON serializer.

When to use it

✓ Reach for SSR + hydration when

  • The site is content-driven and needs FCP under ~1.5s on mobile.
  • SEO or a social-card preview matters and content is dynamic per request (logged-in user, A/B test, geo).
  • The app is interactive enough that a pure templating stack (Rails, Django, Razor Pages) would force a round trip on every click.
  • You're already on a meta-framework that defaults to it.

✕ Avoid it when

  • The page has zero JS interactivity — ship plain HTML; you don't need a framework runtime at all.
  • The app is behind auth and SEO/FCP don't matter — CSR is simpler, no SSR infra to run.
  • The page is dynamic per keystroke (a complex editor) — the hydration cost happens once but the bundle stays the same size; you pay for SSR without much FCP benefit if users dwell for minutes.
  • You can't keep server and client output deterministically equal (heavy Date.now, locale APIs, scattered window checks). Fighting mismatches will cost more than the win.
◆

Two narrower alternatives

Reach for islands or RSC when most of the page is static and only a few regions are interactive — product pages, marketing sites, docs, blogs with a comment widget. Reach for resumability when interactivity must feel instant on slow devices and the serialized framework state is small enough to fit in the HTML payload without ballooning bytes-over-wire.

A little history

The term appears in the React ecosystem around 2015, when ReactDOM.render first accepted server-rendered markup, and is named explicitly with ReactDOM.hydrate in React 16 (2017). Before SSR-aware reconciliation, libraries like Meteor and react-dom-stream patched HTML by hand or threw away server markup on mount. The motivation: pure CSR's blank-page problem hurt SEO and Core Web Vitals, while pure server templating (Rails, Django) couldn't deliver SPA-like interactivity. React 18 (2022) reshaped hydration again with hydrateRoot, streaming SSR via renderToPipeableStream, and selective hydration through Suspense boundaries.

How it works

Walk a single request through a React 18 Next.js pipeline — the canonical case:

  1. Request arrives. Next.js routes it to a page module.
  2. Server-side render. renderToPipeableStream(<App/>) walks the tree. A Suspense boundary that hits a pending promise emits a fallback in its HTML slot and rendering continues for its siblings.
  3. Stream flush. onShellReady fires once the non-suspended shell is done; the server pipes that HTML to the client. Extra chunks append as suspended parts resolve.
  4. Payload emitted. Next embeds self.__next_f.push([...]) chunks carrying the RSC payload a serialized description of the rendered tree, including props for client components.
  5. Client receives HTML. The browser parses and paints — FCP happens here, before any framework JS runs.
  6. Client bundle loads. The runtime and every 'use client' component arrive, code-split per route.
  7. hydrateRoot runs. React allocates a Fiber tree; for each fiber it expects a matching DOM node at the current cursor. It adopts existing nodes — it never creates new ones.
  8. Event delegation attaches. React installs delegated listeners at the root so matched fibers can receive synthetic events.
  9. Effects run. useEffect callbacks fire after the initial commit, in the same order as a normal first render.
  10. Selective hydration kicks in. If a Suspense boundary 's JS hasn't arrived, React skips it and keeps hydrating the rest. A click inside a not-yet-hydrated boundary makes React prioritize hydrating that boundary first.

The reconciler the framework's tree-walking engine that matches fibers or vnodes to existing DOM nodes behaves differently per framework once a mismatch appears. React 18 logs an error and, for the offending subtree, falls back to a two-pass render. Vue is more aggressive: any mismatch logs a warning and bails hydration entirely for the affected component, discarding the server DOM and re-rendering it. Svelte walks the existing DOM by node index using compiled code — cheapest of the four at runtime, least forgiving of mismatches.

How resumability differs

Qwik's resumability is a structurally different answer, not just a faster hydration:

  • Hydration re-executes component functions on the client to rebuild the framework's in-memory state. Qwik instead serializes that state.
  • Listener locations become on:click attributes pointing at lazy-loaded chunk URLs.
  • Component boundaries are encoded as HTML comments; reactive state is JSON in a <script type="qwik/json"> block.
  • The first interaction downloads only the closure for that one handler — the framework picks up from the serialized state without running parent components again.
  • The cost lands on the wire (a larger HTML payload) and in the mental model — code has to be written so it survives serialization.

Common failure modes

✕

Date.now() / Math.random() in render

The server clock and client clock differ, so the very first paint mismatches.

✕

Conditional render on typeof window

The server renders one branch, the client renders the other — a guaranteed mismatch.

⚠

Locale-dependent formatting

toLocaleString() and Intl.DateTimeFormat without an explicit timeZone produce different output in Node than in the browser.

⚠

Invalid HTML nesting

A <div> inside a <p>, or a missing <tbody>. The browser parser auto-corrects it; the framework's vnode tree doesn't, so a mismatch follows.

⚠

Browser extensions injecting attributes

Grammarly and password managers add data-* attributes before hydration runs. React 18 tolerates attribute-only mismatches; older versions don't.

✕

Reading localStorage during render

Only available on the client. Common in theme switchers, and a guaranteed first-paint mismatch.

✕

Stale CDN HTML + a fresh JS bundle

A deployed bundle expecting new props meets cached HTML from yesterday's render.

◆

Accepted escape hatches

Render the dynamic part only after mount (useEffect + a state flag), gate it with <ClientOnly> (Nuxt) or client:only (Astro), or annotate the one offending element with suppressHydrationWarning (React) — one level deep and explicitly a silencer, not a fix.

Why it exists

Hydration bridges two contradictory requirements: show something fast and let crawlers read it (favors HTML from the server), and behave like an app (favors a client-side component tree with state and listeners). Without hydration, the only way to satisfy both was to render twice — once as HTML, once as a fresh client mount — and let the client mount visibly clobber the server output. Hydration makes that second mount adopt the first, cutting the flash and the duplicate DOM allocation.

At a deeper level, it exists because the browser's HTML parser and a JS framework's vnode/Fiber tree don't share an internal representation. Hydration is the protocol that reconciles those two representations onto a single set of DOM nodes.

Why it looks the way it does

The obvious alternative — serialize the full framework state on the server and ship it so no re-execution is needed — is what Qwik does. Mainstream frameworks didn't start there because serializing arbitrary JS closures, class instances, and effect graphs is hard: React render functions can close over module-scope variables, third-party hooks, and provider context with no clean JSON form. Re-executing the same code on both sides and reaching the same state is the path of least resistance — no serialization protocol to design.

The two-pass render fallback exists for a similar reason. React could try to patch individual nodes on mismatch, but the reconciler's invariants assume the tree is consistent. Once that invariant is lost in a subtree, throwing it away and re-rendering is the only safe move.

Selective hydration via Suspense exists because all-or-nothing didn't scale: one slow <Comments> component shouldn't block the rest of the page from becoming interactive. Suspense boundaries give the framework a natural unit at which to split the work.

Why it matters now

As of mid-2026 the frontier has moved past "hydrate everything." React Server Components are the default in the Next.js App Router, Astro's island model is the recommended path for content sites, and Qwik has shown near-zero TTI is possible at the cost of a different programming model. Every modern framework roadmap is now dominated by how to ship less hydration, not how to make hydration faster. Understanding the mechanism still matters, because every design choice in those newer models — what counts as a client boundary, what gets serialized, when listeners attach — only makes sense once you know what hydration actually does and what it costs.

Try it yourself

  • Measure the gap between FCP and TTI on a real app with the browser's Performance panel — is hydration the dominant cost, or is it bundle parse time?
  • Force a mismatch (e.g. {new Date().toString()} in a server component) and read the dev-overlay output.
  • Compare bundle sizes for the same page as (a) all client components, (b) RSC + minimal 'use client' leaves, (c) an Astro island.
  • Inspect a Qwik page's HTML payload size — is the serialized state worth the FCP cost on a slow network?
  • Throttle the network and click inside a not-yet-hydrated Suspense boundary to confirm React prioritizes it.
  • The code folder has a runnable SSR + hydrateRoot demo that exercises a deliberate mismatch and shows the recovery.
