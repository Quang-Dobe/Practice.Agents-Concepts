Overview

◔ ~3 min read ✎ intuition-first

A server turns your component tree into a string of HTML and ships it to the browser. The user sees real content right away, but clicking anything does nothing yet — no JavaScript has run.

ⓘ

In 30 seconds

The framework's JS bundle then loads, walks the same component tree on the client, and lines itself up against the DOM that's already there: same nodes, same order, now wired up with handlers and state. That second pass is hydration. You get a fast first paint and search-engine-friendly HTML without giving up an interactive app.

The mental model

Think of the server response as an unfurnished house that's already built — walls, floors, windows in the right places. The user can walk through it the moment they arrive. A moving truck (the JS bundle) shows up a few seconds later carrying the appliances, light switches, and remote controls.

The critical detail: the DOM is not thrown away and rebuilt. Hydration adopts what's already there. Re-rendering from scratch would defeat the speed win the server just gave you. If the client's tree doesn't line up with the server's — a wall in the wrong spot — that's a hydration mismatch the server HTML and what the client would have rendered disagree, and the framework has to patch it up or throw the mismatched part away and re-render it.

What it is not

⚠

Common mix-ups

  • Not client-side rendering (CSR). CSR ships a near-empty <div id="root"> and makes the browser render everything from JS. No HTML until JS runs.
  • Not plain server-side rendering (SSR). Pure SSR sends HTML and stops. The page is visible but inert — no state, no click handlers.
  • Not server-side templating (Jinja, ERB, Razor). Those render HTML once and reload the whole page for every click; there's no client-side component tree to line up against.
  • Not static site generation (SSG) by itself, though SSG output usually gets hydrated the same way SSR output does.

When to reach for it — and when not to

✓ Reach for it when

  • You need fast FCP and good SEO, but the app has rich client-side interactivity (dashboards, e-commerce, social feeds).
  • You're using a meta-framework that defaults to it: Next.js, Nuxt, SvelteKit, SolidStart, Remix.
  • Your content is partly dynamic per user (logged-in state, personalization), so a pure static cache isn't enough.

✕ Skip it when

  • It's a pure marketing site with no interactivity — ship static HTML and a sprinkle of vanilla JS; you don't need a framework runtime.
  • It's an internal tool behind a login where TTI matters more than FCP — a plain CSR single-page app is simpler.
  • The content is truly static and SEO-driven — SSG without hydration, or with islands mostly static HTML with a few isolated interactive regions that hydrate on their own, gives you smaller bundles.

Key vocabulary

SSR
Server-side rendering — producing HTML on the server per request.
SSG
Static site generation — producing HTML once at build time.
CSR
Client-side rendering — the browser builds the DOM from JS.
FCP
First Contentful Paint — when the user first sees real content.
TTI
Time To Interactive — when the page actually responds to clicks.
Hydration mismatch
Server HTML and client render disagree; React logs an error and may discard the server tree.
hydrateRoot
The React 18+ API that hydrates a server-rendered tree (replaces the older ReactDOM.hydrate).
Partial / progressive hydration
Hydrating only some components, or hydrating them over time instead of all at once.
Islands architecture
Ship mostly static HTML with isolated interactive islands that hydrate independently (Astro, Fresh).
Resumability
Qwik's alternative to hydration; the server serializes enough state that the client can pick up without re-running component code.
