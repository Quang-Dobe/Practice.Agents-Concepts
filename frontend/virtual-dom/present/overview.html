Overview

◔ ~3 min read ✎ intuition-first

The browser's DOM is a live tree, and touching it — creating nodes, setting attributes, reading layout — is slow. Naive UI code touches it constantly.

ⓘ

In 30 seconds

A Virtual DOM describes what the UI should look like as plain JS objects — a vnode a plain JS object describing one element: its type, props, and children tree. The framework compares the new description to the old one and only then writes the difference to the real DOM. React popularized the idea in 2013; Vue, Preact, Inferno, and Snabbdom use the same shape of trick.

The mental model

Picture a teacher standing at a whiteboard full of equations. A student walks up every few seconds and says "here is what the board should look like now," holding out a fresh photo. The teacher has two choices:

  • The lazy choice. Erase the whole board and copy the new photo from scratch. Correct, but slow, and the class watches it flicker the whole time.
  • The smart choice. Hold the old photo next to the new one, spot the parts that actually differ, and erase-and-rewrite only those. Most of the board stays untouched.

The Virtual DOM is the photo: cheap to make (just objects in memory), cheap to compare (just walking two trees), and the one expensive step — touching the whiteboard — happens once per update, in a tight batch, only for the cells that changed. A vnode itself is nothing fancy:

{ type: 'div', props: { className: 'card' }, children: [
  { type: 'h1', props: {}, children: ['Hello'] }
]}

Your render function returns one of these trees every time. The framework keeps the last tree it saw, runs reconciliation the diff-then-patch process that turns two trees into a minimal set of real DOM writes against the new one, and emits real DOM calls — createElement, setAttribute, removeChild — only for what changed. You write declarative code; the framework does the imperative surgery.

The pipeline in one line each

  • Render. A component function returns a fresh vtree describing the wanted UI.
  • Diff. The framework compares that tree to the last one it committed.
  • Patch. Only the real DOM calls for what changed actually run.

What it is not

⚠

Common mix-ups

  • Not the real DOM. It's a plain-object mirror; the browser never sees it.
  • Not the Shadow DOM. Shadow DOM is a browser feature for style and scope encapsulation in Web Components — a different, unrelated thing.
  • Not automatically faster than hand-written DOM code. A careful imperative update will beat it. VDOM trades peak speed for a sane programming model.
  • Not required for reactivity. Svelte and SolidJS skip the VDOM entirely and still get fine-grained updates.

When to reach for it — and when not to

✓ Reach for it when

  • State changes ripple across many nodes and you don't want to track which DOM bits to mutate by hand.
  • You want a declarative state → UI function and are willing to pay a small diffing cost for it.
  • You're picking a framework (React, Vue, Preact) — the VDOM comes with the box.

✕ Skip it when

  • You're updating one counter on an otherwise static page — textContent = is faster and simpler.
  • You need the lowest possible latency per keystroke (high-frequency canvas or game UIs) — go imperative or use a compiler-based framework like Svelte.
  • Your app is server-rendered HTML with a sprinkle of interactivity — htmx or vanilla JS is lighter.

Key vocabulary

DOM
The browser's live tree of element nodes.
VNode
A plain JS object describing one element (type, props, children).
VTree
A tree of vnodes — what one render pass produces.
Diff
Walking the old and new vtrees to find what changed.
Patch
The list of real-DOM operations the diff produces.
Reconciliation
The whole diff-then-patch process.
Key
A stable identifier on a list item so the diff can match nodes across renders instead of guessing.
Mount / Unmount
First insertion of a vnode into the DOM, and its removal.
