Practice — how it plays out for real

● ~10 min read ✎ best practices · anti-patterns · checklist

Where you'll meet it

The Virtual DOM is invisible until the day a list jitters during reorder, an input loses focus on every keystroke, or the Performance tab shows 80 ms of scripting per click — at which point it's suddenly the whole job. Four shapes come up again and again:

Long, reorderable lists

Kanban boards, inbox views, query result tables.

Form-heavy screens

Every keystroke causes a parent re-render.

Dashboards

The same context fans out to dozens of widgets.

Editor-like UIs

Rich text, canvas overlays, drag-and-drop — where VDOM ownership collides with imperative DOM state.

Best practices

1

Key list items by stable identity, never by array index

Do

Use the item's own id — key={user.id}, key={message.uuid}, key={`${row.id}-${col.id}`} for grids. If your data has no id, generate one at creation time, not render time, and store it with the item.

Why

The diff matches children by key. Index keys work silently until rows reorder, insert at the head, or get filtered — then DOM state (input value, focus, animation, video position) follows the position instead of the item. It's the single most common reconciliation bug.

Avoid

key={i}, key={Math.random()}, key={JSON.stringify(item)}. The first lies about identity, the second forces an unmount and remount every render, the third is slow and brittle.

// Bad — type into row 2, delete row 1, your text is now in row 1.
{rows.map((row, i) => <Row key={i} row={row} />)}

// Good — text follows the row because identity is stable.
{rows.map(row => <Row key={row.id} row={row} />)}
2

Stabilize prop references before reaching for memo

Do

Wrap callbacks in useCallback, derived objects and arrays in useMemo, and hoist literals out of render. Only then wrap the receiving child in React.memo. In Vue 3, prefer shallowRef for big objects you replace by reference (chart data, editor documents).

Why

React.memo does a shallow comparisonchecking prop equality one level deep, by reference, not by deep value of props. If the parent re-renders and passes a fresh object or inline function, the reference is new every time, equality fails, and memo does nothing except cost a comparison.

Avoid

Sprinkling memo on every component "just in case" without checking what props it actually receives. Premature memo is dead code with a benchmark cost.

3

Lift state down, not up, when only a leaf cares

Do

If only a search box needs the query string, keep its useState inside that component, not the page-level parent. Split a fat parent into children that own their own slices.

Why

A re-render of a parent re-renders every child whose memoization fails. Keeping state at the leaf turns a 200-component re-render into a 1-component re-render with no memo gymnastics.

Avoid

Hoisting every piece of state to the top "because it's cleaner." It centralizes complexity and broadcasts re-renders.

4

Treat context values as immutable identities

Do

Memoize the value passed to a Provider. Split unrelated state into separate contexts — one for theme, one for auth, one for the current user — instead of one mega-context.

Why

Every consumer of a context re-renders when the provider's value identity changes. A fresh object literal on every parent render fans out to every consumer in the tree.

Avoid

<Ctx.Provider value={{ user, setUser }}> written inline. That object is fresh every render.

5

Read the Profiler before optimizing

Do

Open React DevTools Profiler, enable "record why each component rendered," run the interaction, then read the flamegraph. Warm-colored bars are slow renders; gray bars didn't re-render.

Why

Memoization decisions made without measurement are almost always wrong. The Profiler names which prop's identity changed and which subtree to actually fix.

Avoid

Optimizing components you haven't measured. In Vue 3, the Vue DevTools Performance tab does the same job — look for components that light up on every update when they shouldn't.

6

Use v-memo and shallowRef deliberately in Vue 3

Do

Reach for v-memo on large v-for lists whose items rarely change (v-memo="[item.id, item.updatedAt]"). Use shallowRef when wrapping objects you mutate by replacement — chart datasets, editor instances, large parsed ASTs.

Why

Vue's runtime is already cheap thanks to patch flags, but big lists and deeply nested reactive proxies are where it still hurts. shallowRef skips reactivity recursion below the root.

Avoid

Wrapping every ref in shallowRef "for performance." You lose reactivity on mutations and spend an afternoon debugging why the UI doesn't update.

7

Virtualize lists past a few hundred rows

Do

Use react-window, react-virtuoso, or vue-virtual-scroller once row count exceeds the viewport by more than roughly 3×. This is virtualizationrendering only the rows currently visible, recycling a small pool of DOM nodes as the user scrolls.

Why

VDOM cost is per node, not per pixel. The diff is O(n), but n = 10,000 still allocates 10,000 vnodes per render. Virtualization caps n at "what's visible."

Avoid

Building your own "render only what's visible" with scrollTop listeners. Edge cases — variable row height, keyboard navigation, screen readers — eat months.

8

Escape the VDOM with refs for imperative APIs, not to "fix" rendering

Do

Use a ref when the browser API is imperative by nature: input.focus(), element.scrollIntoView(), attaching a third-party widget to a <div>. For layered UI (modals, tooltips, toasts) use a portalrendering a node into a different part of the real DOM tree while it stays in the same place in the component tree logically so it renders into document.body while the framework still owns its lifecycle.

Why

Refs are the sanctioned escape hatch. Portals keep stacking-context bugs out of your tree without breaking event bubbling or context.

Avoid

Calling flushSync to "force a render," mutating DOM children the framework also renders, or stashing DOM nodes you appended yourself inside a managed parent. The next reconciliation overwrites or orphans them.

9

Don't define components inside other components

Do

Declare every component at module scope. If it needs to close over props, pass them in explicitly.

Why

A component declared inside a parent's function body gets a new function identity on every parent render. The framework sees a different type, tears down the whole subtree, and remounts it — state, focus, and animations all reset.

Avoid

Inline component declarations inside JSX, render props that close over state setters without useCallback, and higher-order components applied inside render.

10

Know when to leave the VDOM behind

Do

For input-heavy or animation-heavy surfaces — trading grids, audio meters, real-time canvas overlays, large form builders — evaluate Solid, Svelte 5, or Vue Vapor Mode. They skip the diff in the steady state and update only the bound DOM nodes.

Why

The VDOM has a fixed per-render floor: allocate vnodes, walk the tree, compare props. At 120 Hz on a 5,000-node screen, that floor becomes the bottleneck no amount of memo can fix.

Avoid

Rewriting a CRUD dashboard in Solid to chase a 2 ms benchmark. Most apps are bound by ergonomics, not by the VDOM. The rewrite is worth it only when the Profiler shows the reconciler itself, not your code, as the long pole.

Anti-patterns to recognize

✕

key={Math.random()} or key={Date.now()}

Looks like it gives every item a unique key; actually forces an unmount and remount every render, destroying state and animations. Use the item's own id.

✕

A new object literal in a memoized child's props

<Child style={{margin: 8}} /> next to React.memo(Child). Memo never hits; everything re-renders. Hoist the literal out of render or useMemo it.

✕

Context as a state-management bus

One Provider with a giant combined value re-renders every consumer on any change. Split contexts by update frequency and audience.

✕

Conditional element type

{condition ? <div>…</div> : <section>…</section>} around the same children. The type change forces a full unmount. Put the conditional inside the element, not around it.

✕

Calling forceUpdate or flushSync to "make it render now"

Almost always covers for state that should live in the framework's reactivity and doesn't. Move the state in; remove the force.

✕

Direct DOM mutation on managed nodes

document.querySelector('.row').classList.add(...) inside a component the framework also renders. The next reconciliation overwrites it. Use props or a ref scoped to your own element.

✕

Defining a component inside another component's body

Looks tidy; remounts the whole subtree on every parent render. Hoist it to module scope.

✕

Spreading unknown props all the way down

<Wrapper {...props}> with no shape contract — every parent prop change reaches every leaf, and memoization is impossible because identities you don't own keep changing.

Real-world usage patterns

Inbox-style list, 5k–50k items

Email, chat, and support-ticket teams key by message id, virtualize with react-virtuoso, and memoize rows on (id, isRead, updatedAt). Lesson: the row's click handler must be stable too — an unstable inline handler alone defeats memo and the whole list re-renders on every selection.

Realtime dashboard, 30+ widgets

Each widget subscribes to its own slice via a selectora function that reads one slice of shared store state so a component re-renders only when that slice changes hook rather than one global context. Lesson: keep the WebSocket handler outside the component tree, writing to the store — putting the socket inside a top-level component re-renders the world on every tick.

Drag-and-drop kanban board

Cards use stable ids as keys; the drag preview renders through a portal so it can escape overflow: hidden. Lesson: optimistic reordering must commit a new array with new positions but the same item references, or memoization breaks downstream.

Form builder, 200+ live inputs

Each field owns its own state; the form-level value is assembled on submit via refs or a form library that bypasses controlled-input re-renders. Lesson: a single top-level controlled form re-renders every field on every keystroke — local state at the leaf is the cheapest possible memoization.

Trading grid, 100+ updates/second

After exhausting memoization, the team replaced the hot grid with a Solid island inside an otherwise React app. Lesson: you don't have to pick one framework for the whole app — render the hot surface with fine-grained reactivity and keep the chrome as-is. The boundary is a single mount point.

Operational checklist

✓

Before you call it done

  • Lists: does every .map(...) use a stable, non-index key derived from data identity?
  • Profiler: does a recent recording exist for the screen's primary interaction, with a known reason for every warm bar?
  • Memoization: has every React.memo been verified to actually skip renders (gray in the Profiler on unrelated updates)?
  • Context: is each Provider's value memoized, and are mega-contexts split by audience?
  • Virtualization: is any list expected to exceed a few hundred items virtualized, with row-height assumptions documented?
  • Refs vs render: does imperative DOM work (focus, scroll, third-party widgets) go through refs, never through flushSync hacks?
  • Portals: does overlay UI (modals, tooltips) use portals, with event bubbling and focus traps tested?
  • Effects: does no effect write state that the same effect depends on?
  • Onboarding: do new engineers know how to open the Profiler, read a flamegraph, and find the prop whose identity changed?

How it evolves in a codebase

  1. Ignore it. State lives at the top, callbacks are inline, props are object literals, lists are keyed by index. It works because the app is small and the framework is fast enough.
  2. First jank ticket. A screen crosses roughly 50 components, or a list crosses a few hundred rows, and reactive memoization begins: someone discovers React.memo and useCallback and sprinkles them across the codebase for a partial win. The Profiler flushes out bad keys, fresh object literals, and mega-contexts along the way.
  3. Architectural phase. State is colocated with the components that read it, a store with selector hooks handles genuinely shared state, long lists are virtualized, and the team makes a deliberate VDOM-vs-fine-grained choice for hot spots. The painful migration is usually moving from one big context or one big form state to selectors — it touches every consumer.
  4. Compiler trust. With React 19's compiler and Vue's Vapor Mode shipping, the next migration is removing hand-written useMemo / useCallback once the team trusts the compiler to do it instead.
