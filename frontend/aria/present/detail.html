Detail — the deep dive

◑ ~11 min read ✎ What · Where · When · How · Why

What it is

WAI-ARIA (Accessible Rich Internet Applications) is a W3C spec. It defines an ontology of roles, states, and properties that you attach to host-language elements (HTML, SVG).

  • Those attributes change how an element shows up in the browser's accessibility tree.
  • From there, the browser hands it to the operating system's accessibility API the OS-level interface (UIA, AX API, ATK…) that screen readers query, which assistive technology consumes.
  • Current Recommendation: WAI-ARIA 1.2, published 6 June 2023.
  • Next: WAI-ARIA 1.3 is still a Working Draft. The latest draft is dated 4 June 2026.
ⓘ

The one fact everything else follows from

ARIA is declarative and semantic only. It changes what the accessibility tree reports. It does not change focusability, keyboard handling, layout, or event dispatch.

The core building blocks

Roles
Declare what an element is (role="tab"). ARIA 1.2 groups them into: abstract roles (ontology-only, never authored: widget, landmark), widget roles (button, tab, combobox, slider), document structure roles (heading, list, generic), landmark roles (navigation, main, search), live region roles (alert, status, log), and window roles (dialog, alertdialog).
States
Values expected to change with interaction: aria-expanded, aria-checked, aria-selected, aria-pressed. Your script owns keeping them true.
Properties
Mostly static traits and relationships: aria-label, aria-labelledby, aria-describedby, aria-controls, aria-required. IDREF an attribute value that points at another element's id properties create edges between elements that aren't DOM ancestors of each other.
Live region attributes
aria-live, aria-atomic, aria-relevant, aria-busy. They tell the browser to raise announcement events when a subtree changes.
Name and description computation
accname 1.2: the algorithm that turns markup into the single string a screen reader speaks for an element.
Accessibility API Mappings (AAMs)
Core-AAM maps each ARIA role/state to platform APIs. HTML-AAM does the same for native HTML. The ARIA in HTML Recommendation says which ARIA is allowed on which HTML element (what validators like axe check against).
APG
The ARIA Authoring Practices Guide: non-normative patterns that spell out the keyboard contract each widget role implies (tabs, combobox, treeview, grid, menu, dialog).

How it relates to the wider landscape

  • Same layer: ARIA belongs to the semantic exposure layer, next to native HTML semantics (always preferred) and the mobile equivalents: Android contentDescription/AccessibilityNodeInfo, iOS accessibilityTraits, React Native accessibilityRole, Flutter Semantics.
  • Not WCAG: WCAG defines success criteria. ARIA helps you meet 4.1.2 Name, Role, Value.
  • Not a component library: React Aria and Radix ship the behavior ARIA does not.
  • Sibling modules: DPUB-ARIA (digital publishing) and Graphics-ARIA (SVG charts) extend the vocabulary for niche domains.

Where it lives

Where you'll typically meet it

Headless component libraries

React Aria (Adobe), Radix UI, Headless UI, Ariakit, Angular CDK a11y. ARIA is their primary output.

Design systems

GOV.UK Frontend, Material, Fluent UI, Carbon. Every custom combobox, tabs, or menu is ARIA plus scripted keyboard handling.

SPA frameworks

Route-change announcements and toasts use live regions, because there is no page load for the screen reader to notice.

Rich editors and grids

Google Docs, AG Grid, and spreadsheet-style UIs lean on role="grid", aria-activedescendant, and live regions.

Test tooling

Testing Library getByRole and Playwright getByRole query the computed role and name, so ARIA directly shapes your selectors.

Ecosystem and tooling

  • Authoring guidance: APG patterns; ARIA in HTML for allowed attributes per element.
  • Automated checks: axe-core (Deque; also powers Lighthouse's accessibility audit), WAVE (WebAIM), IBM Equal Access Checker, eslint-plugin-jsx-a11y.
  • Inspecting the tree: Chrome DevTools Accessibility pane and full-page tree view, Firefox Accessibility Inspector, Accessibility Insights for Windows, macOS Accessibility Inspector.
  • Regression tests: Playwright toMatchAriaSnapshot (since v1.49) asserts a YAML snapshot of the tree; Testing Library role queries.
  • Real AT testing: NVDA (free, Windows), JAWS, VoiceOver (macOS/iOS), TalkBack (Android), Narrator. The W3C ARIA-AT project publishes interop results for APG patterns across AT/browser pairs.

When to use it

◆

A little history

  • ~2005: Ajax-era apps built menus, trees, and tab panels from <div> and <span>. Screen readers saw only text. IBM's Becky Gibson and Rich Schwerdtfeger described the fix in "DHTML Accessibility: Solving the JavaScript Accessibility Problem".
  • Before ARIA, the options were: avoid scripted widgets, ship a separate "accessible version", or hack with hidden form controls.
  • September 2006: W3C publishes the WAI-ARIA Roadmap and first drafts.
  • 20 March 2014: ARIA 1.0 Recommendation. 14 December 2017: 1.1. 6 June 2023: 1.2.
  • The long gaps reflect the hard part: getting four browser engines and many screen readers to agree on mappings.

✓ Reach for it when

  • You need a widget HTML has no element for: tabs, treeview, combobox with filtering, grid, toolbar, feed.
  • You must expose state native HTML can't express: aria-expanded on a disclosure trigger, aria-current="page" on a nav link, aria-invalid on a field after validation.
  • You need a relationship across DOM positions: aria-describedby from an input to its error text, aria-labelledby from a dialog to its heading.
  • Content updates without navigation and must be announced (status messages, route changes, async search results).
  • An icon-only control has no visible text (aria-label="Close").

✕ Skip it when

  • A native element exists: <button>, <a href>, <dialog>, <details>/<summary>, <select>, <input type="checkbox">, popover. These bring focus, keyboard, and platform mappings for free.
  • You won't implement the role's full keyboard contract. role="menu" promises arrow keys and typeahead; a site nav called a menu with only Tab support breaks expectations.
  • You're adding it "just in case." Redundant ARIA (<button role="button">) is noise; wrong ARIA overrides correct native semantics.
  • You're on a non-web surface (native iOS/Android, Flutter, terminal). Use that platform's accessibility API.

How it works

What the browser and the screen reader do, from markup to spoken word:

  1. Parse and style. The engine builds the DOM and computed style. display: none, visibility: hidden, the hidden attribute, inert, and aria-hidden="true" all remove nodes from the tree, with different side effects on focus and rendering.
  2. Compute role. An explicit role wins over the implicit HTML role if it's valid for that element. Otherwise the HTML-AAM mapping applies (<nav> → navigation, <div> → generic). Invalid or abstract roles are ignored and the engine falls back.
  3. Compute name and description. accname 1.2 runs a strict precedence order (see the ladder below).
  4. Compute states and relations. aria-* states are normalized (invalid tokens fall back to defaults). IDREF relations resolve within the same DOM tree scope, so a plain id reference cannot cross a shadow root boundary.
  5. Map and serialize. Each node maps to platform objects per Core-AAM: button → ROLE_SYSTEM_PUSHBUTTON (MSAA), UIA Button, ATK ROLE_PUSH_BUTTON, AXButton (macOS). Adding aria-pressed turns it into a toggle-button mapping. In multi-process browsers the tree is serialized from the renderer to the browser process, which answers AT queries.
  6. AT consumption. Windows screen readers (JAWS, NVDA) build a virtual buffer and default to browse mode the screen reader grabs arrow keys and letter shortcuts, e.g. H for next heading. On focus of a widget like a textbox or grid, they switch to focus mode keys pass straight through to the page's own handlers. role="application" forces focus mode for a whole subtree.
  7. Your script runs. Keydown handlers move focus with roving tabindex only the active item has tabindex="0"; the rest have -1, and arrow keys move it or update aria-activedescendant, and flip states like aria-selected. Each change fires a platform event (focus, state change, name change) and the AT announces it.
  8. Live regions. When a node inside aria-live="polite" (or role="status") changes, the browser fires a live-region-changed event. polite waits for the user to go idle; assertive interrupts. The region must already exist in the tree before its content changes, or the change is often missed.

Name precedence: who wins

accname 1.2 checks sources in a fixed order and stops at the first one that yields text. In short: aria-labelledby beats aria-label, which beats <label>, which beats inner text.

What a correct tabs widget needs

Per APG, attributes are only half of it. A tabs widget needs all of this (the code folder has a runnable version):

  • role="tablist" containing role="tab" elements, each with aria-selected and aria-controls.
  • role="tabpanel" with aria-labelledby pointing back to its tab.
  • One tab in the Tab sequence (tabindex="0"), the others -1.
  • Left/Right arrows move between tabs; Home/End jump to first/last.
  • A choice between automatic activation (arrow selects) and manual activation (arrow focuses, Enter/Space selects).

Common failure modes

✕

"Button" that does nothing on Enter

Cause: role="button" on a <div> without tabindex="0" and keydown handling for Enter and Space.

✕

Focus disappears into a void

Cause: aria-hidden="true" on an ancestor of a focused or focusable element. Chrome now blocks it on a focused subtree and logs "Blocked aria-hidden on an element because its descendant retained focus", recommending inert.

⚠

Toast never announced

Cause: the live region was inserted into the DOM in the same tick as its text, or toggled from display:none.

⚠

Wrong name spoken

Cause: aria-label overriding visible text. It also breaks voice control: the user says "click Submit" but the name is "btn-primary".

⚠

aria-labelledby silently empty

Cause: duplicate IDs, a typo, or the referenced node lives inside a different shadow root.

✕

Site nav unusable

Cause: role="menu"/menuitem on links, which puts AT into a menu interaction model the page doesn't implement.

✕

State lies

Cause: aria-expanded or aria-selected set at render and never updated by the click handler; framework re-renders reset attributes.

⚠

Mobile users stuck

Cause: keyboard-only patterns (arrow keys) with no touch or swipe equivalent. VoiceOver on iOS does not send arrow keys.

Why it exists

Accessibility is a separation-of-concerns problem: visual look and semantic meaning travel on different channels.

  • A sighted user infers "this is a tab, it's selected" from pixels.
  • A screen reader user gets only what the platform accessibility API reports.
  • Once the web started drawing its own controls instead of using OS widgets, the semantic channel went silent.
  • ARIA restores it with the smallest possible mechanism: metadata on existing elements, mapped by the browser into APIs that AT already understands.
  • It's a legal concern too: WCAG 2.1/2.2 success criterion 4.1.2 (Name, Role, Value) is effectively unmeetable for custom widgets without ARIA.

Why it looks the way it does

The obvious alternative was new HTML elements for every widget (<tabs>, <tree>, <combobox>). That would bundle semantics and behavior correctly, but each element needs years of standards work in every engine. Authors in 2006 needed something that worked on existing markup right away. So ARIA chose attributes, not elements, and semantics, not behavior:

  • Attributes are backwards compatible. Browsers that don't understand them ignore them; layout is unaffected.
  • Behavior was left to authors because it varies by platform and design. Specifying it would have brought back the "new elements" problem.

The cost is ARIA's central failure mode: semantics and behavior can drift apart, and nothing in the browser enforces the contract. That's why the Using ARIA note's rules read like guardrails:

  1. Use native HTML if you can.
  2. Don't change native semantics unless you must.
  3. All interactive ARIA controls must be keyboard operable.
  4. Never put role="presentation" or aria-hidden="true" on a focusable element.
  5. All interactive elements must have an accessible name.

The original alternative is now coming back in stages: <dialog>, popover, inert, and customizable <select> let HTML carry both semantics and behavior, shrinking ARIA's job to the remaining gaps.

Why it matters now

Three pressures make ARIA more relevant in 2026, not less:

Regulation
  • The European Accessibility Act has applied since 28 June 2025.
  • US: the DOJ's ADA Title II rule requires WCAG 2.1 AA for state and local governments.
  • An April 2026 interim final rule pushed deadlines to April 2027 and April 2028 (JD Supra).
Volume and quality
  • WebAIM Million 2026: ARIA on 82.7% of top home pages.
  • Average 133.6 attributes per page: up 27% in a year, over six times 2019 levels.
  • Pages with ARIA averaged 59.1 detected errors vs 42.0 without.
  • WebAIM partly blames third-party frameworks and AI-assisted coding, which sprinkle aria-* without the matching behavior.
Platform evolution
  • Element reflection (ariaLabelledByElements): Baseline since April 2025 per MDN.
  • ariaNotify(), and Reference Target for cross-shadow-root ARIA (approved for Chrome 151 in mid-2026, blink-dev) close long-standing gaps for Web Components.
  • ARIA 1.3 drafts add aria-description, aria-braillelabel, and the suggestion/comment/mark roles.

Open questions to verify in practice

ⓘ

Check these with real tools, not the spec

  • Does your tabs widget announce "tab, 2 of 4, selected" the same way in NVDA + Firefox, JAWS + Chrome, and VoiceOver + Safari? Where does each pair diverge?
  • When aria-labelledby, aria-label, and visible text all conflict, what name does the Chrome DevTools accessibility tree show? Does it match accname step order?
  • How long must a live region exist before an update is reliably announced? Does a framework re-render that replaces the region node break it?
  • Is aria-activedescendant on a combobox input announced consistently, or does roving focus behave better with your target AT?
  • With ariaNotify() in Chrome and Firefox, what fallback do you ship for Safari, and does double-announcing occur?
  • Does your widget stay operable with VoiceOver on iOS and TalkBack swipe gestures, where arrow-key handlers never fire?
