Overview

◔ ~4 min read ✎ intuition-first

Opening a database connection is expensive. Connection pooling opens a handful of connections up front, hands them out to callers, and puts them back on the shelf when done — instead of opening and closing one for every single request.

ⓘ

In 30 seconds

A TCP handshake, a TLS handshake, a login, and session setup add up to 20–100ms of pure overhead before a query even runs. If a web app opened a fresh connection per request, most of the request budget would go to saying hello. A pool opens N connections once, then lets callers acquireborrow a connection from the pool — also called "checkout" one, use it, and releasereturn it to the pool when done — also called "checkin" it. Faster responses, and a database that stops sweating under load.

The mental model

Picture a busy hotel with one concierge desk on the top floor. Every guest needs the concierge, but the concierge has to walk down each time — slow, and the elevator gets clogged.

The fix: hire ten concierges, station them permanently in the lobby, and hand guests a numbered ticket. A guest walks up, grabs whichever concierge is free, gets an answer, and hands the concierge back for the next guest. If all ten are busy, the guest waits in a short line. At 3am when traffic dies down, most concierges just stand by, ready.

The interesting knobs fall straight out of the analogy: how many concierges to keep on duty, how long a guest waits before giving up, and whether a concierge who dozed off gets checked before being handed to the next guest.

Two ideas will matter later. A connection leakcode that acquires a connection and never releases it — the classic pool-killer bug is a guest who walks off with the concierge and never sends them back. And code that can't keep its own lobby staffed — a serverless function, for instance — leans on an external pooler to do the hiring for it.

What it is not

⚠

Common mix-ups

  • Not a cache. Caches store query results. Pools store the pipes you send queries through.
  • Not a load balancer. A pool sits inside one app talking to one database (or one cluster endpoint). It doesn't decide which database to hit.
  • Not HTTP keep-alive — though it's the cousin. Keep-alive reuses a TCP connection for HTTP; a connection pool reuses a full, authenticated database session.
  • Not free. A pool is state. Misconfigured, it becomes the bottleneck it was meant to fix.

When to reach for it — and when not to

✓ Reach for it when

  • Any web service or API talks to a relational database under real traffic.
  • Long-running workers fire many small queries — a fresh connection per query would dominate cost.
  • Serverless functions sit behind a pooler like PgBouncer or RDS Proxy, since the functions can't hold a pool themselves.
  • "Open connection" shows up hot in a flamegraph of any client library.

✕ Skip it when

  • A one-shot CLI script runs one query and exits — open, query, close, done.
  • Traffic is extremely low, and a single connection covers everything.
  • Each caller genuinely needs isolated session state (temp tables, session variables) and can't tolerate a reused connection — unless the pool explicitly resets sessions.

Key vocabulary

Pool
The collection of reusable connections.
Min / max pool size
The floor and ceiling on how many connections stay open.
Acquire (checkout)
Borrowing a connection from the pool.
Release (checkin)
Returning it when done.
Connection lifetime
How long a connection may live before it's retired.
Idle timeout
How long an unused connection sits before the pool closes it.
Acquire timeout
How long a caller waits for a free connection before failing.
Validation / liveness check
A ping (e.g. SELECT 1) that confirms a connection is still alive before it's lent out.
External pooler
A separate process (PgBouncer, RDS Proxy) that pools on behalf of many apps.
Connection leak
Code that acquires a connection but never releases it — the classic pool-killer bug.
