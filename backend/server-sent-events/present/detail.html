Detail — the deep dive

◑ ~10 min read ✎ What · Where · When · How · Why

What it is

SSE is two things paired together: a wire format, text/event-stream, and a client processing model, the EventSource interface.

  • Where it's defined. Both live in the WHATWG HTML Living Standard, section "Server-sent events". The W3C published a standalone Server-Sent Events Recommendation on 3 February 2015. That one is now marked superseded; the WHATWG text is the normative one.
  • Direction. One-way, server to client.
  • Carrier. The body of a single, long-lived HTTP GET response.
  • Framing. UTF-8 and line-oriented.
  • Reconnect. The client owns it. The server can supply a resume cursor the id value; the client echoes it back so the server knows where to continue.

The core building blocks

text/event-stream
Always UTF-8: the spec says "there is no way to specify another character encoding". A leading BOM is stripped. Lines may end in CRLF, LF, or a bare CR.
Line grammar
A line starting with : is a comment. A line containing : splits into field name and value, and one leading space is removed from the value. A line with no colon is a field name with an empty value. Unknown field names are ignored, which keeps the format forward-compatible.
data
Appends its value plus an LF to the data buffer.
event
Sets the event type.
id
Sets the last-event-ID buffer, unless the value contains U+0000 NULL; then the field is ignored.
retry
Sets the reconnection time in milliseconds, but only if the value is all ASCII digits.
Dispatch on blank line
A blank line ends the event. The trailing LF is stripped from the data buffer. Empty buffer → nothing is dispatched. Otherwise a MessageEvent fires with type message, or the event value if one was set.
Sticky last event ID
The ID buffer is not cleared between events. An event without an id: line inherits the previous ID. An empty id: line resets it.
EventSource interface
url, withCredentials (false by default), readyState (CONNECTING = 0, OPEN = 1, CLOSED = 2), the open / message / error events, and close().
Last-Event-ID header
On reconnect, the browser sends it with the stored ID if that ID is non-empty.
Reconnection time
The spec leaves the default to the browser ("probably in the region of a few seconds"). Chromium and WebKit hard-code defaultReconnectDelay = 3000 ms in EventSource.cpp.

Where it lives

SSE is an application-layer (L7) convention on top of HTTP. It has no transport of its own. What it rides on depends on the HTTP version:

HTTP/1.1

The body is usually sent chunked Transfer-Encoding: chunked: the body goes out in pieces with no total length up front. Each flush becomes one or more chunks. The stream holds the whole TCP connection.

HTTP/2 (RFC 9113)

A sequence of DATA frames on one stream of a multiplexed many independent request streams sharing one TCP connection connection.

HTTP/3

One QUIC stream, so a lost packet on another stream does not stall it.

On the server, an SSE endpoint is ordinary handler code that writes and flushes without returning. Every hop between client and origin has to pass bytes through as they arrive. That one requirement causes most production incidents.

Where you typically meet it

LLM APIs

OpenAI Chat Completions streams data-only events and ends with data: [DONE]. The Anthropic Messages API uses named events: message_start, content_block_start, content_block_delta, content_block_stop, message_delta, message_stop, plus ping and error.

Model Context Protocol

Streamable HTTP answers a POST with either JSON or a text/event-stream response scoped to that request.

Mercure

A pub/sub hub protocol built on SSE with JWS authorization, published as an IETF Internet-Draft (draft-dunglas-mercure).

Dashboards, CI logs, notifications

Classic one-way fan-out with low write rates.

Ecosystem and tooling

Serving from .NET
  • TypedResults.ServerSentEvents(IAsyncEnumerable<T>) is new in ASP.NET Core 10; works in Minimal APIs and controllers.
  • SseItem<T> carries Data, EventType, EventId, ReconnectionInterval.
  • SseFormatter (.NET 10) handles field serialization.
Serving from other stacks
  • Spring: SseEmitter.
  • Python: sse-starlette.
  • Node: write to res and flush.
Consuming outside the browser
  • .NET: SseParser in System.Net.ServerSentEvents (first shipped with .NET 9; also targets netstandard2.0).
  • Node: undici's spec-compliant EventSource, global behind --experimental-eventsource (status depends on the Node version).
Browser clients beyond EventSource
  • @microsoft/fetch-event-source: adds POST, custom headers, and custom retry on top of fetch.
  • eventsource-parser: a parser alone, for when you bring your own transport.
Multi-node fan-out

Redis Pub/Sub, Redis Streams (which add replay), NATS, or Kafka sit behind the SSE nodes. A Mercure hub can take over the job entirely.

Debugging

curl -N turns off curl's output buffering. Chrome DevTools shows an "EventStream" tab for EventSource requests.

When to use it

◆

A little history

  • 2004. Ian Hickson starts specifying SSE in the WHATWG "Web Applications 1.0" draft.
  • September 2006. Opera 9 ships a prototype as an <event-source> element. Feedback pushes a redesign into a script object modelled on XMLHttpRequest.
  • 2010–2011. Safari, Chrome, and Firefox ship EventSource.
  • December 2011. WebSocket (RFC 6455) arrives at almost the same time and takes most of the attention.
  • 2020. Internet Explorer never shipped it; Microsoft support arrives with Chromium-based Edge 79.

Before SSE, push meant Comet: long polling, "forever iframe" streaming, XHR streaming with home-made framing, or Flash sockets. Every team reinvented framing, parsing, and reconnect logic.

SSE's revival had two causes: HTTP/2 (2015) removed its biggest practical limit, the HTTP/1.1 connection pool; and from around 2023, LLM APIs needed to stream tokens one way, which is exactly SSE's shape.

✓ Reach for it when

  • Data flows mostly server to client, and client actions fit normal POST/PUT requests.
  • Payloads are text or JSON.
  • You want push to pass through existing HTTP infrastructure (auth middleware, cookies, CORS, HTTP/2, observability) with no protocol upgrade.
  • Clients can tolerate reconnect gaps, or you can keep a replay log keyed by event ID.
  • You serve over HTTP/2 or HTTP/3, or each client needs only one stream.

✕ Skip it when

  • Both directions are chatty and latency-sensitive (games, collaborative cursors). A POST per upstream message adds a request per message. Use WebSocket or WebTransport.
  • Payloads are binary. Base64 inflates them by about 33% and costs CPU.
  • You need guaranteed delivery with acknowledgements. SSE has no ack channel, so you'd be building a message broker by hand.
  • Delivery must reach users whose page is closed. Use Web Push.
  • Your platform cuts long responses short (serverless hard execution limits, gateways with fixed response timeouts). Per-request SSE (the MCP model) still works there; long-lived subscription streams do not.

How it works

One connection from construction to termination:

  1. Construct. new EventSource(url, { withCredentials }) sets readyState = CONNECTING and sends a GET with Accept: text/event-stream and cache mode no-store. Cross-origin requests follow CORS; withCredentials: true maps to credentials mode include.
  2. Validate the response. Status not 200, or Content-Type not text/event-stream → the browser fails the connection: readyState = CLOSED, an error event fires, and it does not reconnect. 204 No Content is the usual way for a server to say "stop retrying". 301 and 307 redirects are followed.
  3. Open. readyState = OPEN and open fires.
  4. Parse incrementally. Bytes are decoded as UTF-8 and split into lines. Lines fill the data, event-type, and ID buffers. A blank line dispatches a MessageEvent with data, origin, and lastEventId filled in.
  5. Server writes and flushes. Each event is serialized and flushed. Without the flush it sits in the server or proxy buffer. The server may mix in : comment lines as heartbeats; the spec suggests one about every 15 seconds for old proxies.
  6. Drop. On a network error or a clean server close, readyState goes back to CONNECTING and error fires. The browser waits the reconnection time (the retry value, or the default); the spec allows exponential backoff after failed attempts. Then it re-sends the GET with Last-Event-ID.
  7. Resume. The server reads Last-Event-ID, replays everything after it from a durable log an ordered event store that outlives a single connection: a ring buffer, Redis Stream, or Kafka offset, then continues live. Without such a log the header is useless.
  8. Terminate. The client calls close(), or the server answers a reconnect with 204 or any non-200 status.

Parsing a multi-line payload

id: 7
event: log
data: line one
data: line two

: heartbeat
  • Dispatches one log event.
  • data === "line one\nline two" (the two data: lines are joined with a newline).
  • lastEventId === "7".
  • The comment line dispatches nothing.

Server cost model

  • Idle client cost. In async servers such as Kestrel or Node: one socket, a small buffer, and a subscription entry. It does not hold a thread.
  • Fan-out across instances. It needs a backplane a shared message bus every server node subscribes to, so any node can deliver any event, because the client that needs event N may sit on a different node from the one that produced it.
  • HTTP/2 stream cap. Kestrel caps streams per connection with Http2Limits.MaxStreamsPerConnection, default 100. RFC 9113 recommends advertising no fewer than 100 concurrent streams.

Common failure modes

✕

Events arrive in one burst at the end

Cause: response buffering. nginx proxy_buffering is on by default; compression middleware and missing Flush calls do the same. Fix: X-Accel-Buffering: no or proxy_buffering off, and exclude text/event-stream from gzip/brotli.

✕

The stream dies at exactly 60 or 100 seconds

Cause: idle timeouts. nginx proxy_read_timeout defaults to 60 s, AWS ALB idle timeout to 60 s, Cloudflare's proxy read timeout to 100 s. Send heartbeats well inside the smallest one.

⚠

The seventh tab hangs forever

Cause: the HTTP/1.1 limit of about 6 connections per origin, across all tabs. Chrome and Firefox marked this "Won't fix" (Eric Lawrence's write-up).

⚠

CPU spikes right after a deploy

Cause: every client reconnects after the same fixed delay (3 s in Chromium). Spread restarts out, and vary retry per client to add jitter.

✕

Gaps after reconnect

Cause: the server emits id: but has no replay log, or emits no id: at all.

✕

Injected or truncated events

Cause: user text containing \n was written into a single data: line. The server must split on newlines and emit one data: line per piece.

⚠

Server memory grows with churn

Cause: the handler ignores client disconnect (HttpContext.RequestAborted / CancellationToken), leaving zombie subscriptions.

⚠

onmessage never fires

Cause: the server sets event: foo. Named events only reach addEventListener("foo", …).

✕

401 loop or silent stop

Cause: the auth token expired. A non-200 response fails the connection permanently, so the app must notice CLOSED and rebuild the EventSource.

Why it exists

HTTP is client-initiated. Without push, keeping data fresh means polling, and polling has two costs that don't depend on whether anything changed:

  • Staleness. With poll interval T, data is on average T/2 old when the client sees it.
  • Load. N clients generate N/T requests per second, changes or not.
  • Long polling cuts the waste but still pays a full request round-trip per message, and every team reinvented its framing.
  • SSE makes push cost scale with events actually sent, at roughly one-way network latency, while staying inside HTTP's auth, routing, and caching rules.

Why it looks the way it does

The design keeps the protocol small and standardizes only what teams kept reinventing: framing, parsing, and reconnect.

  • The alternative was WebSocket's approach. An Upgrade handshake, then a new binary framing layer with masking and its own ping/pong. That gains duplex and binary, but intermediaries must understand the Upgrade, and HTTP features (status codes, caching rules, HTTP/2 multiplexing) no longer apply. RFC 8441 later had to bolt WebSocket onto HTTP/2 separately. SSE bets that most push is one-way and the upstream direction is already solved by HTTP requests.
  • Text over binary. Any server that can write and flush a string can emit SSE, and you can read the stream in a terminal.
  • Client-side reconnect with a server-supplied cursor. The server stays stateless about connections and only stateful about events: a log indexed by ID. That splits the work the way Kafka consumer offsets do.
  • GET-only. Inference, not stated in the spec: automatic reconnect means the browser re-sends the request without asking the app. That is only safe for an idempotent safe to repeat: sending it twice has the same effect as once method, which would explain why the native API never grew POST. fetch-based clients add POST and accept that risk.
  • A counter-example. MCP's 2026-07-28 revision removed its long-lived GET stream, protocol-level sessions, and Last-Event-ID resumability. It keeps SSE only as a per-request response stream. That shows what resumable long-lived streams cost to run behind load balancers and on serverless platforms.

Why it matters now

As of 2026, SSE is growing:

  • AI APIs. It is the de facto streaming transport for LLM APIs and agent protocols, so most engineers now consume it even if they never served it.
  • HTTP/2 and HTTP/3. Both are the default at major CDNs and browsers, which removes the old connection-pool objection for most deployments.
  • Platform support. .NET 10 made SSE a first-class result type, a sign it is now a mainstream backend primitive.

WebSocket remains the answer for duplex traffic, and WebTransport is the long-term candidate for multi-stream binary. Neither has displaced SSE for one-way text push.

ⓘ

Open questions to verify in practice

  • Does my exact proxy chain (CDN → load balancer → nginx or YARP → Kestrel) deliver each event immediately? Measure with curl -N and timestamps at each hop.
  • What reconnect delay and backoff does each target browser actually apply after repeated failures, and does a server-sent retry: override the backoff?
  • What does TypedResults.ServerSentEvents do about heartbeats and flushing? Do I still need my own : comments to survive a 60 s idle timeout?
  • How much replay history (time window or event count) covers realistic reconnect gaps, and what do I send when Last-Event-ID is older than the log?
  • How many concurrent SSE connections can one Kestrel instance hold before memory or file-descriptor limits bite, and how does that change between HTTP/1.1 and HTTP/2?
  • How do I authenticate the stream: cookies with withCredentials, a short-lived token in the query string (which ends up in access logs), or a fetch-based client with an Authorization header?
