Overview

◔ ~3 min read ✎ intuition-first

Plain HTTP is ask-and-answer: the client asks, the server answers once, and the exchange is over. Live scores, build logs, notifications, and an LLM writing tokens one at a time don't fit that shape.

ⓘ

In 30 seconds

SSE makes the smallest possible change to HTTP. The server answers with Content-Type: text/event-stream and then simply doesn't finish the response. Browsers ship a built-in client, EventSource, that:

  • parses the stream,
  • fires one JavaScript event per message,
  • reconnects on its own if the connection drops.

You get server push the server sends data the moment it has it, without the client asking again without leaving HTTP.

The mental model

Think of a radio station versus a phone call.

  • Normal HTTP is a phone call to a help desk. You ask, they answer, you hang up. To learn whether anything changed, you call again. That is polling asking the server for updates on a timer, whether or not anything changed.
  • SSE is tuning a radio. You pick a station once (open the request). From then on the station broadcasts and you listen.
  • You can't talk back through the radio. To say something, use a different channel, such as a normal POST.
  • If the signal cuts out, the radio retunes itself to the same station.
  • A good station numbers its bulletins ("this was bulletin 42"). When you come back you say "I last heard 42" and get only what you missed.

What one event looks like on the wire

Each broadcast is a few plain-text lines, then a blank line:

id: 42
event: price-update
data: {"symbol":"ACME","price":101.5}

The browser side is a few lines:

const source = new EventSource("/stream");
source.addEventListener("price-update", (e) => render(JSON.parse(e.data)));

Because it's still HTTP, proxies, load balancers, cookies, and auth middleware mostly work as usual. The main exception is response buffering a proxy or server holding output until it has "enough", so events arrive late or all at once, which the Detail page covers.

What it is not

⚠

Common mix-ups

  • Not WebSockets. WebSockets are a separate two-way protocol, carry binary frames, and start with a connection upgrade. SSE is one-way, text-only, plain HTTP.
  • Not long polling. Long polling holds a request until one message arrives, then the client asks again. SSE keeps one response open for many messages.
  • Not Web Push. Web Push wakes a service worker through the browser vendor's push service even when your page is closed. SSE only works while the page holds the connection.
  • Not a message queue. SSE has no persistence, acks, or delivery guarantees on its own. Replay after a reconnect only works if your server stores events and implements it.

When to reach for it — and when not to

✓ Reach for it when

  • Streaming LLM output token by token. Most major model APIs stream this way.
  • Live dashboards, tickers, and progress bars: the server talks, the client watches.
  • Notification feeds, activity streams, and live CI build logs.
  • Any push feature where you'd rather not run WebSocket infrastructure, and client → server can stay normal HTTP requests.

✕ Skip it when

  • Chat, multiplayer games, collaborative editing: frequent messages both ways point to WebSockets (or WebTransport).
  • Binary payloads such as audio or video frames. SSE is UTF-8 text, so binary must be base64 a way to write binary bytes as plain text characters-encoded.
  • Notifying users whose tab is closed. Use Web Push.
  • Many SSE streams per tab over HTTP/1.1. Browsers allow about 6 connections per origin and each open stream holds one. Serve over HTTP/2 or HTTP/3.
  • You need custom request headers from the browser. Native EventSource only does GET and can't set headers like Authorization; use cookies or a fetch-based client instead.

Key vocabulary

text/event-stream
The response content type that marks a response as an SSE stream.
EventSource
The browser's built-in SSE client.
Event
One message: field lines ended by a blank line.
data:
The payload field. Several data: lines in one event are joined with newlines.
event:
Optional event name, so clients can listen per type instead of to everything.
id:
Optional event ID. The browser remembers the last one it received.
Last-Event-ID
The request header the browser sends on reconnect so the server can resume.
retry:
The server's instruction for how many milliseconds to wait before reconnecting.
Comment / heartbeat
A line starting with :, which clients ignore. Servers send them now and then so idle proxies don't kill the connection.
