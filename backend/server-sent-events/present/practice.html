Practice — how it plays out for real

● ~10 min read ✎ best practices · anti-patterns · checklist

Where you'll meet it

Three settings cover almost every SSE stream you'll run in production:

AI product backend

Your API calls an LLM provider, receives its SSE stream, and relays tokens to the browser through a second SSE stream of your own. That relay owns three expensive things at once: a provider bill, a long-lived connection, and the user's patience.

The "live" corner of a SaaS app

Notification bells, job progress bars, CI log tailing, admin dashboards. SSE is a thin layer between a message bus (Redis, Kafka, NATS) and the browser. Most problems come from the proxies in between, not the code.

High fan-out broadcast

Sports scores, flash-sale counters, status pages: one event goes to tens of thousands of open connections. Here SSE stops being an endpoint and becomes its own tier, with its own capacity planning.

Best practices

1

Prove streaming through the real proxy chain, not localhost

Do

Add a smoke test that runs curl -N against staging through the CDN, load balancer, and reverse proxy, and asserts the first event arrives within a second. Send X-Accel-Buffering: no, and exclude text/event-stream from gzip/brotli at every hop.

Why

Localhost has no buffering proxy, so the "every event arrives in one burst at the end" bug only shows up after deploy (see Detail → Common failure modes).

Avoid

Assuming "it streams in Kestrel" means it streams for users.

2

Heartbeat well inside the smallest idle timeout

Do

Send a : comment roughly every 15 s. If your framework helper can't emit comments, send a named ping event instead. Anthropic's Messages API does exactly that.

Why

nginx proxy_read_timeout and AWS ALB both default to 60 s, and Cloudflare cuts at 100 s. Without a heartbeat, quiet streams die on schedule and reconnect in lockstep.

Avoid

Raising every timeout to an hour instead. One hop you forgot will still cut the stream.

3

Tie every subscription to cancellation, including shutdown

Do

Link HttpContext.RequestAborted with IHostApplicationLifetime.ApplicationStopping, and unsubscribe in a finally block.

Why

Ignore disconnect → zombie subscriptions and memory that grows with churn. Ignore shutdown → every pod blocks for the full HostOptions.ShutdownTimeout (30 s by default) on each deploy, then Kubernetes kills it hard.

Avoid

A while (true) loop that only exits when a write throws.

4

Give each client a bounded queue and a slow-consumer policy

Do

Put a Channel.CreateBounded<T> between the bus and each connection. When it fills, drop stale updates (DropOldest) or close the stream and let the client resume by ID.

Why

One client on a bad mobile link otherwise buffers unbounded events in your process. Multiply that by a few thousand and the node runs out of memory.

Avoid

Writing straight from the bus callback to the socket, so a slow client stalls the publisher.

5

Make id: a real cursor into a log, and define the "too old" case

Do

Use IDs from a durable, ordered log (Redis Stream entry IDs, Kafka offsets). On reconnect, replay after Last-Event-ID. If that ID has aged out, send a reset event telling the client to refetch a snapshot the full current state, fetched by a normal request, that later events apply on top of.

Why

Without a log, id: promises a resume that silently drops events. Without a reset path, a client back from a laptop sleep shows stale state forever.

Avoid

A per-process counter as the ID. It restarts at 1 on every deploy and means nothing on another node.

6

Add a backplane the day you run a second instance

Do

Publish events to Redis Pub/Sub, NATS, or Kafka, and have every SSE node subscribe to it.

Why

With an in-memory subscriber list behind a load balancer, about half your users stop getting events the moment you scale to two pods.

Avoid

Sticky sessions the load balancer pins each client to the same server as the fix. They pin connections but don't route events produced on another node.

7

One multiplexed stream per tab, over HTTP/2

Do

Open a single EventSource per tab that carries all topics, and route events with event: names. Serve browsers over HTTP/2 or HTTP/3.

Why

On HTTP/1.1, the ~6-connections-per-origin limit is shared across tabs, so the seventh tab hangs. Even on HTTP/2, nginx usually speaks HTTP/1.1 upstream, so each stream is still one upstream TCP connection.

Avoid

One EventSource per widget.

8

Authenticate the connection, then authorize every event

Do

Use cookies with withCredentials, or a short-lived (~60 s) single-use ticket in the query string that you exchange at connect time. Filter fan-out copying one event to many subscribers by tenant and user before writing each event. Cap open streams per user.

Why

A long-lived bearer token in the URL ends up in access logs. A topic-wide broadcast that skips per-event checks leaks one tenant's data to another.

Avoid

Checking auth only at connect and then trusting a ?channel= parameter supplied by the client.

9

Let a formatter write the wire format

Do

Use TypedResults.ServerSentEvents / SseFormatter (.NET 10) or your stack's equivalent, and JSON-serialize payloads, which escapes newlines.

Why

A raw \n in user text written into one data: line ends the event early. That lets an attacker inject fake event:/id: lines.

Avoid

$"data: {message}\n\n".

10

Handle the permanent-failure path on the client

Do

Watch for readyState === CLOSED, which follows a non-200 response such as an expired-auth 401. Refresh credentials, then recreate the EventSource with jittered randomly varied, so clients don't all retry at the same instant backoff, and pass the last seen ID as a query parameter.

Why

The browser auto-retries only network drops. After a 401 the stream stops for good and the UI looks frozen with no error shown.

Avoid

Treating every error event as fatal. It also fires on each normal reconnect.

11

Size per-node capacity with a load test, not a guess

Do

Load-test with a non-browser client (Shopify used okhttp-eventsource) and record connections per pod at your memory and CPU ceiling. Check file-descriptor limits, net.core.somaxconn, and proxy ephemeral ports the short-lived local ports an outgoing connection borrows; one per open upstream connection.

Why

The limits are usually in the OS, not in SSE. Linux's default port range (32768–60999) gives one proxy about 28K concurrent connections to one upstream IP:port.

Avoid

Autoscaling on CPU alone. Idle SSE connections use memory and descriptors, not CPU.

Anti-patterns to recognize

✕

The static subscriber list

A static ConcurrentDictionary of open responses that the publish endpoint loops over. Works perfectly with one instance, silently loses events with two. Add a backplane from the first deploy with more than one replica.

✕

The "helpful" reconnect wrapper

onerror = () => { es.close(); es = new EventSource(url); }. It throws away the browser's Last-Event-ID, skips its retry delay, and turns a blip into a reconnect storm. Let the browser reconnect on its own, and rebuild only on CLOSED.

✕

IDs without memory

The server emits id: because a tutorial did, but keeps no log. Reconnects look healthy in dashboards while users miss events. Back the IDs with a log, or omit them so nobody assumes resume works.

✕

Orphaned upstream generation

An LLM relay that keeps reading from the provider after the browser disconnects. You pay for every token nobody reads; on a busy chat product that's a visible share of the bill. Propagate cancellation upstream, unless you deliberately chose resumable generation (see the LLM pattern below).

✕

SSE on the API pods

Stream endpoints share pods with an API you deploy 20 times a day. Every deploy disconnects every user at once, and they all hit the new pods together. Move streams to a separate, rarely deployed tier, or drain pods gradually with jittered retry:.

✕

Fat broadcast, thin authorization

Pushing full records to a topic channel because "everyone on this page can see it anyway". The first shared dashboard across tenants leaks data. Filter per subscriber, or send thin events ("order 123 changed") that make the client refetch through normal authorization.

Real-world usage patterns

LLM chat relay

A backend turns provider SSE events into its own simpler stream. Two camps on disconnects:

  • Cancel-on-disconnect aborts the upstream call to save tokens.
  • Resumable generation (Vercel AI SDK with the Redis-backed resumable-stream) keeps generating into Redis so a reload can reattach. The AI SDK docs warn that client aborts are then only disconnects and must not cancel generation.

Tie-breaker is task length: seconds → cancel; minute-long agent runs → resume. Lesson: decide up front, because a separate "stop" endpoint and the resume mode interact in non-obvious ways.

Shopify BFCM Live Map

Replaced clients polling a mailbox at least every 10 s. Flink writes to Kafka; a Go SSE server behind nginx pushes each update as it arrives. Clients sent JWTs through an EventSource polyfill, because native EventSource can't set headers. Lesson: the SSE tier stayed stateless and scaled horizontally because Kafka was the log; per-pod capacity came from a load-test client, not estimates.

LinkedIn instant messaging

Chose SSE over WebSockets for compatibility and reached 100K persistent connections per node. Every wall was outside the protocol:

  • somaxconn at 128,
  • a 30K file-descriptor limit (raised to 200K),
  • roughly 20 KB of TLS state per connection, pushing the heap to 16 GB.

Lesson: SSE capacity planning is kernel and memory tuning.

Enterprise B2B behind corporate proxies

One customer's legacy proxy held the chunked stream until it closed. Logins took 20 minutes while server metrics were all green. Fix: the client acknowledges receipt; if no ack arrives within seconds, the server closes the stream, which forces the proxy to flush. Lesson: you can't see client-side buffering from the server. Measure time-to-first-event on the client.

Operational checklist

✓

Before you call it done

  • Dashboards: open connections per node, connection opens per second, and a connection-duration histogram? A spike at exactly 60 s or 100 s points to an intermediary timeout.
  • Latency: is publish-to-render measured, with a server timestamp in the payload and the delta reported by the client?
  • Heartbeat: is the interval shorter than the smallest idle timeout in the chain, and is that chain written down?
  • Smoke test: does staging fail when any hop starts buffering or compressing text/event-stream?
  • Pod killed mid-stream: tested? Do clients resume on another node with no gaps and no duplicates?
  • Too-old cursor: when Last-Event-ID is older than retention, does the client get a reset/snapshot rather than silence?
  • Security: tokens kept out of long-lived URLs, authorization checked per event, streams per user capped?
  • Cost: does a client disconnect cancel upstream work (LLM calls, DB cursors)? Are SSE endpoints kept off duration-billed serverless runtimes?
  • Onboarding: does the README say "one EventSource per tab, named events, never recreate it on error"?

How it evolves in a codebase

  1. One endpoint, in-memory subscribers. Often added for a single feature like a progress bar. It works, so a second feature reuses it.
  2. Second replica → Redis Pub/Sub backplane. Scaling to two replicas makes half the users miss events; the first painful fix is a Pub/Sub backplane. Pub/Sub is fire-and-forget, so reconnect gaps remain.
  3. Redis Streams or Kafka. Now id: finally means something. This retrofit is the expensive migration: every producer must write to one ordered log, every client must handle a reset event, and old clients that cached counter-based IDs send cursors that no longer mean anything. Teams that design IDs and snapshot-plus-delta from day one skip this rewrite.
  4. Its own tier. At larger scale, streaming splits into a dedicated SSE gateway with its own deploy schedule, autoscaling on connection count, and kernel tuning, or moves to a hub such as Mercure or a managed push service. The trigger is usually deploy pain: once a routine API deploy disconnects every user, separate infrastructure pays for itself.

Run the MVP

  • Needs .NET SDK 10.0+. The projects target net10.0 because SseItem<T> and TypedResults.ServerSentEvents don't exist in .NET 8 or 9.
  • Run: dotnet run --project Api, then curl -N http://localhost:5199/prices in a second terminal.
  • What it shows: a tick every 200 ms, IDs that are log sequence numbers, gap-free resume via Last-Event-ID, and a reset event when the cursor is older than the 5-tick replay log.
  • Hygiene built in: cancellation from RequestAborted + ApplicationStopping, a bounded DropOldest queue (64 items) per client, and retry: 1000 sent once per connection.
