Practice — how it plays out for real

● ~10 min read ✎ best practices · anti-patterns · checklist

Where you'll meet it

In a typical SaaS backend, rate limiting is the thin layer between your auth middleware and your business logic — a couple dozen lines of config plus a Redis dependency the team forgets exists until Redis hiccups. It's invisible when it works and deafening when it doesn't. You'll meet it in four settings:

App middleware

A couple dozen lines of config in Program.cs, keyed by user or tenant, backed by Redis.

The gateway

Kong, Envoy, or AWS API Gateway plugins, where per-tenant SLOs live separately from per-endpoint business rules.

The edge

Cloudflare or AWS WAF rate-based rules that shed obvious abuse before it costs you origin compute.

Client-side wrapper

A Polly rate-limit policy or a SemaphoreSlim around a third-party SDK — because OpenAI, Stripe, Twilio, and SendGrid all impose limits on you.

If you work on a public API, a login endpoint, an LLM-backed feature, or anything multi-tenant, rate limiting is load-bearing. Treat it that way.

Best practices

1

Key on identity, not on IP, whenever you have one

Do

Extract the limit key from the strongest identifier available — the sub claim from a verified JWT, an API key hash, a tenant ID — and fall back to IP only for anonymous traffic.

Why

Office NATs, mobile CGNAT, and corporate proxies aggregate thousands of legitimate users behind one IP. Keying on IP turns a legitimate burst into a customer-wide outage.

Avoid

Defaulting to client_ip everywhere because it's the easy first parameter to grab.

2

Make the Redis call atomic with a Lua script

Do

Implement check-refill-decrement as one EVAL/EVALSHA Lua script. Use redis-cell (GCRA in C) if you can install Redis modules.

Why

A two-step INCR + EXPIRE has a race where the EXPIRE is skipped if the client dies between calls, and the counter never expires — multiply by your key cardinality and Redis memory climbs without bound.

Avoid

"We'll just do INCR and EXPIRE separately — it'll be fine most of the time."

3

Decide fail-open vs. fail-closed explicitly, and instrument both

Do

Pick per endpoint. Public read endpoints fail open (availability over correctness). Auth, payment, and LLM endpoints fail closed (cost and security over availability). Emit a metric every time the fallback fires.

Why

Silent fail-open during a Redis outage is how a $40,000 LLM bill gets generated overnight. Silent fail-closed is how a Redis blip takes the whole product down.

Avoid

Inheriting the library's default and never reading the docs to find out what it is.

4

Always set Retry-After, and jitter it server-side

Do

Return Retry-After in seconds with ±20% random jitter so clients don't synchronize. Also emit RateLimit-Limit, RateLimit-Remaining, RateLimit-Reset per the IETF draft.

Why

A deterministic Retry-After produces a thundering herd at exactly the reset time — a clean traffic cliff followed by a near-vertical spike that re-trips the limiter.

Avoid

Returning a 429 with no header and hoping the client implements exponential backoff on its own.

5

Two-tier the limiter: local first, distributed second

Do

Run a small in-process token bucket (per replica, generous limit) in front of the Redis-backed global limiter. The local one absorbs hot-key bursts without a network call.

Why

A single-instance Redis hitting 100% CPU on Lua execution is a real incident — Stripe and Shopify have both written about it. A local first tier cuts Redis QPS by 10–100×.

Avoid

Sending every request to Redis when 95% of the answer is "obviously allowed, the bucket is full."

6

Dark-launch every new limit before enforcing it

Do

Run the limiter in dark-launch — log-only — mode for a week. Compare what would have been blocked against complaint volume and real traffic patterns. Then flip to enforce.

Why

This is Stripe's published playbook. Limits set by guessing in a meeting room are almost always wrong by at least one order of magnitude, in one direction or the other.

Avoid

Shipping a new limit on Friday afternoon "to be safe" and finding out Monday that you blocked your biggest customer's nightly batch job.

7

Scope limits to key × route-class, not just key

Do

Bucket routes into classes — route-class a group of similar endpoints, e.g. read / write / expensive, sharing one limit like read, write, expensive (search, export, AI) — and apply different limits per class. The key becomes (tenant, route-class).

Why

A flat per-user limit means one heavy /reports/export call consumes the budget for fifty cheap /me polls — UX that feels broken for reasons the user can't see.

Avoid

One global "1,000 req/min per user" knob applied to everything from /healthz to /ai/generate.

8

Cost-shape, not just count-shape, for expensive endpoints

Do

For LLM and similar pay-per-call backends, enforce two parallel limits: requests per minute (RPM) and a cost-weighted limit — TPM for tokens, or dollars per hour. Charge the bucket by estimated cost on entry, reconcile on exit.

Why

A 200,000-token prompt is 1,000× more expensive than a 200-token one. RPM alone lets a single customer rack up a five-figure bill while staying "within limits."

Avoid

Counting only request volume on endpoints where per-request cost varies by orders of magnitude.

9

Bound the key-space cardinality

Do

Hash long keys to a fixed length, set Redis maxmemory-policy allkeys-lru, and reject or aggregate keys that would explode cardinality — e.g. per-path limits on a path that includes a UUID.

Why

Naive keying on (user, path) for a path like /orders/{id} produces unbounded keys, and Redis OOM-kills itself overnight.

Avoid

Using the raw URL as part of the key without normalizing it to a route template first.

10

Make the limiter observable from day one

Do

Emit four metrics: ratelimit.allowed, ratelimit.rejected, ratelimit.fallback, and p99 ratelimit.latency_ms, each tagged by route and tier. Alert on rejection-rate spikes and on fallback-mode activation.

Why

Without the rejection metric you'll only learn about a misconfigured limit from a support ticket. Without the fallback metric you won't know your limiter has been silently disabled for three weeks.

Avoid

Logging rejections to stdout and calling it observability.

Anti-patterns to recognize

✕

The IP-only limiter on an authenticated endpoint

Looks fine in dev, where everyone has a different IP; in production one shared corporate NAT triggers limits for thousands of real users. Use the authenticated identity once you have it.

✕

The INCR-then-EXPIRE racer

Two Redis calls instead of a Lua script. Under partial failure the TTL is never set and the counter leaks. Use one atomic script.

✕

The fail-open default no one chose

The library failed open, the team never noticed, and the limiter was effectively disabled for the eighteen months since the last Redis incident. Make the choice explicit and alert on it.

✕

The synchronized retry stampede

Server returns Retry-After: 60, ten thousand clients retry at second 61, the limiter trips again, infinite loop. Jitter server-side, back off exponentially client-side.

✕

The global single-Redis bottleneck

All limiter traffic hits one Redis primary, which becomes the production-traffic CPU ceiling. Shard by key, or add a per-replica local first tier.

✕

The unbounded key-space

Keying by raw path or query string creates a new Redis key per unique URL; memory grows linearly with traffic until the box dies. Normalize to route templates.

✕

The "we'll add limits later" project

Limits get retrofitted after the first incident, set conservatively to avoid breaking anyone, and then become permanent because nobody dares raise them. Dark-launch from the start, even at generous values.

✕

The limiter that punishes its own retries

Internal retry logic — Polly, gRPC's built-in retry — fires three attempts that each consume a token, so legitimate clients get rate-limited by their own resilience code. Retry-budget separately, or charge once per logical operation.

Real-world usage patterns

Public REST API, tiered pricing

A B2B SaaS exposes a versioned REST API: free tier gets 60 req/min, Pro gets 1,000, Enterprise is negotiated. Token bucket per (API key, route-class) in Redis, IETF RateLimit-* headers on every response, dark-launched for two weeks before enforcement. Lesson: the headers themselves became a feature — customers built dashboards on RateLimit-Remaining and noticed problems before support did.

Login / credential-stuffing defense

An e-commerce backend rate-limits POST /auth/login by (email, IP) at 5/min and by IP alone at 30/min. The limiter fails closed: a Redis blip is preferable to an open door. Paired with a CAPTCHA after N rejections rather than a hard block. Lesson: keying purely by email lets an attacker lock out a target user; the tuple key prevents that.

LLM gateway in front of OpenAI/Anthropic

An internal gateway enforces both RPM and TPM per team, charging the token bucket by estimated tokens at request time and reconciling on response. Spillover above quota is queued (leaky bucket) rather than rejected, since the calling code is batch-style. Lesson: queue depth is the leading indicator of cost overruns.

Multi-tenant background-job runner

A scheduler runs tenant-owned jobs on shared workers. The limit is concurrency-based — SemaphoreSlim(8) per tenant — not RPM, because the scarce resource is worker slots, not API throughput. Lesson: rate limiting and concurrency limiting are different tools; pick by what's actually scarce.

Operational checklist

✓

Before you call it done

  • Monitoring: are allowed, rejected, fallback, and limiter p99 latency all on a dashboard with alerts on each?
  • Failure handling: when Redis goes away, do you know within 60 seconds whether you're failing open or closed — and is that the choice you made on purpose?
  • Atomicity: is check-and-decrement a single Lua script or redis-cell call, with no INCR+EXPIRE two-step anywhere?
  • Headers: do 429 responses include Retry-After with server-side jitter, plus the standard RateLimit-* triple?
  • Key hygiene: are limit keys normalized to route templates, hashed if long, and bounded so Redis memory can't grow unbounded?
  • Security: is the login endpoint keyed by (email, IP), not just email (lockout abuse) or just IP (shared NAT)?
  • Cost: on every paid-per-call backend, is there a cost-weighted limit, not only a request-count one?
  • Onboarding: can a new engineer find the limit config in under five minutes and tell you which limits are enforced vs. log-only?
  • Tests: is there an integration test that simulates Redis being unreachable and asserts the documented fallback behavior?
  • Client behavior: do your own internal clients and shipped SDKs respect Retry-After with jitter and exponential backoff?

How it evolves in a codebase

  1. In-process middleware. AddFixedWindowLimiter in ASP.NET or express-rate-limit in Node, keyed by IP, single instance, no observability. Works for the first six months on low traffic and one replica.
  2. Redis-backed shared state. At horizontal scale-out, three replicas make the effective limit 3× what's configured, forcing the move to Redis. This is the painful point — a Lua script gets written, atomicity bugs surface, and someone learns what fail-open means at 2 a.m. during a Redis failover.
  3. Tiered limits. Once the product becomes multi-tenant or adds pricing tiers, limits move per-tenant and per-route-class, and config moves out of code into a database or feature-flag system, because product now owns the values.
  4. Dedicated limit service. Reached by maybe one in five projects: a shared gRPC service — often envoyproxy/ratelimit — across the fleet, with adaptive limits that move with downstream health. By then rate limiting is a platform capability with its own on-call rotation.
