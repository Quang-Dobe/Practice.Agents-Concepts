Detail — the deep dive

◑ ~10 min read ✎ What · Where · When · How · Why

What it is

Rate limiting enforces an upper bound on the rate of accepted requests from an identifiable caller — an IP, a user, an API key, a tenant, a route — over a finite time window. It works by counting events against shared state and rejecting or shaping any event that would push the count past a configured threshold.

  • Core idea. It's a special case of admission control deciding whether to accept work at all, before it starts. A circuit breaker reacts to downstream health; a load shedder reacts to local resource pressure; a rate limiter reacts to caller behavior.
  • Formally. For a stream of events arriving over time, the limiter decides allow/deny per event so that in every window of length W, the number of allowed events for a given key never exceeds N.

The core building blocks

Key extraction
Pulling the identifier the limit is scoped to — an API key header, the sub claim from a JWT, the client IP after trusting X-Forwarded-For for N hops, or a pair like (tenant, route).
Counter store
Where per-key state lives: an in-memory dictionary, a Redis hash, a sorted set, or a distributed counter.
Algorithm
The policy that turns (state, now, request) into allow/deny: fixed window, sliding window log, sliding window counter, leaky bucket, token bucket, or GCRA.
Decision plane
The code path that either accepts and updates state, or returns 429 Too Many Requests with a Retry-After header.
Policy configuration
Per-route or per-tier limits, usually loaded from config — Envoy YAML, ASP.NET Core AddFixedWindowLimiter, Nginx limit_req_zone.

It sits in the family of traffic management primitives alongside load shedding, prioritization, and queueing. Its closest siblings:

  • Quotas — a longer horizon, billing-shaped.
  • Concurrency limiters — cap requests in-flight rather than per-second.
  • Bulkheads — isolate failure domains.
  • Circuit breakers — open on downstream failure, not on caller volume.

All five overlap in practice but solve different problems: a token bucket cannot save you from a flapping downstream, and a circuit breaker cannot stop a credential-stuffing attack.

Where it lives

A request can be rate-limited at up to four layers, often simultaneously:

1 · Edge / CDN

Cloudflare, Fastly, AWS WAF. Cheapest to enforce; stops abuse before it touches your origin. Coarse keys: IP, ASN, country.

2 · API gateway / mesh

Kong, Apigee, Envoy + Lyft's ratelimit service. Enforced after TLS termination but before app code; knows routes and auth claims.

3 · Application middleware

ASP.NET Core RateLimiter, Express express-rate-limit, Django Ratelimit. Knows business-level identifiers: user ID, plan tier.

4 · Downstream resource wrappers

A SemaphoreSlim or a Polly rate-limit policy around a third-party SDK, to respect their limits.

You'll meet real implementations everywhere: Stripe publishes per-account read/write limits enforced by a token bucket backed by Redis; the GitHub REST API allows 5,000 authenticated requests/hour, surfaced via X-RateLimit-* headers; every AWS service has its own per-region, per-account TPS limit; Cloudflare Rate Limiting Rules count at the edge on any request attribute; and OpenAI / Anthropic APIs enforce both RPM (requests per minute) and TPM (tokens per minute), the second being a cost-aware variant.

Ecosystem and tooling

  • .NET: Microsoft.AspNetCore.RateLimiting (built in since .NET 7, four algorithms shipped), paired with StackExchange.Redis and a Lua script for distributed state.
  • Node/Express: express-rate-limit; rate-limiter-flexible for Redis, Memcached, Mongo, or clustered Node.
  • Mesh / gateway: Envoy's ratelimit_filter + the envoyproxy/ratelimit gRPC service; Kong's rate-limiting-advanced; NGINX limit_req_zone.
  • Edge: Cloudflare Rate Limiting Rules, AWS WAF rate-based rules, Fastly VCL ratecounter.
  • Redis-based custom limiters: the redis-cell module (GCRA in C), the RedisRateLimiting NuGet package, Stripe's open-source ratelimit Lua scripts.
  • Client-side compliance: Polly (.NET), tenacity (Python), retry-axios (Node) — all parse Retry-After and back off with jitter.

When to use it

✓ Reach for it when

  • The endpoint is reachable by untrusted or partially trusted callers.
  • One caller's pathological behavior could degrade other callers sharing a DB, queue, or cache.
  • You need per-tier differentiation — free vs. paid.
  • The endpoint has expensive backing cost — LLM inference, geocoding, transactional email.
  • You depend on a third-party API with its own limits and need to stay under them.

✕ Skip it when

  • Traffic is purely east-west, mTLS-authenticated, inside a trusted mesh — use timeouts, concurrency caps, and load shedding instead.
  • The real problem is DDoS volume at L3/L4 — that needs a scrubbing service, not an app limiter that will itself get saturated.
  • Fairness must be strict and queue-like, FIFO — use an explicit queue.
  • Calls are batched and asynchronous with no per-call latency SLA — a queue-based throughput controller is clearer.

A little history

The pattern predates HTTP. GCRA was specified by the ATM Forum in 1996 as a leaky-bucket variant for cell-switched networks; token bucket appeared in network QoS literature in the late 1980s. Web-scale rate limiting became a daily concern around 2006–2010, when public APIs like Twitter, Flickr, and AWS S3 discovered that one buggy client could exhaust their capacity. The 429 status was standardized in RFC 6585 (2012). As of 2026 the IETF draft draft-ietf-httpapi-ratelimit-headers (revision 10) is trying to standardize RateLimit-Limit, RateLimit-Remaining, and RateLimit-Reset, replacing the long-standing zoo of vendor-prefixed X-RateLimit-* headers.

How it works

Walk a single request through an app-level, Redis-backed token-bucket limiter:

  1. Key extraction. Middleware reads Authorization: Bearer …, validates the JWT, takes sub as the key. Falls back to client IP for anonymous requests.
  2. Atomic check-and-decrement. The middleware invokes a Lua script via EVALSHA on Redis. The script reads two fields from a hash: tokens (current count) and last_refill (epoch ms).
  3. Refill. The script computes elapsed = now - last_refill, then new_tokens = min(capacity, tokens + elapsed * refill_rate).
  4. Decision. If new_tokens ≥ 1, decrement by 1, write back, return allowed with the remaining count. Otherwise write back unchanged and return the retry delay: ceil((1 - new_tokens) / refill_rate).
  5. TTL. The script sets a TTL of capacity / refill_rate so idle keys evict.
  6. Response shaping. On reject, the middleware short-circuits the pipeline, emits 429, sets Retry-After, RateLimit-Limit, RateLimit-Remaining: 0, RateLimit-Reset, and increments a ratelimit.rejected metric.

A sliding window log works differently: storage is a Redis sorted set keyed by user, each request adds a member scored by now. The script evicts anything older than the window, counts what's left, and rejects past N — exact, but O(N) memory per key. The sliding window counter approximates this with just two integers (the current and previous fixed-window counts), accurate to within a few percent at O(1) memory.

Common failure modes

⚠

Thundering herd on Retry-After

All clients get the same reset time and retry at once. Cause: a deterministic, un-jittered Retry-After value.

✕

Counter-leak race

A counter is incremented but its TTL is never set, so the key lives forever. Cause: a two-call INCR + EXPIRE instead of one Lua script.

⚠

Edge-of-window double burst

A client sends 2N requests across a window boundary. Cause: fixed window with no smoothing.

⚠

NAT / shared-IP punishment

One key — an office NAT, a corporate proxy — represents thousands of legitimate users. Cause: keying by IP when an authenticated identity was available.

✕

Limiter as the bottleneck

Redis hits 100% CPU running the Lua script. Cause: a single-instance Redis serving all keys; fix with hash-slot sharding or a local first tier.

⚠

Clock skew across nodes

A sliding window log evicts the wrong entries. Cause: using each node's local wall clock instead of a server-side time call.

✕

Silent failure under a Redis outage

The limiter fails open and admits all traffic. Cause: no explicit fail-closed policy on a cache miss or timeout.

✕

Retry-storm amplification

Clients get a 429, retry immediately, get another 429, retry again. Cause: an aggressive client retry budget interacting with a too-tight limit.

Why it exists

Every shared resource — CPU, DB connections, third-party quota, dollars per inference call — is finite. Without admission control, a system's behavior under overload is unspecified: typically queue growth, latency blowup, and cascading timeouts. Rate limiting collapses that into one explicit contract — up to N per W, beyond that a 429 — that's cheap to enforce, cheap to communicate, and gives clients deterministic feedback.

Why it looks the way it does

Token bucket dominates because it captures the only two facts a real API cares about: the steady-state rate (the drip) and the tolerable burst (the bucket size). Pure leaky bucket forces queueing, which complicates HTTP semantics and adds latency. Pure fixed window is too crude — it lets through nearly double the intended rate right at the window edge:

Sliding window log is too memory-hungry at scale. Token bucket is the middle ground: O(1) state, two intuitive knobs, room for the bursts real clients produce on cold start, and a graceful decay to a flat rate under sustained load. The 429 + Retry-After design (instead of a silent TCP reset) exists because HTTP is request-response and clients need to know why. Choosing to fail open let all traffic through when the limiter itself breaks, favoring availability or fail closed reject traffic when the limiter breaks, favoring cost and safety over availability during an outage is deliberate: most public APIs fail open, while billing-sensitive systems like LLM APIs fail closed, because cost matters more than availability there.

Why it matters now

As of 2026, three pressures keep rate limiting central. First, LLM API costs are real money per call, so token-aware limits (RPM plus TPM) are now a first-class product surface. Second, agentic clients — AI agents looping with retries — produce traffic patterns humans never did; naive limits either let them run away or strangle legitimate automation, so adaptive, identity-aware limits are becoming the baseline. Third, multi-tenant SaaS has matured to where per-tenant fairness during a noisy-neighbor incident is a contractual SLA, not a nice-to-have. The IETF RateLimit headers draft is on track to become an RFC, which should finally end the X-RateLimit-* dialect war.
