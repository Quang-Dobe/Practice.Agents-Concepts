Overview

◔ ~3 min read ✎ intuition-first

Servers, databases, and downstream APIs all have finite capacity. Rate limiting caps how many requests one caller can make in a given window of time, so a runaway script, a scraper, or an attacker can't starve everyone else.

ⓘ

In 30 seconds

It's the cheapest, most reliable line of defense between "the service is healthy" and "the on-call phone rings at 3 a.m." It also doubles as a billing and fairness knob: a free tier might get 100 requests/minute while a paid tier gets 10,000.

The mental model

Picture a popular nightclub with one bouncer at the door. The club holds 200 people comfortably, but tonight 5,000 want in. The bouncer doesn't try to stuff everyone inside — he hands out wristbands at a steady pace and tells the rest to wait or come back later.

Now give each guest a bucket. Every time they enter, a token drops into their bucket. The bouncer refills each bucket slowly — say one token per second, up to a max of ten. A guest with an empty bucket gets turned away with a polite "try again soon." This is the token bucket tokens refill at a steady rate; each request spends one; a full bucket lets a burst through algorithm, and it's what Stripe, AWS, and most modern APIs use under the hood.

The key insight: rate limiting is not about blocking traffic — it's about shaping it. Bursts get through because the bucket starts full, but sustained abuse drains the bucket faster than it refills, and the offender is automatically held back. When the bucket is empty, the caller gets a 429 the "Too Many Requests" HTTP status code response with a Retry-After a response header telling the caller how many seconds to wait before trying again header, not silence.

What it is not

⚠

Common mix-ups

  • Not a firewall. Firewalls block by IP or port; rate limiters count behavior over time.
  • Not a load balancer. Load balancers spread traffic across servers; rate limiters reject excess traffic outright.
  • Not a circuit breaker. Circuit breakers trip when downstream services fail; rate limiters trip when upstream callers misbehave.
  • Not a quota. Quotas are usually daily or monthly billing caps; rate limits are short-window protection — seconds to minutes.

When to reach for it — and when not to

✓ Reach for it when

  • You run a public API where any anonymous caller could hammer you.
  • You're protecting login and password-reset endpoints from credential-stuffing attacks.
  • The endpoint is expensive — search, report generation, AI inference — and costs real money per call.
  • You run tiered SaaS pricing where free vs. paid users get different request budgets.
  • You need to protect a fragile downstream: a legacy system, a third-party API with its own limits, or a slow database.

✕ Skip it when

  • It's internal service-to-service traffic inside a trusted mesh — use timeouts, retries, and bulkheads instead.
  • You need hard fairness across a very small number of users — explicit queues are clearer.
  • You're trying to stop a determined DDoS — that's a job for a CDN or scrubbing service like Cloudflare, not your app-layer limiter.

Key vocabulary

Token bucket
Refill tokens at a steady rate; each request spends one. Allows bursts.
Leaky bucket
Requests queue and drain at a fixed rate. Smooths bursts into a flat line.
Fixed window
Count requests inside a clock-aligned window (e.g. 12:00:00–12:00:59). Simple, but allows double-bursts at window edges.
Sliding window
A rolling time frame that fixes the edge-burst problem.
429 Too Many Requests
The HTTP status code returned when a client is rate-limited.
Retry-After
Response header telling the client when it's safe to try again.
Backoff
Client-side strategy of waiting — often exponentially longer each time — before retrying.
Distributed rate limiter
Shared state, usually Redis, so limits work across many app servers.
