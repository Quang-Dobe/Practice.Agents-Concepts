Practice — how it plays out for real

● ~11 min read ✎ best practices · anti-patterns · checklist

Where you'll meet it

In a polyglot backend, gRPC is the wire between internal services — a Go ingest pipeline calling a C# pricing service, a Python model scorer fronting a Java order service. Any team that said "we'll just use JSON for now" and then watched p99 climb tends to reach for it next quarter. In Kubernetes-native infrastructure it's already there whether a team picked it or not: the kubelet talks CRI over gRPC, CSI/CNI plugins are gRPC servers, and OpenTelemetry collectors accept OTLP/gRPC.

Polyglot backend

Different languages, one shared contract, all generated from the same .proto files.

Kubernetes-native infra

CRI, CSI, CNI, the Envoy control plane, OpenTelemetry collectors — all gRPC whether the team chose it or not.

ML serving & platform tools

TensorFlow Serving, NVIDIA Triton, Temporal, etcd, Dapr — application teams meet gRPC as a client before they run a server of their own.

Product code

gRPC internally, plus a thin REST/JSON facade (grpc-gateway, JSON transcoding, or a hand-written BFF) at the edge for browsers and partners.

Best practices

1

Treat the .proto repo as a product, not a side artifact

Do

Store .proto files in a dedicated repo or top-level /proto tree, lint with buf lint, run buf breaking against the main branch in CI, and publish generated stubs as versioned packages (NuGet, npm, Go module).

Why

Schemas are the contract between teams that ship on different cadences. If proto changes land via copy-paste, client and server quietly disagree on field numbers — the single worst class of gRPC bug, because it deserializes successfully but into the wrong field.

Avoid

Hand-copying .proto files into each service repo "for convenience."

2

Evolve schemas additively, and reserved everything you remove

Do

Add new fields with new numbers. When deleting one, replace it with reserved 7; reserved "old_field_name";. Never change a field number or type.

Why

Protobuf identity is the field number. Reusing number 7 for a new meaning silently corrupts old clients' data — the bytes decode fine, just into the wrong slot. The bug surfaces as ghost values weeks later.

Avoid

"We're the only client, it's fine to renumber." There is always one stale pod, one cached binary, one old mobile app you forgot.

3

Set a deadline on every outbound call, and propagate the inbound one

Do

Configure a per-call deadline in client code. In a server handler, derive outbound deadlines from the inbound one so the time budget shrinks down the call graph.

Why

Without a deadline, a slow downstream pins server threads or goroutines forever. One stuck dependency takes the whole fleet to its connection limit in minutes.

Avoid

Relying on TCP timeouts or "the load balancer will kill it." Neither one knows your RPC's semantics.

4

Pick a retry strategy explicitly, and only retry idempotent methods

Do

Configure retries in gRPC's service config with explicit retryable codes — typically UNAVAILABLE, sometimes RESOURCE_EXHAUSTED — using exponential backoff with jitter. Mark mutating methods non-retryable, or require an idempotency key a client-generated ID that lets a retried write be recognized and deduplicated in the request.

Why

Auto-retrying a CreateOrder on UNAVAILABLE after the server already committed — but before the trailer arrived — creates duplicate orders. A retry token bucket exists to stop retries from turning a brownout into a full outage.

Avoid

A blanket 5-attempt retry policy on every method. That's how brownouts become full outages.

5

Use client-side load balancing with a real resolver, not a plain ClusterIP

Do

In Kubernetes, expose the gRPC server as a headless service a Kubernetes Service with no ClusterIP, so DNS returns every pod's address for the client to load-balance across, use a dns:// resolver, and enable round-robin on the channel. Or front the service with an L7-aware proxy (Envoy, Linkerd, Istio).

Why

A normal ClusterIP load-balances at L4. gRPC opens one HTTP/2 connection and multiplexes thousands of streams over it — so 100% of one client's traffic lands on one pod. Adding replicas does nothing. This is the single most common gRPC-on-Kubernetes surprise.

Avoid

Assuming "Kubernetes load-balances for me." It does — just at the wrong layer for HTTP/2.

6

Use canonical status codes, and rich error detail when you need it

Do

Map domain errors to the 16 non-OK codes: INVALID_ARGUMENT for validation, FAILED_PRECONDITION for state-machine errors, ABORTED for concurrency conflicts, UNAVAILABLE only for "try again." Attach structured detail (BadRequest, RetryInfo, ErrorInfo) when a client needs more than a code.

Why

Retries, breakers, and dashboards all key off the code. INTERNAL for everything destroys observability and makes safe retries impossible.

Avoid

Throwing raw exceptions and letting the framework map them all to UNKNOWN.

7

Wrap every call in interceptors for auth, tracing, and metrics

Do

Install one chain: an auth interceptor (validate the token or mTLS identity), an OpenTelemetry interceptor (propagate traceparent, record status), and a metrics interceptor (rate, errors, duration per method).

Why

Per-method observability is the difference between "one RPC is slow" and "we have no idea." Interceptors are the only place to add it once and cover unary plus all three streaming shapes consistently.

Avoid

Logging inside each handler. You'll forget half of them and double-log the rest.

8

Enforce TLS, prefer mTLS between services

Do

Terminate TLS at the server or its sidecar, using ALPN's h2. For service-to-service traffic, use mTLS — a mesh, or SPIFFE/SPIRE-issued short-lived identities. Disable cleartext h2c outside localhost.

Why

gRPC metadata routinely carries bearer tokens and tenant IDs. Cleartext between pods is a compliance failure and a credential-leak vector. mTLS makes "who called me" a property of the connection, not a header you have to trust.

Avoid

A hand-rolled "shared secret in metadata" scheme. That's reinventing auth, badly.

9

Disable server reflection in production

Do

Register the reflection service only behind an env flag or an internal-only port. Keep it on in dev so grpcurl / grpcui / Postman work with no .proto files on hand.

Why

Reflection lets anyone with network reach enumerate every service, method, and message shape — your full API surface, no auth required. That's the recon step you don't want to make free.

Avoid

Shipping the same chart from dev to prod with reflection always on.

10

Cap message size, and stream anything that could grow

Do

Keep the default 4 MiB inbound limit. If a payload could exceed roughly 1 MiB, switch the RPC to a server- or client-streaming shape that emits chunks. For genuinely huge blobs, hand out a presigned URL to object storage instead.

Why

A single 200 MiB message blocks one stream's flow-control window for the duration, holds a contiguous buffer in memory on both ends, and makes deadlines nearly meaningless.

Avoid

Raising the max message size to 100 MiB to "just make it work." That's papering over a design issue.

11

Handle streaming backpressure and half-close explicitly

Do

On a server-stream, check write-readiness before each send. On a bidi stream, treat the client's half-close as a normal signal, not an error. Bound any in-memory queue between business logic and the stream writer.

Why

A fast producer with a slow consumer and an unbounded queue is an out-of-memory crash waiting to happen. Forgetting half-close semantics leads to streams that hang until the deadline fires, every time.

Avoid

Writing to a stream in a tight loop with no flow control. Looks fine in tests, melts under load.

12

Keep one channel per target, not one per call

Do

Construct one channel per target service, reuse it for the process lifetime, and let it manage subchannels. Configure a keepalive of roughly 30–60s so idle connections survive NAT and load-balancer timeouts.

Why

Channel construction is expensive — TLS handshake, name resolution, HTTP/2 settings exchange. Creating one per call defeats every benefit of HTTP/2 and can quadruple p99 latency.

Avoid

Opening a fresh channel inside a request handler.

Anti-patterns to recognize

✕

gRPC as a public API

Exposing raw gRPC to third-party developers. Browsers can't call it natively, SDKs lag, and you lose the curl-able debuggability REST gives free. Use REST/OpenAPI or grpc-gateway/Connect at the edge instead.

✕

Renumbering a field "because it's cleaner"

Moving customer_id from field 3 to field 4. Compiles fine, passes tests, silently writes customer IDs into the wrong slot for any client still on the old schema. Always additive; always reserved.

✕

Catch-all INTERNAL errors

Every server exception becomes Status.Internal("something went wrong"). Clients can't tell retryable from permanent; dashboards go flat. Map to specific codes; use rich details for context.

✕

L4 load balancer in front of HTTP/2

A cloud load balancer routing gRPC at L4. One TCP connection means one backend pod gets everything. Use headless DNS with client-side LB, or an L7 mesh.

✕

Reflection enabled in production

Convenient for grpcurl, but it hands attackers your schema for free. Toggle via env flag; never default-on.

✕

Deadlines set only at the edge

The API gateway has a 30s deadline; downstream services have none. The first hung dependency exhausts the call stack. Propagate the inbound deadline into every outbound call.

✕

Streaming used as "long-lived RPC" with no keepalive

A bidi stream the load balancer silently drops after 60s idle, and neither side notices for hours. Configure HTTP/2 ping keepalive and treat stream errors as recoverable.

✕

One giant .proto file with every service

Works fine at 3 services, agony at 30. Split by bounded context; version with package foo.v1; add foo.v2 rather than mutating v1.

Real-world usage patterns

Internal mesh, mid-size SaaS

50–200 services across Go, .NET, and Python. gRPC handles sync calls; Kafka handles events. Proto files live in a monorepo with buf for lint and breaking-change CI. Lesson: the CI breaking-change check is what makes "additive only" real instead of a guideline nobody enforces.

ML inference platform

Triton or a custom TF Serving fork; clients send tensors, the server streams back batched results. Max message size is intentionally bumped to ~32 MiB. Lesson: isolate the inference service behind its own channel and retry policy — don't inherit settings tuned for 1 KiB CRUD calls.

Kubernetes-native control plane

Envoy xDS or an internal operator streams config over a long-lived bidi gRPC stream to data-plane sidecars. Lesson: streaming gRPC at infra scale is mostly about reconnect logic, not the happy path — pod churn kills streams constantly.

Mobile-first product with a BFF

Native apps speak gRPC to a backend-for-frontend, which fans out to internal gRPC services. Deadline budget is 2s at the BFF, down to 1.2s by the slowest downstream. Lesson: a strict per-hop deadline budget is cheap, effective tail-latency control.

Browser SPA via Connect-RPC / gRPC-Web

Frontend calls a Connect-RPC server that also speaks native gRPC internally — no Envoy hop needed. Lesson: Connect avoids the proxy tax if you're starting fresh, but its ecosystem is smaller than mainline gRPC's.

Operational checklist

✓

Before you call it done

  • Metrics: per-method RPS, error rate by grpc-status, p50/p95/p99 latency, in-flight stream count, channel state — exported by an interceptor, not hand-rolled per handler.
  • Tracing: does traceparent propagate via metadata across every hop, including streams?
  • Deadlines: is there a default at the channel level, and does it propagate through handlers into outbound calls?
  • Retries: which methods are retryable, is the policy in service config (not buried in client code), and are mutating RPCs excluded?
  • Schema CI: does buf breaking run on every pull request and block merges?
  • Load balancing: is the Kubernetes service headless, or fronted by an L7 mesh — verified under real load, not just by reading config?
  • TLS: is h2c disabled outside localhost? Are certs rotated, and who issues identities for mTLS?
  • Reflection: gated behind an env flag or an internal-only listener in production?
  • Message size: what's the configured max, what's the p99 actual size, and is anything close to the limit a candidate for streaming?
  • Onboarding: can a new engineer call a service with grpcurl in under 5 minutes, and do they know which interceptors run by default?

How it evolves in a codebase

  1. Tutorial stack. One .proto file in the same repo as the first service, hand-copied into the client. No buf, no breaking-change CI, deadlines optional, the Kubernetes service is a plain ClusterIP. Fine with two services and four engineers.
  2. First painful migration, around 10 services. The proto file has fanned out into copies that no longer match, a renamed field has caused a quiet production bug, and someone notices that adding pods doesn't spread the load. The fix: a proto monorepo with buf, published generated packages, and either a mesh or headless services with client-side load balancing. This migration takes a quarter and is always underestimated.
  3. Mature shape, a year or two later. A proto registry, generated stubs as versioned packages, mesh-issued mTLS, deadlines and retries codified in service config, OpenTelemetry interceptors as a shared library, and a clear v1/v2 versioning convention. The hard problem stops being "does gRPC work" and becomes "how do we deprecate v1 without paging the on-call."
