Detail — the deep dive

◑ ~11 min read ✎ What · Where · When · How · Why

What it is

gRPC is an open-source RPC framework: it defines services and messages in Protocol Buffers, serializes them into a compact binary format, and sends them as length-prefixed messages inside HTTP/2 frames over one multiplexed connection. The call's final status arrives out of band, as HTTP/2 trailers.

  • Core idea. Agree on the contract once, generate the plumbing in every language you need.
  • Four call shapes. Unary, server-streaming, client-streaming, bidirectional-streaming — each is just one HTTP/2 stream used a different way.
  • Family. Schema-first RPC, alongside Apache Thrift and Cap'n Proto (and, historically, CORBA and DCE/RPC) — a different family from REST/OpenAPI or GraphQL.

The core building blocks

Protocol Buffers (proto3 / editions)
The interface-definition language and binary format. Source of truth for messages, services, and field numbering.
protoc + language plugins
The compiler that turns .proto files into generated stubs (client) and base classes (server) in 11+ languages.
HTTP/2 transport
Provides streams, frame multiplexing, header compression (HPACK), and trailers.
Length-prefixed framing
Each message inside a DATA frame is prefixed with a 5-byte header: 1 byte compression flag, 4 bytes big-endian length.
Channel
A long-lived, load-balanced abstraction over one or more HTTP/2 connections. Stubs are stateless wrappers around a channel.
Metadata
Key-value pairs carried in HTTP/2 header frames — the gRPC equivalent of HTTP headers.
Status model
17 canonical codes carried as a grpc-status trailer, plus optional rich detail.
Interceptors
Middleware that wraps unary or streaming calls on either side for auth, logging, tracing.

Compared with Thrift, gRPC fixes one transport (HTTP/2) and one serialization (Protobuf) instead of a pluggable matrix — less flexible, more interoperable. Compared with GraphQL, gRPC is method-oriented and fixed-shape: a client cannot ask for "only these fields."

Where it lives

gRPC sits at the application layer (L7). It replaces or sits alongside JSON-over-HTTP between services — it does not replace a message bus (Kafka, NATS), a service mesh (Envoy, Linkerd — which often carries gRPC traffic), or a database's own wire protocol.

Where you'll run into it

Kubernetes internals

The kubelet talks to the container runtime (CRI) over gRPC; CSI and CNI plugins are gRPC servers too.

etcd

Its client protocol is gRPC.

Envoy xDS

Control-plane configuration is streamed to sidecars over gRPC.

ML serving

TensorFlow Serving and NVIDIA Triton expose model inference as gRPC.

Dapr

Sidecar-to-app communication.

Cloud APIs

Google Cloud APIs and many internal AWS services use gRPC on the wire; REST is often a generated facade on top.

Ecosystem and tooling

  • Schema management: protoc, and buf for linting and breaking-change detection.
  • .NET runtime: Grpc.AspNetCore (server) and Grpc.Net.Client (client), built on Kestrel and HttpClient.
  • Other runtimes: grpc-go, grpc-java, grpc-python, and a shared C-core used by C++, Ruby, PHP, Python, Objective-C.
  • Browsers: gRPC-Web plus a proxy (Envoy), or Connect-RPC as a wire-compatible alternative.
  • Debugging: grpcurl, grpcui, Postman, Kreya, BloomRPC — all rely on server reflection.
  • REST bridging: grpc-gateway (Go), Envoy transcoding, ASP.NET's JSON transcoding.

When to use it

✓ Reach for it when

  • Both ends are services you own and can regenerate clients for.
  • A polyglot backend needs one source of truth for contracts.
  • Latency or payload size is a measured cost — mobile, high-QPS internal APIs, large messages.
  • You need streaming (server push, telemetry, live updates) without hand-rolled WebSocket plumbing.
  • Deadlines and cancellation need to propagate across a call graph — hedging, tail-latency control.

✕ Skip it when

  • The API is consumed by unknown third parties.
  • The primary client is a browser and you can't run a proxy.
  • The team has no discipline for generated code and breaking-change review.
  • The workload is fire-and-forget event distribution — that's a message-bus problem.

A little history

Google open-sourced gRPC in 2015 as the public face of Stubby, its internal RPC system already used for over a decade. The trigger was HTTP/2 (RFC 7540, May 2015) finally giving the open ecosystem a transport with multiplexing, binary framing, and header compression — exactly what Stubby had relied on internally. Before gRPC, typed cross-service calls meant Thrift (Facebook, 2007), Avro RPC, or hand-rolled JSON over HTTP.

How it works

Walk a single unary call end to end:

  1. Compile time. protoc turns rpc Bar(Req) returns (Resp) into a client stub method and a server base class to override.
  2. Channel setup. The client opens (or reuses) an HTTP/2 connection. TLS is negotiated via ALPN's h2 token; cleartext h2c is allowed on trusted networks.
  3. Stream open. A new client-initiated HTTP/2 stream is allocated. The path is /<package>.<Service>/<Method>.
  4. Request sent. HEADERS carry method, path, content-type: application/grpc+proto, and a grpc-timeout; DATA carries the length-prefixed Protobuf payload.
  5. Server dispatch. The server reads the length prefix, decodes the message, and calls the generated handler.
  6. Response sent. HEADERS (200 OK) then DATA frames carry the encoded response, same framing.
  7. Trailers. A second HEADERS frame carries grpc-status (0 = OK), optionally grpc-message and rich error details, then END_STREAM closes it.

The four call shapes differ only in which side keeps the stream open:

ShapeClient DATA framesServer DATA frames
Unary11
Server-stream1N (until server closes)
Client-streamN (until client closes)1
Bidi-streamNN (interleaved)

Why the wire format is this compact

Every field is written as a tag — (field_number << 3) | wire_type — followed by a value, both varint-encoded where applicable. Signed types use zig-zag pre-encoding so small negatives stay small — without it, -1 would always take 10 bytes. Fields left at their default value are never transmitted; the receiver fills the default in. There are no field names on the wire, only numbers — which is why renaming a field is free and reusing its number is dangerous.

Deadlines travel as the grpc-timeout header (e.g. 1500m for 1500 ms). They are absolute from the caller's view: when a service receives an inbound RPC, it computes the remaining time and uses it as the default deadline for any outbound RPC made inside that handler. A downstream service can shorten a deadline; it cannot extend it. When time runs out, both sides see DEADLINE_EXCEEDED and in-flight work tied to that call is cancelled.

Metadata is just HTTP/2 headers in two buckets: initial (sent with the first HEADERS frame) and trailing (sent with the trailers). Binary values need a -bin key suffix and travel base64-encoded. Auth tokens, trace context (traceparent), and tenant IDs are the usual passengers.

Interceptors are typed middleware: given the inbound call and a next continuation, do work before, call next, do work after. Unary and streaming interceptors are separate types in most implementations, because the streaming form has to observe each message individually.

Status travels as a grpc-status trailer, one of 17 canonical codes:

0 OK · 1 CANCELLED · 2 UNKNOWN · 3 INVALID_ARGUMENT · 4 DEADLINE_EXCEEDED · 5 NOT_FOUND · 6 ALREADY_EXISTS · 7 PERMISSION_DENIED · 8 RESOURCE_EXHAUSTED · 9 FAILED_PRECONDITION · 10 ABORTED · 11 OUT_OF_RANGE · 12 UNIMPLEMENTED · 13 INTERNAL · 14 UNAVAILABLE · 15 DATA_LOSS · 16 UNAUTHENTICATED

For richer detail, a server can pack a google.rpc.Status { code, message, repeated Any details } into grpc-status-details-bin — standard detail types include BadRequest, RetryInfo, QuotaFailure, PreconditionFailure, ErrorInfo, DebugInfo, Help, LocalizedMessage.

Server reflection is itself a gRPC service: a bidi-streaming method that lets a client ask "what services do you expose?" and fetch the descriptors over the wire. It's how grpcurl can call a server with no .proto file on disk.

Common failure modes

⚠

Single channel saturation

All streams share one TCP connection; hitting MAX_CONCURRENT_STREAMS (often 100) or saturating one L4 hop queues new RPCs. Fix: subchannels, multiple channels, client-side load balancing.

✕

Load balancer mis-routing

An L4 load balancer pins a TCP connection to one backend, so it sends 100% of a client's traffic to one pod. gRPC needs an L7-aware LB or client-side load balancing.

✕

Field number reuse

Deleting a field and reusing its number in a later schema silently corrupts old data. Mitigation: reserved 4; in the .proto.

⚠

Missing trailer handling at a proxy

Older proxies or middleboxes that don't forward HTTP/2 trailers make every call look hung, or return UNKNOWN.

✕

No deadline set

A client with no deadline plus a slow server pins server resources indefinitely — threads or goroutines pile up.

⚠

UNAVAILABLE on cold start

TLS handshake plus name resolution race with the first RPC. Mitigation: explicit channel warmup, or retry with backoff.

⚠

Browser unreachability

Forgetting that browsers can't speak native gRPC, then discovering it at integration time.

Why it exists

The problem gRPC solves: typed, low-overhead, cross-language service calls at scale. Every hop in a microservice graph pays for serialization, transport, and contract drift. JSON over HTTP/1.1 makes all three worse — text parsing costs CPU, HTTP/1.1 forces one connection per request or head-of-line-blocked pipelining, and the contract lives in tribal knowledge or an OpenAPI file that quietly drifts from the server. gRPC folds contract, transport, and code generation into one pipeline.

Why it looks the way it does

  • HTTP/2, not raw TCP. The open internet already lets HTTP/2 through firewalls and proxies for the web — riding on top gets free transit. A custom TCP protocol gets blocked almost everywhere.
  • Protobuf, not JSON or MessagePack. Protobuf's wire format is meaningless without the schema, which forces teams to keep the schema honest. JSON's self-describing nature is exactly what lets contracts rot. MessagePack is compact but has no schema either.
  • Field numbers, not field names. Names cost bytes on every field of every message, and renaming is a routine refactor. Numbers decouple wire identity from source identity — the single most important property for a service that has to change over years.
  • Status in trailers, not the response code. A streaming server can discover an error halfway through the stream, after the 200 OK headers are already sent. Trailers let the final outcome arrive after the body — something HTTP/1.1 could not do cleanly.

Why it matters now

As of 2026, gRPC is mature rather than novel. It's the default internal protocol for Kubernetes-native infrastructure (CRI, CSI, CNI, xDS, OpenTelemetry collectors), most cloud-provider control planes, and AI/ML serving (TensorFlow Serving, Triton, Ray). The interesting movement is at the edges: Connect-RPC offers a wire-compatible alternative with better browser ergonomics; gRPC over QUIC / HTTP/3 is being prototyped to address TCP head-of-line blocking; buf has largely replaced ad-hoc protoc workflows for schema governance.
