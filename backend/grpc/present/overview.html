Overview

◔ ~3 min read ✎ intuition-first

Two services need to talk over a network. REST bolts a text format onto HTTP and hopes both sides agree on the shape of the JSON. gRPC picks the shape first, in a contract file, and generates the code that speaks it.

ⓘ

In 30 seconds

gRPC is Google's open-source framework for service-to-service calls. You write one .proto file describing methods and messages, run a compiler, and get typed client and server code in your language — 11+ languages are supported. Calls travel over HTTP/2 as binary Protobuf, smaller and faster to parse than JSON over HTTP/1.1, with streaming built in.

The mental model

REST is like sending postcards. Each request is its own note: a verb (GET, POST), an address (/users/42), and human-readable JSON inside. Every postcard re-states the destination and re-opens a fresh envelope.

gRPC is more like installing a direct phone line between two services. Both sides agree up front on exactly which functions exist and what their arguments look like — that agreement is the .proto contract a schema file that defines a service's methods and message shapes:

service UserService {
  rpc GetUser (GetUserRequest) returns (User);
  rpc WatchUserEvents (UserId) returns (stream UserEvent);
}

From the caller's side, client.GetUser(req) looks like an ordinary function call. The generated stub client-side code that makes a remote call look like a local one does the real work underneath: turning the arguments into binary, sending them down a shared connection, and turning the answer back into a typed object.

Because HTTP/2 lets one connection carry many streams at the same time, that same phone line can also carry a server pushing updates, a client pushing updates, or both at once — no WebSocket handshake, no long-polling. Two ideas carry most of the design: the schema is the source of truth (no more guessing what fields an endpoint returns), and the wire format is binary and streamable (no more parsing megabytes of JSON to read three fields).

What it is not

⚠

Common mix-ups

  • Not REST. REST is resource-oriented over HTTP/1.1 with human-readable JSON; gRPC is method-oriented over HTTP/2 with binary Protobuf.
  • Not GraphQL. GraphQL lets clients shape their own queries; gRPC locks the shape to the .proto contract.
  • Not a message queue. gRPC is synchronous request/response, plus streaming; Kafka or RabbitMQ handle asynchronous, durable, fan-out messaging.
  • Not browser-native. Browsers can't speak raw gRPC — you need gRPC-Web and a proxy in front.

When to reach for it — and when not to

✓ Reach for it when

  • Internal service-to-service calls, where you control both ends.
  • A polyglot backend — Go here, C# there, Python somewhere else — needs one shared contract.
  • Latency or payload size is a real cost: JSON parsing and HTTP/1.1 overhead show up in the numbers.
  • Real-time features need streaming: live telemetry, chat, progress updates, server push.
  • Mobile clients, where payload size and battery matter.

✕ Skip it when

  • Public APIs for third-party developers — REST and OpenAPI are still the common language.
  • Browser apps with no proxy layer in front.
  • Simple CRUD you'd rather poke with curl.
  • The team has no discipline yet for generated code, breaking-change review, and schema versioning.

Key vocabulary

RPC
Remote Procedure Call — calling a function that actually runs on another machine.
Protocol Buffers (Protobuf)
Google's compact binary serialization format and schema language.
.proto file
The contract: defines services, methods, and message types.
Stub
Generated client code that makes remote calls look local.
HTTP/2
The transport; multiplexes many streams over a single connection.
Unary RPC
One request, one response — the default shape.
Streaming RPC
Client-stream, server-stream, or bidirectional.
Channel
A long-lived connection a client reuses to issue many calls.
Deadline
A per-call timeout that propagates across services.
gRPC-Web
A variant that lets browsers talk to gRPC through a proxy.
