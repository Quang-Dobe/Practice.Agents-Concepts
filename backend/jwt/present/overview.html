Overview

◔ ~4 min read ✎ intuition-first

A JWT is a self-contained authentication token. The server signs a tiny JSON document and hands it to the client, which sends it back on every later request — usually in an Authorization: Bearer <token> header.

ⓘ

In 30 seconds

Because the token is signed, the server can trust its contents just by checking the signature — no database lookup, no in-memory session table. That's what makes a JWT stateless the server keeps no record of the token; everything needed to trust it travels inside the token itself, and it's why JWT became the default for stateless APIs, microservices, and single sign-on.

The mental model

Think of a JWT as a tamper-evident wristband at a music festival. At the gate, security checks your ID once and snaps a wristband on you with your access tier printed on it. For the rest of the night, no booth re-checks your ID — they just glance at the wristband. A holographic seal makes it impossible to fake without the festival's special machine; scratch out "general admission" and write "VIP" and the seal breaks instantly. The festival keeps no list of who got a wristband — the wristband itself carries the proof.

The wristband is a string with three parts separated by dots:

  • Header — says which signing algorithm was used, e.g. {"alg":"HS256","typ":"JWT"}.
  • Payload — the claims key/value facts about the subject, e.g. who the user is or when the token expires: who the user is, when the token expires, what they're allowed to do, e.g. {"sub":"123","name":"Alice","exp":1735689600}.
  • Signature — the cryptographic seal, computed over the first two parts plus a secret (or private key) only the server knows.

Verifying a JWT means recomputing the signature and checking it matches. If it does, the payload is trustworthy; if anyone flipped a single character in it, the signature breaks. Crucially, the payload is encoded, not encrypted — anyone can paste a JWT into a site like jwt.io and read it. The signature stops tampering, not snooping.

What it is not

⚠

Common mix-ups

  • Not encryption. The payload is readable by anyone who has the token. Use JWE (a separate spec) if you need confidentiality.
  • Not a session. A session lives in the server's memory or database; a JWT lives in the client's storage. That difference is the whole point.
  • Not an OAuth replacement. OAuth 2.0 is the protocol for issuing tokens. JWT is just one format a token can take.
  • Not a long-term credential. It's a short-lived proof, not a password.

When to reach for it — and when not to

✓ Reach for it when

  • You run stateless REST or gRPC APIs that should scale horizontally without sticky sessions.
  • You need service-to-service auth inside a microservice mesh.
  • You run single sign-on flows (OpenID Connect — the ID token is a JWT).
  • You issue short-lived access tokens from an OAuth 2.0 authorization server.

✕ Skip it when

  • It's a classic monolithic web app where a server-side session cookie is simpler and easier to revoke.
  • You need to invalidate a token immediately on logout — JWTs stay valid until they expire unless you build a denylist, which kills the "stateless" benefit.
  • You're tempted to store anything sensitive in the payload — passwords, PII, secrets. It's readable.

Key vocabulary

Claim
A key/value pair in the payload (sub, exp, iat, aud, iss, plus custom ones).
Signature
The cryptographic proof of integrity.
HS256
Symmetric signing with a shared secret (HMAC-SHA256).
RS256 / ES256
Asymmetric signing — the server signs with a private key, anyone verifies with the public key.
Bearer token
"Whoever holds it, gets in" — how JWTs are sent in the Authorization header.
exp claim
Expiration timestamp — the single most important field in the payload.
alg: none
A footgun: the spec allows an unsigned JWT. A naive verifier that accepts it is trivially exploitable. Always pin the allowed algorithm.
