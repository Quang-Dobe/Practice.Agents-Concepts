Detail — the deep dive

◑ ~10 min read ✎ What · Where · When · How · Why

What it is

A JWT is a compact, URL-safe set of claims — a JSON object — that has been cryptographically protected, almost always by a JSON Web Signature (JWS). The rules live across four specs, usually called JOSE JavaScript Object Signing and Encryption — the family of specs a JWT is built from: RFC 7519 (the token format itself), RFC 7515 (the signing layer, JWS), RFC 7518 (the algorithm registry, JWA), and RFC 7517 (the key format, JWK). In practice "JWT" almost always means a JWS in Compact Serialization — three base64url segments separated by dots.

  • Core idea. Sign a small JSON claims set so any verifier can trust it with one cryptographic check, no callback to the issuer.
  • Building blocks. A JOSE header, a claims payload, and a signature — see below.
  • Family. One format inside JOSE, which competes with PASETO (no algorithm choice), Macaroons (caveat-based), and classic opaque tokens backed by a server-side store.
JOSE header
JSON describing how the token is protected. Required: alg. Common optional: typ ("JWT"), kid (key id), jku (JWKS URL), cty (content type, for nested JWTs).
Claims set (payload)
Three buckets: registered (IANA three-letter names — iss, sub, aud, exp, nbf, iat, jti), public (registered in IANA's claims registry, or a collision-resistant URI), and private (anything else two parties agree on, e.g. role, tenant_id — no collision guarantee).
Signature
Bytes from SIGN(alg, key, header_b64 + "." + payload_b64). Base64url is base64 with +→-, /→_, no padding.
JWE (rare)
Encrypts the payload with key-wrapping + AEAD — five segments instead of three. Needed only when confidentiality, not just integrity, matters.

Inside OAuth 2.0, JWT is one possible format for access tokens — RFC 9068 formalizes it as a profile — and it is the mandatory format for OpenID Connect ID tokens.

Where it lives

JWT sits at the application / auth layer, carried over HTTP, gRPC metadata, or message-queue headers. An identity provider or auth service issues it; every resource server, gateway, or sidecar that needs to authorize a request verifies it. The token itself is stateless data — it lives wherever the client keeps it.

OAuth 2.0 / OIDC

Access tokens from Auth0, Okta, Keycloak, Cognito, Entra ID, Google Identity; the OIDC id_token is always a JWT.

Service-to-service

Sidecar meshes (Istio, Linkerd) and gateways (Kong, Envoy) validate JWTs at the edge so downstream services trust pre-authenticated requests.

Workload identity

Kubernetes service-account tokens, GitHub Actions OIDC, AWS IRSA, HashiCorp Vault JWT auth — federation without long-lived keys.

Magic links

Short-lived, single-use JWTs in URLs for password-reset and login flows — with real caveats, see Failure modes.

Common tooling: Microsoft.IdentityModel.Tokens / System.IdentityModel.Tokens.Jwt (.NET), jjwt / Nimbus JOSE+JWT (Java), jsonwebtoken / jose (Node.js), PyJWT / authlib (Python), golang-jwt/jwt (Go) — plus jwt.io for quick decoding.

When to use it

✓ Reach for it when

  • You run a horizontally scaled, stateless API and want to skip a shared session store.
  • You operate a federated identity boundary — issuer and verifier are different services, maybe different organizations.
  • Tokens are short-lived (minutes, not days), so no instant revocation is acceptable.
  • You need a workload-identity primitive (Kubernetes, CI/CD OIDC).
  • Downstream services need to read claims (roles, tenant, scopes) without calling back to the IdP.

✕ Skip it when

  • You need immediate revocation on logout (banking, admin consoles, compliance-driven systems).
  • The token must live for days or weeks — that's an unrevocable bearer credential.
  • Your app is a classic monolith with one web tier — cookies + a session table are less code and easier to debug.
  • You want confidential data in the token. JWS is signed, not encrypted.

A little history

JWT was first drafted in late 2010 and standardized as RFC 7519 in May 2015, alongside the rest of JOSE. It grew out of two pressures: SAML assertions were XML-heavy and painful for browsers and mobile, and OAuth 2.0 (RFC 6749, 2012) deliberately left token format unspecified. JWT filled that gap with a compact, JSON-native, URL-safe format that fits naturally into Authorization: Bearer headers.

How it works

A signed JWT round trip, end to end:

  1. Authenticate. The client authenticates to the authorization server (password, refresh token, authorization code, client credentials, …).
  2. Build claims. E.g. {"iss":"https://auth.example.com","sub":"user_123","aud":"api.example.com","exp":1735689600,"iat":1735686000,"jti":"8f3...","scope":"read:orders"}.
  3. Build header. E.g. {"alg":"RS256","typ":"JWT","kid":"2026-01-key"}. The kid lets verifiers pick the right key during rotation.
  4. Encode and sign. Base64url-encode header and payload, join with a dot, sign with the private (or shared) key.
  5. Return the token. The client stores it and sends it as Authorization: Bearer <jwt> on every call.
  6. Validate, in order. Split on dots (reject if not 3 segments) → enforce an algorithm allow-list locally (never trust the header's alg alone) → look up the key by kid from a cached JWKS → verify the signature → check exp > now (30–60s clock-skew leeway) → check nbf if present → check iss exact match → check aud contains this server's identifier → apply application-level authorization on scope/roles.
  7. Any check fails → 401. Skipping a single one of these is a CVE waiting to happen.
  8. Refresh on expiry. The client trades a long-lived, opaque, server-side, revocable refresh token for a new access JWT — the standard fix for JWT's weak revocation story.

Key trade-offs

ChoiceGainGive up
HS256 (HMAC-SHA-256, symmetric)Fast, simple, one secretEvery verifier holds the signing secret; one compromise forges any token. Only viable when issuer == verifier.
RS256 / ES256 (asymmetric)Verifiers only need the public key; safe to publish via JWKS; clean issuer/verifier separationSlower signing, larger signatures, more key management. ES256 is smaller and faster than RS256 at equivalent security.
Stateless JWTNo session store, no shared DB, horizontal scale trivialRevocation is hard; token bloat in every request; payload visible to client.
Short exp (5–15 min) + refresh tokenLimits the blast radius of a stolen tokenExtra round trip to refresh; refresh token itself becomes the long-lived secret.
Putting roles/claims in the tokenDownstream services skip an IdP call per requestStale data — role changes don't propagate until the token expires.

Common failure modes

✕

alg: none accepted

The spec lists "none" as a valid algorithm; a naive verifier that honors the header skips signature verification entirely. Cause: trusting header.alg instead of an allow-list.

✕

HS256/RS256 algorithm confusion

Server is configured for RS256 but its verifier picks the algorithm from the header. Attacker sends alg: HS256 and signs the forged token using the server's public key as the HMAC secret — the server verifies it as valid HMAC. Full auth bypass. Cause: dynamic algorithm selection from the header.

⚠

Weak HMAC secret

HS256 with a short or human-chosen secret is brute-forceable offline once you have any valid token. Cause: secret under 256 bits of entropy.

✕

Missing aud check

A token issued for service A is replayed against service B that shares the issuer. Cause: verifier skipped the audience claim.

⚠

Missing iss check

A token from a rogue issuer, signed with a key the verifier happens to trust, is accepted. Cause: JWKS configured for multiple issuers without binding.

⚠

Sensitive data in the payload

SSNs, emails, internal IDs leak because someone assumed "signed" meant "encrypted." Cause: confusing JWS with JWE.

⚠

JWT in the URL

Magic links and OAuth implicit-flow fragments end up in browser history, Referer headers, and server access logs. Cause: convenience over hygiene.

⚠

Oversized tokens

Packing every permission as a claim grows tokens to 4–8 KB, blowing HTTP header limits and inviting cache poisoning. Cause: using JWT as a permissions database.

⚠

Clock skew and stale kid

A verifier with a fast clock rejects freshly issued tokens (no leeway configured). During key rotation, a verifier with no kid or no JWKS refresh-on-miss tries the old key against a new token.

Why it exists

JWT exists because distributed systems need a way for one service to trust an assertion made by another service without calling back to the source on every request. The pre-JWT options were a shared session store (couples services, becomes the bottleneck), SAML (XML, heavyweight, browser-hostile), or opaque tokens with introspection (a network round trip per request). A signed, self-describing token collapses identity propagation to a local cryptographic check — that is the entire value proposition.

Why it looks the way it does

Three design choices are worth understanding. First, why three base64url segments instead of a binary format like CBOR/COSE? JOSE optimized for the HTTP/browser world circa 2013 — URL-safe, header-safe, copy-pasteable, JSON-debuggable. CBOR Web Tokens (CWT, RFC 8392) exist for constrained environments like IoT with the same idea in binary form.

Second — and this is the one worth drawing — why is asymmetric signing a first-class option?

The issuer publishes a JWKS JSON Web Key Set — the issuer's public keys, published at a well-known URL so any verifier can fetch them at /.well-known/jwks.json; anyone can verify without ever holding a secret. This is what makes OIDC and workload identity federation work.

Third, why short expiry plus refresh tokens instead of a real revocation list? Because a revocation list re-introduces the stateful lookup JWT was designed to avoid. The compromise: tokens are short enough that the revocation window is acceptable, and the refresh token — which is stateful and revocable — carries the long-lived trust. It's an explicit, named trade-off, not an accident.

Why it matters now

As of 2026, JWT is the dominant access-token format across OAuth 2.0 and OIDC deployments, and the substrate for workload identity federation (GitHub Actions OIDC, AWS IRSA, GCP Workload Identity, SPIFFE). The interesting movement is around JWT, not away from it: sender-constrained tokens (DPoP, RFC 9449) and mTLS-bound tokens (RFC 8705) are tightening the bearer-token model. PASETO and Biscuit exist as opinionated alternatives but haven't displaced JWT in the enterprise stack.
