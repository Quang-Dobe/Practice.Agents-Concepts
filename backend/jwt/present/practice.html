Practice — how it plays out for real

● ~10 min read ✎ best practices · anti-patterns · checklist

Where you'll meet it

If you've ever added [Authorize] to a controller and configured AddJwtBearer, you've been a JWT verifier whether you realized it or not. JWT is almost never the interesting part of a feature — it's the load-bearing piece underneath that quietly breaks audits, scaling, and on-call shifts when someone gets a detail wrong.

SaaS backend

The auth service hands out a JWT after login; every downstream API, gateway, and sidecar verifies it locally instead of calling the auth DB per request.

Microservice mesh

An API gateway (Kong, Envoy, AWS API Gateway) validates the token at the edge, then forwards it — or a re-signed internal version — so each service reads sub, tenant_id, and scope without re-authenticating.

Federated / workload identity

OIDC logins, GitHub Actions deploying to AWS, Kubernetes service accounts. JWT is the interchange format: the issuer publishes a public JWKS, the verifier caches it, and the token crosses an org boundary on nothing but a signature.

Best practices

1

Use short-lived access tokens + opaque refresh tokens

Do

Issue access JWTs with exp of 5–15 minutes, paired with a long-lived (days–weeks) refresh token that is opaque, random, and stored server-side (user_id, family_id, expires_at, revoked_at). Rotate the refresh token on every use; if a used one reappears, revoke the whole family.

Why

JWT has no native revocation. A short access-token life means a stolen one is useful for minutes, not weeks. The refresh token can be revoked because it lives in your database.

Avoid

Long-lived (hours or days) access JWTs with no refresh flow — that's a bearer credential you cannot recall.

2

Pick the algorithm based on issuer/verifier trust

Do

Use HS256 only when the same service signs and verifies (single binary, shared secret, no third party). Use RS256 or ES256 whenever issuer and verifier are different services or organizations. Prefer ES256 for new systems — signatures around 64 bytes vs. ~256 for RS256, faster to verify, equivalent security at a smaller key size.

Why

With HS256, every verifier holds the signing secret. One compromised verifier forges tokens for the whole system. Asymmetric signing lets verifiers hold only the public key.

Avoid

HS256 with a secret shared across teams or environments — it will leak via a config file, a Docker image, or a Slack message.

3

Pin the alg to an allow-list on verify

Do

Hard-code the accepted algorithms in your verifier config and never let the token's own header decide:

jwt.verify(token, key, {
  algorithms: ['RS256'],   // allow-list, not "whatever the header says"
  issuer: 'https://auth.example.com',
  audience: 'api.example.com',
});
Why

The alg: none bypass and the classic RS256→HS256 confusion attack both depend on the verifier trusting the header. An allow-list shuts both down.

Avoid

Calling verify(token, key) with no algorithms option — some libraries still default to "any."

4

Always verify signature, exp, iss, and aud — in that order

Do

Run the full check on every request, even between internal services. Signature first (reject forgeries before parsing claims), then exp with 30–60s leeway, then iss exact-match, then aud contains your service's identifier.

Why

Skipping aud lets a token issued for service A be replayed against service B. Skipping iss lets a rogue IdP whose key you happen to trust mint valid tokens for you. Both are real CVE patterns.

Avoid

"It came through the gateway, so it's fine." Defense in depth means every hop verifies.

5

Fetch verification keys from a JWKS endpoint with kid-aware caching

Do

Resolve keys via the issuer's /.well-known/jwks.json (or the OIDC discovery document). Cache the JWKS in memory, refresh only on an unknown kid (rate-limited, e.g. minimum 5 minutes between refetches). Set kid on every token you sign.

Why

Key rotation is when systems break. JWKS + kid is how rotation happens with zero downtime — the issuer publishes the new key, signs with it, verifiers pick it up on the next miss.

Avoid

Hard-coding the public key in config (someone forgets to rotate it), or refetching JWKS on every request (you'll take down your own IdP).

6

Pick client-side storage with eyes open about XSS vs. CSRF

Do

For browser apps, default to httpOnly; Secure; SameSite=Lax (or Strict) cookies plus CSRF protection on state-changing endpoints. For SPAs needing cross-origin calls, an in-memory access token + httpOnly refresh-token cookie is the modern compromise.

Why

localStorage is readable by any JS on the page — one XSS and every token is exfiltrated. Cookies are immune to that but reintroduce CSRF. There's no option without a trade-off; pick consciously.

Avoid

Putting the JWT in localStorage "because it's easier," and never putting a JWT in a URL query string — it ends up in history, Referer headers, and proxy logs.

7

Keep payloads small and free of PII

Do

Put sub, iss, aud, exp, iat, jti, and a handful of authorization claims (scope, roles, tenant_id). Anything bigger — full profile, permission matrix — belongs behind a lookup the resource server does once and caches.

Why

Every request carries the token. Past roughly 4 KB, tokens start hitting default header limits in Nginx, ALB, and CloudFront (commonly an 8 KB total request-header budget). PII in the payload means a token leak is also a data-protection incident.

Avoid

Stuffing every permission into the token "so downstream doesn't have to look anything up." That's how you discover the 8 KB header limit at 2 a.m.

8

Design revocation before you need it

Do

Decide upfront: short exp is your primary revocation strategy. For logout / disabled accounts / suspected theft, add a deny-list a store of revoked token IDs (jti) that verifiers check after signature verification keyed on jti in Redis, TTL'd to the token's remaining lifetime. Rotating the signing key invalidates every token in flight, for "something bad happened."

Why

"We'll add revocation later" becomes "we have no way to log a user out" during an incident. Decide which scenarios you actually need to cover, and which the short exp already handles.

Avoid

A deny-list every request hits unconditionally — you've reinvented sessions, more slowly, with worse semantics.

9

Separate secrets per environment, rotate signing keys on a schedule

Do

Use different signing keys per environment (dev, staging, prod). Rotate on a schedule (quarterly is common) and immediately on suspected compromise. Keep the previous key in the JWKS during the overlap window so in-flight tokens still verify.

Why

A leaked staging key that also signs prod tokens is an instant production breach. Scheduled rotation forces the rotation machinery to actually work.

Avoid

One .env value reused across environments — or one key signing tokens since 2019.

10

Know the standardized profiles you're actually implementing

Do

Issuing OAuth 2.0 access tokens as JWTs? Follow RFC 9068 (typ: at+jwt, required claims, audience binding). Doing OIDC? Follow the id_token rules in the OIDC Core spec — it's for the client, not for authorizing API calls. If token theft is in your threat model, look at DPoP Demonstrating Proof of Possession, RFC 9449 — binds a token to a private key the client holds, so a stolen token alone isn't enough (RFC 9449) or mTLS-bound tokens (RFC 8705).

Why

Reinventing these profiles guarantees subtle interop bugs with Auth0, Okta, Entra ID, and every SDK that expects them.

Avoid

Using an OIDC id_token as an API access token — a common confusion that breaks audience semantics.

Anti-patterns to recognize

✕

"Just decode it to read the user id"

Code calls a decode function (no signature check) to pull sub out and never adds the verify step later. Any attacker can mint a token with any sub. Always verify, then read claims — never the reverse.

✕

Trusting the header's alg

The verifier picks the algorithm dynamically from token.header.alg. Enables alg: none and RS256→HS256 confusion. Fix: an explicit allow-list in the verify call.

✕

Storing passwords or full PII in claims

Assuming "signed" means "encrypted." Anyone who captures the token reads it on jwt.io. Fix: claims hold IDs and authorization data only; lookups happen server-side.

✕

Infinite-lived tokens

exp set to a year, or missing entirely, "because refresh is annoying." A single stolen token = a year of access. Fix: short exp + refresh tokens, always.

✕

Same signing key across environments

A dev laptop's .env leaks the key that also signs production tokens. Fix: per-environment keys, rotated on a schedule.

✕

JWTs in URLs

Magic links, implicit-flow fragments, ?token=... query parameters. They leak via browser history, Referer headers, CDN logs, and screenshots. Fix: POST bodies or the Authorization header; for magic links, a short-lived single-use code exchanged over POST.

✕

No aud enforcement in a multi-API system

The same IdP issues tokens for multiple APIs; one API skips aud and accepts tokens minted for any of them. Fix: every resource server pins its own audience identifier and rejects mismatches.

✕

Refresh tokens that never rotate

A refresh token is reused indefinitely; theft is undetectable. Fix: rotate on every refresh, revoke the family if an old one reappears (RFC 9700, the OAuth 2.0 BCP).

Real-world usage patterns

B2B SaaS with tenant isolation

Auth service issues RS256 JWTs with sub, tenant_id, roles, scope, 15-minute exp. Every API validates against the auth service's JWKS, enforces aud=api.example.com, and scopes every query by tenant_id. Lesson: role changes don't propagate until the access token expires — "removing a user takes up to 15 minutes" needs to be a known product fact, or you need a deny-list path.

Microservice mesh behind a gateway

Envoy validates the external customer JWT at the edge, then mints a short-lived internal JWT signed by the mesh CA for downstream services, which trust only that CA's JWKS. Lesson: re-minting at the edge lets internal-only claims (trace context, downstream-only roles) travel without ever reaching the customer. The cost is one extra signing operation per request — measure it.

CI/CD workload identity

GitHub publishes a JWKS at a well-known URL; AWS STS verifies the OIDC token's signature, iss, aud, and a sub pattern like repo:org/repo:ref:refs/heads/main before assuming a role — no long-lived AWS keys. Lesson: the whole model rests on the sub trust-policy condition; writing a wildcard match instead of an exact one silently grants any repo in the org access to your prod role.

Mobile app with biometric re-auth

The access JWT lives in memory only. The refresh token sits in the OS keychain, protected by biometrics; on app foreground, it's exchanged for a fresh access JWT. Lesson: keychain-backed refresh tokens are the closest thing to "device-bound" without DPoP — they survive app reinstalls badly, so clearing the keychain entry is the actual logout.

Operational checklist

✓

Before you call it done

  • Monitoring: are verification-failure metrics broken down by reason (expired, bad_signature, wrong_aud, unknown_kid)? A spike in bad_signature is either a bad key rotation or an attack.
  • Failure handling: if the JWKS endpoint is down, is the cache stale-while-revalidate or fail-closed — and has that been tested in a chaos drill?
  • Algorithm pinning: does every verify call pass an explicit algorithms allow-list? Grep the codebase for a decode-without-verify pattern.
  • Audience and issuer pinning: does every resource server have its own aud identifier and a configured (not inferred) issuer URL?
  • Token size: is the p99 access-token size tracked as a metric and kept under 4 KB?
  • Refresh-token storage: are refresh tokens hashed at rest, rotated on use, and family-revoked on reuse detection?
  • Key management: do signing keys differ per environment, and has the rotation runbook been run at least once outside an emergency?
  • Logging hygiene: no raw Authorization headers in logs — is Bearer redaction covered by a test?
  • Onboarding: can a new engineer find the issuer URL, JWKS URL, expected aud, and token TTL in one place?

How it evolves in a codebase

  1. HS256 and a shared secret. Every tutorial starts here. It works until a second service needs to verify tokens and someone copies the secret into a second .env file.
  2. Migration to RS256/ES256 + JWKS. Usually triggered by a leaked-config-file incident, or by adopting a hosted IdP (Auth0, Cognito, Entra ID) that issues asymmetric tokens by default.
  3. The revocation inflection point. Early systems ship without it — short exp is "good enough" until support needs to instantly log out a compromised account. Teams either add a Redis deny-list keyed on jti, or accept and document the window. Shortening long-lived tokens later is the painful migration: every client that mishandles refresh breaks at once.
  4. Maturity. Hosted or hardened IdP, ES256 signing, JWKS with scheduled kid rotation, 5–15 minute access tokens, rotating refresh tokens with family revocation, and DPoP or mTLS-bound tokens for high-value APIs. The remaining work is about which claims go in the token and who's allowed to add new ones — claim bloat is the long-term threat, not crypto.

Further reading

  • RFC 9700 — Best Current Practice for OAuth 2.0 Security — the IETF's consolidated advice; the refresh-token rotation and sender-constraint sections are essential.
  • RFC 9068 — JWT Profile for OAuth 2.0 Access Tokens — turns "JWTs as access tokens" from convention into requirement; states exactly which claims must appear.
  • RFC 9449 — DPoP (Demonstrating Proof of Possession) — the modern answer to bearer-token theft; worth reading even if you don't implement it yet.
  • Auth0 — Refresh Token Rotation — a clean, concrete writeup of the rotation-with-family-revocation pattern.
  • OWASP — JSON Web Token Cheat Sheet — the attack-surface counterpart to the RFCs; covers the alg-confusion and none attacks at implementation level.
  • PortSwigger Web Security Academy — JWT Attacks — interactive labs for every classic JWT vulnerability; do them once and you will never write a vulnerable verifier.
