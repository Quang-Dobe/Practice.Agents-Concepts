Practice — how it plays out for real

● ~10 min read ✎ best practices · anti-patterns · checklist

Where you'll meet it

The breaker is invisible until the day one dependency gets slow — then it's the single component that decides whether your checkout page degrades gracefully or stops responding for thirty minutes. You'll meet it in four settings:

SaaS backend

Between your HttpClient and every third-party you can't trust: payment gateway, SMS provider, identity provider, LLM endpoint.

Microservice mesh

Twice — as an in-process library on the client side, and as a config knob on the mesh (Envoy outlier detection, Istio DestinationRule) for the calls you forgot to wrap.

Data tier

Around databases and caches that hang: Postgres failover, a Redis cluster repartitioning, an Elasticsearch node GC-pausing.

LLM features

Inference endpoints have wide tail latency, partial outages, and rate-limit storms. The breaker stops one bad provider from holding every web worker hostage.

Best practices

1

One breaker per downstream dependency, not per call site

Do

Keep one breaker instance per logical dependency (payments-api, geocoder-api) and inject it everywhere. In Polly v8, that's one named ResiliencePipeline per upstream, registered with IHttpClientFactory.

Why

Health is a property of the callee, not the call site. Per-call-site breakers fragment state — ten endpoints learn Payments is down independently, ten times.

Avoid

Constructing a new CircuitBreaker(...) inside a handler. State resets every request and the breaker never trips.

2

Pick granularity deliberately: per-service in-process, per-host at the mesh

Do

Use a per-service breaker in application code, and let Envoy outlier detection the mesh feature that ejects an individual sick replica from the pool eject individual sick replicas at the sidecar.

Why

A per-service breaker treats one bad replica as a global outage; a per-host breaker treats a whole-service outage as ten independent ejections that flap. Each covers what the other can't.

Avoid

Implementing per-host breaking in application code. You'll reinvent a load balancer badly.

3

Choose error-rate thresholds, not consecutive counts, above toy scale

Do

Use a sliding-window failure-ratio threshold — e.g. 50% over the last 100 calls or 30 seconds — with a non-trivial minimum throughput (20–100 depending on traffic).

Why

Consecutive-failure counts trip on bursty traffic and miss slow degradations where 40% of calls fail forever. Ratios with a sample floor are stable under both spikes and lulls.

Avoid

"Trip after 5 failures in a row." That's the Hystrix-era default, and it's wrong for almost every production service.

4

Tune thresholds to your traffic shape, then leave them alone

Do

Start at 50% failure ratio, minimum throughput set so the breaker sees at least one full sample per minute at normal load, and a break duration of 15–60 seconds. Watch state-transition metrics for a week, then adjust once.

Why

Too tight (10% failure, throughput 5) flaps on routine 502s and the team learns to ignore alerts. Too loose (90% failure, throughput 1000) means the breaker never trips before the thread pool is gone.

Avoid

Copying defaults from a blog post. Polly's (10% failure, 100 throughput, 5s break) and resilience4j's (50%, 100, 60s) are conservative starting points, not production values.

5

Always include slow-call detection

Do

Treat calls over a latency threshold as failures (slowCallDurationThreshold in resilience4j, a custom predicate in Polly). Set it at roughly your p99 + headroom, not your timeout.

Why

The failure that kills you isn't 500s — it's calls that succeed in 28 seconds when they normally take 80ms. Pure error-rate breakers happily watch a dependency drag you under as long as it eventually returns 200.

Avoid

Relying on the request timeout alone to convert slowness into a failure. By the time the timeout fires, the thread is already gone.

6

Order the pipeline: timeout (inner) → retry → circuit breaker (outer)

Do

Wrap so the timeout fires per attempt, retries happen inside the breaker's view of "one call" (e.g. MaxRetryAttempts = 2 with exponential backoff), and the breaker observes the final outcome of that attempt-bundle all retries of a single logical call, counted by the breaker as one outcome.

Why

If retry is inside the breaker, one bad call is counted as N failures and it trips too fast. If the breaker is inside retry, retries keep hammering an open breaker.

Avoid

Wiring three independent decorators in arbitrary order and assuming it works. This is the single most common Polly/resilience4j misconfiguration.

7

Design the fallback before you ship the breaker

Do

Decide per breaker exactly what happens when it's open: stale cache, a default object, a degraded UI, or a 503 with Retry-After. Implement and test that path explicitly.

Why

A breaker without a fallback just converts a slow failure into a fast one. Sometimes that's correct — a faster 503 beats thread starvation — but the choice should be deliberate.

Avoid

A "fallback" that calls a second flaky service synchronously. You've doubled the failure surface.

8

Emit state transitions as first-class events; alert on duration-Open

Do

Wire OnOpened, OnHalfOpened, OnClosed into OpenTelemetry / Micrometer. Track state, trip count, half-open success rate, and short-circuit count. Alert when a breaker stays Open longer than N minutes.

Why

Open breakers hide upstream errors — your usual "5xx from dependency X" alert goes silent because you stopped calling X. The breaker becomes the only honest signal.

Avoid

Logging only. State transitions buried in app logs are unfindable during an incident.

9

Don't share one breaker across unrelated calls

Do

Separate breakers for /charge and /refund if they hit different upstream subsystems, even on the same vendor. Likewise for read vs. write paths on the same database.

Why

A read-only replica being down should not stop you from writing. One breaker conflates two health signals and trips on the union.

Avoid

A single "stripe" breaker covering every Stripe endpoint your app uses.

10

Make 4xx not count (mostly)

Do

Configure the classifier to count network errors, 5xx, gRPC UNAVAILABLE / DEADLINE_EXCEEDED, and slow calls. Exclude 4xx — except 429 in some setups, and never 408.

Why

A 404 or 401 means your call was wrong, not that the upstream is sick. Counting them trips the breaker during a bad deploy of your own service.

Avoid

The default "any exception trips" from toy implementations.

11

Accept per-pod state, or push to the mesh

Do

If you run N replicas, decide consciously whether N independent breaker states is acceptable (usually yes — they converge fast under shared traffic) or whether you need Envoy/Istio enforcement for a global view.

Why

Synchronising breaker state across pods through Redis is a classic anti-pattern: you've added a new single point of failure to protect against one.

Avoid

Building a "distributed circuit breaker" with shared storage. The pattern is intentionally local.

Anti-patterns to recognize

✕

Breaker around in-process code

Wrapping a local function call "for safety". There's no thread pool to protect and no recovery semantics — you've added latency and a state machine for nothing. Let the exception propagate.

✕

Retries inside the breaker

A 5× retry nested inside a 50% threshold breaker amplifies one failed call into five recorded failures and trips on a single bad request. Put the breaker outside the retry, or count attempt-bundles.

✕

Shared breaker across unrelated calls

One httpClient breaker covering payments, search, and analytics. Now a search outage stops payments. Split per dependency.

✕

Breaker without timeouts

The breaker only sees failures it can observe; a call that hangs forever never trips it. Always pair with a per-attempt timeout.

✕

Health-check-driven breaker

Driving breaker state from a separate /health poller. Health checks lie — only real call outcomes are truthful. Use traffic, not pings.

✕

Breaker as load balancer

Using state to "pick a healthier upstream". That's outlier detection's job at the mesh layer. A breaker decides whether to call, not where.

✕

Set-and-forget thresholds

Tuning once at launch and never revisiting. Traffic shape changes — what was a 50% sample at launch is now 5% of one second's traffic. Re-tune annually or when load changes by >2×.

✕

Fallback hiding a real bug

Returning cached prices from 2 weeks ago because the breaker has been Open for 2 weeks. The fallback worked; the alerting didn't. Alert on Open duration, not just upstream errors.

Real-world usage patterns

E-commerce checkout, flaky payments

Mid-size retailer, ~500 RPS peak. A per-vendor breaker wraps each processor (Stripe, Adyen, a regional bank). When one vendor's p99 jumps past 3s the breaker opens and checkout fails over to a secondary. Lesson: fast failure is what makes the fallback cheap enough to use inside the user's patience budget.

LLM feature, primary + fallback model

A SaaS app using GPT-class inference for summarisation. A breaker wraps the premium model; on Open, requests fall back to a smaller, faster model with a quality disclaimer. Slow-call detection dominates — 5xx is rare, but 45-second responses are common during provider incidents. Lesson: without slow-call detection, the breaker is decorative on LLM endpoints.

Mesh outlier detection, polyglot fleet

A platform team running Istio across Go, Python, and Node configures DestinationRule.outlierDetection once per namespace. Per-host ejection happens transparently; app code stays clean. Lesson: mesh enforcement is uniform but coarse — keep an in-process breaker for when "200 OK with {error: ...}" is a failure.

Database connection breaker on failover

A reporting service with a Postgres primary that occasionally fails over. A breaker around the connection pool fast-fails for 30 seconds after detecting connection refusals, letting the read-replica path take over instantly. Lesson: breakers belong around data tiers too — the same starvation dynamics apply to connection pools.

Operational checklist

✓

Before you call it done

  • Metrics: are state, trip count, short-circuit count, half-open success rate, and time-in-Open all exported to your dashboard?
  • Alerting: does an alert fire when any breaker stays Open longer than your SLO threshold (typically 5–15 minutes)?
  • Fallback tested: is the Open-state code path covered by a test that forces the breaker open?
  • Pipeline order: is it timeout → retry → breaker (innermost to outermost), and the same in every service?
  • Predicate sanity: does the classifier exclude 4xx (other than 429/408) and include slow calls?
  • Granularity audit: exactly one breaker per logical dependency — not per call site, not shared across vendors?
  • Per-attempt timeout: does every breaker have a sibling timeout so hanging calls never go unobserved?
  • Onboarding: can a new engineer find the config in under 2 minutes and explain what trips it?
  • Mesh vs library: is it documented which layer owns breaking for each dependency, so the two don't fight?

How it evolves in a codebase

  1. No breaker → first incident. A slow third-party API pins every worker thread. The fix is a copy-pasted breaker around that one call, usually with consecutive failures = 5 because that's what the README showed. It works for a quarter.
  2. Proliferation → consolidation. Every team adds its own breaker with different defaults and metrics. A platform team consolidates behind a shared library — Microsoft.Extensions.Http.Resilience in .NET shops, a resilience4j-spring-boot3 starter in Java shops — so every outbound HttpClient shares one pipeline. This is the painful migration: delete every bespoke breaker and debate thresholds team by team.
  3. Push concerns to the mesh. As the org adopts Istio or Linkerd, outlier detection covers the per-host layer and application breakers shrink to where they add unique value: bulkhead isolating resource pools so one bad dependency can't drain them all-style isolation, business-error classification, and typed fallbacks. Teams that reach this stage stop talking about circuit breakers and start talking about SLOs.
