Detail — the deep dive

◑ ~9 min read ✎ What · Where · When · How · Why

What it is

A circuit breaker is a stateful proxy around a fallible operation — almost always a remote call — driven by a state machine a fixed set of named states with deterministic moves between them with three states: Closed, Open, Half-Open.

  • Closed. It forwards calls and records outcomes against a windowed health metric.
  • Open. When that metric crosses a threshold it short-circuits — every call throws a sentinel exception (BrokenCircuitException in Polly, CallNotPermittedException in resilience4j) without touching the network.
  • Half-Open. After a cool-down it admits a bounded number of trial calls, then returns to Closed or back to Open based on their outcomes.

It belongs to the Stability Patterns family that Michael Nygard named in Release It! (2007). Think of it as the "fail fast" complement to retries and timeouts.

The core building blocks

State machine
Three named states with deterministic transitions. Some implementations add a fourth virtual Forced Open / Disabled state for manual operator override.
Outcome classifier
A predicate that decides whether a result is a failure: exceptions, HTTP 5xx, gRPC UNAVAILABLE, and crucially slow calls (latency over a threshold).
Health window
Aggregates recent outcomes. Three flavours: consecutive-count (Hystrix-era, brittle), count-based sliding window (resilience4j default, N = 100), and time-based sliding window (Polly v8's only model).
Threshold + minimum throughput
A failure ratio plus a floor on sample size, so the breaker doesn't trip on 1 failure out of 1 call.
Break duration
How long to stay Open before probing (the reset timeout).
Half-open permit pool
A bounded counter controlling how many trial calls may run at once.
Fallback
Optional alternate path — cached value, default, degraded response — returned on short-circuit.

In the wider family it sits alongside retry, timeout, bulkhead, rate limiter, hedging, and fallback. Retry assumes a transient failure and tries again now; the breaker assumes a sustained one and refuses to try. A bulkhead bounds the resources a dependency may consume; the breaker bounds the attempts. In Polly v8 and resilience4j these are composable strategies in one pipeline, not competing options.

Where it lives

A breaker sits at the client side of every outbound synchronous call, one instance per logical dependency (or, more aggressively, per upstream host). It can run at four distinct layers:

1 · In-process library

Polly (.NET), resilience4j (JVM), Opossum (Node), gobreaker (Go), pybreaker (Python). State is per-instance and per-process. Rich, application-typed signals; typed fallbacks.

2 · Sidecar proxy

Envoy enforces connection-pool and outlier detection transparently to the app; Linkerd's proxy similarly. L4/L7 wire signals only.

3 · Service mesh control plane

Istio's DestinationRule.trafficPolicy.outlierDetection and connectionPool configure Envoy across the mesh declaratively.

4 · API gateway / edge

Kong, NGINX, AWS API Gateway, and Azure APIM expose breaker-like upstream-health features.

The in-process and mesh variants are not equivalent. An in-process breaker reads specific exception types, business error codes, and payload size. A mesh breaker sees only HTTP status, TCP errors, and latency — but applies uniformly across languages.

When to use it

✓ Reach for it when

  • You make synchronous outbound calls whose failure can stall caller threads or connections.
  • A dependency degrades slowly rather than failing fast — slow-call detection is where breakers genuinely save you.
  • You have an acceptable fallback, or fast failure itself beats a long hang.
  • You operate at fan-in scale where one slow dependency can deplete a shared worker pool.

✕ Skip it when

  • The call is in-process — nothing to break.
  • The work is async and queue-based — the queue is the bulkhead.
  • It's an idempotent cheap read where retry-with-jitter alone is enough.
  • There's no acceptable fallback and the request must eventually succeed.
  • The system is small enough that a slow dependency cannot cascade.

A little history

Nygard named the pattern in 2007. Netflix open-sourced Hystrix in 2012 — the JVM default for half a decade — but it entered maintenance mode in 2018, and Netflix now points new projects at resilience4j. .NET's Polly followed the same arc; its v8 release (Nov 2023) rewrote the API around a unified ResiliencePipeline with first-class telemetry.

How it works

Walk a single request through a Polly-style pipeline (Retry → CircuitBreaker → Timeout → HttpClient):

  1. Pre-check. Read the current state — atomic and lock-free in both resilience4j and Polly.
  2. Open path. If Open and the break duration hasn't elapsed, throw the short-circuit exception immediately. No thread held, no socket allocated.
  3. Half-open path. If Open and the timer has elapsed, transition to Half-Open and reset a permit counter. The first N callers each take a permit and run as probes; excess concurrent callers are rejected as if Open.
  4. Closed path. Forward the call and start a stopwatch.
  5. Outcome capture. Classify the result: success, exception, or slow call a call whose latency exceeds slowCallDurationThreshold — counted as a failure even though it returned.
  6. Window update. Append the outcome to the sliding window the recent-outcomes buffer the failure ratio is computed from. The count-based window is a fixed ring buffer; the time-based window is a bucketed array (one bucket per second) so the ratio stays O(1) per call.
  7. Threshold evaluation. Only after minimum throughput the minimum number of recorded calls before the ratio is even checked is the failure ratio computed. If it crosses failureRateThreshold — or the slow-call ratio crosses its own threshold — transition to Open and stamp the open-at time.
  8. Half-open resolution. Once the permitted probes complete, compute their failure ratio. Below threshold → Closed and reset the window. Above → Open and restart the break duration, often with exponential backoff in production.

How the window decides to trip

The breaker only trips once it has enough samples. Below, a count-based window of the last 10 calls: 6 failed, so the 60% ratio clears a 50% threshold and the breaker moves Closed → Open. The oldest outcome slides off the left as each new one arrives on the right.

Library defaults — starting points, not production values

Polly v8 (.NET)
  • FailureRatio = 0.1 (10%)
  • MinimumThroughput = 100
  • SamplingDuration = 30s
  • BreakDuration = 5s
  • Time-based window only; throws BrokenCircuitException
resilience4j (JVM)
  • failureRateThreshold = 50
  • slidingWindowSize = 100
  • minimumNumberOfCalls = 100
  • waitDurationInOpenState = 60s
  • permittedNumberOfCallsInHalfOpenState = 10
  • slowCallDurationThreshold = 60s; throws CallNotPermittedException

A Polly v8 sketch, illustrative only — the runnable version lives in the code folder:

new ResiliencePipelineBuilder<HttpResponseMessage>()
    .AddCircuitBreaker(new()
    {
        FailureRatio       = 0.5,   // trip at 50% failure
        MinimumThroughput  = 20,    // need 20+ samples first
        SamplingDuration   = TimeSpan.FromSeconds(30),
        BreakDuration      = TimeSpan.FromSeconds(15),
        ShouldHandle = new PredicateBuilder<HttpResponseMessage>()
            .Handle<HttpRequestException>()
            .HandleResult(r => (int)r.StatusCode >= 500)
    })
    .Build();

Both libraries' authors are explicit: these defaults are conservative starting points, and you must tune them to your own traffic.

Common failure modes

✕

Window too small + low threshold

Two timeouts trip a global breaker. Cause: minimumThroughput left at the default while real traffic is sparse.

⚠

Thundering herd on recovery

On Open → Half-Open, every pending caller races to probe and re-overloads the upstream. Cause: no permit gating, or a wide permit pool. Mitigation: small probe pool, jittered break duration, or serialised single-probe recovery.

⚠

All-or-nothing breaker for a partial outage

One bad replica out of ten trips the service-level breaker for everyone. Cause: per-service rather than per-host state. Mitigation: Envoy outlier detection at the sidecar.

✕

Breaker hides a config bug

100% of calls fail because of a wrong URL; the breaker sits Open forever with alarms silent. Cause: missing state-transition alerts. Fix: alert on Open-state duration, not just upstream errors.

✕

Retries inside the breaker amplify failures

A 5× retry policy inside a 50% threshold breaker makes the breaker count one failure as five. Cause: pipeline order. Fix: breaker outside retry, or count attempt-bundles rather than individual attempts.

⚠

Per-process state, multi-pod fleet

Each pod has its own opinion, so one pod still hammers the upstream. Cause: in-process breakers don't share state. Fix: accept the eventual consistency, or push enforcement to the mesh.

⚠

Half-open starvation

Under heavy load every Half-Open transition burns its probes instantly and almost always re-trips. Cause: upstream recovers slowly relative to your traffic. Fix: longer break duration, or a gradual ramp instead of binary closed/open.

Why it exists

Synchronous RPC is the default in microservices, and synchronous calls couple liveness budgets. If A waits on B and B waits on C, then C's latency becomes A's latency and C's failure becomes A's resource exhaustion. The most expensive failure in production distributed systems is thread-pool or connection-pool starvation caused by waiting on a slow dependency — once the pool is empty, the caller stops serving unrelated traffic. The breaker puts a strict upper bound on how much of your own capacity one sick dependency can consume.

Why it looks the way it does

An obvious alternative — a global health-check daemon that pings each dependency and publishes "up/down" to all callers — was tried and largely abandoned:

  • Health checks lie. A /health endpoint that returns 200 in 10ms says nothing about whether the expensive code path is healthy.
  • Real call outcomes are the only truthful signal. A breaker is driven by the traffic that actually matters.
  • State must be local to be fast. Consulting a central oracle on every call adds a network hop to every call — the exact thing you're trying to avoid.

The three-state machine (rather than just Open / Closed) exists to solve the recovery problem. With two states you either keep the circuit Open forever or flip it Closed and immediately blast a recovering service with full traffic. Half-Open is the controlled re-introduction of load — a deliberately small probe whose only job is a binary "are you better?" signal at minimal cost. The bounded permit count is what keeps the thundering herd from being baked into the pattern.

Why it matters now

As of 2026, almost every non-trivial backend calls at least one third-party API — payment, identity, LLM inference, search, analytics — whose tail latency you don't control. LLM and generative endpoints in particular have wide, unpredictable latency and frequent partial outages, and Polly v8's AddStandardResilienceHandler was explicitly shaped around that workload. Meshes have made the pattern cheaper (one Istio DestinationRule covers a namespace), and observability libraries finally treat state transitions as first-class events. There's no successor on the horizon — the next step is adaptive breakers that tune thresholds from live traffic, but the underlying state machine is unchanged.
