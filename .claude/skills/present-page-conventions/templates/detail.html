Detail — the deep dive

◑ ~8 min read ✎ What · Where · When · How · Why

What it is

Open with one precise sentence. Then break the doc's dense definition into bullets:

  • Core idea. The one mechanism everything else hangs off.
  • Building blocks. Name each part in a word or two.
  • Family. The neighborhood of related patterns it belongs to.

When the doc lists the parts, a .vocab list reads better than a paragraph:

The named states and the moves between them.
Outcome classifier

Where it lives

Mesh / edge

When to use it

Summarize the trigger conditions in a tight list, and flag the boundaries with a callout.

◆

Rule of thumb

Reach for it around synchronous calls whose slowness can exhaust your own capacity — not for cheap in-process work.

How it works

Walk the lifecycle of a single request. The .steps list numbers each stage:

  1. Pre-check. Read current state (atomic, lock-free).
  2. Open path. If open, fail fast — no thread held, no socket used.
  3. Half-open path. Admit a bounded number of probe calls.
  4. Record + evaluate. Classify the outcome, update the window, re-check the threshold.

Key trade-offs

ChoiceGainGive up
Count-based windowSimple, predictable memoryDistorted by traffic bursts
Time-based windowStable under variable trafficMore memory, eviction overhead
Short cool-downFast recovery on blipsRe-trips on slow-recovering deps
Many probesFaster confidence to recoverBigger herd on a fragile service

Common failure modes

✕

Window too small + low threshold

Two failures trip a global switch. Cause: sample-size floor left at its default under sparse traffic.

⚠

Thundering herd on recovery

Every pending caller races to probe at once and re-overloads the service. Fix: a small probe pool and jittered cool-down.
