Detail — the deep dive

◑ ~10 min read ✎ What · Where · When · How · Why

What it is

An LSM tree is a disk-based index made of several components that defers and batches mutations instead of writing them in place. A new value, an update, and a delete are all just newer entries that shadow older ones — nothing is ever edited on disk.

  • Core idea. Buffer writes in a sorted in-memory structure; flush the whole buffer to disk as one immutable file once it fills.
  • Never in place. Records are never rewritten on disk — only created (flush) or dropped (compaction).
  • Background reconciliation. A job called compaction periodically merges files (a k-way merge sort) to discard shadowed or deleted data and cap how many files a read must check.

The canonical model comes from O'Neil, Cheng, Gawlick, and O'Neil, The Log-Structured Merge-Tree (LSM-Tree), Acta Informatica 33, 1996.

The core building blocks

Memtable
The mutable in-memory buffer, kept sorted by key (usually a skip list or balanced tree). Inserts are O(log n); reads here are the freshest data.
WAL / commit log
An append-only file written before the memtable insert is acknowledged — the durability mechanism. The memtable is volatile; the WAL is what survives a crash and gets replayed on restart.
SSTable
Sorted String Table — an immutable on-disk file of key-value pairs sorted by key. Once written, never modified, only created or deleted. Carries a sparse index and a Bloom filter alongside it.
Sparse index
Keys plus file offsets recorded at intervals (e.g. one per block), kept in or near memory. Narrows a lookup to one block, which is then scanned linearly.
Bloom filter
A probabilistic membership check per SSTable. Answers "definitely absent" or "probably present," letting a read skip files that cannot contain the key.
Tombstone
A special marker entry recording that a key was deleted at a given time. Shadows older live values until compaction physically removes both.
Compaction
The background merge that reclaims space and bounds read fan-out, run by a compaction strategy.

LSM trees and B+-trees are the two dominant families of on-disk ordered index. The B+-tree — the engine behind InnoDB, Postgres, and most classic relational databases — mutates pages in place and optimizes for read latency and bounded space. The LSM tree is the write-optimized sibling: it turns random writes into sequential ones and pays for that on the read and space side. Hash-based log structures like Bitcask are a simpler cousin with no range scans. The whole design descends from the log-structured file system idea (Rosenblum & Ousterhout, 1992).

Where it lives

The LSM tree is the storage engine — the layer beneath the query/transaction layer and above the block device. It owns the on-disk format, the memory buffers, the WAL, and the compaction scheduler. It doesn't parse queries or speak a wire protocol; a database embeds it.

Embeddable engine

RocksDB (the de facto reference, forked from LevelDB), LevelDB itself, Pebble (CockroachDB's Go rewrite), BadgerDB.

Wide-column store

Apache Cassandra and ScyllaDB built directly on the LSM/SSTable model; HBase and Google Bigtable, the lineage that popularized SSTables.

NewSQL on RocksDB

CockroachDB, TiKV, and MyRocks use RocksDB (or a fork of it) as the underlying store for a SQL or distributed-SQL engine.

Time-series

InfluxDB and Prometheus's TSM/TSDB variants use LSM-like append-and-compact designs for ingestion.

Tooling reflects that split: RocksDB exposes its statistics and LOG/OPTIONS files; Cassandra ships nodetool tablestats and nodetool compactionstats plus per-table compaction settings. On the theory side, the RUM conjecture and the Dostoevsky/Monkey line of research study how far you can push the amplification trade-offs below.

When to use it

✓ Reach for it when

  • Writes and updates dominate — ingestion pipelines, time-series, metrics, event logs, IoT.
  • The disk strongly prefers sequential I/O — this still helps SSDs by cutting write churn and improving compression.
  • You need good on-disk compression; sorted immutable blocks compress well.
  • You can trade background CPU/I/O on compaction for cheap front-door writes.

✕ Skip it when

  • Point-read latency is the headline metric and the working set doesn't fit in cache — a B-tree's single seek often wins.
  • The workload is read-mostly with rare writes — you'd pay compaction cost for little write benefit.
  • You need strict, predictable tail latency and can't absorb compaction-induced stalls.
  • The dataset is small enough to fit a simpler in-memory or B-tree index.

How it works

The write path:

  1. Append + fsync. The mutation hits the WAL first, durably, before anything else happens.
  2. Insert into the memtable. A sorted structure absorbs the write in O(log n). The client is acknowledged here.
  3. Flip to immutable. Once the memtable hits its size threshold, freeze it, start a fresh active memtable, and queue the frozen one for flush.
  4. Flush. Write the frozen memtable to a new SSTable in one sequential pass, building its sparse index and Bloom filter along the way. The matching WAL segment can now be discarded.

The read path — newest wins

A key may exist in several places at once, so a read walks them from newest to oldest:

  • Check the active memtable, then any immutable-but-not-yet-flushed memtables.
  • For each on-disk SSTable, consult its Bloom filter a probabilistic check that answers "definitely absent" or "probably present" for a key first. "Definitely absent" skips the file with zero disk I/O.
  • On "probably present," binary-search the sparse index key-to-offset entries recorded at intervals, used to jump straight to the right disk block to the right block and scan it for the key.
  • Return the entry with the highest timestamp. A tombstone counts as "found, but deleted."

With around 10 bits per key, a Bloom filter's false-positive rate sits near 1% — so only about 1 in 100 negative lookups triggers a wasted block read. Without it, a read that misses would have to check every SSTable on disk.

Compaction strategies — the central design lever

Size-tiered (STCS)

Merges SSTables of similar size into one bigger SSTable. Low write amplification; high space amplification (a merge can need up to ~2x space transiently) and higher read amplification. Cassandra's default is SizeTieredCompactionStrategy.

Leveled (LCS)

Data sits in levels L0, L1, L2… Beyond L0, key ranges within a level don't overlap, and each level is a fixed multiple bigger than the one above (RocksDB's max_bytes_for_level_multiplier defaults to 10). A point read touches at most one SSTable per level — low read and space amplification, but write amplification climbs above 10x.

Tiered + leveled (hybrid)

Tiered for the small upper levels, leveled for the large lower ones — a middle ground used by RocksDB's "level" style compaction and others.

Key trade-offs

Design choiceGainedGiven up
Out-of-place writes (append, never overwrite)Sequential write throughput, simple crash recoveryStale copies on disk until compaction (space amplification)
Multi-level / multi-SSTable layoutCheap flushes, batched mergesReads may fan out across files (read amplification)
Background compactionBounded read fan-out, space reclaimCompaction burns CPU/I/O; can cause write stalls
Leveled vs size-tieredLeveled: low read/space amplificationLeveled: high write amplification; STCS inverts the trade
Bloom filtersSkip absent-key SSTables cheaplyExtra memory; tunable false positives

These three knobs — write amplification extra bytes physically rewritten by compaction per logical write, read amplification, and space amplification — cannot all be minimized at once; the RUM conjecture formalizes that you pick at most two.

Common failure modes

✕

Write stalls / stop-the-world

Ingestion outpaces flush and compaction, L0 fills up, and the engine throttles or blocks writers. Cause: under-provisioned compaction threads or I/O.

⚠

Read amplification blowup

Too many overlapping SSTables — often under size-tiered — make point reads scan many files. Cause: compaction falling behind, or the wrong strategy for a read-heavy table.

⚠

Space amplification spike

Obsolete data plus in-flight merge copies bloat disk far beyond the logical size. Cause: size-tiered merges of large tiers, or compaction lag.

✕

Tombstone accumulation

Masses of deletes or TTL expirations linger and slow reads — range scans must read past them. Cause: a tombstone survives until it and the shadowed data are compacted together and gc_grace_seconds (Cassandra default 864000s = 10 days) has elapsed.

⚠

Bloom filter under-sizing

Too few bits per key raises the false-positive rate, turning what should be cheap skips into wasted disk reads.

Why it exists

The hardware fact underneath everything: storage devices serve large sequential writes far better than small random ones, and historically writing a record was the expensive part of indexing. A B-tree pays a random-I/O tax on every insert to stay sorted and read-optimal at all times. The LSM tree removes that tax: defer ordering work, batch it, and amortize it across many records in the background. It's a latency-vs-throughput, now-vs-later bargain on write cost.

Why it looks the way it does

The obvious alternative — keep a single sorted file and merge each new write into it in place — is a non-starter: every write would rewrite the whole file. The next alternative, an in-place-updated B-tree, is exactly what the LSM tree reacts against. The multi-component shape (one mutable memory tier, many immutable disk tiers) falls out of two constraints: writes must be cheap, so buffer and append; and disk files must be safe to share without locking, so make them immutable and reconcile by timestamp. Immutability is the non-obvious linchpin — it makes flushes lock-free, makes SSTables trivially cacheable and replicable, and turns crash recovery into a WAL replay instead of a structural repair. The cost it imports — stale data and read fan-out — is exactly what compaction and Bloom filters exist to contain.

Why it matters now

As of 2026 the LSM tree is the default storage engine for write-heavy and distributed data systems, not a niche choice. RocksDB and its descendants (Pebble, TiKV) sit under a large share of NewSQL and cloud-native databases, and the time-series and observability boom keeps ingestion-first workloads growing. Research keeps pushing the amplification frontier — learned indexes, learned Bloom filters, adaptive compaction — but it's worth understanding precisely because so many systems quietly inherit its trade-offs.
