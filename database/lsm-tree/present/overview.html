Overview

◔ ~3 min read ✎ intuition-first

Databases that take a firehose of writes — Cassandra, RocksDB, LevelDB, ScyllaDB — sit on top of an LSM tree. Its core trick: don't find a record on disk and overwrite it. Buffer changes in memory, then flush them to disk in big sequential batches.

ⓘ

In 30 seconds

Reads get a little harder — you may have to check several places for the latest value — and a background job called compaction constantly merges those batches to keep things tidy. You reach for this when you have a firehose of writes and disks that hate scattered, random I/O.

The mental model

Picture a busy chef during a dinner rush. Orders come in faster than anyone can file them neatly. So the chef scribbles each order on a sticky note and slaps it on a board — instant, no searching. The board is memtable the in-memory, sorted buffer where new writes land first.

When the board fills up, the chef doesn't throw the notes away. They grab the whole stack, sort it, staple it into a labeled binder, and start a fresh board. Each binder is an SSTable Sorted String Table — an immutable file on disk, written once and never edited — a file on disk, written once, never edited again.

Over a night you build up many binders. To find "table 7's current order" you check the newest binder first, then older ones, stopping at the first match — the latest note always wins. A delete is just a sticky note that says "table 7, cancelled" — a tombstone a marker recording that a key was deleted. Periodically, a helper merges several binders into one cleaner binder, dropping cancelled and replaced orders — that merging is compaction the background job that merges files, drops stale data, and keeps the shelf small.

That's the whole shape: fast append-only writes up front, sorted immutable files on disk, newest-wins lookups, and continuous background cleanup.

What it is not

⚠

Common mix-ups

  • Not a B-tree / B+-tree. Those update records in place and optimize for reads; an LSM tree optimizes for writes.
  • Not a write-ahead log. A WAL is the crash-recovery journal an LSM tree uses alongside memory; the LSM tree is the whole indexed structure, not just the journal.
  • Not a cache. The data here is the durable source of truth, not a throwaway speed layer.
  • Not a query language or a database itself. It's the storage engine underneath one.

When to reach for it — and when not to

✓ Reach for it when

  • The workload is write-heavy: time-series, event logs, metrics, IoT ingestion.
  • Sequential disk throughput matters more than single-record read latency.
  • You need high insert/update rates with good on-disk compression.
  • You're picking a database (Cassandra, ScyllaDB, RocksDB-backed stores) for ingestion-first use cases.

✕ Skip it when

  • Read latency is critical and a B-tree's single-seek read would win.
  • The workload does heavy in-place updates — compaction burns CPU and I/O for little gain.
  • The dataset is small enough to fit a simpler indexed structure.
  • The system can't tolerate the occasional compaction-induced stall.

Key vocabulary

Memtable
The in-memory, sorted buffer where new writes land first.
WAL (write-ahead log)
An append-only crash-recovery log written before a write is acknowledged.
SSTable
Sorted String Table — an immutable, sorted file on disk (a "binder").
Flush
Moving a full memtable out to disk as a new SSTable.
Compaction
Merging SSTables to drop stale or deleted data and reduce how many files a read must check.
Tombstone
A marker recording that a key was deleted.
Write amplification
Extra bytes physically written, via compaction, per logical write.
Read amplification
Extra files checked to answer one read.
Bloom filter
A probabilistic index that skips SSTables that definitely lack a key.
