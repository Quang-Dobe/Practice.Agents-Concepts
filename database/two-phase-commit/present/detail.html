Detail — the deep dive

◑ ~11 min read ✎ What · Where · When · How · Why

What it is

Two-phase commit is an atomic commitment protocol a way for independent resource managers to all reach the same commit-or-abort outcome for one distributed transaction, under a crash-recovery failure model.

  • Safety: guaranteed. No two participants ever reach different outcomes, and a commit happens only if every participant voted yes.
  • Liveness: not guaranteed. If the coordinator fails after participants voted yes, they block until it recovers.
  • Formally, 2PC is consensus on a binary value (commit / abort) where the “proposal” needs unanimity, and the coordinator is a single, unreplicated decider.

The core building blocks

Coordinator / Transaction Manager (TM)
Drives the protocol and owns the decision log. Its durable write of the COMMIT record is the commit point for the whole transaction.
Participants / Resource Managers (RM)
Databases, brokers, or queues that do the work locally and vote. Examples: PostgreSQL, MySQL/InnoDB, IBM MQ, Kafka (as a participant via KIP-939).
Global transaction ID (GTRID / XID / GID)
The name that ties together the local branches on each RM. PostgreSQL limits a GID to under 200 bytes.
Prepared state
A YES-voter force-writes its redo/undo and its “prepared” record to stable storage, keeps its locks, and gives up the right to abort on its own. This state survives restarts.
Write-ahead logs on both sides
Recovery depends entirely on what was force-written (fsync'd) before each message was sent.
Recovery protocol
After a crash the coordinator re-drives phase 2 from its log, and participants ask “what happened to XID x?” XA exposes this as xa_recover; PostgreSQL as the pg_prepared_xacts view.
X/Open XA specification (1991)
The standard TM↔RM interface: xa_start, xa_end, xa_prepare, xa_commit, xa_rollback, xa_recover, xa_forget. Java exposes it through JTA / Jakarta Transactions (XAResource). MySQL exposes it as SQL (XA START … XA PREPARE … XA COMMIT).

Where it sits in the bigger picture

  • Atomic commitment family: 2PC, three-phase commit (3PC, Skeen 1981), and Paxos Commit (Gray & Lamport, 2004/2006).
  • Next to, but distinct from, consensus (Paxos, Raft): those replicate one value across replicas and need only a majority.
  • Distinct from application-level alternatives such as Sagas and the transactional outbox, which give up atomic visibility in exchange for availability.
  • Modern distributed SQL combines both families: 2PC runs across shards, and each shard is a consensus group.

Where it lives

2PC lives at the transaction / storage layer, in one of two places:

  • Inside a distributed database. The engine runs it across shards or ranges. The application issues COMMIT and never sees the protocol.
  • In the application tier, across separate databases. A TM library (Narayana, Atomikos) or an OS service (MSDTC) is the coordinator. The RMs are separate database or broker processes reached over the network through XA-capable drivers.

Where you typically meet it

Google Spanner

Transactions touching more than one Paxos group run 2PC across the group leaders; one is the “coordinator leader.” Commit timestamps come from TrueTime, followed by a commit wait.

CockroachDB

A 2PC-derived protocol with a transaction record and write intents. Since v19.2, Parallel Commits marks the record STAGING so a commit costs one round of consensus instead of two.

Citus (PostgreSQL extension)

Multi-node writes issue PREPARE TRANSACTION / COMMIT PREPARED to the workers. Recovery records live in pg_dist_transaction.

Vitess

transaction_mode=TWOPC gives atomic cross-shard commits. Redesigned and reintroduced as experimental in v21 (October 2024).

Java EE / Jakarta EE, Spring + JTA

XA across a database and a JMS broker.

.NET System.Transactions

TransactionScope escalates from the Lightweight Transaction Manager to MSDTC when a second durable resource enlists. .NET 7 restored this on Windows only.

Ecosystem and tooling

  • Native database 2PC: PostgreSQL PREPARE TRANSACTION / COMMIT PREPARED / ROLLBACK PREPARED (gated by max_prepared_transactions, default 0). MySQL/InnoDB XA statements with XA RECOVER. SQL Server and Oracle through MSDTC or XA.
  • Standalone transaction managers: Narayana (JBoss/WildFly, Quarkus), Atomikos (embedded in Spring Boot apps), MSDTC (Windows). Bitronix is historical and unmaintained.
  • Broker participation: IBM MQ and ActiveMQ/Artemis support XA. Kafka has used its own internal 2PC-style protocol for exactly-once transactions since 0.11. KIP-939 (accepted, targeted at 4.1) lets Kafka act as a participant under an external coordinator — check client and broker versions before relying on it.
  • Formal references: Gray, Notes on Data Base Operating Systems (1978). Mohan, Lindsay and Obermarck, Transaction Management in the R* Distributed DBMS, ACM TODS 11(4), 1986 — defines presumed abort and presumed commit. Gray & Lamport, Consensus on Transaction Commit.

When to use it

◆

A little history

  • Mid-1970s: IBM's IMS and System R make atomic, durable transactions on one machine routine.
  • Then distributed databases (SDD-1, R*) break that guarantee: a transaction can commit at one site and fail at another.
  • 1976 / 1978: Lampson and Sturgis (Xerox PARC, 1976) and Gray (1978) describe the protocol now called 2PC.
  • 1986: R* refines it with presumed abort and presumed commit to cut log forces and messages.
  • 1991: X/Open standardizes the TM↔RM API as XA, so mixed databases and TP monitors (CICS, Tuxedo, Encina) can interoperate.
  • Before 2PC: manual reconciliation, batch jobs, and “commit and hope.”

✓ Reach for it when

  • You need atomic visibility: no reader may ever see one side committed and the other not.
  • Every participant is a system you operate that can actually prepare: databases and XA-capable brokers, not HTTP APIs.
  • The participant count is small (2 to a handful) on a low-latency network, usually one datacenter or region.
  • The coordinator's log can be durable and highly available: a persistent volume, a replicated store, or a database engine that does it internally.
  • Your distributed database already runs 2PC internally — you get it with no extra work.

✕ Skip it when

  • Participants are microservices owned by other teams. A prepared transaction in their database holds their locks hostage to your coordinator's uptime.
  • Any participant is a third-party SaaS or HTTP endpoint. These have no prepare / commit split.
  • You run on ephemeral compute (stateless pods, serverless) with no durable home for the TM log. A lost log means permanently in-doubt transactions.
  • The workload is write-hot or latency-critical. Locks are held across at least one network round trip plus two fsyncs, which caps throughput on contended rows.
  • Eventual consistency is acceptable. Outbox plus idempotent consumers, or a Saga with compensations, removes the coordinator altogether.

How it works

The classic protocol with presumed abort if no decision record exists, the answer is ABORT — so aborts cost no forced write, the variant most XA implementations use. “Force fsync to disk before continuing” marks every write that must hit disk before the next message goes out.

  1. Execute. The application does its work on each RM under one XID. Each RM takes locks and writes uncommitted changes as usual.
  2. Prepare request. The coordinator sends PREPARE(xid) to every participant. Under presumed abort it writes nothing yet.
  3. Participant vote.
    • Can commit: force a PREPARED record (with enough redo/undo to finish either way), keep locks, reply YES.
    • Can't: abort locally, reply NO, and forget the transaction.
    • Only read data: reply READ-ONLY, release locks, drop out of phase 2.
  4. Decision. All YES → the coordinator forces a COMMIT(xid, participants) record. This fsync is the commit point. Any NO or a timeout → abort, with no forced write.
  5. Phase 2. The coordinator sends COMMIT or ABORT to every YES-voter.
  6. Participant completion. The participant forces a COMMIT record, releases its locks, and sends an ACK. Under presumed abort, ABORT needs no ACK.
  7. Forget. After all ACKs, the coordinator writes a non-forced END record and can garbage-collect the transaction.
ⓘ

What one commit costs, with n participants

  • 4n messages: prepare, vote, decision, ack.
  • 2 round trips.
  • 2n + 1 forced writes: n prepares, 1 decision, n commits.
  • Example, n = 2: 8 messages and 5 fsyncs.

The participant state machine

What recovery does at each crash point

Crash pointRecovery outcome
Participant crashes before forcing PREPAREDIt restarts with no record of the transaction and aborts. The coordinator times out and aborts.
Participant crashes after PREPAREDIt restarts in-doubt. Its locks are reacquired and it asks the coordinator for the outcome.
Coordinator crashes before forcing COMMITOn restart there is no decision record, so presumed abort applies. Participants that ask are told ABORT.
Coordinator crashes after forcing COMMITOn restart it re-sends COMMIT until every participant ACKs.
Coordinator's log is lost permanentlyPrepared participants are stuck forever. Only an operator heuristic a manual commit or rollback made without the coordinator's decision decision clears them, and it can break atomicity.

Presumed commit is the mirror image:

  • The coordinator forces a “collecting” record listing the participants before prepare.
  • Commits then need no ACKs; aborts do.
  • Cheaper when commits dominate, but it costs an extra forced write up front.

Key trade-offs

Unanimous vote (vs majority)Every RM agrees on the outcome — true atomicity.Any single RM can veto or stall the transaction, so availability is the product of the participants' availabilities.
Single unreplicated coordinatorSimple; only one decision record to force.Blocking: a coordinator crash after votes leaves participants in-doubt. Paxos Commit / Spanner replicate the coordinator to remove this.
Prepared state holds locksParticipants can honor a commit decision no matter when it arrives.Lock hold time grows by ≥ 1 RTT + 2 fsyncs. Contention and deadlocks rise with participant count.
Presumed abort vs presumed commitPA: aborts and read-only branches are nearly free. PC: commits skip ACKs.PA: commits still need ACKs. PC: an extra forced write before every transaction.
Synchronous phase 2Each participant shows the committed data as soon as the client gets success.Higher commit latency. Async phase 2 returns sooner, but readers on a lagging participant can briefly see pre-commit state.

Common failure modes

✕

Orphaned prepared transactions in PostgreSQL

The TM crashed or lost its log, so rows in pg_prepared_xacts never resolve. They hold locks, block VACUUM from removing dead tuples, and in the extreme push toward XID-wraparound shutdown.

⚠

max_prepared_transactions left at 0, or below max_connections

PREPARE TRANSACTION errors out, or concurrent 2PC traffic fails under load.

✕

Coordinator on ephemeral storage

The pod is rescheduled and its TM log vanishes. In-doubt branches pile up on every RM, and nobody can resolve them.

✕

Heuristic mixed outcome

A DBA manually commits a branch on one RM while the coordinator decides abort. The data now diverges.

⚠

Lock amplification under contention

A hot row is held across a cross-AZ round trip, so throughput collapses to roughly 1 / (lock hold time) per row.

⚠

MySQL XA crash bugs on older versions

  • Before 8.0.30: a crash during XA PREPARE / XA COMMIT could leave the binary log and InnoDB disagreeing, because prepare was not atomic between the server and the engine.
  • Before 5.7.7: prepared XA transactions were rolled back on client disconnect.
✕

Timeouts treated as aborts after a YES vote

A participant or broker that auto-aborts a prepared branch (Kafka before KIP-939) breaks atomicity silently.

⚠

GID collisions or reuse

The TM reuses identifiers across restarts, and recovery commits or rolls back the wrong branch.

Why it exists

  • One machine: a local transaction gets atomicity from one write-ahead log. One fsync of one commit record decides everything.
  • Many machines: there is no single log, and the machines crash independently.
  • 2PC rebuilds the single decision point. Every participant first reaches a state where it can go either way (prepared). Then the outcome is recorded in exactly one durable place: the coordinator's log.
  • The principles at stake: atomicity under partial failure, and the fact that a message cannot be un-sent. A participant that commits before it knows everyone else can commit cannot take that commit back.

Why it looks the way it does

The non-obvious part is the prepared state: a participant voluntarily gives up its right to abort on its own. Without that promise the coordinator's decision would only be advice — a participant could still abort later — and atomic commit would be impossible.

Alternatives, and why they lost:

  • One phase (“commit everywhere, then fix up”). One fewer round trip, but no atomicity. This is the status quo 2PC replaced. Sagas formalize it with compensations.
  • Three-phase commit. Adds a pre-commit phase so surviving participants can finish without the coordinator. It is non-blocking only if the network is synchronous with bounded delays. Under a network partition, two halves can reach different decisions. It costs an extra round trip and gives up safety in exactly the failures that matter, so production systems rarely use it.
  • Replicate the coordinator (Paxos Commit). Gray and Lamport show classic 2PC is Paxos Commit with F = 0. With 2F + 1 coordinators it tolerates F failures, keeps the same stable-storage write delay, and spends more messages. Spanner takes this route (each participant and the coordinator are Paxos groups); CockroachDB, YugabyteDB and TiDB do the same with Raft.

So the modern answer to “2PC blocks” is not a different commit protocol. It is a coordinator that cannot disappear.

Why it matters now

As of 2026, 2PC is moving downward, not dying:

  • Losing ground: application-level XA across mixed systems, replaced by Sagas and the transactional outbox in microservices. It couples availability across team boundaries and does not fit stateless, container-based deployment.
  • Gaining ground: the core of every distributed SQL engine (Spanner, CockroachDB, YugabyteDB, TiDB, Citus, Vitess), with consensus-replicated coordinators and latency tricks such as Parallel Commits.
  • Coming back: streaming systems as participants. Kafka's KIP-939 targets the long-standing “write to the database and Kafka atomically” dual-write problem.

If you work with any of these systems, 2PC explains their commit latency, their lock behavior, and their recovery tooling.

Open questions to verify in practice

  • In PostgreSQL, what does pg_prepared_xacts show after you kill -9 the coordinator between PREPARE TRANSACTION and COMMIT PREPARED? How long do locks stay held, and does VACUUM visibly stall?
  • What is the measured commit latency of 2PC versus a local commit on the same hardware — closer to 1 RTT or 2, given that synchronous_commit changes fsync behavior?
  • Does a prepared transaction survive failover to a physical streaming replica, and who resolves it after promotion?
  • How does your TM (Narayana, Atomikos, MSDTC) store its log, and what happens when that log's volume is lost?
  • Under contention on one hot row, how does throughput degrade as you add a second and third participant?
  • If you use Kafka, does your client/broker version actually ship KIP-939's prepareTransaction() / completeTransaction() APIs, and what timeout behavior applies in 2PC mode?
