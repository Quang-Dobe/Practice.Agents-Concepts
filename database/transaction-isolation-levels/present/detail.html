Detail — the deep dive

◑ ~11 min read ✎ What · Where · When · How · Why

What it is

An isolation level is a contract between the database and one client transaction. It states which anomalies (non-serializable interleavings) the engine may expose to that transaction.

  • The reference point is serializability the result of running transactions concurrently equals the result of some one-at-a-time order of the same transactions.
  • Each weaker level allows a defined set of departures from it, in exchange for less blocking or fewer aborts.
  • ANSI SQL-92 defines four levels by the phenomena they forbid. That definition turned out ambiguous and tied to lock-based engines.
  • The working definitions today come from two later sources:
    • Berenson et al., "A Critique of ANSI SQL Isolation Levels" (SIGMOD 1995) — added Snapshot Isolation and new phenomena.
    • Atul Adya's 1999 MIT thesis — defines anomalies as cycles in a dependency graph (G0, G1, G2-item, G2), independent of how the engine is built.

The phenomena (Berenson et al. vocabulary)

P0 · dirty write
Overwriting another transaction's uncommitted write.
P1 · dirty read
Reading another transaction's uncommitted write.
P2 · non-repeatable read
The same row read twice returns different values.
P3 · phantom
A predicate read returns a different row set when re-run.
P4 · lost update
A read-modify-write is overwritten by a concurrent one.
A5A · read skew
You see a mix of pre- and post-commit state across two related items.
A5B · write skew
Two transactions read overlapping data, write disjoint rows, and break a rule together.

The core building blocks

Dependency graph
Nodes are transactions. Edges are ww (write-write), wr (write-read), and rw (read-write, an anti-dependency T1 read a version that T2 then overwrote, so T1 must come before T2). An execution is serializable when the graph has no cycle. Every anomaly is a specific cycle shape.
Locks
Shared (S) and exclusive (X) locks on rows, plus range locks predicate locks that also cover rows that do not exist yet, so inserts into the range block (SQL Server key-range locks, InnoDB next-key and gap locks). Lock duration — statement vs. transaction — is what separates the lock-based levels.
Snapshots
A read view of the database at a point in time, built from multiple row versions (MVCC, which has its own topic in this notebook). The snapshot's scope — per statement or per transaction — separates the snapshot-based levels.
Write-conflict rule
Under Snapshot Isolation, two concurrent transactions that write the same row cannot both commit. The usual rule is first-updater-wins the second writer waits; if the first commits, the second aborts.
Serialization failure
The abort the engine raises to keep its guarantee: SQLSTATE 40001 in PostgreSQL and CockroachDB, error 3960 in SQL Server SNAPSHOT, ORA-08177 in Oracle.

How it relates to the wider landscape

  • Isolation is the "I" in ACID and belongs to the concurrency-control family, next to two-phase locking (2PL), MVCC, and optimistic concurrency control (OCC).
  • It is a different axis from distributed consistency models (linearizability, causal, eventual), which describe what replicas show to readers.
  • The two meet in strict serializability — serializable plus real-time order — which Spanner advertises as "external consistency".

Where it lives

  • Enforced inside the engine by the transaction manager and lock manager (or the version-visibility check).
  • Chosen by the client: per transaction (SET TRANSACTION ISOLATION LEVEL ... or BEGIN ISOLATION LEVEL ...), per session, or as a server or database default.
  • The application only selects the level and handles the failures it produces. It cannot add isolation the engine does not provide.

Ecosystem and tooling

Set the level from code

JDBC Connection.setTransactionIsolation, .NET System.Data.IsolationLevel (ADO.NET and EF Core BeginTransaction), Spring @Transactional(isolation = ...), SQLAlchemy isolation_level, Django OPTIONS["isolation_level"] for PostgreSQL.

Observe locks and versions
  • PostgreSQL: pg_locks; predicate locks show as SIReadLock.
  • SQL Server: sys.dm_tran_locks, sys.dm_tran_version_store_space_usage.
  • MySQL: performance_schema.data_locks, SHOW ENGINE INNODB STATUS for history list length.
Test what an engine really does

Hermitage runs hand-written interleavings per engine. Jepsen's Elle checks transaction histories for dependency cycles.

Tuning knobs
  • PostgreSQL: max_pred_locks_per_transaction, default_transaction_isolation.
  • MySQL: transaction_isolation.
  • SQL Server: READ_COMMITTED_SNAPSHOT, ALLOW_SNAPSHOT_ISOLATION.

When it emerged

  • 1976. Gray et al. defined "degrees of consistency" 0–3 for lock-based systems. The degrees differed in which locks a transaction took and whether it held them until commit.
  • SQL-92. The standard renamed the degrees as the four levels and defined them through phenomena P1–P3, so vendors could describe them without naming locks. The standard default is SERIALIZABLE.
  • Snapshot engines. Oracle already shipped multiversion reads. Its "serializable" passed the ANSI phenomenon tests yet still allowed write skew. That gap drove the 1995 Berenson critique, which formally defined Snapshot Isolation.
  • 2005. SQL Server 2005 added SNAPSHOT and RCSI to cut reader/writer blocking.
  • 2008–2011. Cahill, Röhm and Fekete published Serializable Snapshot Isolation (SIGMOD 2008). PostgreSQL 9.1 shipped it in 2011, the first production implementation.
  • Since then. Distributed SQL went the other way: launched serializable-only, then added weaker levels — CockroachDB Read Committed in 23.2/24.1, and Repeatable Read (Snapshot Isolation) in Spanner.

When to choose a non-default level

✓ Reach for it when

  • Serializable — a rule spans rows or predicates ("at least one doctor on call", "sum of allocations ≤ budget", "no overlapping bookings"), the transaction is short, and you can wrap it in a retry loop.
  • Repeatable Read or Snapshot — one unit of work runs several reads that must agree: reports, exports, balance checks across tables, consistent backups.
  • Read Committed + explicit locks — contention is high on a few hot rows. SELECT ... FOR UPDATE, conditional UPDATE ... WHERE version = ?, or a unique constraint turns the race into a write-write conflict every level handles.
  • RCSI — on SQL Server, readers block writers under the lock-based default and you want PostgreSQL-like Read Committed.

✕ Avoid it when

  • Serializable everywhere — no retry path, long transactions, or hot rows colliding constantly. Abort rates climb; under lock-based Serializable (SQL Server, MySQL) deadlocks and blocking climb too.
  • Read Uncommitted for speed — with MVCC, readers don't block writers at Read Committed anyway. In SQL Server, NOLOCK can return rows twice or skip them during page splits, not only uncommitted ones.
  • Repeatable Read for "no lost updates" on MySQL — InnoDB Repeatable Read does not detect write-write conflicts. Use FOR UPDATE or an atomic UPDATE.
  • Raising the level for a single-row race — a unique index or an atomic UPDATE ... SET qty = qty - 1 WHERE qty > 0 is cheaper and holds at every level.
◆

Rule of thumb

Name the anomaly first, then pick the cheapest tool that stops it. Often that is a constraint or a row lock, not a higher level.

How it works

Engines use one of three mechanisms. The SQL names map onto them differently in each engine.

A · Lock-based (two-phase locking)

SQL Server's default levels and InnoDB's locking reads work this way.

  1. Writes. Every write takes an X lock held until commit. This prevents P0 at every level.
  2. Reads — the level decides.
    • Read Uncommitted takes no S lock.
    • Read Committed takes an S lock and releases it right after the read.
    • Repeatable Read holds S locks until commit.
    • Serializable also holds range locks on the scanned key interval, so concurrent inserts into it block. This is how phantoms are prevented.
  3. Conflicts. They show up as blocking. Cycles in the wait-for graph are resolved by the deadlock detector killing a victim.

B · Snapshot-based (MVCC)

Used by PostgreSQL, Oracle, InnoDB plain reads, SQL Server RCSI and SNAPSHOT.

  1. Take a snapshot. At the first statement (Read Committed: every statement). In PostgreSQL that is xmin, xmax and the list of in-progress transaction IDs; in InnoDB it is the "read view".
  2. Filter versions. A row version is visible only if its creator committed before the snapshot. Readers never block on writers.
  3. Update a row a concurrent transaction changed.
    • PostgreSQL Read Committed waits, then re-checks the WHERE clause against the newest version and proceeds.
    • PostgreSQL Repeatable Read, SQL Server SNAPSHOT and Oracle Serializable apply first-updater-wins: wait; if the other committed, abort (could not serialize access due to concurrent update); if it rolled back, continue.
    • InnoDB Repeatable Read updates the latest committed version without aborting. That is the lost-update hole.
  4. Only write-write is checked. Snapshot Isolation checks only write-write conflicts, so a write skew touching disjoint rows passes.

C · Serializable Snapshot Isolation (SSI)

PostgreSQL Serializable works this way.

  1. Run under SI. Exactly as in B.
  2. Record reads. Every read becomes a non-blocking SIREAD lock a marker of what was read; it blocks nobody and only feeds conflict detection. It starts at tuple granularity and is promoted to page or relation when memory runs short.
  3. Track rw edges. When T1 reads something a concurrent T2 writes, record an rw edge T1 → T2.
  4. Spot the danger. Cahill's theorem: every non-serializable SI execution contains a dangerous structure two consecutive rw edges T_in → T_pivot → T_out, where T_out commits first. Abort one participant when it appears, typically at commit time.
  5. Accept false positives. The check is conservative and does not search for full cycles, so some aborts are false positives. Coarser SIREAD locks add more of them.

Common failure modes

✕

Serializable in production returns 500s under load

Cause: 40001 / 3960 / ORA-08177 raised with no retry wrapper. The retry must re-run the reads too, not only the final write.

✕

Account balance loses decrements on MySQL

Cause: app-side read-modify-write under InnoDB Repeatable Read, which does not detect lost updates.

✕

Write skew in "Serializable" Oracle code

Cause: Oracle Serializable is Snapshot Isolation. Cross-row rules need SELECT ... FOR UPDATE or a constraint.

✕

SSI guarantee silently void

Cause: one writer in the conflict runs at Read Committed. SSI covers only transactions that all run at Serializable.

⚠

Abort storm after a schema or data change

Cause: SIREAD locks promoted to relation level, because max_pred_locks_per_transaction is too low or a sequential scan replaced an index scan.

⚠

Disk or tempdb growth, slow queries hours later

Cause: one long-open transaction pins the snapshot horizon. PostgreSQL vacuum cannot remove dead tuples, the InnoDB history list grows, the SQL Server version store fills.

⚠

Deadlocks on MySQL insert-if-absent

Cause: Repeatable Read gap and next-key locks taken by SELECT ... FOR UPDATE on a missing key, followed by concurrent INSERTs into the same gap.

⚠

SQL Server report blocks the OLTP workload

Cause: the lock-based Read Committed default. Readers hold S locks while writers queue. RCSI is off unless you turn it on.

✕

Isolation level leaks across requests

Cause: a session-level SET on a pooled connection persists for the next borrower.

Why it exists

  • Concurrency raises throughput and lowers latency.
  • But interleaved reads and writes can produce states no serial run could reach.
  • Full serializability has a cost: blocking under locks, or aborts under optimistic schemes.
  • That cost depends on the workload, so one fixed choice would be wrong for many apps.
  • Isolation levels make the trade-off explicit and selectable per transaction: a nightly report runs at a snapshot without blocking checkout, while the payment transfer runs Serializable.

Why it looks the way it does

  • The four ANSI names are 1970s lock durations dressed up as phenomena. That is why they fit snapshot engines badly.
  • Snapshot Isolation prevents every ANSI phenomenon in its strict reading — and still is not serializable.
  • Vendors kept the familiar names and mapped their own mechanisms onto them, which produced the engine table above.

The non-obvious design insight is SSI. Two other ways to make SI serializable were on the table:

  • Bring back read locks or range locks. That turns it into 2PL and gives up non-blocking reads.
  • Static analysis of the application ("Making Snapshot Isolation Serializable", Fekete et al., 2005): find dangerous transaction pairs and add artificial write conflicts by hand. It breaks whenever the code changes.
  • SSI instead accepts some false-positive aborts to keep reads non-blocking and need no application analysis. Because the cost is paid only when transactions conflict, PostgreSQL could make it the meaning of SERIALIZABLE.

Why it matters now

Isolation is under active change in 2025–2026:

  • Distributed SQL systems that launched serializable-only added weaker levels for compatibility and latency: CockroachDB Read Committed (GA in 24.1), Spanner Repeatable Read.
  • Aurora DSQL offers only strong Snapshot Isolation, so write skew is a design constraint you must handle in the schema.
  • MariaDB 11.8 changed Repeatable Read semantics by default.
  • SQL Server 2025 added optimized locking (TID locking, lock-after-qualification under RCSI).

Teams moving between Postgres-compatible clouds, or from MySQL to PostgreSQL, get the same level names with different guarantees — and the bugs only show up under concurrency. The topic is stable in theory and changing in practice.

Open questions to verify in practice

  • Does my driver or ORM set a level on connect, or inherit the server default? Check SHOW transaction_isolation / SELECT @@transaction_isolation / DBCC USEROPTIONS on a pooled connection.
  • Reproduce the doctors' write skew on PostgreSQL at Repeatable Read, then confirm Serializable aborts one transaction with 40001.
  • Reproduce a lost update on MySQL 8.4 Repeatable Read; compare with PostgreSQL Repeatable Read, which should raise could not serialize access.
  • Measure the abort rate of a Serializable hot-row workload, and how it changes with an index scan vs. a sequential scan (that changes SIREAD granularity).
  • On SQL Server, compare blocking for the same report with READ_COMMITTED_SNAPSHOT OFF vs. ON, and watch version-store growth while a long transaction stays open.
  • Write a retry wrapper and confirm it re-runs the whole transaction body, reads included, with bounded backoff.
