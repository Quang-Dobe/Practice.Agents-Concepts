Overview

◔ ~3 min read ✎ intuition-first

When two transactions touch the same data at the same time, the database has to decide what each one may see. An isolation level is that decision, written down as a setting.

ⓘ

In 30 seconds

  • Perfect isolation — every transaction acts as if it ran alone — costs throughput.
  • So SQL gives you a dial with four standard stops: Read Uncommitted, Read Committed, Repeatable Read, Serializable.
  • Each stop forbids a set of anomalies wrong results that can only happen because transactions interleaved.
  • Your database's default stop almost certainly allows some of them.
  • The bugs they cause show up under load, are hard to reproduce, and look like "impossible" data.

The mental model

Picture an office where several clerks update one shared paper ledger. Each clerk works on a task (a transaction) made of several reads and writes. The four levels are four rules about what a clerk is allowed to look at.

  • Read Uncommitted — you can read a colleague's pencil marks while they are still writing. If they erase them, you acted on numbers that never existed.
  • Read Committed — you only see entries written in ink (committed). But every time you look up, the ledger may have changed. Read the balance twice in one task and you can get two answers.
  • Repeatable Read — the moment you start, you get a photocopy of the ledger, a snapshot a frozen point-in-time view of the data. Your reads never move. The catch: you write on the real ledger, and your photocopy cannot tell you what other clerks are writing right now.
  • Serializable — the result is guaranteed to match some order in which the clerks took turns, one at a time. Clerks may still work in parallel, but if their work cannot be lined up into a valid order, one clerk is told "start over."

The photocopy trap

This is the one that bites. Two on-call doctors each check "is at least one other doctor on call?" Each sees "yes" on their own photocopy, and each signs off. Both writes succeed and nobody is on call. This is write skew two transactions read overlapping data, write different rows, and together break a rule, and only Serializable reliably stops it.

What it is not

⚠

Common mix-ups

  • Not atomicity. Atomicity is all-or-nothing for one transaction. Isolation is about how concurrent transactions see each other.
  • Not durability or replication consistency. "Read-your-writes" and eventual consistency describe replicas. Isolation levels describe transactions inside one database.
  • Not the same across engines. The names come from the ANSI SQL standard, but PostgreSQL, MySQL InnoDB, SQL Server, and Oracle each build them differently. PostgreSQL's Repeatable Read is really Snapshot Isolation, and so is Oracle's "Serializable".
  • Not MVCC multi-version concurrency control: keep several versions of each row so readers get a consistent view. MVCC is one technique engines use to build several of these levels. It has its own topic in this notebook.
  • Not a replacement for locks you take on purpose. SELECT ... FOR UPDATE and unique constraints are often the better fix for a specific race.

When to reach for it — and when not to

✓ Reach for it when

  • Money, inventory, or seat-booking logic where two requests can read-then-write the same data at the same time.
  • Rules spread across rows ("at least one admin", "total allocation ≤ budget") that no single-row constraint can enforce.
  • Reports that run several queries and need them all to agree (Repeatable Read or a snapshot).
  • Debugging duplicate charges, negative stock, or counters that "lose" increments under load.

✕ Skip it when

  • It's a single-statement update like UPDATE stock SET qty = qty - 1 WHERE id = 7 AND qty > 0. The row lock already makes it safe.
  • You want to crank everything to Serializable "just in case". You pay in retries and aborts, and code that doesn't handle a serialization failure the error the engine raises when it aborts a transaction to keep its guarantee; the client should retry breaks.
  • You want Read Uncommitted for "speed". PostgreSQL does not even implement it (it behaves as Read Committed); elsewhere it gives wrong answers, not faster ones.

Key vocabulary

Anomaly
An incorrect result that can only happen because transactions interleaved.
Dirty read
Seeing another transaction's uncommitted write.
Non-repeatable read
Reading the same row twice and getting different values.
Phantom read
Re-running a query and getting a different set of rows.
Lost update
Two read-modify-write cycles overlap and one write silently overwrites the other.
Write skew
Two transactions read overlapping data, write different rows, and together break a rule.
Snapshot Isolation
Every transaction reads from a frozen point-in-time view. Not one of the four ANSI levels, but what many engines actually ship.
Serialization failure
The error a Serializable transaction gets when the engine aborts it to stay correct. The client is expected to retry.
Default level
Read Committed in PostgreSQL, SQL Server, and Oracle. Repeatable Read in MySQL InnoDB.
