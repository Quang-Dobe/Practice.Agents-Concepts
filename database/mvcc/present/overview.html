Overview

◔ ~4 min read ✎ intuition-first

Many transactions read and write the same rows at once. MVCC lets them do that without readers waiting on writers, or writers waiting on readers.

ⓘ

In 30 seconds

Instead of locking a row so only one transaction can touch it, the database keeps the old version around whenever someone updates a row. Each transaction reads from a snapshot a frozen picture of the database, taken the instant the transaction began — a frozen picture of the database taken the moment it started. This is the default concurrency model in Postgres, MySQL/InnoDB, Oracle, SQL Server (under RCSI/Snapshot mode), and MongoDB's WiredTiger engine.

The mental model

Picture a shared document with version history always turned on:

  • Alice opens the doc at 9:00. She starts reading paragraph 3.
  • Bob edits paragraph 3 and saves at 9:01.
  • In a lock-based world, Alice would see Bob's cursor land on her paragraph and have to wait — or worse, see half-written text.
  • In the shared-doc world, Alice keeps seeing the 9:00 text until she explicitly refreshes. Bob's edit becomes a new revision sitting alongside the old one.
  • Anyone who opens the doc at 9:02 sees Bob's version. Anyone who opened it at 8:59 still sees the old one.

That is MVCC. The database never overwrites a row in place — it writes a new row version one historical copy of a row, tagged with the transaction that created it and tags it with the transaction that created it. Every transaction carries a snapshot ID, and when it reads a row it walks the version chain and picks the version that was visible at that snapshot. Readers never block writers. Writers never block readers. The only thing two transactions actually fight over is writing the same row — and that conflict is handled separately, with ordinary row locks.

What it is not

⚠

Common mix-ups

  • Not the same as locking. Pessimistic two-phase locking makes readers and writers queue up. MVCC sidesteps that for the read path entirely.
  • Not "no locks ever." Writers still take row-level locks so two transactions can't create conflicting new versions of the same row.
  • Not free. Old versions pile up and must be garbage-collected — Postgres calls this VACUUM, InnoDB calls it purge.
  • Not the same as serializable isolation. MVCC gives you snapshot isolation by default — strong, but it allows a subtle anomaly called write skew. True serializability needs extra machinery on top (Postgres calls it SSI).

When to reach for it — and when not to

✓ Reach for it when

  • Reads and writes happen concurrently on the same hot rows in an OLTP workload.
  • Reporting queries need a consistent view of a live, mutating dataset.
  • Read latency matters and readers can't afford to wait on write locks.
  • You are running long analytical queries against a transactional store.

✕ Skip it when

  • You mostly don't get a choice — for OLTP databases MVCC is essentially the default. The real question is which implementation, not whether.
  • Workloads of tiny, single-row updates with no contention may find plain in-place updates slightly cheaper — less bloat, less garbage collection.
  • Embedded or single-writer stores (SQLite in many setups) have no concurrency to manage in the first place.

Key vocabulary

Tuple / row version
One historical copy of a row.
Snapshot
The set of transaction IDs a transaction considers already committed and visible.
xmin / xmax
Postgres's per-row stamps for "who created me" and "who deleted me."
Undo log
InnoDB/Oracle's way of rebuilding old versions on demand instead of storing them inline.
Visibility rules
The logic that decides which version of a row a given transaction sees.
Snapshot isolation
The isolation level MVCC naturally provides.
Write skew
The anomaly snapshot isolation does not prevent.
VACUUM / purge
The background job that reclaims space from row versions no transaction can still see.
Bloat
The disk-space cost of accumulated dead versions.
Snapshot-too-old
The error you get when a long-running transaction needs a version that has already been purged.
