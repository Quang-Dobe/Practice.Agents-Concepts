Detail — the deep dive

◑ ~10 min read ✎ What · Where · When · How · Why

What it is

MVCC is a concurrency-control protocol where every logical row is an ordered chain of immutable physical versions, each stamped with the transaction that created it and, if deleted, the one that obsoleted it. A reading transaction never takes a shared lock. Instead it carries a snapshot a record of which transactions were already committed the moment this transaction began and walks each row's version chain, picking the one version that snapshot can see. Writers append new versions, take row-level exclusive locks only to keep two writers from clashing on the same row, and commit by marking their transaction ID as committed in a central commit log (Postgres clog, InnoDB trx_sys, Oracle's SCN-stamped transaction table). The protocol's native isolation level is snapshot isolation; true serializability is an opt-in layer on top.

The core building blocks

Transaction ID (XID / trx_id / SCN)
A monotonically assigned ID per write transaction. Postgres uses a 32-bit XID; InnoDB a 48-bit trx_id; Oracle a 6-byte System Change Number; CockroachDB/YugabyteDB a 64-bit Hybrid Logical Clock timestamp.
Row version (tuple)
One physical copy of a row plus a header carrying the creator XID, the deleter XID (or none), and engine-specific bits.
Version chain
The linked sequence of versions of one logical row, walked newest to oldest.
Snapshot
A triple: every XID below a horizon is settled, every XID at or above a ceiling is in the future, and a short list of XIDs were in flight the instant the snapshot was taken.
Visibility rule
A yes/no check: is this version's creator committed and visible to my snapshot, and is its deleter not?
Garbage collector
The background process that removes versions no live snapshot can still see — Postgres VACUUM/autovacuum, InnoDB's purge thread, Oracle's UNDO retention recycling.
Commit log
The authoritative record of which XIDs committed vs. aborted, consulted by every visibility check.

MVCC is one of three families of concurrency control:

  • Pessimistic locking — strict two-phase locking (S2PL), used by DB2 and pre-2005 SQL Server.
  • Optimistic concurrency control — validate at commit time, used by some in-memory engines like Hekaton.
  • Multi-version (MVCC) — this one.

MVCC is usually paired with row-level write locks, so it is not lock-free overall — it is lock-free for readers. Its closest cousin is the optimistic MVCC used in distributed systems (Spanner, CockroachDB), which adds a timestamp-ordering layer so MVCC works across nodes without one central XID allocator.

Where it lives

Inside the storage engine, in the tuple access layer that sits between the buffer manager and the query executor. The visibility check runs on every tuple read by every plan node — one of the hottest code paths in the system. In Postgres it is the function HeapTupleSatisfiesMVCC; in InnoDB it is ReadView::changes_visible.

Single-node OLTP

PostgreSQL (its only concurrency model), MySQL/InnoDB (default since 5.5 — MyISAM had none), Oracle (since v3, the original commercial MVCC).

Optional in the box

SQL Server under READ_COMMITTED_SNAPSHOT or ALLOW_SNAPSHOT_ISOLATION (off by default; lock-based otherwise). MongoDB via WiredTiger (default since 3.2).

Distributed SQL

CockroachDB, YugabyteDB, Google Spanner, TiDB, FoundationDB — MVCC is the substrate that makes consistent reads across shards possible.

Tooling to know

  • Postgres bloat: pgstattuple, pg_visibility, the pg_stat_user_tables view, plus pg_repack / pg_squeeze for online table rebuilds.
  • InnoDB undo: INFORMATION_SCHEMA.INNODB_TRX, innodb_undo_tablespaces, and the History list length metric in SHOW ENGINE INNODB STATUS.
  • Oracle: V$UNDOSTAT, DBA_HIST_UNDOSTAT, the UNDO_RETENTION parameter.
  • Distributed MVCC: CockroachDB's crdb_internal.kv_inflight_trace_spans, YugabyteDB's yb-admin with HLC inspection.

When to use it

✓ Reach for it when

  • Reads and writes touch the same hot rows and readers cannot tolerate waiting.
  • You need point-in-time consistent reads — reporting, backups, change-data-capture — against a live OLTP store.
  • Many application threads share a connection pool and need predictable per-transaction views.
  • You are picking a database. At this point MVCC is the default; the question is which flavour.

✕ Skip or tune it down when

  • You run very long transactions on a high-write table — they pin old versions and starve VACUUM/purge, ballooning storage.
  • You expect snapshot isolation to be serializable. It is not — invariants prone to write skew (on-call rosters, account balances across rows) need SSI or SELECT ... FOR UPDATE.
  • You have a single-writer workload with no real concurrency (SQLite in WAL mode is fine; full MVCC is overkill).
  • You are doing bulk UPDATEs on most of a Postgres table — append-in-place MVCC produces bloat equal to the update size and forces a heavy VACUUM.

How it works

Walk a read through a version chain the linked sequence of versions of one logical row, walked newest to oldest, and a write through it right after:

There are two dominant ways to build that chain. Both give the same outward behaviour; the storage differs.

Family 1: append-new-version-in-place (Postgres)

Each heap tuple carries a creator XID (t_xmin) and a deleter XID (t_xmax, zero if still live) in its header.

  1. Begin. A virtual XID is allocated; a real XID is assigned lazily on first write.
  2. First read. Take a snapshot: the oldest still-running XID, the next XID to be handed out, and the list of XIDs currently active.
  3. Update. Write a new tuple with t_xmin = my_xid; set the old tuple's t_xmax = my_xid. The old tuple's pointer (ctid) links to the new one — that link is the version chain. The HOT optimisation skips re-indexing when it can.
  4. Commit. Write "my XID → committed" to the commit log. No tuples are touched.
  5. Later read. Check visibility: is the creator committed, below my snapshot's ceiling, and not in my in-flight list? Is the deleter either unset, aborted, or above my snapshot? Both pass → the version is visible.
  6. VACUUM. Scans for tuples whose deleter is committed and older than every live snapshot, then reclaims their space. Autovacuum triggers at autovacuum_vacuum_scale_factor — default 0.2, i.e. 20% of a table dead.
  7. Freezing. XIDs are 32-bit and wrap near 4.3 billion. Before half that space is used, VACUUM stamps old tuples as permanently visible. autovacuum_freeze_max_age defaults to 200 million; missing the deadline forces single-user-mode recovery.

Family 2: current-version-in-place with an undo chain (InnoDB, Oracle)

The clustered index always holds the current version. Older versions are rebuilt on demand.

  1. Update. Modify the row in place, but first write a before-image undo record to the rollback segment and point the row's DB_ROLL_PTR at it.
  2. Reader snapshot. Build a ReadView — InnoDB's snapshot object. Under REPEATABLE READ it is built once per transaction; under READ COMMITTED, once per statement.
  3. Read. If the in-place row's transaction ID is invisible to the ReadView, walk DB_ROLL_PTR into the undo log, applying records in reverse until a visible version turns up. More CPU per read, but the row never moves, so index pointers stay valid.
  4. Purge. A background thread (innodb_purge_threads, default 4 since 5.7) drops undo records once no active ReadView needs them. The History list length — the depth of un-purged records — climbing past 1 million is the classic sign of a stuck long transaction.
  5. Oracle. Same model with UNDO tablespaces and an UNDO_RETENTION parameter; running past retention throws the well-known ORA-01555 snapshot too old.

Isolation levels under MVCC

LevelPostgresInnoDB
READ UNCOMMITTEDTreated as READ COMMITTEDReads latest committed (no dirty reads)
READ COMMITTEDNew snapshot per statementNew ReadView per statement
REPEATABLE READSingle snapshot per transaction, no phantoms (true SI)Single ReadView per transaction; gap locks added on locking reads to block phantoms
SERIALIZABLESI + predicate-locking SSI on topFalls back to S2PL (degenerates to locking)

Postgres's REPEATABLE READ already forbids phantom reads because the snapshot is genuinely consistent — stronger than the plain SQL-92 definition of the level.

Serializable Snapshot Isolation (SSI)

  • Postgres 9.1+ implements Cahill, Röhm & Fekete's 2008 algorithm.
  • It tracks rw-antidependencies between concurrent snapshot-isolation transactions using SIReadLock predicate locks — held only by serializable transactions, and never blocking a write.
  • When two consecutive rw-edges form a dangerous structure in the conflict graph, one transaction is aborted with SQLSTATE 40001. The application must retry.
  • SSI removes write skew while keeping the read-never-blocks-write property of plain SI. The cost is a false-positive abort rate under contention.

Common failure modes

✕

Postgres table bloat under wide UPDATEs

Updating every row of a 100 GB table writes 100 GB of new tuples and marks 100 GB dead. Cause: append-in-place semantics.

⚠

"Idle in transaction" holding the xmin horizon

A forgotten open transaction in an app pool pins the horizon, so VACUUM can't reclaim anything system-wide.

⚠

InnoDB history list explosion

Same pattern: a long-running REPEATABLE READ transaction blocks purge; the undo tablespace grows without bound.

✕

ORA-01555 snapshot too old

A long query needs an undo record already recycled under UNDO_RETENTION pressure. Cause: undo is finite, MVCC is not.

✕

XID wraparound emergency shutdown (Postgres)

Autovacuum is disabled or stuck; the database's frozen-XID age approaches 2 billion; Postgres refuses writes. Cause: freezing did not keep up.

⚠

SSI serialization-failure storms

A heavily contended predicate (e.g. counting rows where status = pending) produces a high rate of 40001 aborts under serializable. Cause: false positives in dangerous-structure detection.

✕

Write skew under SI

Two transactions read a shared invariant, each verifies it, each updates a different row, both commit — the invariant is now violated. Cause: SI is not serializable.

Why it exists

The problem MVCC solves is the read-write contention tax of single-version stores. In a single-version world, a consistent read either takes a shared lock — blocking writers and queueing behind them — or sees torn, half-written state. Neither is acceptable for a database that must also serve reporting queries. MVCC decouples the read path from the write path by trading storage (multiple versions) for concurrency — the central time-space-concurrency trade in database design.

Why it looks the way it does

An alternative — timestamp-ordered single-version reads with a restart on out-of-order access — was tried. System R prototyped it and it lost, because of cascading aborts and starvation under skewed workloads. Multi-versioning sidesteps both: an out-of-order read simply reads the older version, no restart needed.

The split between append-in-place (Postgres) and undo-chain (InnoDB/Oracle) is not arbitrary either. Postgres assumed cheap sequential writes and aggressive background cleanup. InnoDB assumed a clustered-index layout where moving a row is expensive because it invalidates secondary-index pointers. Both are coherent designs reflecting different priors about workload shape — neither is universally better.

The other deliberate choice is snapshot isolation, not serializability, as the default. SI gives 95% of the intuitive correctness for 0% of the lock overhead. True serializability was the SQL standard's original goal but proved too expensive in practice. SSI is the modern compromise: serializability with SI's non-blocking read path intact, paid for in commit-time aborts instead of lock waits.

Why it matters now

In 2026, every default-choice OLTP database — open source, commercial, single-node, distributed — runs MVCC. The growth area is distributed MVCC: CockroachDB, YugabyteDB, Spanner, TiDB, and the newer serverless Postgres-compatible stores (Neon, Aurora DSQL) all extend MVCC over Hybrid Logical Clocks or TrueTime to deliver consistent snapshots across regions. The single-node fundamentals here are the prerequisite for reasoning about them — every distributed-transaction failure eventually reduces to "whose snapshot saw whose version, and when did the garbage collector run."
