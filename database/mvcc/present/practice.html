Practice — how it plays out for real

● ~11 min read ✎ best practices · anti-patterns · checklist

Where you'll meet it

In a typical SaaS backend, MVCC is the invisible substrate every ORM call relies on — and the first thing you blame when the database gets slow at 3am. You meet it for real the day a long-running cron job pins the visibility horizon and a table balloons over a weekend, or the day a payment service double-charges a customer because two requests both passed a balance check under snapshot isolation. The recurring theme: MVCC is forgiving until someone holds a transaction open too long, assumes snapshot isolation is serializable, or fights the garbage collector.

SaaS backend

A forgotten open transaction pins the horizon; autovacuum stalls; a 200 GB table balloons to 600 GB over a weekend.

Payments

Two requests both pass a balance check under snapshot isolation and commit independently — a double charge.

Analytics-heavy product

A 40-minute report runs against the live OLTP primary without locking out writers — and your DBA still tells you not to.

Distributed SQL

CockroachDB, Spanner, and YugabyteDB extend MVCC over Hybrid Logical Clock timestamps so cross-region snapshot reads are reasoned about at all.

Best practices

1

Default to READ COMMITTED, escalate per query

Do

Run ordinary OLTP traffic at READ COMMITTED. Reach for REPEATABLE READ only when one transaction makes several reads that must agree. Reach for SERIALIZABLE only for money-moving or invariant-protecting work where write skew would corrupt state.

Why

Higher isolation levels pin snapshots longer and raise the serialization-failure rate. Paying that cost on every read wastes it; skipping it on the 1% that needs it is a bug.

Avoid

Setting SERIALIZABLE globally "to be safe." You get 40001 storms under contention and no one knows how to retry.

2

Keep transactions short — milliseconds, not minutes

Do

Open the transaction as late as possible and commit as soon as the last write lands. Move validation, I/O, and external calls outside the begin/commit block. Target p99 transaction duration under 100ms for OLTP.

Why

Every live transaction pins the global visibility horizon. One forgotten transaction from 10 minutes ago tells the database "any dead row newer than that might still be needed" — VACUUM gives up and bloat accumulates.

Avoid

Wrapping an HTTP call to a payment provider inside a database transaction. You've handed the database a multi-second pin per request.

3

Never hold a transaction across user think-time or external I/O

Do

Read data, close the transaction, let the user think, then start a new transaction with SELECT ... FOR UPDATE or an optimistic version check when they submit.

Why

This is the #1 cause of the idle in transaction a connection that returned results to the app but was never told to commit or roll back — its snapshot is still pinned pathology. In a 200-connection pool, a handful of stalled ones can stall vacuum across the whole cluster.

Avoid

ORM patterns that auto-open a transaction on first query and leave it open until end of request. Make transaction scope explicit.

4

Configure idle_in_transaction_session_timeout aggressively

Do

On Postgres, set idle_in_transaction_session_timeout = '60s' for service accounts, lower for interactive logins. Pair it with statement_timeout and a pool-side idle timeout.

Why

This is your seatbelt against a bug in application code or a wedged client. The session is killed, the snapshot releases, vacuum proceeds. The request fails loud instead of quietly rotting the database.

Avoid

Leaving it at the default of disabled in production — flagged by multiple cloud vendors as the single most effective Postgres tuning knob for OLTP.

5

Use SELECT ... FOR UPDATE for read-modify-write on one row

Do

When the logic is "read a row, decide, then update it," use SELECT ... FOR UPDATE inside the transaction. Use FOR UPDATE SKIP LOCKED for queue-style workers grabbing the next job.

Why

Plain snapshot isolation lets two transactions both read the same balance, both decide it's sufficient, both deduct, both commit. FOR UPDATE opts that one row into pessimistic locking instead.

Avoid

Reaching for SERIALIZABLE when one well-placed FOR UPDATE would do. Row locks are cheap and predictable; SSI's false-positive aborts are not.

6

Prefer upsert over check-then-insert

Do

Use INSERT ... ON CONFLICT (key) DO UPDATE in Postgres, INSERT ... ON DUPLICATE KEY UPDATE in MySQL, or MERGE where supported — one statement, no gap.

Why

"Does the row exist? No? Insert it." is two statements with a snapshot gap between them. Under snapshot isolation, two concurrent sessions can both pass the existence check and both try to insert — a race.

Avoid

if not exists: insert() in application code. It's a bug under every isolation level except true serializable.

7

Treat serialization failures as a first-class control-flow case

Do

Wrap any SERIALIZABLE (and ideally REPEATABLE READ) transaction in a bounded retry loop with backoff. Postgres SQLSTATE 40001 and 40P01 (deadlock) are expected outcomes, not bugs.

Why

SSI achieves serializability by aborting one transaction in any dangerous structure. If the app doesn't retry, the user sees an error for what is actually normal protocol behaviour.

Avoid

Logging 40001 as an error and paging on-call. It's informational at low rates — alarm on the rate, not the event.

8

Chunk bulk updates into bounded batches

Do

For an update touching millions of rows, loop over 5,000–50,000 rows per transaction with a stable key window (WHERE id BETWEEN ? AND ?), committing between batches.

Why

One transaction updating 100M rows writes 100M new versions, marks 100M dead, and holds a horizon pin for hours — doubling table size and blocking vacuum the whole time.

Avoid

"It's a one-time migration, who cares" — that one-time migration is what pages you at 3am.

9

Don't UPDATE columns that didn't change

Do

Omit unchanged columns from the UPDATE set list, or check dirty-tracking in your ORM.

Why

Postgres's HOT optimisation skips index updates only if no indexed column changed and the new row fits the same page. Rewriting every column defeats it and forces a full secondary-index update per row.

Avoid

"Update the whole row, it's simpler" — simple to write, expensive to vacuum.

10

Leave autovacuum on, but tune it per table

Do

Lower autovacuum_vacuum_scale_factor from the 0.2 default to 0.05 or 0.02 on hot tables. Raise autovacuum_vacuum_cost_limit from the 200 default to 1000+ on SSD-backed systems.

Why

20% dead is fine for a 1M-row table (a minute of vacuum) and catastrophic for a 1B-row table (an hour of churn). Vacuum isn't the enemy — late vacuum is.

Avoid

Disabling autovacuum "to save I/O during business hours." You pay double at 2am when the anti-wraparound vacuum kicks in and can't be cancelled.

11

Route long analytical queries off the OLTP primary

Do

Send 30-second-plus reporting queries to a read replica, a logical-decoding subscriber, or a separate analytics store. Reserve the primary for sub-second OLTP.

Why

A long query on the primary pins the horizon just like a long write does — vacuum can't reclaim anything newer than that query's snapshot.

Avoid

Running BI dashboards against the OLTP primary "because it's the freshest data" — right up until it's also the most bloated.

12

Know your write-skew shapes

Do

Before shipping a multi-row invariant (on-call rotations, ledger debit/credit, inventory across SKUs), ask: could two concurrent transactions each read the rule as satisfied and each act on a different row? If yes, use SERIALIZABLE with retry, or put the invariant on one row and lock it with FOR UPDATE.

Why

The canonical case: the rule is "at least one doctor on-call." Two doctors each check it, see two on-call, both go off-call, both commit — rule broken. Snapshot isolation can't see the conflict because they touched different rows.

Avoid

Assuming snapshot isolation equals serializable. It does not — REPEATABLE READ allows write skew two concurrent transactions each read a shared rule as true, each change a different row, and both commit — the rule ends up broken; only SERIALIZABLE rejects it.

Anti-patterns to recognize

✕

The transactional HTTP call

Wrapping an external API request inside begin/commit. The snapshot is pinned for the full network round-trip; under load this stalls vacuum cluster-wide. Pull the I/O out of the transaction.

✕

The "wide" UPDATE

One statement updating tens of millions of rows. Postgres bloats the table by roughly 100%; InnoDB's undo tablespace explodes. Chunk it into batches instead.

✕

The ORM-rewrites-every-column UPDATE

Saving an entity rewrites all 30 columns, including the 28 unchanged ones. HOT misses, every secondary index updates per row, bloat scales with column count.

✕

Disabling autovacuum

Done "because vacuum was causing I/O spikes." The I/O is the cost of correctness, paid daily instead of in one emergency. Tune cost limits up and scale factor down instead.

✕

Catching and swallowing 40001

The app catches the serialization failure, logs it, and returns success to the user. The write never happened. Always retry; only surface a terminal failure.

✕

SELECT ... FOR UPDATE on too broad a query

SELECT * FROM orders WHERE status='pending' FOR UPDATE in a queue worker locks every pending row at once, serialising every worker. Use LIMIT 1 ... FOR UPDATE SKIP LOCKED instead.

✕

Trusting count(*) on a big table to be fast

There is no shortcut — every visible tuple must be visited because visibility depends on the caller's snapshot. Cache the count, or maintain a running counter.

✕

Long-running pg_dump on the primary

It opens a REPEATABLE READ transaction for its full duration. On a high-churn 500 GB database that's hours of pinned horizon. Dump from a replica.

Real-world usage patterns

Payments ledger (fintech, ~2k TPS)

One row per account balance. Debits use SELECT ... FOR UPDATE on the contested row, then update and insert a ledger entry. SSI was tried; the false-positive abort rate at peak made p99 latency unpredictable. Lesson: SSI is cleaner in theory, but FOR UPDATE on the contested row is more operable.

Multi-tenant SaaS CRM (~500 RPS, Postgres)

An 80M-row customers table had last_seen_at in an index, so HOT never fired and bloat hit 3x weekly. Dropping the index let HOT kick in; bloat stabilised under 20%. Lesson: every index on a hot-updated column taxes MVCC garbage collection.

Job queue on Postgres

20 workers pull from a jobs table with SELECT id ... ORDER BY priority LIMIT 1 FOR UPDATE SKIP LOCKED. Every worker gets a different job, no contention, no polling storm. Lesson: SKIP LOCKED turns a hard distributed-systems problem into one line of SQL.

Analytics-on-OLTP gone wrong (InnoDB)

A nightly 4-hour REPEATABLE READ join against the production primary grew the history list length from ~10k to over 50M; the undo tablespace hit 400 GB and replica lag spiked. Lesson: monitor history list length; treat sustained growth as a page-worthy incident.

Operational checklist

✓

Before you call it done

  • Long transactions: alert on any Postgres session idle in transaction for over 5 minutes; page past 30 minutes.
  • Horizon age: monitor the oldest live snapshot's age; alert above 50M, page above 200M.
  • Bloat: chart dead-tuple percent weekly on your top-20 hottest tables.
  • Replication slots: alert on any inactive logical slot older than an hour — it pins the horizon too.
  • InnoDB history list length: history list length — warn at 100k sustained, page at 1M.
  • Serialization-failure rate: a baseline of a few 40001s per minute is fine; a spike to thousands means a hot predicate has become contended.
  • Deadlocks: should sit near zero in a healthy system.
  • idle_in_transaction_session_timeout: set on every instance, including dev and staging?
  • Retry wrappers: does every SERIALIZABLE transaction sit in a retry loop?
  • Anti-wraparound headroom (Postgres): frozen-XID age should sit well under 200M — alert at 1B, page at 1.5B.

How it evolves in a codebase

  1. Year one. No one thinks about MVCC. The default isolation level works, the database is small, autovacuum keeps up.
  2. Year two. Tables hit ~100M rows. A 10M-row backfill in one transaction doubles the table's size overnight. The team learns about VACUUM, sets idle_in_transaction_session_timeout, and misdiagnoses the first 40001 as a database bug.
  3. Year three-plus. A write-skew bug ships and reaches a customer report. The postmortem reveals snapshot isolation is not serializable. The team adds SELECT FOR UPDATE in critical paths, retry wrappers around serializable transactions, per-table autovacuum tuning, and a replica for analytics.
  4. The painful migration. Moving from "one big OLTP database" to "OLTP + replica + analytics store." Every long query that was tolerable on the primary now needs an explicit decision about where it runs.
