Overview

◔ ~3 min read ✎ intuition-first

Your database is fine until it isn't. One day a table has 500 million rows, the disk is full, and one primary machine can't keep up with writes.

ⓘ

In 30 seconds

Sharding chops the data horizontally. Every row still looks the same, but rows live on different machines based on a routing rule — usually a hash of user_id or a range of dates. Each machine only sees its own slice, called a shard one physical database holding a slice of the data. You scale by adding more boxes instead of buying one bigger box.

The mental model

Picture one giant filing cabinet in an office. It works fine until the office has ten thousand employees — now it won't fit in the room, and three people are always queued at the drawers.

So you buy ten smaller cabinets, one per hallway, and make a rule: last names A–C live in cabinet 1, D–F in cabinet 2, and so on. Anyone looking up a folder checks the rule, walks to the right cabinet, and pulls the file. Nobody ever opens all ten cabinets to find one folder.

That rule is the shard key the column value that decides which machine a row lives on — e.g. user_id. The cabinets are the shards. The person who knows the rule and walks you to the right cabinet is the router the component that maps a query to the right shard, called the routing layer. Every cabinet has the same drawer layout — the same schema — they just hold different folders.

The whole game is picking a key where the folders spread out evenly, so most lookups only ever touch one cabinet.

What it is not

⚠

Common mix-ups

  • Not replication. Replication makes copies of the same data on many nodes, for read scale or failover. Sharding puts different data on different nodes.
  • Not vertical partitioning. Vertical partitioning splits a table by columns (move a big blob column to its own table). Sharding splits by rows.
  • Not the same as table partitioning. Postgres/MySQL "partitions" usually live on the same server, same disk, same process. Sharding spans multiple servers.
  • Not free horizontal scaling. It buys throughput at the cost of cross-shard joins, distributed transactions, and rebalancing pain.

When to reach for it — and when not to

✓ Reach for it when

  • One primary node can't absorb the write rate, even after vertical scaling.
  • The working dataset no longer fits in RAM on one machine and cache hit rates are collapsing.
  • You need geographic locality — EU users on EU shards, US on US — for latency or data residency.
  • Tenants are naturally isolated, like a multi-tenant SaaS where one customer's data rarely mixes with another's.

✕ Skip it when

  • Your database fits on one box and the real problem is a missing index. Fix the index.
  • You need ACID transactions spanning many rows of unrelated entities — distributed transactions are slow and fragile.
  • Your workload is heavily analytical, with big joins across the whole dataset. Reach for a warehouse or columnar store instead.
  • You're under 100 GB of hot data. The operational tax almost certainly costs more than a bigger instance.

Key vocabulary

Shard
One physical database holding a slice of the data.
Shard key
The column whose value decides which shard a row goes to (e.g. user_id).
Routing layer
The component that maps a query to the right shard — client, proxy, or the database itself.
Hash sharding
shard = hash(key) % N. Even distribution, bad for range scans.
Range sharding
shard = lookup(key in [lo, hi]). Great for range scans, prone to hotspots.
Directory / lookup sharding
A separate table maps each key to a shard. Flexible, but the lookup itself becomes a bottleneck.
Hotspot
One shard getting disproportionate traffic — e.g. sharding by country when 60% of users are in one country.
Resharding
Redistributing data when shards are added or removed. The hardest part of operating a sharded system.
Cross-shard query
A query that must touch more than one shard. Slow, hard to keep transactional, easy to get wrong.
