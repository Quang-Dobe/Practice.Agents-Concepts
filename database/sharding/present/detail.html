Detail — the deep dive

◑ ~10 min read ✎ What · Where · When · How · Why

What it is

Sharding is horizontal partitioning of one logical dataset across independent physical database instances. Each instance — a shard — owns a disjoint slice of the keyspace and handles both reads and writes for that slice. A routing function decides ownership.

  • Core idea. The union of all shards reconstitutes the original table; the intersection of any two shards is empty. Rows are not copied across shards — that's replication's job, and it happens inside each shard, not between them.
  • Architecture. This is a share-nothing shards do not share memory, disk, or a write log — coordination across them is explicit and costly design in Michael Stonebraker's sense.
  • Family. It sits in the data-distribution family alongside replication (same data, many nodes, for fault tolerance), federation (different services own different tables), and vertical partitioning (different columns, different stores). Most sharded systems also replicate each shard for high availability — Cassandra and DynamoDB fold both concerns into one ring; MongoDB and Vitess keep them separate, so each shard is itself a replica set. NewSQL systems (Spanner, CockroachDB, TiDB) shard automatically underneath a plain SQL surface.

The core building blocks

Shard key
The column(s) the routing function reads. The choice is permanent in most systems — changing it means a full data migration.
Routing function
A pure function from key to shard. Three families: hash (hash(key) % N, or consistent hashing), range (key ∈ [lo, hi)), or directory (lookup in a metadata table).
Router / query layer
Runs the routing function and forwards the query. Lives in the client driver (Cassandra), a proxy (Vitess vtgate, MongoDB mongos), or the database itself (Citus coordinator).
Shard map / topology
Metadata describing which shard owns which range, stored in a strongly-consistent store — Zookeeper or etcd (Vitess), Spanner's universe master, MongoDB's config servers.
Rebalancer / mover
Background process that migrates data between shards when adding capacity or fixing skew — MongoDB's balancer, Vitess's VReplication, Citus's rebalance_table_shards().
Reference / global tables
Small, mostly-read tables (currencies, country codes) copied to every shard so joins never go cross-shard.

Where it lives

Sharding sits at the data tier, but the routing piece can live at three different layers:

1 · Client-side

The Cassandra driver computes the token from the key and contacts the owning replica directly. Lowest latency, but every client must know the topology.

2 · Proxy

vtgate (Vitess), mongos (MongoDB), ProxySQL, Figma's DBProxy. Clients speak unmodified SQL; the proxy parses, rewrites, and routes. Adds a hop, centralizes logic.

3 · Database engine

Spanner, CockroachDB, YugabyteDB, Citus handle sharding internally — the client sees one plain SQL endpoint.

Systems you'll actually run into: Vitess (sharded MySQL at YouTube, Slack, GitHub, Shopify), Citus (distributed Postgres, now Azure Cosmos DB for PostgreSQL), MongoDB sharded clusters, Cassandra/ScyllaDB (a consistent-hashing ring, no router process), DynamoDB (partitioning is automatic and invisible), Spanner/CockroachDB/TiDB (automatic range-sharded storage), and Elasticsearch/OpenSearch (index sharding for search).

When to use it

✓ Reach for it when

  • One primary can't take the write rate after vertical scaling, read replicas, and connection pooling are exhausted.
  • The hot working set exceeds RAM on the largest economical instance — typically 256 GB–2 TB depending on the cloud SKU.
  • Data residency requires geographic partitioning — EU users on EU shards under GDPR Article 44+.
  • There's a natural tenant boundary where over 95% of queries scope to a single tenant.
  • You're already on a system with first-class sharding (Vitess, Spanner, DynamoDB), so adding a shard is cheap.

✕ Skip it when

  • The bottleneck is a missing index, an N+1 query, or unbatched writes. Profile first.
  • The workload is OLAP with full-table aggregations — use a columnar warehouse instead.
  • You need cross-entity ACID transactions touching arbitrary rows.
  • Total hot data is under roughly 100 GB — the operational tax exceeds the savings.
  • The team has never operated a distributed database and has no SRE bandwidth.

A little history

The commercial roots trace to Google's late-1990s search index and eBay's early-2000s "functional and horizontal segmentation." The term went mainstream through Flickr's 2006 engineering post, "Federation at Flickr: Doing Billions of Queries Per Day," and the LiveJournal/Friendster/MySpace era popularized the per-user-bucket pattern. NoSQL systems — BigTable (2006), Dynamo (2007), Cassandra (2008) — then made sharding a built-in property instead of an application-level retrofit.

How it works

Reading through a sharded cluster

Concrete example: a Vitess cluster with 4 shards keyed on customer_id.

  1. Parse. The router (vtgate) parses the SQL and finds predicates on the shard key — e.g. WHERE customer_id = 12345.
  2. Route. It applies the routing rule — Vitess calls it a vindex — e.g. hash(12345) maps into keyspace range [0x40, 0x80), currently owned by shard -80.
  3. Look up topology. The shard-to-tablet map is read from the topology service (etcd or Consul), usually cached in-process with a TTL of a few seconds.
  4. Forward. The query goes to the primary tablet of shard -80 — an ordinary MySQL instance.
  5. Execute locally. MySQL plans and runs the query against its slice — a normal InnoDB table containing only that key range's rows.
  6. Return. Result rows stream back through vtgate to the client.

Queries without the shard key in the predicate — SELECT * FROM orders WHERE status='pending' — trigger scatter-gather the router sends the query to every shard in parallel, then merges, dedupes, and sorts the results itself. Cost scales with the number of shards.

How resharding works

Resharding splits shard -80 into -60 and 60-80 because it grew hot:

  1. Provision. Spin up the two new shards empty.
  2. Snapshot. Snapshot the source shard at a logical position — a binlog GTID for MySQL, a change-feed cursor for MongoDB.
  3. Bulk-copy. Copy rows whose hash falls in each new range to the matching destination.
  4. Catch up. Tail the binlog and apply ongoing writes to both destinations — Vitess VReplication, MongoDB chunk migration.
  5. Verify. Check row counts and checksums; throttle if replication lag grows.
  6. Cut over. Briefly stop writes — Vitess reports a few seconds of read-only — update the shard map, resume on the new shards.
  7. Retire. Drop or archive the old shard.

Figma's 2023 team avoided physical resharding as long as possible: they built logical "sharded views" on one still-unsharded Postgres instance, routed through their own DBProxy, and flipped reads/writes with a feature flag they could revert in seconds.

Common failure modes

✕

Celebrity hot key

One key — a viral post, a celebrity account — draws 100x the traffic of any other. The shard that owns it saturates while its siblings idle.

✕

Monotonic shard key on range sharding

Sharding events by timestamp puts every new write on the rightmost shard. Auto-increment IDs hit the same trap.

⚠

Low-cardinality shard key

Sharding by country_code when 70% of users are in the US. MongoDB creates at most one chunk per unique value, so you end up with one giant US chunk.

⚠

Cross-shard query storm

A feature change adds a query without the shard key in its predicate. Every request now scatters to all shards and tail latency explodes.

✕

Resharding lag spiral

Bulk copy can't keep up with the source shard's write rate, so the catch-up phase never finishes.

⚠

Shard-map cache staleness

Clients keep routing to the old owner after a split. Reads return phantom-empty results; writes hit a tablet that's already demoted.

✕

DynamoDB hot partition

A single partition key exceeds the hard 3,000 RCU / 1,000 WCU per-partition ceiling. Adaptive capacity and "split for heat" help, but with a delay.

⚠

Schema migration drift

A DDL succeeds on 7 of 8 shards and fails on the 8th. Queries hitting that column now fail for one slice of users.

Why it exists

A single machine has finite CPU, RAM, disk, and network. Once a workload crosses that ceiling, there are two paths: build a pricier single machine (vertical), or split the work across many machines (horizontal). Vertical scaling hits physics — the largest cloud VMs cap around a few TB of RAM — and a price curve where the top SKU costs more than 10x the median box. Horizontal scaling, which sharding is the stateful-storage form of, is the only path that keeps cost-per-unit roughly linear.

Sharding also buys two other things directly: a smaller blast radius (a failed shard takes down 1/N of users, not everyone) and geographic locality (a Frankfurt shard serves EU users at sub-20 ms latency a Virginia primary can't match).

Why it looks the way it does

"Pick the shard key up front, keep the routing function essentially fixed" is not the only possible design. Spanner-class engines instead do automatic range splitting: no user-chosen key, the system watches load and splits ranges itself. That approach never won for MySQL/Postgres-based sharding, for two reasons:

  • Automatic splitting needs the storage engine to expose stable, ordered ranges as a first-class primitive — Spanner's splits, CockroachDB's ranges. InnoDB and Postgres heap files don't expose that, so retrofitting means building an entirely new storage layer.
  • Co-locating related rows — a user and their orders on the same shard, for a cheap join — is far easier to reason about when the key is explicit and stable. The trade is one annoying up-front decision in exchange for predictable single-shard transactions and joins.

The same logic explains why consistent hashing with virtual nodes (Cassandra, Dynamo) beat plain modulo hashing: hash(k) % N moves (N-1)/N of the keys whenever N changes; consistent hashing moves only K/N. Jump consistent hash is more memory-efficient still, but only lets you remove the last bucket — fine for a stateless cache, unacceptable for storage where any specific node may need retiring.

Why it matters now

In 2026 the relevance is shifting, not fading. DIY application-level sharding (Flickr-style user buckets) is in retreat — too expensive operationally for most teams. But the concept is more common than ever, just hidden: every serverless database (DynamoDB, Cosmos DB, Aurora DSQL, Spanner, Turso) is sharded under the hood, and understanding the shard key is still the difference between a $200/month bill and a $20,000/month one. Vitess, Citus, and Spanner all shipped meaningful resharding and online-DDL improvements in 2024–2025, and Figma's 2023 write-up has become a reference architecture. Above mid-five-figure QPS or low-terabyte data, sharding is in your stack somewhere — the only question is whether you run it yourself or pay a vendor to hide it.

Worth checking on your own system

  • What fraction of your queries actually carry the shard key? Below ~95% will hurt under scatter-gather.
  • What's the real cardinality and access skew of your candidate key? Group and count before committing.
  • How does your system handle a node failure mid-resharding — a forced kill, not just a clean shutdown?
  • What's the real p50/p99 cost of a cross-shard 2PC commit in your environment, measured, not assumed?
  • For DynamoDB/Cosmos: what's your write distribution per partition key over a 5-minute window?
