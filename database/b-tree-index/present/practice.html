Practice — how it plays out for real

● ~12 min read ✎ best practices · anti-patterns · checklist

Where you'll meet it

Every OLTP backend leans on a small set of B-tree indexes that hold the whole system up: the primary key on users, the foreign key from orders to users, a composite that powers every listing page, a partial unique index that enforces "one active row per account." Pull any one of them and a 30 ms page load turns into a 4-second one.

SaaS OLTP schema

Primary keys, foreign keys, and the one composite index every listing endpoint depends on.

E-commerce / marketplace

What makes ORDER BY created_at DESC LIMIT 50 finish in single-digit milliseconds at 50M rows.

Multi-tenant analytics

The difference between a report that scans a hot table and one that hits a covering index and never touches the heap.

Hidden everywhere

Every UNIQUE constraint, every PRIMARY KEY, every FK validation in InnoDB. Most "the index is wrong" tickets trace back to column order or a predicate the planner can't use.

Best practices

1

Index foreign keys, but only the ones you actually filter or join on

Do

Add a B-tree on every FK that appears in a WHERE or JOIN, and on FKs the parent's deletes or updates cascade through.

Why

Postgres does not auto-index FKs the way MySQL does. A missing FK index turns every DELETE on the parent into a full scan on the child, and cascade locks can stall writes for seconds.

Avoid

Indexing every FK by reflex. One that's never queried just costs writes and storage.

2

Put the most selective column first — except when a range query says otherwise

Do

For WHERE tenant_id = ? AND status = 'open', index (tenant_id, status). For WHERE tenant_id = ? AND created_at > ?, still lead with the equality column, tenant_id, then the range column.

Why

The tree is physically sorted left to right. Equality on the leading column collapses the search to one contiguous run; a range after that is a single leaf walk. A range in the middle of a composite kills every column to its right.

Avoid

(created_at, tenant_id) for tenant-scoped queries — every tenant's rows scatter across the whole timeline.

3

Respect the leftmost-prefix rule or you're paying for an unused index

Do

For an index on (a, b, c), make sure real queries filter on a, on (a, b), or on (a, b, c).

Why

A query filtering only on b can't seek — b is only locally ordered inside each a bucket. The planner silently falls back to a scan, and idx_scan for that index sits at zero forever.

Avoid

Building one fat five-column index and assuming it covers every subset of those columns.

4

Don't wrap indexed columns in functions — build an expression index

Do

If you query WHERE lower(email) = $1, create CREATE INDEX ON users (lower(email)). Same idea for date_trunc('day', created_at).

Why

An index on email is sorted by email, not by lower(email). A function-wrapped column always triggers a full scan unless a matching expression index exists.

Avoid

Casting in the app to "match" the column type — implicit casts (e.g. WHERE int_col = '42') also defeat indexes in some drivers.

5

Use partial indexes when a predicate is always present and narrow

Do

Build CREATE INDEX ON orders (created_at) WHERE status = 'pending' if your hot query is "show pending orders by date."

Why

A partial index an index built over only the rows matching a WHERE clause can be 5–100× smaller than the full one and fits in cache. Especially strong for soft-delete (WHERE deleted_at IS NULL) and "one active row" uniqueness.

Avoid

A partial predicate that doesn't match the query verbatim — the planner won't use the index at all.

6

Skip indexes on low-cardinality columns; fold them into composites instead

Do

Instead of CREATE INDEX ON orders (status), build (status, created_at), or make the index partial on the rare value.

Why

A boolean or 3-value status column has tens of millions of duplicates. The planner correctly picks a full scan over 10M random heap fetches, so the standalone index is dead weight that still costs every write.

Avoid

Indexing is_active, is_deleted, gender, or country alone. They earn their place only as the trailing column of a composite, or inside a partial index's predicate.

7

Reach for INCLUDE when one query is hot and one extra column makes it index-only

Do

Build CREATE INDEX ON sales (customer_id, sold_at) INCLUDE (amount) if the hot query is SELECT amount FROM sales WHERE customer_id = ? AND sold_at > ?.

Why

The included column lives in the leaf without being part of the sort key, so writes don't reorder the tree. The plan flips from Index Scan plus heap fetch to an index-only scan a scan that answers the query from the index alone, skipping the row fetch — roughly halving the I/O.

Avoid

Stuffing every selected column into INCLUDE. Wide leaves lower fan-out and raise tree height — include 1–2 small columns, not 8.

8

Pick monotonic primary keys; if you need UUIDs, use v7 or ULID, not v4

Do

Default to bigint identity / bigserial. If you need a globally unique opaque ID, use UUIDv7, ULID, or a Snowflake-style ID — all time-ordered.

Why

UUIDv4 inserts land at random positions in the tree. Pages split everywhere and the index stabilizes around 60–70% full instead of 90%; benchmarks show 2–5× slower insert throughput and 5–10× more I/O per insert from the cascading splits. UUIDv7 keeps inserts at the right edge — the same write pattern as a plain sequence.

Avoid

Switching to UUIDv4 primary keys "for security" — they expose nothing v7 doesn't, and they wreck the write path.

9

Read EXPLAIN before you trust the index

Do

Run EXPLAIN (ANALYZE, BUFFERS) and learn the four shapes: Index Scan (fetch matching rows from the heap), Index Only Scan (the index covers everything — best case), Bitmap Index Scan + Bitmap Heap Scan (medium selectivity, often optimal at 0.5–5%), and Seq Scan (correct once over ~10% of rows match).

Why

Adding an index doesn't guarantee it's used. The planner decides from pg_statistic; stale ANALYZE or a mistuned random_page_cost makes it pick wrong.

Avoid

"I created the index, so the query must be fast now" — without ever checking the plan.

10

Treat index bloat as a real maintenance task

Do

Watch index size vs. table size with pgstattuple. Run REINDEX INDEX CONCURRENTLY or pg_repack once bloat passes ~30%. In InnoDB, use OPTIMIZE TABLE during a maintenance window.

Why

A long-running transaction blocks VACUUM; dead entries pile up; a 2 GB index becomes 6 GB; the working set stops fitting in shared_buffers; latencies climb 10×. Bloat is silent until it isn't.

Avoid

Plain REINDEX on a production table — it takes an exclusive lock. Always use CONCURRENTLY on Postgres 12+.

11

Match index direction when sorts are paginated

Do

For ORDER BY created_at DESC LIMIT 50, a plain ascending index is fine — Postgres can scan it backwards. For mixed directions like (a ASC, b DESC), build CREATE INDEX ON t (a ASC, b DESC) to match.

Why

Mixed-direction ordering is the one case a backward scan can't cover. Without a matching index the planner adds a Sort node, which spills to disk on large results and breaks keyset pagination paging by "give me rows after this cursor value" instead of by OFFSET.

Avoid

Designing the index without ever looking at the real ORDER BY clause.

12

Tune fillfactor on heavily-updated indexes; leave the default everywhere else

Do

Postgres defaults to fillfactor 90 for B-tree indexes. For a table with very frequent updates on indexed columns, lower it to 70–80 so HOT updates stay on-page and new entries fit without splitting.

Why

Lower fillfactor trades storage for fewer page splits and less bloat over time. Higher fillfactor (100, for append-only tables) packs leaves tighter and shrinks the index.

Avoid

Cargo-culting fillfactor 70 on every table — for append-only or read-mostly tables you're just wasting space.

Anti-patterns to recognize

✕

The "index everything" reflex

Every column gets its own index "just in case." Writes slow down as index count grows, the working set blows past RAM, and most of those indexes are never read. Index from observed queries, not speculation.

✕

Composite column order matches the schema, not the query

Columns get listed in the order they appear in the table — (created_at, tenant_id) — while queries filter WHERE tenant_id = ?. The index sits unused. Order columns by query shape, not table shape.

✕

Indexing a column a trigger rewrites

A BEFORE INSERT trigger reshapes the value at insert time, but the WHERE clause searches on the original input. A classic timezone or collation pitfall — index the post-trigger form.

✕

SELECT * over a covering index

The index covers six of seven columns; the seventh forces a heap fetch, and the plan silently degrades from Index Only Scan to Index Scan. Project explicit columns when relying on INCLUDE.

✕

Indexed boolean as the primary filter

WHERE is_active = true on a table where 95% of rows are active. The planner ignores the index. Either flip to a partial index on the rare value, or drop the index.

✕

Re-adding a redundant index

An index on (a, b) already serves queries filtering on a alone — a separate index on (a) is pure write-amplification.

✕

Trusting idx_scan > 0 as proof it's needed

Postgres counts a single use, ever, as a hit. Compare idx_scan against table writes and against other indexes over time — a single lifetime hit is not evidence.

Real-world usage patterns

Multi-tenant SaaS list views

~10K tenants, 500M total rows. Every list endpoint filters by tenant_id first, so the pattern is (tenant_id, sort_column) INCLUDE (2–3 hot columns) per dominant query shape. Lesson: in multi-tenant systems, tenant_id leads almost every useful index — skip it and one noisy tenant blows up cache for everyone else.

Keyset pagination on a feed

A feed at ~10K writes/sec uses WHERE (created_at, id) < (cursor_ts, cursor_id) ORDER BY created_at DESC, id DESC LIMIT 50 backed by (created_at DESC, id DESC). Lesson: OFFSET 10000 paging gets quadratically slower; keyset pagination plus a matching composite index stays flat.

Soft-delete with a partial unique index

An auth service enforces "one active email per user" while keeping deleted rows: CREATE UNIQUE INDEX ON users (email) WHERE deleted_at IS NULL. Lesson: partial unique indexes express constraints no trigger or app-side check does as cleanly.

Time-series append

An ingestion table at 50K inserts/sec keyed on a Snowflake ID. The clustered B+tree fills its rightmost leaf, splits cleanly to ~15/16 full, and stays dense at ~95%. Lesson: monotonic keys trigger storage-engine fast paths random keys never reach.

The covering-index rescue

A three-table reporting join timed out at 8 seconds. Adding (account_id, period) INCLUDE (revenue, cost) to the fact table flipped the plan to Index Only Scan; the query dropped to 40 ms. Lesson: covering indexes are the biggest lever for read-heavy queries stuck on an OLTP database.

Operational checklist

✓

Before you call it done

  • Stats freshness: is autovacuum running, and when did ANALYZE last touch the hot tables?
  • Plan verification: does every new or changed index have an EXPLAIN (ANALYZE, BUFFERS) attached to its PR, showing Index Scan or Index Only Scan, not Seq Scan?
  • Unused-index alert: is there a weekly job listing indexes with idx_scan = 0 over 30 days? Drop them — they're pure write-tax.
  • Bloat monitoring: is index size vs. live-tuple ratio tracked, with an alert past 2× expected size?
  • Lock-safe migrations: is every production CREATE INDEX and REINDEX run CONCURRENTLY?
  • PK choice review: new tables reviewed for bigint vs. UUID — and if UUID, is it v7 or ULID, not v4?
  • Cost ceiling: each new index adds ~10–20% write overhead. Past 10 indexes on a hot table, is that justified?
  • Onboarding: can a new engineer read pg_stat_user_indexes and an EXPLAIN ANALYZE plan on day one?
  • Backup-and-restore size: indexes can be 50–70% of total relation size, and restore time scales with them. Know the number.

How it evolves in a codebase

  1. One index per query. Engineers add a B-tree the first time something is slow, and the database happily obliges. By year two the hottest table has 8–12 indexes, half of them overlapping, and writes have visibly slowed.
  2. A painful migration. Usually one of three things forces it: switching primary-key strategy (UUIDv4 → v7/ULID, rewriting every secondary index), introducing partitioning (B-trees are local to each partition, which changes uniqueness semantics), or moving reports off the OLTP store entirely. The PK migration is the worst — it touches every foreign key in the schema.
  3. A small, repeatable workflow. Query patterns come from pg_stat_statements, indexes are designed from those patterns instead of guessed, and a quarterly review drops the unused ones. Indexes get treated as code — versioned, reviewed, tied to a specific query — not sprinkled on as a performance band-aid.
