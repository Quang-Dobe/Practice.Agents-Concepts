Detail — the deep dive

◑ ~11 min read ✎ What · Where · When · How · Why

What it is

A B-tree index is a self-balancing, on-disk, n-ary search tree where every node is sized to a disk block, every key is held in sorted order within its node, and every leaf sits at the same depth. Almost every mainstream relational database — PostgreSQL, MySQL/InnoDB, SQL Server, Oracle, SQLite — actually implements the B+tree variant of Bayer & McCreight's original 1972 design: internal pages carry only routing keys, no row data, and the leaves form a doubly-linked list for ordered traversal.

  • Core idea. Fat nodes, shaped like a disk block, keep the tree shallow so a lookup costs only a few page reads.
  • The "B". It stands for balanced, not binary. The formal rule: every node except the root holds between ⌈m/2⌉ and m children for some order m — the invariant that keeps the tree even-shaped under any mix of inserts and deletes, with no manual rebalancing.
  • Family. It belongs to the disk-friendly ordered-index family, alongside hash indexes, LSM-trees, bitmap indexes, and geometric indexes (R-tree, GiST, SP-GiST).

The core building blocks

Page (node)
A fixed-size on-disk block — 8 KB by default in Postgres and SQL Server, 16 KB in InnoDB, 4 KB by default in SQLite. One page = one node = one I/O.
Routing key + child pointer
An internal page stores [key₁ | ptr₁ | key₂ | ptr₂ | … ]. Keys partition the key space; pointers are page numbers of children.
Leaf entry
[key | row pointer] — a row's physical address (a TID in Postgres) or, in InnoDB's secondary indexes, the primary key.
High key / right link
Each page records the largest key it covers plus a pointer to its right sibling. This is the Lehman & Yao structure that lets readers traverse without locking.
Metapage
One fixed-location page at the start of the index file, pointing at the current root (the root can move when the tree grows taller).
Fan-out (branching factor)
Children per internal node — typically 100–500, depending on key width.

Within the ordered-index family, the B+tree beat its theoretical cousins — 2-3 trees, red-black trees, skip lists — for one reason: its shape is built around the block-device unit of I/O, not around minimizing comparisons.

Where it lives

A B-tree sits in the storage engine layer: below the SQL parser and query planner, above the buffer manager and OS page cache. Its pages live on disk in the same tablespace as the table and get pulled into the buffer pool one page at a time. For OLTP workloads almost all traffic is served from RAM — the root and upper internal levels are nearly always cached.

Where you'll actually run into one:

PostgreSQL

The default CREATE INDEX and every PRIMARY KEY / UNIQUE constraint.

MySQL InnoDB

The table itself is a clustered B+tree on the primary key; every secondary index is another B+tree pointing back by primary key.

SQLite

Every table is a B+tree keyed by rowid; every index is a separate B-tree.

SQL Server / Oracle

Same story: clustered plus non-clustered B-trees.

MongoDB (WiredTiger)

A B+tree storage engine underneath the document model.

etcd / BoltDB

Embedded key-value stores built on a single B+tree file.

Tooling you'll actually use:

  • Inspection: EXPLAIN (ANALYZE, BUFFERS) in Postgres, EXPLAIN FORMAT=JSON in MySQL, dm_db_index_physical_stats in SQL Server.
  • Low-level forensics: pg_buffercache and pageinspect in Postgres, Jeremy Cole's innodb_ruby visualizer for InnoDB.
  • Maintenance: REINDEX (Postgres), OPTIMIZE TABLE (MySQL), ALTER INDEX … REBUILD (SQL Server).
  • Bloat monitoring: pgstattuple, pg_repack, sys.dm_db_index_physical_stats.

When to use it

✓ Reach for it when

  • The column has high selectivity — an equality match returns under ~5% of rows.
  • You need range queries, ORDER BY, or BETWEEN.
  • You're enforcing uniqueness — it backs UNIQUE constraints for free.
  • The query uses a left-anchored LIKE 'foo%'.
  • The column is a foreign key used in joins.
  • You need a composite index over columns that share a leftmost prefix.

✕ Skip it when

  • Cardinality is tiny (a boolean) — the planner scans anyway.
  • The table is small enough that a full scan is already sub-millisecond.
  • The workload writes to the column heavily and rarely reads it — every insert pays split and log cost.
  • You only need substring search (LIKE '%foo%') — use a trigram/GIN index instead.
  • You need geometric, full-text, or vector similarity — use GiST, GIN, or an ANN index.

A little history

Bayer and McCreight described the B-tree in 1972 at Boeing, targeting disk-resident indexes where one seek cost milliseconds and an in-memory binary tree would have been catastrophically tall. The B+tree refinement (Knuth, mid-1970s) pushed all data to the leaves and linked them, tuned for the workload that actually dominates: range scans. The Lehman & Yao paper (1981) added right-links and high-keys so concurrent reads never need to lock — the exact variant Postgres still runs today.

How it works

Walk a single point lookup from the top:

  1. Start at the metapage. Jump to the current root.
  2. Descend internal pages. Binary-search the keys in each node to find the child whose range covers the search key, and follow that pointer.
  3. Reach a leaf. Binary-search the leaf for the exact key.
  4. Return. Hand back the matching row pointer(s). Total cost: O(logb N), where b is the fan-out.

Fan-out and height

For an 8 KB page with ~20-byte routing entries (an 8-byte bigint key plus a 6-byte pointer plus slot overhead), an internal node holds roughly 400 children. Expect these heights:

10,000,000,0004–5

A point lookup on a 100M-row table costs about 4 page reads — the top 2–3 are essentially always cached in RAM, so the disk-touching cost in steady state is one or two reads.

How a node splits on insert

Descend to the leaf that should hold the new key. If there's room, write it in sorted position and stop. If the leaf is full:

InnoDB special-cases monotonic inserts: if the last insert landed at the end of the page, only the new record goes to the right side, leaving the left page ~15/16 full instead of ~1/2. That's why auto-increment primary keys build dense indexes.

Delete is the mirror image: find the leaf, remove the entry. If occupancy falls below the ⌈m/2⌉ floor, redistribute with a sibling or merge two siblings and pull a key down from the parent. In practice Postgres avoids eager merging — it keeps half-empty pages around and reclaims them during VACUUM. InnoDB merges once occupancy drops below its MERGE_THRESHOLD, default 50%.

Why the leaves are linked, and how concurrent reads stay lock-free

A range scan WHERE x BETWEEN a AND b descends once to the leaf holding a, then walks next_leaf pointers until it passes b — no re-descending, no parent pointers, sequential I/O when the pages were allocated contiguously.

Postgres implements the Lehman & Yao scheme: a reader holds at most one page latch at a time, never two. If a concurrent split moves keys right while a reader is descending, the reader notices its key exceeds the page's high-key and follows the right link to catch up. Writers take page-level latches only at the leaf being changed. This is why B-tree reads scale linearly with cores.

Composite indexes and the leftmost-prefix rule

An index on (last_name, first_name, dob) is physically sorted by last_name first, then by first_name within each last_name, then by dob within each (last_name, first_name) pair. This is not a planner limitation — it's a direct consequence of the tree's physical sort order.

Query filters onCan the tree seek?
last_nameYes
last_name and first_nameYes
last_name and dobYes for last_name; dob is just a filter within that range
first_name aloneNo — only locally ordered inside each last_name bucket
dob aloneNo — same reason

Clustered vs. non-clustered, and covering indexes

  • Clustered index (InnoDB, SQL Server): the table is the B+tree. Leaves hold the full row. One per table; primary-key lookups need no second hop.
  • PostgreSQL has no true clustered index. The table is a heap; every index points into it by TID. CLUSTER rewrites the heap in index order once, but new inserts immediately start to scatter it again.
  • Secondary (non-clustered) index. The leaf holds (key, row pointer). Resolving the row costs a second I/O — a primary-key lookup in InnoDB, a heap fetch (potentially scattered) in Postgres.
  • Covering index one that includes every column the query needs, so the row-fetching I/O is skipped entirely. Postgres 11+ supports CREATE INDEX … INCLUDE (col); SQL Server has had the equivalent for two decades.

Common failure modes

⚠

Index ignored on low-selectivity predicates

The planner estimates over ~5–10% of rows match, so a sequential scan wins — random I/O for all those heap fetches costs more than streaming the whole table.

⚠

Stale statistics

ANALYZE is out of date, so the planner misjudges selectivity and picks the wrong plan.

✕

Index bloat

A long-running transaction holds back VACUUM; dead entries pile up, leaf pages fragment, and the index grows 2–10× its normal size. Fix: REINDEX CONCURRENTLY.

⚠

Right-edge contention on monotonic keys

Every insert hits the rightmost leaf, so heavy concurrency causes latch contention there. Mitigations: UUIDv7, hash partitioning, or just accept it.

✕

Page splits on random-key inserts (UUIDv4)

Inserts scatter across the whole tree, splitting half-full pages everywhere; the index settles around 50–70% full instead of ~90%.

⚠

Suffix predicates on composite indexes

The query filters only on the second or third column — the index is silently bypassed, per the leftmost-prefix rule above.

⚠

LIKE '%foo'

A leading wildcard kills the sort order — full index or table scan, no way around it.

✕

A function wraps the indexed column

WHERE lower(email) = … can't use a plain index on email — it needs a functional/expression index on lower(email).

Why it exists

The fundamental problem is the gap between random-access cost and sequential-access cost on block storage. A spinning-disk seek is ~10 ms; an SSD random read is ~100 μs; an in-memory access is ~100 ns. A binary tree of N keys is O(log₂ N) deep — for a billion keys, that's 30 hops. Thirty random page reads is 3 ms on SSD, 300 ms on spinning disk. A B+tree turns log₂ into logb with b ≈ 400, collapsing those 30 hops to 4. Fat nodes, sized to one I/O unit, exist purely to amortize the fixed cost of an I/O over hundreds of keys at once.

Why it looks the way it does

  • Why not a hash table on disk? Hash tables don't preserve order, so range scans and ORDER BY would need a full scan.
  • Why not a skip list, the usual in-memory alternative with similar asymptotics? Skip lists keep multiple forward pointers per node and have worse cache locality at block granularity — they suit RAM, not disk.
  • Why push row data to the leaves (B+ vs plain B)? A plain B-tree stores row data in every node, which inflates internal pages and tanks fan-out. Routing-only internals keep far more of the tree resident in cache.
  • Why doubly-link the leaves? So WHERE x > 100 ORDER BY x walks forward through leaves without paying O(log N) to redescend from the root at every step.
  • Why right-links (Lehman & Yao)? So a concurrent split never forces a reader to hold ancestor latches all the way down — it can step sideways instead and stay lock-free.

Why it matters now

It's 2026, and B-trees still index most of the world's transactional data. The constraint that created them hasn't gone away — RAM is still roughly 100× faster than storage per random access, even on NVMe. LSM-trees have taken over the write-heavy log and time-series niche (Cassandra, RocksDB), but for mixed read/write OLTP with secondary indexes and range queries, B+trees remain the default. Current research (FAST '22, transparent-compression SSDs) is actually closing the write-amplification gap with LSM-trees, not the reverse.
