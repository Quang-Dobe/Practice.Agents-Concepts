Overview

◔ ~3 min read ✎ intuition-first

Ask a database for WHERE user_id = 42 and the naive answer is: read every row and check. That works for a hundred rows. It dies at a hundred million.

ⓘ

In 30 seconds

A B-tree index is a separate on-disk structure: a tree of sorted keys with pointers back to the real rows. It turns a linear scan into a handful of hops. It's the default index in PostgreSQL, MySQL/InnoDB, SQL Server, Oracle, and SQLite — fast for exact matches, fast for ranges, and it stays even-shaped as the table grows. Almost every plain CREATE INDEX you've written built one of these.

The mental model

Picture a phone book, but a strange one. The first page isn't names — it's a short list of signposts: "A–F live in volume 1, G–M in volume 2, N–S in volume 3, T–Z in volume 4." You grab volume 2. Its first page is signposts again: "G–H in section 2a, I–J in 2b…" You keep descending.

  • After 3 or 4 hops you land on one page holding a few hundred names, sorted.
  • You scan that single page and you're done.

That's a B-tree. Each node is a "page" holding many sorted keys — often hundreds — plus pointers to child pages. The branching factor, called fan-out how many children one node points to, is deliberately huge. High fan-out keeps the tree shallow: a tree only 3 or 4 levels deep can index hundreds of millions of rows. Hundreds of millions of rows, three or four disk reads — that's the whole trick.

Two properties matter, and both fall straight out of the shape:

  • Sorted. A range query like created_at BETWEEN '2026-01-01' AND '2026-02-01' finds the start key once, then walks sideways along the leaves. No re-descending from the top.
  • Balanced. Every leaf sits at the same depth, so lookups cost the same whether the key is the smallest, the largest, or in the middle.

What it is not

⚠

Common mix-ups

  • Not a hash index. Hash indexes beat B-trees on raw equality but can't do range scans, ORDER BY, or prefix matches.
  • Not a bitmap index. Bitmap indexes shine on low-selectivity columns (gender, status) in warehouses, not on point lookups.
  • Not a full-text index. A B-tree matches whole keys or left-anchored prefixes, not "documents containing the word bicycle."
  • Not the table itself. The index stores keys and row pointers; the row data usually lives elsewhere (the clustered index is the one exception — more in Detail).
  • Not literally called "B-tree" in most engines. It's almost always a B+tree a close cousin: internal nodes hold only routing keys, and all row data sits in the linked leaves, a close cousin covered in the deep dive.

When to reach for it — and when not to

✓ Reach for it when

  • Looking up rows by a primary key or foreign key.
  • Filtering on a high-selectivity column (email, order_id, created_at).
  • Running range queries: BETWEEN, <, >, ORDER BY on the indexed column.
  • Doing left-anchored LIKE 'foo%' searches.
  • Enforcing uniqueness — a UNIQUE constraint is backed by a B-tree.

✕ Skip it when

  • The column has very few distinct values (a boolean like is_active) — it barely narrows anything.
  • The table is small enough that a full scan already takes a few milliseconds.
  • The column is write-heavy and rarely read — maintenance cost outweighs the read gain.
  • You need substring search (LIKE '%foo%') — a leading wildcard defeats the sort order.
  • You need geospatial or vector similarity search — reach for GiST, R-tree, or an ANN index instead.

Key vocabulary

Node / page
One unit of the tree, sized to a disk block — often 8 KB or 16 KB.
Root, internal, leaf
The top, middle, and bottom layers of the tree.
Fan-out
How many children a node can have. High fan-out keeps the tree shallow.
Key
The indexed value — e.g. an email string.
Pointer / row ID
What a leaf entry points to: the physical address of the row.
Selectivity
The fraction of rows a query keeps. Higher is better for index use.
Clustered vs. secondary index
Whether the table itself is stored in index order, or the index sits alongside it.
Balanced
Every leaf is at the same depth. The "B" stands for balanced, not binary.
