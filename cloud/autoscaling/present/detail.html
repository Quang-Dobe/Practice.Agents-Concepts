Detail — the deep dive

◑ ~11 min read ✎ What · Where · When · How · Why

What it is

Autoscaling is a closed-loop feedback controller for compute capacity.

  • It resizes a workload either by replica count (horizontal) or by per-replica resources (vertical).
  • Its goal: keep an observed metric near a setpoint, inside operator-set bounds [min, max].
  • In control terms: the plant is your fleet, the sensor is a metrics pipeline, and the actuator is a provisioning API (launch VM, create pod, patch resources).
  • The system has a lot of dead time the delay between asking for capacity and that capacity serving traffic: capacity requested now is useful only after boot, image pull, and readiness.
  • Scope: cloud VM groups and Kubernetes workloads, not storage auto-growth.

The core building blocks

Scaling target
The thing being resized: an AWS Auto Scaling Group, Azure Virtual Machine Scale Set, GCP Managed Instance Group, or a Kubernetes Deployment / StatefulSet via its /scale subresource.
Metric source
Where the signal comes from: CloudWatch, Azure Monitor, Cloud Monitoring, or the Kubernetes aggregated APIs metrics.k8s.io (usually metrics-server), custom.metrics.k8s.io, and external.metrics.k8s.io.
Policy
The control law. Target tracking (hold metric at X), step/threshold rules (if metric > X add N), scheduled (cron-like), or predictive (forecast-driven).
Bounds
min, max, and the current desired count. Bounds are the only hard guarantee you get. Everything else is best effort.
Damping
Cooldowns, warmup periods, stabilization windows, and tolerance bands. They stop oscillation in a system with lag.
Lifecycle hooks
ASG lifecycle hooks, Kubernetes preStop, terminationGracePeriodSeconds, PodDisruptionBudgets. They make adding and removing capacity safe.
Layered controllers (Kubernetes)
Pod-level (HPA, VPA, KEDA) and node-level (Cluster Autoscaler, Karpenter) controllers that cooperate only through the scheduler's "Pending pod" signal.

Its neighbours

Autoscaling sits in the elasticity / capacity management family:

  • Capacity planning: offline and human-driven.
  • Load balancing: spreads load across the capacity you already have.
  • Admission control / load shedding: rejects work when capacity runs out.
  • Serverless (AWS Lambda, Cloud Run, Azure Container Apps): autoscaling with the knobs hidden. Per-request or per-concurrency scaling, including to zero.
  • Rate limiting (closest sibling): caps demand instead of growing supply.
  • Queue-based load leveling (closest sibling): absorbs bursts in a buffer so the consumer fleet can scale more slowly.

Where it lives

Autoscaling is an infrastructure control-plane concern. It sits outside the request path: no request ever passes through an autoscaler.

On VMs

A regional cloud-provider service that calls the compute API.

Kubernetes HPA

Runs inside kube-controller-manager.

VPA and KEDA

Run as in-cluster operators.

Cluster Autoscaler / Karpenter

In-cluster controllers that call the cloud provider's node APIs.

Your app takes part only by exposing honest metrics, starting fast, having correct readiness probes, and shutting down gracefully.

Where you typically meet it

  • EC2 Auto Scaling groups behind an Application Load Balancer, with target tracking on ASGAverageCPUUtilization or ALBRequestCountPerTarget.
  • Kubernetes HPA on stateless API Deployments. The most common autoscaler in container platforms.
  • KEDA on queue consumers (SQS, Kafka, RabbitMQ, Azure Service Bus). Azure Container Apps uses KEDA scale rules as its native scaling model.
  • Karpenter on EKS (including EKS Auto Mode) and on AKS through Node Auto Provisioning.
  • Knative / Cloud Run for request-concurrency scaling with scale-to-zero.
  • AWS Application Auto Scaling for non-EC2 targets: ECS services, DynamoDB capacity, Lambda provisioned concurrency.

When to use it

◆

A little history

  • Before elastic clouds: capacity was a buying problem. You bought servers for forecast peak plus headroom, and they sat idle most of the day.
  • May 17, 2009: AWS ships Auto Scaling, CloudWatch, and Elastic Load Balancing together. The bundle is the lesson: autoscaling needs a sensor (metrics) and a way to make new instances useful at once (a load balancer), or it is pointless.
  • Kubernetes HPA arrived early in the project's life. autoscaling/v2 went GA in 1.23, adding multiple metrics and the behavior block.
  • April 2021: AWS warm pools. May 2021: native predictive scaling. Both fight dead time.
  • November 2021: Karpenter appears; 1.0 in August 2024. It was built because node-group-based Cluster Autoscaler was slow and rigid about instance types.

✓ Reach for it when

  • Peak-to-trough load ratio is large (roughly 2x or more) and recurs, so fixed peak provisioning wastes real money.
  • The workload is stateless or its state lives elsewhere, so a new replica is useful the moment it passes readiness.
  • Replica startup is well below the time load takes to ramp, so capacity arrives before the spike is over.
  • You have a metric that tracks demand roughly linearly per replica: requests per target, queue lag per consumer, concurrency.
  • Workers drain a queue, where backlog and latency tolerance make reactive scaling safe.

✕ Skip it when

  • The workload is stateful with expensive rebalancing (database primaries, Kafka brokers, Elasticsearch data nodes). Each scale event is a data migration.
  • Load is flat. A fixed fleet plus reserved or committed-use pricing is cheaper and has fewer moving parts.
  • Spikes are shorter than provisioning dead time. Use over-provisioning, warm pools, or scheduled scaling instead.
  • The bottleneck is a shared downstream (DB connections, a licensed API). Scaling callers amplifies contention.
  • Each replica carries a large fixed overhead (JVM warmup, model load onto a GPU). Scale churn costs more than it saves unless the cycles are long.

How it works

1 · The Kubernetes HPA control loop

Every 15 s (--horizontal-pod-autoscaler-sync-period) the controller runs these steps (docs):

  1. Fetch per-pod metrics. CPU utilization is measured relative to the container's resource request. No request means no CPU-based scaling.
  2. Exclude unready pods. Skip pods that are not ready, still initializing (--horizontal-pod-autoscaler-cpu-initialization-period, default 5 min; --horizontal-pod-autoscaler-initial-readiness-delay, default 30 s), or missing metrics.
  3. Compute the proportional answer. desiredReplicas = ceil(currentReplicas × currentMetric / targetMetric). Example: 4 replicas at 90% CPU with a 60% target gives ceil(4 × 1.5) = 6.
  4. Check the tolerance band. Skip the change if the ratio sits inside the tolerance band a dead zone around the target where small wobbles are ignored (default 0.1, so 0.9–1.1). Per-HPA tolerance in behavior.scaleUp/scaleDown: alpha in 1.33, beta in 1.35, GA in 1.37.
  5. Re-run conservatively for excluded pods. Scaling up: missing pods count as 0% usage. Scaling down: they count as 100%. This dampens the move in either direction.
  6. Take the max across metrics. With several metrics, compute one recommendation per metric and take the maximum.
  7. Apply behavior. Default scale-up: 0 s window, allows the larger of +100% or +4 pods per 15 s. Default scale-down: a 300 s stabilization window a look-back period; the HPA uses the highest recommendation seen in it (the highest recommendation in the last 5 min), and up to −100% per 15 s.
  8. Clamp and write. Clamp to [minReplicas, maxReplicas] and write the result to /scale.

2 · Pod scaling and node scaling stack up

HPA only changes a number. The scheduler then tries to place the new pods. If they stay Pending for lack of room, the node layer reacts:

  • Cluster Autoscaler defaults (FAQ): scans every 10 s; a node becomes a scale-down candidate below 50% requested utilization for 10 min; there is a 10 min delay after a scale-up before any scale-down.
  • Karpenter drops node groups for direct instance selection and consolidation replacing or deleting under-used nodes to pack pods tighter. Its disruption budgets default to 10% of nodes at a time.

3 · VM autoscalers

AWS EC2 Auto Scaling
  • Target tracking creates two CloudWatch alarms for you.
  • Commonly reported: 3 consecutive 1-minute breaches to scale out, 15 to scale in. Same up-fast/down-slow asymmetry.
  • New instances stay out of the group metric until the default instance warmup expires.
  • Legacy default cooldown = 300 s, applies only to simple scaling policies (docs).
GCP Managed Instance Groups
  • 60 s default initialization period.
  • 10 min scale-in stabilization period that sizes for the peak load in that window.
Azure Monitor autoscale
  • Threshold rules with per-rule cooldowns (5 min in Microsoft's examples).
  • Before a scale-in, checks whether it would immediately trigger a scale-out.

4 · Event-driven and scale-to-zero

  • KEDA polls each trigger every 30 s by default. It handles the 0↔1 step itself and hands 1↔N to an HPA it generates. Its cooldownPeriod (default 300 s) applies only to the final drop to zero.
  • Core HPA scale-to-zero (HPAScaleToZero, object/external metrics only): alpha from 1.16, beta and on by default in 1.37.
  • Knative KPA scales on in-flight concurrency (target 100 per pod by default). It averages over a 60 s stable window and switches to a 6 s panic window a short look-back used to react fast to a sudden burst when the short-window load hits 200% of target.

5 · Vertical

  • VPA's recommender builds histograms of observed usage and proposes requests.
  • Historically the updater evicted pods to apply new values.
  • In-place pod resize went GA in Kubernetes 1.35.
  • VPA's InPlaceOrRecreate mode patches /resize first and evicts only when the node lacks room.

Key trade-offs

ChoiceYou gainYou give up
Horizontal over verticalNo restart, fault isolation, effectively unbounded ceilingRequires statelessness. Per-replica fixed overhead multiplies
Utilization metric (CPU) over demand metric (RPS, queue lag)Zero setup, always availableIndirect. CPU saturates late for I/O-bound services and lies under throttling
Low target (e.g. 50%) over high (e.g. 80%)Headroom that absorbs the spike while new capacity bootsYou pay for roughly 30% more idle capacity all the time
Fast scale-up, slow scale-in (the default everywhere)Under-provisioning, which is the expensive error, is shortPaying for capacity for 5–15 min after the peak

Common failure modes

⚠

Flapping

Replica count swings every few minutes. Cause: scale-in raises per-replica load past the scale-out threshold. The band between thresholds, or the stabilization window, is too narrow.

✕

HPA does nothing

<unknown>/60% in kubectl get hpa. Cause: containers lack CPU requests, or metrics-server / the adapter is not installed.

✕

Spike outruns capacity

5xx errors for minutes, then recovery once the incident is over. Cause: the spike is shorter than boot time plus metric lag. No headroom or warm pool.

⚠

Pods Pending forever

  • maxReplicas above what node max or cloud quota allows.
  • Instance-type stockout.
  • Node selectors that no node group satisfies.
✕

Dropped requests on scale-in

Cause: no preStop delay or connection draining, so the pod dies before the LB stops routing to it. Or terminationGracePeriodSeconds (30 s default) is shorter than in-flight work.

✕

Scale-out makes it worse

Cause: the shared database hits its connection ceiling. Every new replica opens another pool.

⚠

Nodes never scale in

Cause: pods with emptyDir/local storage, strict PDBs, or safe-to-evict: "false" pin the node. Cluster Autoscaler skips them.

⚠

HPA and VPA fight

Cause: both act on CPU for the same workload. VPA raises requests, utilization drops, HPA scales in, and the cycle repeats.

✕

Retry storm feedback

Cause: client retries inflate RPS during an outage. The autoscaler scales on self-made load and runs out of max.

Why it exists

Two first-principles costs pull in opposite directions:

  • Cost of idle capacity: linear in time × provisioned units.
  • Cost of too little capacity: latency, errors, lost revenue. These grow non-linearly once queues form.
  • Queueing theory makes the second one steep: as utilization nears 100%, wait time grows without bound. You cannot simply run hot.
  • Static provisioning fixes one point on that curve for all hours. Autoscaling moves the operating point with demand.

That turns capacity from a capital-planning decision into a runtime control problem. Elastic, per-second-billed cloud infrastructure made it possible.

Why it looks the way it does

  • Proportional target tracking, not threshold steps or full PID.
    • Step rules ("if CPU > 70% add 2") need hand-tuned step sizes per fleet size and oscillate easily.
    • A full PID controller has derivative terms that amplify noisy metrics, and integral windup during long boot dead time.
    • The proportional formula ceil(n × actual/target) scales the correction with fleet size. The tolerance band plus stabilization windows replace the damping a PID would give.

    This is an engineering reading of the design, not a quote from the Kubernetes or AWS docs.

  • Asymmetric damping. Scale-up reacts at once; scale-in waits 5–15 minutes. The two errors are not equal: an under-provisioned minute gives user-visible errors, an over-provisioned minute costs cents. Scale-in also destroys state: in-flight requests, caches, warmed JITs.
  • Separate pod and node controllers, not one global optimizer. Kubernetes splits "how many pods" from "how many machines" and links them only through the Pending state.
    • One joint controller could react faster and pack better, but it would couple every workload policy to every cloud's instance catalogue.
    • The split lets HPA, KEDA, and VPA evolve apart from Cluster Autoscaler or Karpenter, at the cost of stacked latency.
    • Karpenter narrows the gap by provisioning straight from pending-pod requirements instead of fixed node-group templates.

Why it matters now

  • In 2026 the cost pressure has moved to accelerated compute. An idle GPU node costs many times more per hour than an idle general-purpose VM, and LLM inference load is bursty.
  • Kubernetes responded within the last year: in-place pod resize GA (1.35, December 2025); per-HPA tolerance GA and HPA scale-to-zero beta-by-default (both 1.37, August 2026).
  • Karpenter-style group-less provisioning is now the managed default on EKS Auto Mode and AKS Node Auto Provisioning.
  • The field is changing, not stable. CPU-based HPA is giving way to demand signals (queue depth, concurrency, tokens in flight) and to combined predictive-plus-reactive policies.
ⓘ

Open questions to verify in practice

  • What is the real end-to-end scale-out latency for my workload, from load step to new pod Ready and receiving traffic, with and without a new node? Which stage dominates?
  • Does my metric scale linearly with replicas? Double the load at fixed replicas and check whether actual/target predicts the needed count.
  • On scale-in, are any requests dropped? Load-test while forcing scale-down and inspect LB 5xx and client errors.
  • What does the default 300 s scale-down window cost per day for my traffic shape, and is a per-HPA tolerance or shorter window safe?
  • Which pods pin nodes and block Cluster Autoscaler / Karpenter scale-in (emptyDir, PDBs, annotations)?
  • If a dependency fails and clients retry, does the autoscaler run straight to maxReplicas, and what does that cost?
