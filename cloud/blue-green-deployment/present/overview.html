Overview

◔ ~4 min read ✎ intuition-first

Shipping a new version usually risks two things: users seeing downtime, and you not being able to undo it fast if it breaks. Blue-green deployment fixes both by keeping two full copies of your app running side by side.

ⓘ

In 30 seconds

You run two identical environments — blue (live) and green (standby). You deploy the new build to green, smoke-test it while no real user touches it, then point your router at green. If green misbehaves, you flip back to blue. The cutover the moment traffic shifts from one environment to the other is the only risky-looking step, and by then the real risk is already behind you.

The mental model

Picture a stage with two identical sets behind a curtain:

  • The audience — your users — is watching set A. That's blue.
  • Backstage, the crew dresses set B for the next act. That's green.
  • When B is ready, the curtain shifts and the audience is now looking at B.
  • Set A is still standing, fully dressed, lights on. If a prop falls on B mid-scene, you just shift the curtain back.

Nobody rebuilds a set in front of a live audience. In cloud terms, the curtain is a load balancer with two target groups, a DNS record, or a weighted route. The two sets are two parallel fleets running on the same data, differing only in application version.

After the flip, in-flight requests on blue still need to finish. That's drain letting requests already in progress on the old side complete before it's shut down — the router stops sending new traffic to blue but waits for the old connections to close naturally.

What it is not

⚠

Common mix-ups

  • Not a rolling update. Rolling replaces instances in place, one batch at a time — there's no second full environment and no instant rollback target.
  • Not a canary release. Canary sends a small slice of real users to the new version to measure it; blue-green is all-or-nothing on the cutover.
  • Not feature flags. Flags toggle behavior inside one running build; blue-green swaps the build itself.
  • Not a staging environment. Staging is a permanently separate, lower-fidelity world. In blue-green, both environments are production.

When to reach for it — and when not to

✓ Reach for it when

  • You need near-zero downtime and users notice every hiccup — payments, checkout, public APIs.
  • You want rollback measured in seconds, not "rebuild and redeploy."
  • Your release has a risky binary change that a flag can't easily reverse.
  • Your platform makes a second environment cheap and short-lived — ECS, Kubernetes, Lambda aliases, a weighted-target-group load balancer.

✕ Skip it when

  • Your release makes a stateful, schema-breaking change to a shared database — both colors talk to the same data.
  • Doubling capacity is genuinely too expensive — large stateful clusters, GPU fleets.
  • You need to validate the change against a slice of real users first — that's canary's job.
  • Long-lived sticky sessions, websockets, or in-memory state make the cutover messy without extra work.

Key vocabulary

Blue / Green
The two environments. Names are arbitrary — some teams say A/B or current/next.
Cutover
The moment traffic shifts from one color to the other.
Target group
In AWS ALB terms, the pool of instances behind a listener. Blue and green are two target groups.
Weighted routing
Splitting traffic by percentage across target groups; blue-green typically uses 100/0 then 0/100.
Drain / connection draining
Letting in-flight requests on the old color finish before shutting it down.
Rollback
Flipping the switch back to the previous color when something goes wrong.
Cutover window
The short period both environments serve real traffic during the flip.
Backward-compatible migration
A schema or contract change that lets old and new code coexist — the unspoken prerequisite for clean blue-green on a shared database.
