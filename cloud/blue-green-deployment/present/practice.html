Practice — how it plays out for real

● ~10 min read ✎ best practices · anti-patterns · checklist

Where you'll meet it

In a typical SaaS backend, blue-green is the strategy a platform team picks for the customer-facing API tier — the one whose error budget is most visible. It's wired into CI/CD as a two-step pipeline: deploy to the idle color runs automatically; cutover is a gated button a release manager clicks.

SaaS API tier

The user-data store stays single-tenant and shared; only the stateless compute fleet doubles up during a release.

E-commerce checkout

A 30-second outage is a measurable revenue dent. Catalog and search often use rolling or canary; checkout uses blue-green because the rollback button matters more than the bake time.

Opinionated platforms

Lambda aliases, ECS native blue/green, Cloud Run revisions, Azure slots, Heroku preboot. Nobody there calls it "blue-green" — they call it "the deploy."

Best practices

1

Gate the cutover on real health, not on HTTP 200

Do

Make the readiness check exercise the DB pool, the cache, the message broker, and at least one downstream call. Run a synthetic transaction a scripted real action — e.g. log in, fetch profile, write an event — run against the idle color to prove it actually works against the idle color via a separate test listener before the switch.

Why

A /healthz that returns 200 unconditionally lies. The classic failure is green coming up with an empty DB connection pool or a stale secret — the cutover happens, the pool fills with dead connections, and the whole fleet 5xxs in unison.

Avoid

A health endpoint that only confirms the process is running.

2

Warm caches and JITs before flipping

Do

Replay a few minutes of mirrored traffic, hit the top-N hot endpoints, or run a startup probe that primes the in-process cache and triggers JIT compilation. Only then mark the targets healthy.

Why

A cold green fleet hitting full production traffic spikes p99, blows out downstream connection pools, and looks like a regression that "only happens after deploy." It's not the new code — it's the cold start.

Avoid

Treating "container started" as "ready to serve."

3

Size the drain window to your actual p99, not the default

Do

Measure the slowest legitimate request — file uploads, report exports, long polls. Set the ALB deregistration delay, Kubernetes terminationGracePeriodSeconds, and your app's SIGTERM handler all to the same value, roughly 20% above that p99.

Why

The 300-second AWS default fits a typical API but not a 10-minute CSV export. Mismatched timeouts give you 502s at the edge while the user watches a progress bar.

Avoid

Leaving the default and hoping. Worse: setting terminationGracePeriodSeconds longer than the drain window — the pod dies before the load balancer stops sending to it.

4

Practice expand-contract for every schema change

Do

Split each schema migration into three deploys: expand (add the new column or table, dual-write, both code versions tolerate it), migrate (backfill and switch reads), contract (drop the old column in a later release).

Why

Blue and green share one database. A DROP COLUMN or a NOT NULL rename run at cutover time crashes whichever color reads the old shape — usually blue, mid-drain, in front of real users.

Avoid

Bundling the migration into the same deploy as the code that needs it.

5

Treat feature flags as the complement, not the substitute

Do

Ship risky business logic dark behind a flag and use blue-green for the binary swap. Flip the flag separately, after the cutover settles.

Why

Blue-green gives you instant infrastructure rollback; flags give you instant behavior rollback without redeploying. You want both.

Avoid

Using blue-green as the only rollback knob for behavior changes — you end up reverting an entire release to undo one bad copy change.

6

Push session and stateful work out of the app tier

Do

Sessions in Redis or a JWT, idempotency keys in DynamoDB or Postgres, WebSocket fan-out via a broker. Background workers should use leader election a lock (a Redis lock or a Kubernetes Lease) that makes sure only one running instance does a piece of work so only one color runs the cron.

Why

Sticky-cookie sessions collapse the moment blue's tasks deregister; in-process WebSocket state evaporates; both colors will happily run the nightly billing job twice.

Avoid

Sticky sessions as the primary state mechanism. They're a useful fallback for routing affinity, not a session store.

7

Keep the old color warm only as long as rollback is cheap

Do

Default bake window: 1 hour for high-traffic APIs, up to 24 hours for low-traffic critical paths. Automate teardown — don't leave it to a human ticket.

Why

After about an hour, "rollback to blue" stops being safe anyway — new writes have landed in the shared database and old code may not understand them. You're paying double infra for an option you can't actually use.

Avoid

Leaving the idle color running indefinitely "just in case."

8

Build observability that survives the flip

Do

Tag every metric, log, and trace span with deploy_color and version. Build one dashboard with both colors side by side: request rate, 5xx rate, p50/p95/p99, downstream error rate. Alert on post-cutover green versus pre-cutover blue baseline, not a fixed threshold.

Why

Without the split view, a regression on green looks like a global degradation and on-call rolls back things it shouldn't. With it, "green's p99 is 2x blue's at the same RPS" is a one-glance diagnosis.

Avoid

Alerts that fire on every cutover just because traffic momentarily routes to two backends. They get muted — and then real incidents get muted with them.

9

Automate the rollback button, then test it on a Wednesday

Do

A single command re-flips the listener and rewinds the bake timer. Run a quarterly game-day: deploy a known-broken build, verify rollback completes in under 60 seconds.

Why

Untested rollback paths bit-rot. An IAM permission expires, a script references a renamed target group, the new engineer doesn't know the command — you find out during a real incident.

Avoid

"We can roll back if needed" as a verbal claim with no runbook.

10

Mind the singletons: crons, consumers, migrations

Do

Pin background workers to one color. For Kafka consumers, use one group.id and let the broker partition — don't run two groups in parallel.

Why

During the bake window both colors are alive. A naive setup double-processes events, double-sends emails, or races on a shared lock — the customer sees two charge confirmations.

Avoid

Assuming the load balancer is the only traffic source. Crons and message consumers don't go through it.

Anti-patterns to recognize

✕

Schema migration inside the cutover

Running a migration as a pre-cutover hook. It breaks blue mid-drain because blue's binary doesn't know the new shape. Use expand-contract and run migrations between deploys, not during them.

✕

"Deploy once and forget" blue-green

The bake window runs forever because nobody wired up teardown. The bill doubles silently and the idle fleet drifts out of date until rollback is no longer possible. Automate the scale-to-zero.

✕

Blue-green on a stateful service

Running it in front of a database, a stateful stream-processing app, or a per-node in-memory game server. The "second environment" can't share state cheaply, so the cutover loses sessions or duplicates work. Use rolling with surge for stateful tiers.

✕

Blue-green as a substitute for canary on a high-risk change

Atomic 100% cutover means a bad release hits every user at once. For ML model rollouts, pricing changes, or auth-flow rewrites, run a 1%/5%/25% canary first. Blue-green is for the swap, not for the validation.

✕

DNS-based switch with a 300-second TTL

Route 53 weighted records are fine for region failover, terrible for app deploys — client resolvers cache aggressively and the cutover smears over minutes. Use an L7 load balancer with a real atomic listener change.

✕

Health check that calls itself

/healthz returns 200 from a handler that does nothing. The deploy passes every gate and then breaks on the first real request. The probe must touch the dependencies the request path touches.

✕

Sticky sessions doing the heavy lifting

Affinity cookies are a routing optimization, not a state store. The instant blue's targets deregister, the affinity is meaningless and the session is gone.

Real-world usage patterns

Payments API — ECS Fargate, expand-contract

A fintech runs card-auth as a 12-task ECS service with native blue/green, a 1-hour bake, and a rollback alarm on 5xx > 0.5% sustained 60s. Lesson: the hardest bug wasn't the cutover — it was a background idempotency-key cleaner running on both colors during bake, deleting keys the other color needed. Fixed with a leader-election lock keyed on the active task set.

B2B SaaS — Argo Rollouts with previewService

A Kubernetes shop gates cutover on SLO metrics and auto-rolls-back on burn-rate alerts within the bake window. Lesson: the synthetic tests had to authenticate as a real tenant, so the test tenant's data shape ended up constraining what the team could ship.

Public API — AWS Lambda weighted aliases

A mobile backend shifts traffic 10% → 50% → 100% over 10 minutes via RoutingConfig — technically canary, but the old version stays attached for instant rollback. Lesson: cold-start latency spiked p99 even at 10% traffic; the fix was provisioned concurrency before shifting any traffic.

Internal tool — Azure App Service slot swap

Slot swap is one click; rollback is the same click in reverse. Lesson: settings marked "deployment slot setting" stay with the slot during swap — learned the hard way when a connection-string swap pointed production at staging for about 3 minutes.

Operational checklist

✓

Before you call it done

  • Is deploy_color and version on every metric, log, and trace? Can you draw a dashboard that overlays blue vs. green for RPS, p99, and 5xx?
  • Does your readiness probe touch the DB, cache, and at least one downstream — not just return 200?
  • Is the drain timeout at least 1.2x your measured p99? Is the app's SIGTERM handler aware of it?
  • Is every schema change in the last 90 days expand-contract? Could the previous release run cleanly against today's schema?
  • Is there a single rollback command, owned by on-call, tested last quarter on a deliberately broken deploy?
  • Do background workers, crons, and message consumers have a defined owner color during bake? Is the leader-election mechanism real?
  • Is the idle color torn down automatically after the bake window, or does it linger — and what does that linger cost per month?
  • Does your alert config suppress flap during the cutover window without suppressing real regressions on green?

How this topic typically evolves in a codebase

  1. Rolling by default. Teams start with rolling deploys on a single fleet — the out-of-the-box option in ECS, Kubernetes, and most PaaS.
  2. First outage, hand-rolled fix. Blue-green arrives after a deploy causes an outage a fast rollback would have prevented — often a year or two in. The first version is hand-rolled: a second target group, a script that flips the listener.
  3. The schema wake-up call. The database becomes too entangled for naive deploys. Teams discover they were only getting away with breaking migrations because rolling deploys were slow enough that old code drained out before the new schema mattered. Every PR with a migration now needs an expand-contract review — a culture change that takes months to land.
  4. Method per service tier. Mature teams layer canary on top of blue-green for the highest-risk changes (auth, billing, ML inference), keep blue-green for routine releases, and use rolling for stateless edge tiers where the cost saving matters. The choice moves from someone's head into the service catalog.
