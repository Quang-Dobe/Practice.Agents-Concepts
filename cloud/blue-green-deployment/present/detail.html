Detail — the deep dive

◑ ~10 min read ✎ What · Where · When · How · Why

What it is

Blue-green deployment is a release strategy where two production-grade environments — blue and green — run in parallel, each on one version of the app. A routing primitive atomically shifts 100% of user traffic from one to the other.

  • Deploy and cutover are separate steps. The new build installs and warms up on the idle pool first — the cutover itself is only a pointer flip.
  • Rollback is symmetric. The environment that was just live stays warm for a set window, so rolling back is a second pointer flip, not a redeploy.
  • Family. It's the simplest member of the all-or-nothing release family, alongside recreate — as opposed to progressive delivery (canary, rolling, traffic-shaping).

The core building blocks

Two homogeneous fleets
Same instance type, network, and dependencies — they differ only in application version.
Traffic-switch primitive
The atomic decision point: ALB listener rules, Route 53 weighted records, a Kubernetes Service selector, an Istio VirtualService, Cloud Run traffic tags.
Health gate
Readiness probes, smoke tests, or synthetic checks the idle environment must pass before the switch is allowed.
Drain mechanism
Connection draining that lets in-flight requests on the old fleet finish after the switch.
Shared stateful tier
Usually one database, one cache, one broker — both colors read and write the same data, which is exactly what makes schema changes the hard part.

In the wider deployment strategies family it sits next to rolling, canary, recreate, A/B, and shadow:

  • Rolling replaces instances in place, batch by batch — no second environment, no instant rollback.
  • Canary sends a slice of real traffic to the new version to measure it — progressive, not atomic.
  • Recreate stops blue, then starts green — downtime, no parallel state.
  • Blue-green optimizes for rollback speed at the cost of double infrastructure during the cutover window.

Where it lives

The switch itself lives at the edge / L7 routing layer: an ALB listener, ingress controller, service mesh, API gateway, or DNS. The two fleets sit one layer below, in compute — EC2 auto-scaling group, ECS service, Kubernetes Deployment, Lambda alias, container revision.

The stateful tier — RDS, DynamoDB, Kafka, Redis — is almost always shared between the two colors. Duplicating it turns a blue-green release into a full disaster-recovery exercise.

Where you'll find it built in

AWS ECS

Native ECS blue/green (GA July 2025) and the older CodeDeploy controller both ship it as a first-class deployment type.

AWS Lambda

AWS::Lambda::Alias with RoutingConfig shifts a fixed percentage between two versions; SAM/CodeDeploy wraps this as blue-green.

Kubernetes / Argo Rollouts

The blueGreen strategy uses activeService and previewService fields.

Google Cloud Run

Every deploy creates an immutable revision; traffic tags route between them.

Heroku

preboot is essentially a managed blue-green for dynos.

Azure App Service

Deployment slots with the "swap" operation are the same pattern.

On-prem, IIS's Application Request Routing (ARR) does the same job in front of two app pools.

Ecosystem and tooling

  • Traffic switching: AWS ALB/NLB, Route 53 weighted records, Envoy, Istio, NGINX ingress, HAProxy, Cloudflare load balancers.
  • Orchestration: AWS CodeDeploy, Argo Rollouts, Flagger, Spinnaker, Harness, Octopus Deploy.
  • Schema migrations during cutover: Liquibase, Flyway, Bytebase, Reshape (Postgres), gh-ost / pt-online-schema-change (MySQL).
  • Session and state handling: Redis or DynamoDB as an out-of-process session store so neither color owns the session; sticky cookies only as a fallback.

When to use it

The term was popularized by Daniel Terhorst-North and cemented by Jez Humble and David Farley in Continuous Delivery (2010). Before it, "deployment" meant a Friday-night maintenance window: stop the service, copy the build, run migrations, hope. Cheap virtualization — EC2 from 2006, then containers — made a second full environment for an hour affordable, and blue-green followed naturally.

✓ Reach for it when

  • Your release is a single atomic binary or contract change that's hard to feature-flag.
  • Rollback time matters in seconds, not minutes — payments, checkout, public APIs, regulated systems.
  • Your app tier is stateless or near-stateless — sessions live in Redis, not in memory.
  • Your platform makes a second environment cheap and short-lived — ECS, Lambda, Cloud Run, Argo Rollouts.
  • Your schema changes can be staged through expand-contract splitting a migration into add-and-dual-write, then backfill-and-switch, then drop-the-old-column, across separate deploys so both colors run safely against the same database.

✕ Skip it when

  • The release ships a non-backward-compatible schema migration — a DROP COLUMN is fatal the moment green's migration runs.
  • You need to validate the change against real users before full rollout — that's canary's job.
  • The system holds large in-memory state per node — long-lived websockets, in-process caches, game-server matches.
  • Doubling infrastructure is prohibitive — large stateful clusters, GPU fleets, on-prem capacity you can't conjure on demand.
  • You have no automated smoke tests for the idle environment — without them, "healthy" is a guess.

How it works

Walk one release through a typical ALB + ECS setup:

  1. Steady state. The listener forwards 100% of traffic to tg-blue. tg-green exists with zero registered targets.
  2. Provision green. The controller starts a new task set on the new build. Tasks register into tg-green and pass ALB health checks — typically 5 consecutive 200s on /healthz.
  3. Test traffic (optional). A separate test listener lets a deployer or a CI job hit green directly, without touching production traffic.
  4. Bake. Both versions run; only blue serves users. Pre-cutover hooks can run synthetic checks here.
  5. Cutover. The controller flips the listener — or the Kubernetes Service selector, or the Cloud Run traffic split. From the next request on, production traffic goes to green.
  6. Drain. Old tasks enter DRAINING. The ALB stops sending new connections but waits out the deregistration delay for in-flight requests to finish.
  7. Keep blue warm. Blue stays live for a bake time the window the just-replaced color is kept running so rollback is one pointer flip instead of a redeploy — a configurable duration (CodeDeploy capped it at 2880 minutes, i.e. 48 hours).
  8. Terminate or repurpose. Once bake time passes with no alarms, blue scales to zero or becomes the next deploy's green.

Argo Rollouts runs the same dance with two Kubernetes Service objects: activeService and previewService. Both point at the old ReplicaSet at rest; on promotion, activeService's selector is patched to the new hash, and shortly after, previewService follows.

Common failure modes

✕

Schema breakage on cutover

A migration drops a column blue still uses. Blue starts throwing 500s during drain.

⚠

In-flight long requests dropped

The drain timeout is shorter than the slowest real request — file uploads, long-poll, streaming — so the edge returns 502s.

✕

Sticky session collapse

ALB sticky cookies pinned users to blue's tasks; after drain they're rebalanced and lose session state unless it lives in Redis or DynamoDB.

⚠

DNS-based switch with stale resolvers

A Route 53 weighted-record cutover stretches over the full TTL; some clients keep hitting blue for minutes after teardown.

⚠

Connection pools cached on green

Green came up before DB credentials rotated. Its pool is full of dead connections; /healthz passes but real traffic 500s.

⚠

Asymmetric warm caches

Blue's in-process caches were hot; green starts cold and the cutover spikes p99 latency and downstream load.

✕

Singleton background jobs running on both colors

A nightly cron or a Kafka consumer with a fixed group.id — both environments race or double-process. Needs explicit leader election or worker-pinning.

Why it exists

It answers two tensions: deployment risk vs. release velocity, and rollback cost vs. uptime. Before cloud elasticity, both were resolved with maintenance windows. Once infrastructure became rentable by the minute, the cheapest way to make a release reversible in seconds turned out to be simple: keep the previous version running.

Why it looks the way it does

The obvious alternative is rolling deployment: replace instances one at a time, no second environment. Rolling is cheaper — it reuses existing capacity — but it loses on two fronts:

  • Old and new versions coexist for the entire rollout, not just a short drain window, so backward compatibility has to hold longer and across more version pairs.
  • Rollback is also a rolling process — recovery time grows with fleet size.

Blue-green compresses that coexistence window to seconds or minutes and makes rollback a single API call, at the price of doubling infrastructure for that window. When a bad five minutes costs more than a few extra instance-hours, the trade is an easy call.

The other obvious alternative is canary: send a small slice of real traffic to the new version and measure it. Canary costs less than full blue-green and adds a real safety sample, but it needs per-request traffic splitting, automated metric analysis, and the discipline to actually pause and inspect results. Blue-green is what you reach for when you want the rollback guarantee without that complexity.

Why it matters now

As of 2026, the pattern is moving from "DIY with CodeDeploy" to a first-class platform primitive. AWS shipped native ECS blue/green in July 2025, removing the CodeDeploy hop. Cloud Run revisions and Argo Rollouts made it routine in serverless and Kubernetes respectively. The interesting frontier is no longer the cutover mechanic — that's solved — it's the database tier: expand-contract migrations, online schema-change tools, and dual-write strategies are where most blue-green incidents now start.

Worth checking in your own setup

  • Does your drain timeout actually cover your real p99 request duration?
  • Are all your schema migrations expand-contract, so the previous binary still runs cleanly against the post-migration schema?
  • Where does session state live — would a user mid-flow notice the cutover?
  • Do your background workers, crons, and event consumers behave correctly with both colors running? Who holds the lease?
  • Does your health check exercise the same code paths as production traffic, or just return 200 unconditionally?
