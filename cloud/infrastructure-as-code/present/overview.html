Overview

◔ ~4 min read ✎ intuition-first

Clicking through the AWS or Azure portal to create a VM, a load balancer and a firewall rule works once. It does not work the fifth time, in the third region, for the second engineer, at 3 a.m.

ⓘ

In 30 seconds

You write a file that says "these things should exist, configured this way." A tool reads that file, compares it to what actually exists in your cloud account, and makes reality match. The file goes through pull requests, code review and CI like any other code. The payoff: spinning up an identical staging environment stops being a two-day archaeology project and becomes one command.

The mental model

Think of the difference between a recipe and a food order.

  • A recipe is imperative. "Create the VPC, then the subnet, then attach the gateway, then launch the instance." Perfect the first time. Run it a second time and you get two VPCs, or an error — a recipe assumes you start with an empty kitchen.
  • A food order is declarative. "A table set for six, with three plates of pasta." The kitchen walks over, sees four plates already on the table, removes one, adds two chairs. Give the same order again and nothing happens, because the table already matches.

That "nothing happens the second time" property is idempotency running it twice produces the same result as running it once, and it is the whole reason IaC scales.

To pull this off, the tool needs a memory of what it put there — a state file the tool's record mapping each config address to the real cloud resource it created. State is how Terraform knows the web-01 instance in your config is the same instance as i-0abc123 in AWS. When someone changes that instance by hand in the console, config and reality diverge; that gap is drift real infrastructure no longer matching the config, usually from manual edits, and the tool's plan step is what surfaces it.

◆

The model in one line

config = what you want · cloud = what exists · state = the mapping between them · plan = the diff.

What it is not

⚠

Common mix-ups

  • Not configuration management. Ansible, Chef and Puppet configure software inside machines. IaC provisions the machines themselves. They overlap but solve different halves.
  • Not a deployment pipeline. CI/CD ships your application code. IaC ships the platform it runs on. They usually run in the same pipeline, in that order.
  • Not containers. A Dockerfile describes one image. IaC describes the cluster, network and IAM that image needs.
  • Not just "scripts in Git." A bash script full of az cli calls is automation, not IaC — it has no state, no plan, no idempotency.

When to reach for it — and when not to

✓ Reach for it when

  • You need staging to actually match production, not approximately match it.
  • More than one person changes infrastructure, and you want review and an audit trail.
  • You build the same stack per customer, per region, or per environment.
  • Disaster recovery must be a rebuild, not a restore-from-memory.

✕ Skip it when

  • It's a one-off experiment you'll delete this afternoon — the console is faster.
  • You're in a genuine production outage — fix it by hand, then reconcile the config afterward.
  • You're on a fully managed platform (Vercel, Heroku) where there's barely any infrastructure to describe.

Key vocabulary

Declarative
You describe the end state, not the steps.
Idempotent
Running it twice produces the same result as running it once.
State
The tool's record mapping your config to real cloud resources.
Plan / diff
A dry run showing what would change before it changes.
Apply
Executing the plan.
Drift
Real infrastructure no longer matching the config, usually from manual edits.
Provider
The plugin that translates config into AWS/Azure/GCP API calls.
Module
A reusable, parameterised bundle of resources.
Immutable infrastructure
Replace resources instead of mutating them in place.
