Detail — the deep dive

◑ ~10 min read ✎ What · Where · When · How · Why

What it is

CDN edge caching places HTTP reverse-proxy caches inside the points of presence (POPs) of a globally distributed network. Responses from an origin server are stored under a deterministic cache key the identifier — usually URL plus selected headers — used to look up a stored response and re-served to later requests whose key matches, for as long as the freshness rules allow. Those rules come straight from HTTP's own cache semantics (RFC 9111, plus the stale-content extensions in RFC 5861).

The core building blocks

POP (Point of Presence)
A physical site with one or more cache servers (Varnish, ATS, nginx, or a vendor's own) terminating TLS and answering user requests.
Cache object
The stored response — headers plus body — indexed by cache key, with metadata: insertion time, TTL, surrogate keys, vary axes.
Cache key
The lookup tuple. Default: scheme + host + path (+ query). Customizable to include selected headers, cookies, device class.
Vary axes
Extra dimensions the cache must split on, declared by the origin's Vary header (e.g. Vary: Accept-Encoding).
Freshness lifetime
How long an object may be served without revalidation: s-maxage → max-age → Expires → heuristic, in that order.
Tier
Edge POP, regional shield, or origin shield. Each tier coalesces misses from the tier below.
Purge / invalidation channel
An out-of-band API that evicts or marks-stale objects by URL, surrogate key, or wildcard.

Edge caching is a specialization of HTTP reverse proxying (Varnish, Squid, nginx in proxy mode), set apart by global distribution and an anycast routing layer that maps each user to the nearest POP. Its siblings:

  • Browser caching — private, per-user.
  • Application caches (Redis, Memcached) — shared, but confined to one datacenter.
  • Edge compute (Workers, Lambda@Edge) — runs code, not just bytes.

A CDN vendor typically bundles all four — caching, routing, TLS, and compute — into one product.

Where it lives

An edge cache sits between the user's TCP stack and your origin's load balancer — the first piece of your infrastructure a request touches (after the user's ISP and the anycast network routing that sends a request to the nearest of many servers advertising the same address network), and the last piece it touches on the way out. It operates at L7: it parses HTTP, decides on headers, and re-emits responses.

Where you typically encounter it

Cloudflare

Full reverse proxy with Workers-integrated cache; default for many sites.

Tight AWS integration, policy-driven cache keys.

Akamai

PaaS-bundled options wired into their own deploy pipelines.

Ecosystem you'll meet alongside it:

  • Open-source cache engines for on-prem/self-hosted setups: Varnish (used by Fastly), Apache Traffic Server (historically Yahoo/Akamai), nginx, HAProxy.
  • Config / IaC: per-vendor Terraform providers, Cloudflare Wrangler, Fastly VCL and Compute@Edge.
  • Observability: per-vendor log streams (Cloudflare Logpush, Fastly Real-Time Analytics, CloudFront logs) and X-Cache: HIT/MISS debug headers.
  • Specs worth knowing: RFC 9111 (HTTP caching), RFC 5861 (stale extensions), the Edge Architecture Specification (ESI), RFC 8246 (immutable).

When to use it

✓ Reach for it when

  • You serve any static asset (JS/CSS/images/video/fonts) to more than one region.
  • Origin RPS for a hot path exceeds what a single instance handles comfortably, and responses are cacheable for at least seconds.
  • You need to absorb spikes — launches, virality, mild DDoS — without scaling origin.
  • You serve large files where origin egress would be expensive; CDN transit is usually far cheaper than your cloud bill.
  • You need TLS termination, HTTP/3, or Brotli at every region without operating it yourself.

✕ Skip it when

  • Responses are fully personalized per request with no shared shape (raw GraphQL for an authenticated dashboard).
  • Strong read-after-write consistency is mandatory at sub-second scale (live order book, checkout inventory).
  • Traffic is low and geographically concentrated near a nearby origin — the cache never warms up.
  • Compliance forbids data leaving certain jurisdictions and the CDN can't guarantee residency.

A little history

Akamai launched in 1999 to solve a concrete problem: the 1998 World Cup site collapsed under load, and one datacenter couldn't feed a global audience without unacceptable round-trip time. Before CDNs, the workaround was DNS-based mirroring — manually replicated FTP/HTTP servers per region. CDNs automated that, added consistent invalidation, and later absorbed TLS termination, DDoS scrubbing, and edge compute. The shift from plain object caching to full-stack edge platforms accelerated after ~2017 with Cloudflare Workers.

How it works

Walk a single request through a modern POP:

  1. Route. Anycast sends the user's TCP SYN to the closest POP by BGP path, terminates TLS, and parses the HTTP request.
  2. Compute the key. Default: (scheme, host, path), plus whatever the vendor's cache policy adds — sorted query params, selected headers, device class.
  3. Look up. If present and fresh (age < freshness lifetime), return immediately with X-Cache: HIT.
  4. Stale handling. If present but stale: serve it now and refresh in the background if stale-while-revalidate serve the stale copy immediately while a background fetch refreshes it is set; serve stale only on error if stale-if-error is set; otherwise send a conditional request to origin.
  5. Miss + coalesce. If absent, forward to the next tier — a regional shield in tiered setups, otherwise origin. Concurrent misses for the same key are coalesced collapsing many concurrent requests for the same cold object into one origin fetch: one fetch goes upstream, the rest wait on it. Cloudflare, Fastly, CloudFront, and Vercel all implement this.
  6. Storability check. Parse the origin response and decide whether it's storable, using Cache-Control (public vs. private, no-store, s-maxage, and vendor-specific Set-Cookie heuristics).
  7. Write. Store the object on disk/RAM, index by cache key, tag it with any Surrogate-Key headers, and send the response to the user.
  8. Invalidate later. Purge events arrive over a separate channel and either delete the object (hard purge) or flip a stale flag (soft purge).

Cache-key construction

The default key is narrow on purpose — every extra dimension multiplies the cache footprint and shrinks the hit ratio.

  • Query strings. Tracking params (utm_*, fbclid, gclid) explode the key space if included. Most vendors offer "ignore query string" or "include only these" modes; Cloudflare's Query String Sort collapses ?a=1&b=2 and ?b=2&a=1 into one key.
  • Headers. Including raw User-Agent is almost always a mistake — thousands of variants. Use a normalized class instead (CF-Device-Type: mobile/tablet/desktop).
  • Cookies. The classic foot-gun: Vary: Cookie plus a per-user session ID gives one cache entry per user — the same as no cache. Strip session cookies before lookup, or key only on specific named cookies (e.g. theme=dark).
  • Vary header. Tells the downstream cache to split on a request header. Vary: Accept-Encoding is essential (separate gzip vs. br bodies); Vary: * means "don't cache."

TTL governance

Freshness is decided by precedence: s-maxage (shared caches only) > max-age > Expires > heuristic (typically 10% of Last-Modified age). Useful directives:

  • Cache-Control: public, max-age=60, s-maxage=3600 — browsers cache 1 min, CDN caches 1 hour. Standard for HTML-with-personalization.
  • stale-while-revalidate=600 — keep serving for 10 min past TTL while a background fetch refreshes.
  • stale-if-error=86400 — survive a 24-hour origin outage on cached paths.
  • immutable (RFC 8246) — for fingerprinted assets; tells browsers not to revalidate on reload.
  • Surrogate-Control — a TTL the CDN sees but the browser ignores, stripped at the edge.

Origin overrides ("page rules", "cache rules") can force a TTL regardless of what the origin sent — useful when you don't control the origin (S3, a third-party API) but want longer edge retention.

Invalidation

Three escalating mechanisms:

  1. URL purge. Invalidate one exact key. Cheap, surgical — but misses variants from Vary or query strings.
  2. Tag / surrogate-key purge. The origin attaches Surrogate-Key: product-42 category-shoes; one later API call purges everything tagged product-42. Fastly pioneered this pattern; Cloudflare's equivalent is Cache-Tag (Enterprise).
  3. Full purge / wildcard. Nukes everything. Use sparingly — it triggers a stampede on the next wave of traffic.

A hard purge deletes the object immediately, so the next request is a guaranteed MISS. A soft purge marks it stale instead, keeping it eligible for stale-while-revalidate and stale-if-error — prefer soft purge in production; it spreads origin load and tolerates origin downtime. The most reliable "invalidation" is not invalidating at all: ship assets as /static/app.4f2a1b.js and change the filename on every build. The old key ages out; the new key is a fresh miss followed by long-lived hits — the only safe way to pair Cache-Control: max-age=31536000, immutable with iterative development.

Tiered caching and request coalescing

Without tiering, every POP that misses goes straight to origin — N POPs producing N origin fetches for the same cold object. Tiered caching inserts a smaller set of upper-tier POPs between edges and origin (user → edge POP → regional shield → upper tier → origin). Cloudflare's Smart Tiered Cache auto-picks the tier closest to origin; Regional Tiered Cache adds a hub layer; CloudFront calls its variant Origin Shield; Bunny's Perma-Cache goes further and replicates objects to permanent regional storage so origin is contacted at most once. The cost is a small extra hop on MISS for a major drop in origin RPS.

When a popular object's TTL expires and 10,000 requests arrive at once, a naive cache sends 10,000 fetches to origin. Request coalescing holds back all but one, lets that one fill the cache, and serves the rest from the now-fresh object. Every major CDN implements this per-POP; tiered caches extend it across POPs through the shared upper tier — the combination is what makes a 30-second TTL on a viral resource safe.

Dynamic-content acceleration

  • ESI (Edge Side Includes). The origin returns a page skeleton with <esi:include src="/header"/> tags; the edge fetches and assembles fragments, each with its own TTL — cache the static 90% at 1 hour while re-fetching the personalized 10% every request. Supported by Akamai, Fastly, Varnish, LiteSpeed; not by Cloudflare's default cache.
  • Micro-caching. TTLs of 1–10 seconds on otherwise "uncacheable" pages. Under load a 5-second TTL still collapses thousands of requests into one origin fetch; under no load the staleness is invisible. Originally an nginx pattern for WordPress, now standard for news sites.
  • Edge functions with custom cache logic. Cloudflare Workers' Cache API and CloudFront Functions compute a personalized cache key (country + plan tier) and serve from cache for the slice of users who share it.

Common failure modes

✕

Cache poisoning via unkeyed input

Origin reflects an unkeyed header (e.g. X-Forwarded-Host) into the response; one attacker request pollutes the entry for everyone. Fix: include reflected inputs in the key, or strip them.

✕

Vary: Cookie with session IDs

Collapses hit ratio to ~0%. Fix: strip session cookies before lookup, or use a custom cache key.

✕

Set-Cookie on a cached response

Many CDNs refuse to cache responses with Set-Cookie; others cache it and leak the cookie to other users. Always strip it on cacheable paths.

⚠

Stampede after a full purge

Flushing everything causes a synchronized MISS storm. Fix: soft purge, or warm via crawl.

⚠

TTL drift between browser and edge

max-age shared between both leads to browsers holding old assets long after an edge purge. Fix: split via s-maxage, or use fingerprinted URLs.

⚠

Heuristic caching of headerless responses

Without Cache-Control or Expires, some caches assign a heuristic TTL and cache things you never intended. Fix: always send explicit headers.

⚠

Query-string explosion from tracking params

UTM and fbclid params create unique keys per link variant. Fix: strip or sort query strings at the edge.

Why it exists

Latency is bounded by physics — roughly 1 ms per 100 km one-way over fiber, plus switching. A request from Sydney to Virginia is ~160 ms round-trip at minimum, before TCP handshakes, TLS, or any origin processing. Edge caching attacks this two ways: it moves the response close to the user, eliminating most of that round trip, and it removes the origin from the critical path entirely for cacheable content. The same mechanism doubles as an economic optimization (origin egress is expensive, CDN egress is cheap) and as resilience (origin can be down for hours while cached paths keep serving).

Why it looks the way it does

The obvious alternative is replicated origins — full app servers and databases in every region (active-active multi-region). Teams build that, but it forces solving distributed consistency for write paths, which is expensive in engineering time and infrastructure. Edge caching deliberately punts on writes:

  • It caches only idempotent GETs.
  • It accepts bounded staleness.
  • It lets the origin remain the single source of truth.

That asymmetry — cache reads, centralize writes — is why it scales so cheaply: caches don't need a consensus protocol. The design also leans on HTTP's existing cache semantics rather than inventing new ones, which is why most of the configuration you write is just Cache-Control headers your origin already understood.

Why it matters now

In 2026, edge caching is table stakes — every major framework (Next.js, Remix, SvelteKit, Astro) emits Cache-Control headers automatically and assumes a CDN sits in front. The frontier has shifted: edge platforms increasingly blur the line between cache and compute (Cloudflare Workers KV, Vercel Data Cache, Fastly Compute), and ML inference is being pushed to the edge for latency. Understanding the cache primitives precisely is what lets you reason about those products instead of treating them as magic.
