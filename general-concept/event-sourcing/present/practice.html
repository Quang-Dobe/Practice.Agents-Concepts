Practice — how it plays out for real

● ~10 min read ✎ best practices · anti-patterns · checklist

Where you'll meet it

In a typical fintech back-end, event sourcing is the persistence layer behind whatever owns money movement — wallet, ledger, payouts, settlement. Everything else (notifications, statements, fraud, reporting) lives downstream as a projection off that one log. In e-commerce and logistics, it shows up on the order or shipment aggregate: the thing with a long lifecycle and many outside actors. In claims, policy, and health records, it's the thing compliance eventually forces on you if you don't pick it on day one.

Fintech ledger

Wallet, payouts, settlement. "What did the balance look like at 14:02?" is answered by replay until timestamp, not a forensic SQL hunt.

Order / shipment workflow

A long-lived aggregate mutated asynchronously by warehouses, carriers, and support — the order is a story, not a row.

Claims, policy, EHR

Anywhere "who knew what, when" is legally load-bearing, you end up with an append-only log — designed for, or bolted on.

Everywhere else — a red flag

Admin panels, settings, CMS. If event sourcing shows up here, someone has overreached.

Best practices

1

Pick the aggregates that justify the cost, not the service

Do

Event-source the 1–3 aggregates where history is the business — Order, Wallet, Policy. Keep User, Settings, ProductCatalog as boring CRUD in the same service.

Why

The complexity tax — projections, eventual consistency, schema evolution — compounds per aggregate. Spending it on a UserPreferences aggregate pays nothing back and slows every feature.

Avoid

"We're an event-sourced shop" — making every entity a stream just because the team adopted the pattern.

2

Name events as past-tense business facts, not state diffs

Do

Emit OrderShipped, PaymentCaptured, AddressCorrected. The name should make sense to a domain expert with no code context.

Why

Generic events like OrderUpdated { fields } are CRUD in disguise — they carry no intent, so projections can't react meaningfully and the history reads like a diff log.

Avoid

EntityCreated, EntityUpdated, EntityDeleted. If your event names look like HTTP verbs, you've audited CRUD, not sourced events.

3

Decide event granularity around invariants and consumers

Do

Use one event per business decision. If shipping requires picking a carrier, allocating stock, and printing a label, pick one OrderShipped event or three based on which consumer needs to react to which step.

Why

Too fine, and every command becomes a 10-event burst that forces projections to reassemble state. Too coarse, and you can't add a new consumer without re-deriving from payloads.

Avoid

Splitting events to mirror UI form fields. The form is not the domain.

4

Make every projection and integration handler idempotent

Do

Store the last processed global position per projection in the same transaction as the update. Use upserts keyed on event id for side effects.

Why

Subscriptions are at-least-once. A pod restart mid-batch redelivers the last events. Without idempotency, you double-charge cards or double-send emails — and only find out from customers.

Avoid

Trusting "we haven't seen a duplicate yet." The next deploy will give you one.

5

Treat snapshots as a cache, never a source of truth

Do

Snapshot on a measurable trigger — say, every 200 events, or when warm-load p95 exceeds 50ms. Version the snapshot schema. Be able to delete every snapshot and have the system still work.

Why

A snapshot written by yesterday's aggregate code, replayed against today's invariants, produces silently wrong state. If snapshots are load-bearing, an aggregate refactor becomes a data migration.

Avoid

Snapshotting by default from day one. Most aggregates never get long enough to need it.

6

Pick a schema-evolution strategy before your second deploy

Do

Default to additive changes. Add upcasters when a shape changes. Reserve copy-and-transform for last-resort renames. Chain upcasters — V1 → V2 → V3, never V1 → V3 directly.

Why

Events are forever. Six months in, you'll have 50 million events across three event versions in the wild, and "just run a migration" stops being an option.

Avoid

Mutating old events in place. The moment you do this you've lost the one property the whole pattern is built on.

7

Plan for GDPR / "right to be forgotten" before accepting PII

Do

Either keep PII out of the event entirely — store a customerId and look up the name from a deletable side-table, the forgettable payload keeping personal data out of events, referenced only by id from a table you can actually delete from pattern — or encrypt PII per-subject with a key you can shred. Decide which, per aggregate, in design review.

Why

Once an email or address is sprayed across 8 streams and 40,000 events, a single deletion request becomes an engineering project. Note: EU regulators have argued encrypted personal data is still personal data, so crypto-shredding is defensible practice, not a guaranteed legal shield — talk to your DPO.

Avoid

Putting full customer profiles into event payloads "because it makes projections easier."

8

Project asynchronously, monitor lag, but design the UX for it

Do

Default to async projections. Expose projection lag, in events and seconds, as a first-class metric. Where a user expects to see their own change immediately, return the new state from the command handler or use an optimistic UI update.

Why

Eventual consistency is fine for analytics, terrible for "I just placed an order and the order list is empty." The lag is rarely the problem — the surprise is.

Avoid

Forcing inline projections everywhere to dodge the UX problem. You lose the scale-out story and recreate distributed-transaction pain.

9

Choose the store that matches your operational reality

Do

For .NET teams already on Postgres, Marten is the boring-and-correct default — same database, inline projections available, no new ops surface. For polyglot orgs or very high write throughput on long streams, KurrentDB earns its keep with built-in subscriptions and cluster semantics.

Why

A dedicated event store you don't operate well is worse than a Postgres you already operate well. The bottleneck in practice is the team's ability to debug at 3 a.m., not the store's max appends per second.

Avoid

Using Kafka as the event store. Kafka is transport with retention; it has no per-aggregate optimistic concurrency and no readStream(streamId) primitive. You'll reinvent both, badly.

10

Version your projections by name and own their rebuild

Do

Name projection tables with a version suffix (orders_read_v3). To change one, deploy v4 alongside v3, rebuild v4 from position 0, cut reads over, drop v3.

Why

Mutating a live projection schema in place means your read model briefly disagrees with your events — and "briefly" tends to mean "until someone notices in production."

Avoid

Reusing the same projection name across breaking changes. There's no good way to tell partially-rebuilt data from fully-rebuilt data after the fact.

11

Measure cold rebuild time of your biggest projection, on real hardware

Do

Run it. Write the number down. Re-measure quarterly. Parallelize by stream-id partition once it climbs past your deploy-window tolerance.

Why

Teams discover their rebuild takes 14 hours during the incident that requires the rebuild. That is the worst possible time to find out.

Avoid

Estimating rebuild time from event count alone — projection cost per event varies by two orders of magnitude.

Anti-patterns to recognize

✕

CRUD-in-disguise events

Events named XUpdated with a full state payload. The log carries no semantics, so nothing downstream can do anything useful with it. Rename to business facts and re-derive payloads from intent.

✕

Event-sourcing the whole service

Every entity gets a stream "for consistency." The complexity tax bankrupts feature velocity — keep event sourcing scoped to the aggregates whose history is the product.

✕

No versioning plan

The first event-schema change ships as a breaking edit to the existing event type. Old events deserialize wrong forever. Introduce versioned types and upcasters before the second schema change, not the tenth.

✕

Eager inline projections everywhere

Every command transactionally updates six read models. Writes get slow and brittle, and coupling returns through the back door. Push everything except read-your-write critical views to async subscriptions.

✕

Fat events

Embedding the full customer record, product, and address into every event "so projections don't need joins." Schema evolution becomes immovable and PII is everywhere — carry ids, denormalize in the projection instead.

✕

Snapshots as truth

A snapshot gets hand-edited to fix a bug. Now events and state disagree silently, forever. Snapshots must be rebuildable from events, full stop.

✕

Replay cliff

No checkpointing, no partitioned projection workers, no idea how long a rebuild takes. The day you need a rebuild is the day you discover it takes 11 hours. Measure and parallelize before then.

✕

Broker-as-store

A Kafka topic with 7-day retention treated as the source of truth. After day 8, history is gone. The event store and the broker are different jobs — run both.

Real-world usage patterns

Fintech ledger, ~500 TPS

A wallet service per user, each wallet a stream, events like FundsCredited, HoldPlaced, HoldReleased. Balance and statements are projections; nightly reconciliation replays the day against a sealed prior snapshot. Lesson: storing the running balance inside the event sounds redundant but pinpoints the first event where a reconciliation drift began.

Retail order workflow, multi-region

Order is event-sourced; everything else is CRUD. Events drive shipping, billing, fraud, and email as independent subscriptions. Checkout uses optimistic UI to mask a 200–800ms projection lag. Lesson: a team that tried to make the order list strongly consistent ended up with a distributed transaction across two databases, then rolled back to async-plus-optimistic-UI six months later.

Insurance claims, decade-long retention

Every claim is a stream that may stay open for years. Snapshots fire every 50 events. PII lives in a separate vault keyed by claimant id; events carry only the id. Lesson: a "new" actuarial report was satisfied by replaying history since 2018 — no warehouse migration, no ETL, just replay from 0.

Multiplayer game state

Each match is a stream; events are player actions; the server replays to reconcile clients. Streams are deleted wholesale 30 days after match end. Lesson: short-lived streams flip several defaults — no snapshots needed, GDPR is easy (delete the stream), but hot-stream concurrency is brutal, so the aggregate boundary is "match," not "player."

Operational checklist

✓

Before you call it done

  • Monitoring: per-projection lag (events and seconds behind), append latency p99, optimistic-concurrency-conflict rate per stream, subscription checkpoint age.
  • Failure handling: is there a runbook for "projection X is corrupt — rebuild it," executed in staging this quarter?
  • Idempotency: every subscription handler tested with a deliberately replayed event batch.
  • Schema evolution: versioning convention documented, at least one upcaster shipped, an integration test that loads streams with every historical event version.
  • PII / GDPR: a decision recorded per aggregate (forgettable payload vs. crypto-shredding vs. no PII), deletion path tested end-to-end.
  • Snapshots: trigger documented; "delete all snapshots, system still works" verified in CI.
  • Rebuild cost: cold rebuild time of the largest projection measured on production-sized data, within deploy-window tolerance.
  • Store choice: backup, restore, and point-in-time recovery rehearsed for the actual event store — not assumed because "it's just Postgres."
  • Onboarding: a new engineer can find an ADR explaining which aggregates are event-sourced and why, run a local replay, and knows the difference between a domain event and an integration event in this codebase.

How it evolves in a codebase

  1. Day one. One event-sourced aggregate, hand-rolled on Postgres with an events table and a unique (stream_id, version) index. Projections are inline SQL views. Life is good for 3–6 months.
  2. First schema change. Someone adds a field to an event payload, deploys, and old events deserialize wrong. This forces a versioning convention and the first upcaster.
  3. Read model gets slow. The team builds its first async subscription with a checkpoint table. Eventual consistency starts showing up in QA tickets, and the team retrofits idempotency and a rebuild runbook.
  4. The painful migration, 12–24 months in. An event needs renaming or splitting, a GDPR request lands with PII everywhere, or a cold rebuild is needed in production and nobody knows how long it takes. Teams that planned for versioning, forgettable payloads, and partitioned rebuilds glide through. Teams that didn't roll back to CRUD for that aggregate, or spend a quarter on a copy-and-transform migration — after which they take event design seriously and the pattern starts paying back.

Further reading

  • Greg Young — "A Decade of DDD, CQRS, Event Sourcing" — the originator's retrospective; calibrates expectations on what the pattern is actually good at.
  • Mathias Verraes — "Eventsourcing Patterns: Crypto-Shredding" — short, precise treatment of the canonical GDPR mitigation.
  • Oskar Dudycz — "How to deal with privacy and GDPR in event-driven systems" — the most balanced write-up on forgettable payloads vs. crypto-shredding, including the legal caveats.
  • Marten documentation — Event Store and Projections — even outside Marten, the clearest reference on inline vs. async projection trade-offs on Postgres.
  • "Scaling Event Sourcing at Jet" — concrete numbers and design choices from a real high-volume system, especially good on partitioning projections.
  • Microsoft — Event Sourcing pattern (Azure Architecture Center) — a neutral, framework-agnostic reference.
