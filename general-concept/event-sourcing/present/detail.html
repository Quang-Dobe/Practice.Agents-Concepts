Detail — the deep dive

◑ ~9 min read ✎ What · Where · When · How · Why

What it is

Event sourcing is a persistence pattern where the true state of a system is a totally-ordered, immutable, append-only sequence of domain events. Any state you can query is a deterministic fold over that sequence. Writes produce events; reads consume projections of events; events themselves are never updated or deleted.

  • Core idea. The log is the source of truth. Every "current value" is derived, on demand, from the log.
  • Never edited. Events are immutable facts, named in the past tense (OrderPlaced, ItemRemoved).
  • Family. Named by Greg Young around 2006, it grew out of Domain-Driven Design — it's the persistence half of what DDD calls the aggregate.

The core building blocks

Event
An immutable record of something that already happened. Carries a payload, a stream id, a stream version, a global position, an event id, and a timestamp.
Stream
The per-aggregate sequence of events, identified by an id like order-7. Each event has a monotonically increasing stream version (0, 1, 2, …).
Event store
The database that persists streams. Exposes at minimum appendToStream(streamId, expectedVersion, events) and readStream(streamId, fromVersion).
Aggregate
The in-memory domain object, loaded by replaying its stream. New commands produce new events appended to the same stream.
Command
An intent to change state (PlaceOrder). The aggregate validates it and either emits events or rejects it.
Projection / read model
A materialized view derived from one or more streams, optimized for queries, rebuildable from position 0.
Subscription
A long-lived reader that pulls events from the store in order and feeds projections or other handlers.
Snapshot
An optional cached aggregate state at version N, so replay can start from N instead of 0.
Upcaster
Code that transforms an old event payload into the current schema at read time.

Event sourcing sits in the family of log-oriented persistence:

  • Alongside write-ahead logs (Postgres WAL, RocksDB), distributed commit logs (Kafka, Pulsar), and CRDT operation logs — but it's distinct from each.
  • A WAL is an implementation detail of a row store, not a domain model.
  • Kafka is transport with retention, typically without per-aggregate concurrency control.
  • Its closest cousin is CQRS — independently useful, but it pairs naturally, because event sourcing already separates the write model (events) from the read model (projections).

Where it lives

Event sourcing lives at the persistence layer of a service — not on the wire. The event store replaces, or sits alongside, a relational database for that service's write side.

  • Projections may live in the same store, in a separate query database (Postgres, Elasticsearch, Redis, ClickHouse), or both.
  • Cross-service events are usually integration events a translated, deliberately smaller subset of a service's internal domain events, published so aggregate internals don't leak to other teams — not the raw domain events themselves.

Where you'll typically encounter it:

Financial / fintech

Stripe-like ledgers, exchange trading engines, payment processors.

Insurance and claims

Policy lifecycle, claims adjudication where every decision must be defensible years later.

Logistics and supply chain

Shipment workflows where every scan, exception, and handoff is itself the data.

Healthcare records

EHR systems where regulators care what the chart said at a given moment.

Gaming / collaborative editing

Multiplayer state where deterministic replay is needed for debugging or rollback.

Tooling by role:

Dedicated event stores

KurrentDB (formerly EventStoreDB), AxonServer.

Library on a relational DB

Marten (Postgres, .NET), Eventuous (.NET), Axon Framework (JVM), Commanded (Elixir/Postgres), EventFlow (.NET), node-event-storage.

Roll-your-own

Postgres with an events table plus a unique index on (stream_id, version); DynamoDB with a conditional PutItem; MongoDB with a versioned document per stream.

Projections & schema tooling

A SQL view for simple reads; Kafka Connect or Debezium to a warehouse; Redis or Elasticsearch for low-latency reads; JSON Schema / Avro / Protobuf plus hand-written upcasters for evolution.

When to use it

✓ Reach for it when

  • The audit trail is a hard requirement, not a nice-to-have.
  • Domain experts naturally describe the system as business events ("when a shipment is dispatched…").
  • You expect to add read models or analytics later and want to backfill from history, not a separate ETL pipeline.
  • Reproducing production bugs by replaying real events would be high value.
  • Multiple consumers care about why state changed, not just its current value.

✕ Skip it when

  • The domain is fundamentally CRUD: admin screens, user preferences, CMS-style content.
  • You have hard "right to be forgotten" requirements with no appetite for crypto-shredding.
  • The team is unfamiliar with DDD, async messaging, and eventual consistency — shallow adoption gets punished.
  • The data has no historical value and disk is already a cost concern — events accumulate forever by default.

A little history

The idea predates the name: double-entry bookkeeping (15th century) is event sourcing on paper, and write-ahead logs use the same trick internally. Greg Young formalized it for application code around 2005–2006 in the DDD community, partly as a reaction to the information loss that came with ORM-driven, row-overwrite CRUD. The mid-2010s rise of Kafka popularized "log as source of truth" thinking and made the pattern more approachable — teams already had log-shaped infrastructure.

How it works

Walk a single command through the lifecycle, using the shopping-cart example from the overview — a user removes item B from cart 7:

  1. Load. The handler calls eventStore.readStream("cart-7") and gets the ordered events at versions 0 and 1.
  2. Fold. It rehydrates a Cart aggregate by applying each event to an empty instance. The aggregate is now in memory at stream version 1.
  3. Decide. The handler calls cart.removeItem("B"). The aggregate checks the invariant (the item exists) and produces a proposed event — nothing is saved yet.
  4. Append. The handler calls eventStore.appendToStream("cart-7", expectedVersion: 1, [ItemRemoved B]). The store accepts only if the current head of cart-7 is still at version 1.
  5. Conflict or commit. If another writer appended first, the head is now version 2 and the store rejects with a concurrency exception; the handler retries the whole load-decide-append cycle. If accepted, the event lands at version 2 with a fresh global position.
  6. Propagate. A subscription tails the store from its last position and pushes the new event to projection handlers. Other consumers — search index, analytics, integration outbox — receive it independently.
  7. Acknowledge. Each projection persists a checkpoint so it can resume after a crash without losing or double-counting events.

Internally, an event store is just an append-only table. A typical Postgres-based version:

events(global_position BIGSERIAL, stream_id TEXT, version INT,
       event_type TEXT, payload JSONB, metadata JSONB, occurred_at TIMESTAMPTZ,
       UNIQUE(stream_id, version))

The unique index on (stream_id, version) is what gives you optimistic concurrency letting writes proceed without a lock, then rejecting one if two writers targeted the same version for free — two competing inserts at the same (stream_id, version) cannot both succeed.

Snapshots: skipping the long replay

When a stream gets long — say, an account with around 50,000 events — replay-from-zero becomes a latency problem. The fix: periodically write a snapshot of the aggregate state and the version it represents. On load, fetch the latest snapshot, then read only the events after it. Common triggers: every N events, every N minutes, or only once measured replay time crosses a threshold. Snapshots must always be rebuildable — never let one become the source of truth.

Projections and idempotency

Two projection flavors exist. Inline projections update in the same transaction as the append — strongly consistent, but only work when the projection lives in the same database (Marten supports this on Postgres). Async projections update via a subscription — eventually consistent, but they scale to external stores. Async is the default, and the source of the eventual-consistency tax.

  • Subscriptions deliver at-least-once: the same event can arrive twice after a crash or rebalance.
  • Projections handle this by storing the last processed global position per projection, in the same transaction as the update, and skipping anything at or before that checkpoint.
  • Naturally idempotent updates (SET status = 'shipped') are fine too — duplicate writes are no-ops.

Schema evolution — five tactics, in order of rising cost

  1. Additive only. Add optional fields; old consumers ignore them. Cheapest, works for most changes.
  2. Versioned event types. OrderPlacedV2. Old handlers stay; a new handler is added for V2.
  3. Weak schema. Deserialize into a tolerant shape (dictionary, dynamic) and let the aggregate cope.
  4. Upcasting. On read, transform V1 → V2 → V3 so the aggregate only ever sees V3. Chain upcasters; never jump versions.
  5. Copy-and-transform. Rewrite the whole stream into a new one with new shapes. Expensive, last resort, breaks ordering with prior history.

Common failure modes

✕

CRUD events

Emitting CartUpdated { state: ... } instead of ItemAdded / ItemRemoved. You pay the full cost of event sourcing and get none of the benefit — the history carries no meaning.

⚠

Fat events

Stuffing entire denormalized payloads into events so projections "don't need joins." Schema evolution becomes a nightmare and PII leaks everywhere.

✕

Replay cliff

A read-model rebuild on a 200-million-event store takes 14 hours and blocks a deploy. Cause: no checkpointing, no parallel projection workers, no snapshots.

⚠

Hot stream contention

A single aggregate — a popular product, a global counter — gets concurrent commands and every write loses the optimistic race. Cause: the aggregate boundary is modeled too coarsely.

⚠

Projection drift

A projection's code changed but the projection was never rebuilt — the read model now disagrees with the events. Cause: no rebuild discipline, no versioned projection name.

⚠

Lossy upcaster

Upcasting V1 → V2 invents a default value for a new field, and later business logic assumes that value is real. Cause: treating upcasting as a free lunch.

✕

GDPR collision

A "delete this user" request arrives and the user's email is embedded in 40,000 events across 8 streams. Mitigations: store PII outside the event store and reference it by id (forgettable payloads), or encrypt per-user fields with a key you can shred (crypto-shredding) — though EU regulators have argued encrypted personal data is still personal data, so this is not unambiguously compliant.

✕

Broker confused with store

Treating Kafka topic retention as the source of truth, then losing data when retention expires. Kafka is transport; an event store is durable history.

Why it exists

Three forces drive it:

  • Information loss. Row-overwrite CRUD throws away exactly the data — the history of change — that businesses increasingly care about.
  • Separation of concerns. Write-side invariants and read-side query shapes have different lifecycles and scaling profiles; stuffing both into one normalized schema makes both worse.
  • Debuggability. Distributed systems are easier to reason about when state is a function of an ordered input than when it's a graph of mutually-updating rows.

The obvious alternative — keep a history table next to your tables — fails for a structural reason: that history is derived from the writes, not the source of them. The moment the application has a bug, the live table and the history table can silently disagree.

Optimistic concurrency on stream version, rather than pessimistic locking on a row, is the second non-obvious choice. It lets writes scale horizontally per aggregate while still giving each aggregate strict serializability — the consistency model the domain actually needs. Checking expectedVersion on every append is the deliberate, minimal amount of coordination needed to keep concurrent writers honest without taking a lock up front.

Why it matters now

  • KurrentDB (formerly EventStoreDB, v24.10+) and Marten 7 on Postgres are both stable, well-documented options for .NET teams.
  • Regulatory pressure — PSD3, DORA, evolving AI-act audit requirements — is making "what did the system know, and when" a first-class engineering requirement in finance and healthcare.
  • LLM-assisted debugging makes a replayable event log more valuable: agents can re-run scenarios deterministically.
  • The pattern is not winning the CRUD market and never will, but it's firmly established wherever history is the product.
