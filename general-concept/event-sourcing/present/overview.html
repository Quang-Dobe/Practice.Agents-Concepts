Overview

◔ ~3 min read ✎ intuition-first

A normal database overwrites old values on every update, so history disappears the moment you write. Event sourcing keeps every change as a fact and rebuilds current state by replaying those facts in order.

ⓘ

In 30 seconds

Instead of one orders row that gets overwritten, the source of truth becomes an append-only log of facts: OrderPlaced, ItemAdded, OrderPaid, OrderShipped. The current state of an order is a value you compute by folding combining a sequence of events, in order, into one current value those events together — not a row you read directly. Reach for this when how the data got to its current shape matters as much as the shape itself: audits, financial ledgers, regulated workflows, bug-hunting by replay.

The mental model

Think of your bank account. Your bank does not store one row that says balance: $1,432.18 and overwrite it every transaction. It stores a ledger — a list of entries — and the balance is just the sum of the ledger. If a transaction is disputed, the bank does not edit the past; it appends a correcting entry instead. Yesterday's balance is still recoverable by adding up entries only up through yesterday, and next month's audit is trivial because nothing was ever overwritten.

Event sourcing applies that ledger discipline to any entity in your system, not just money. An Order is no longer a row — it is a stream of events. The table you actually query is a projection a cached, rebuildable view derived by folding a stream of events, not the source of truth.

A concrete case: a shopping cart. In plain CRUD, adding item A, adding item B, then removing B leaves you with one fact — the cart contains [A]. You cannot answer "did the user briefly consider B?" — that fact was overwritten. Event-sourced, the same actions leave three events: ItemAdded A, ItemAdded B, ItemRemoved B. Folding them still gives you [A] as the current state — but you can also answer what got abandoned, which is useful for analytics, fraud detection, and recommendations.

What it is not

⚠

Common mix-ups

  • Not an audit log bolted onto CRUD. An audit log is a derived sidecar; here, the events are the database.
  • Not CQRS. CQRS separates read and write models. It pairs well with event sourcing but is a distinct idea.
  • Not message queues / Kafka-as-a-bus. A broker moves events between services; an event store is the durable source of truth for one service's own state.
  • Not "just append rows and never delete." Soft deletes alone give you no replay, no projections, no queries against a past point in time.

When to reach for it — and when not to

✓ Reach for it when

  • You're building financial ledgers, billing, or double-entry accounting — every change must be defensible.
  • You're in a regulated domain (healthcare, insurance, trading) where auditors ask "what did the system know at 14:02?"
  • The domain has complex behavior over time — order workflows, claims processing, multi-step approvals.
  • You expect to add new read models later and want to rebuild them from history instead of backfilling.
  • Reproducing production bugs by replaying a real event stream would be valuable.

✕ Skip it when

  • It's a simple CRUD admin screen, settings page, or content management system — the complexity tax isn't worth it.
  • You have hard "right to be forgotten" requirements with no appetite for crypto-shredding.
  • Your team is new to domain-driven design and distributed systems — missteps here are expensive.
  • The data has no historical value worth its storage and complexity cost.

Key vocabulary

Event
An immutable, past-tense fact (OrderPlaced) — never a command or an intent.
Event store
The append-only database that holds events, ordered per entity.
Stream
The ordered sequence of events for one entity — one order, one account.
Aggregate
The domain object whose state is rebuilt by folding its stream.
Projection / read model
A materialized view derived from events, optimized for queries.
Replay
Recomputing state or a projection by reading events from the start.
Snapshot
A cached state at version N so replay doesn't always start from event 1.
CQRS
Command Query Responsibility Segregation — a common companion pattern, not the same thing.
Upcaster / event versioning
Code that migrates old event shapes forward as your schema evolves.
