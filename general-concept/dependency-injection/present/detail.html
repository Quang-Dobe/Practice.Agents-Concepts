What it is

Dependency Injection (DI) is a technique where a component's collaborators are supplied by an outside party, the injector, instead of being built or looked up by the component itself.

  • Needs are public. The component declares its dependencies in its contract: constructor parameters, settable properties, or method parameters.
  • Building moves out. Assembling the object graph the tree of objects and the objects they depend on moves to one place outside the component, the composition root.
  • A case of IoC. DI is a specific case of Inversion of Control. The control being inverted is the acquisition of dependencies.
  • Pairs with DIP, but does not need it. DI makes the Dependency Inversion Principle easy, because the injector can hand over any implementation of an abstraction. Injecting a concrete class or a plain function is still DI.

The core building blocks

Service (dependency)
Any object or function a component needs: a repository, clock, HTTP client, logger.
Client (consumer)
The component that receives the service. Its constructor signature is its list of needs.
Injection point
Where the service enters the client. Fowler (2004) named three: constructor (PicoContainer), setter (Spring) and interface injection (Avalon). Interface injection is mostly historical; method injection (passed per call) replaced it in practice.
Composition root
The single place near the entry point (main, Program.cs, the application factory) where concrete types are chosen and the graph is assembled.
Injector
Whatever runs the composition. Either hand-written code, which Mark Seemann calls Pure DI (formerly "Poor Man's DI"), or a DI container that builds the graph from registrations.
Registration
A container entry mapping a service key (usually a type, sometimes type plus name/key) to a recipe (implementation type, factory delegate, or pre-built instance) and a lifetime.
Lifetime / scope
The rule for when the injector reuses an instance, when it makes a new one, and who disposes it. Common set: singleton, scoped (per request or unit of work), transient.

Its siblings: other ways code gets its collaborators

DI belongs to the family of dependency acquisition strategies. Each answers "how does this code get its collaborators?" differently:

In functional programming the same idea shows up as partial application, the Reader monad, or Scala's given/using context parameters.

Where it lives

DI is not a layer. It is an application-composition concern that lives in two places:

  1. Constructor signatures across the codebase. Each class states its needs here.
  2. The composition root at process startup. The graph is built here.

A container is an in-process library with no network or storage part. Web frameworks plug it into the request pipeline: they open a child scope a short-lived container view that owns its own instances and disposes them when it ends per HTTP request and resolve controllers or handlers from it. So DI touches the application layer and the framework boundary, not transport or persistence.

Where you typically meet it

ASP.NET Core / .NET Generic Host

Microsoft.Extensions.DependencyInjection is built in. Controllers, middleware, hosted services and Razor components all resolve through it. The templates register more than 250 framework services by default (docs).

Spring Framework / Spring Boot

The ApplicationContext is a DI container; IoC was Spring's founding feature. Since Spring 4.3, a class with a single constructor gets constructor injection with no @Autowired (Spring blog).

Angular

Hierarchical injectors: an ElementInjector tree follows the DOM, and an EnvironmentInjector tree handles app-wide providers. The inject() function (Angular 14+) supplements constructor injection (angular.dev).

Android

Dagger 2 and Hilt generate the wiring code at compile time, with no runtime reflection (Dagger README).

FastAPI

Depends() injects per-request dependencies into path-operation functions, a form of method injection.

pytest

Fixtures are DI keyed by parameter name. The test declares db, and pytest builds and tears down the db fixture.

Ecosystem and tooling

  • Runtime (reflection-based) containers: Microsoft.Extensions.DependencyInjection, Autofac (.NET); Spring IoC, Google Guice (JVM); NestJS, InversifyJS, tsyringe (TypeScript); dependency-injector (Python); Uber dig/fx (Go).
  • Compile-time / code-gen injectors: Dagger 2 and Hilt (JVM/Android); Google Wire (Go; the repo was archived in August 2025 as feature-complete); source-generator containers in .NET; Spring Boot 3's AOT processing, which precomputes bean definitions for GraalVM native images.
  • Standards: JSR-330 (javax.inject, final release October 2009, co-led by Rod Johnson of SpringSource and Bob Lee of Google), now jakarta.inject. Jakarta CDI builds scopes and lifecycle on top of it.
  • Graph validation: .NET ServiceProviderOptions.ValidateScopes / ValidateOnBuild; Spring Boot's startup failure on circular references (default since 2.6); Dagger's compile errors.

When to use it

✓ Reach for it when

  • Code touches slow or non-deterministic resources (DB, network, clock, randomness, filesystem) and you want fast, isolated unit tests.
  • The implementation varies by environment, tenant, or feature flag, and you want that choice in one place.
  • Several components should share one instance with a managed lifetime: a connection pool, HttpClient, or cache.
  • Per-request state (unit of work, current user, DB transaction) must reach many components without threading it through every method.
  • Your framework is built around a container (ASP.NET Core, Spring, Angular, NestJS). Fighting it costs more than using it.

✕ Skip it when

  • It is a short script or CLI where main builds two objects. Use plain functions with arguments.
  • The "dependency" is a value object or pure function (Money, slugify). Nothing to swap, no lifetime to manage.
  • You would add a single-implementation interface to every class just to mock it. Inject the concrete class, or test against a real in-memory implementation.
  • You would add a container to a small or medium app with no framework container. Pure DI gives compile-time checking and readable wiring for free.
  • The language idiom resists it. Idiomatic Go wires by hand in main; Python tests often use monkeypatch for one-off seams.

A little history

In the late 1990s, enterprise Java either called new on concrete collaborators, used GoF Singletons, or looked them up through JNDI (EJB 2's service-locator style). All three tied business logic to infrastructure, so testing meant running inside an application server. Lightweight containers were the answer:

  • ~2003: Apache Avalon (interface injection), then PicoContainer (constructor) and Spring (setter).
  • January 2004: Fowler's article coins "Dependency Injection" to set it apart from "IoC" (too generic) and Service Locator.
  • 2007: Guice. 2009: JSR-330.
  • 2010: Seemann, "Service Locator is an Anti-Pattern".
  • 2012: Dagger; Google's Dagger 2 in 2015.
  • 2016: ASP.NET Core ships a container in the box.

DI went from an opt-in library to a default platform feature.

How it works

Pure DI: just ordinary code

The composition root calls constructors in dependency order and keeps shared instances in local variables:

def compose(cfg) -> App:
    pool    = ConnectionPool(cfg.db_url)          # "singleton": one local, reused
    clock   = SystemClock()
    def handle_request(req):                       # "scoped": built per request
        uow   = UnitOfWork(pool)
        repo  = OrderRepo(uow)
        svc   = OrderService(repo, clock)
        return OrderController(svc).handle(req)
    return App(handle_request)

A container automates exactly this

A typical reflection-based container (this matches Microsoft.Extensions.DependencyInjection, Spring and Guice in broad strokes) runs this lifecycle:

  1. Register. The app adds descriptors (service key → recipe, lifetime) to a mutable collection.
    • In .NET, registering the same key twice: the last one wins for a single resolve, while IEnumerable<T> returns all of them in order.
    • Keyed registrations (.NET 8+ AddKeyed*, Spring @Qualifier, Guice binding annotations) tell apart several implementations of one type.
  2. Build. The collection is frozen into a lookup table and a root provider is created. The full graph can be validated now. In .NET's default host, ValidateScopes and ValidateOnBuild are both set to IsDevelopment() (source), so production builds skip these checks unless you opt in.
  3. Resolve T. Find the descriptor and check the lifetime cache. On a miss, select a constructor: .NET picks the one with the most parameters it can resolve, and throws if two are equally good (docs). Then resolve each parameter recursively, depth-first. A "currently resolving" stack catches cycles and fails with a circular-dependency error.
  4. Construct and cache. Call the constructor. Singletons are cached in the root, scoped instances in the current scope, transients nowhere. Every IDisposable the container creates is recorded by the scope that created it.
  5. Compile the plan. Reflection is expensive, so containers cache a per-service resolution plan (a call site .NET's name for the cached recipe of how to build one service) and may compile it to a delegate. After warm-up, a resolve costs about a few dictionary lookups plus the constructor calls.
  6. End the scope. When the request ends, the framework disposes the scope, which disposes its tracked instances in reverse creation order. Singletons are disposed only when the root provider is disposed at shutdown.

Scopes nest inside the root

The one rule that governs lifetimes

ⓘ

Lifetime invariant

A component may depend only on components whose lifetime is equal to or longer than its own.

  • A singleton may take a singleton.
  • A scoped component may take a scoped component or a singleton.
  • Break the rule and the longer-lived object traps the shorter-lived one. Seemann calls this a captive dependency a short-lived object kept alive, and reused, by a longer-lived one that holds it.

Compile-time injectors (Dagger, Wire) run steps 1–3 inside the build. They emit generated source equal to the Pure DI compose() above. Missing bindings and cycles become compile errors, and nothing is reflected at runtime.

Common failure modes

✕

Captive dependency

A singleton holds an EF Core DbContext or session; requests see each other's data or fail on concurrent use. Cause: the lifetime rule is broken, and scope validation is off outside Development.

⚠

Scoped service resolved from the root

Memory grows with no clear bound. Cause: the "scoped" instance lives in the root provider and is in effect promoted to singleton.

⚠

Transient IDisposable resolved from root or a long-lived scope

A leak until shutdown. Cause: the container tracks every disposable it creates, so it holds a reference to each one.

✕

Background worker takes a scoped service in its constructor

A stale or broken connection hours later. Cause: hosted services are singletons. Fix: inject IServiceScopeFactory and create a scope per unit of work.

✕

Missing registration

Production returns a 500 on the first call to a rarely used endpoint. Cause: graph validation runs only in Development, or not at all.

⚠

Circular dependency

Startup fails (BeanCurrentlyInCreationException, .NET "circular dependency was detected"). Cause: two services need each other, which usually means a responsibility is split in the wrong place.

⚠

Silent override

A test or library registration replaces the production implementation. Cause: last-registration-wins semantics.

⚠

Constructor over-injection

A class takes 8 or more dependencies. Cause: an SRP violation that DI makes visible but does not cause.

✕

Service locator in disguise

IServiceProvider or ApplicationContext is injected and queried inside methods. Cause: needs are hidden again, and failures move from startup to runtime.

✕

Reflection broken by trimming or obfuscation

A release build crashes on resolve (R8/ProGuard on Android, .NET trimming/Native AOT). Cause: types reached only through reflection were removed by the build tool.

Why it exists

DI separates using an object from choosing and building it.

  • Choosing is app-wide policy: which database, which environment, how long an instance lives.
  • Using is local mechanism.
  • Mixing them hurts: every policy change edits business code, every test pulls in real infrastructure, and lifetime decisions spread across hundreds of new calls.

Moving construction to one composition root gives you:

  • Substitutability: tests and environments swap implementations without touching consumers.
  • Explicit contracts: the constructor lists every need, so coupling shows up in code review.
  • Central lifetime management: pools, caches and transactions are created, shared and disposed by one owner.

Why it looks the way it does

Why injection rather than a locator? Fowler in 2004 treated the two as close alternatives and gave Service Locator "a slight edge" for application code, as more straightforward. The industry went the other way:

  • A locator call compiles whether or not the service is registered, so missing dependencies surface at runtime, inside a method, on whichever code path runs first.
  • Every class also takes a dependency on the locator API.
  • Constructor injection moves both problems to construction time, where a container (or the compiler, with Pure DI) can check the whole graph at once.
  • Microsoft's ASP.NET Core guidance now says outright to avoid the service locator pattern, including injected factories that resolve services at runtime.
  • Why type-keyed containers? The type system already describes the contract. Keying by type lets the container read a constructor signature and wire it with no per-class config. The cost is ambiguity when one type has several implementations, which is why keyed services and qualifiers exist.
  • Why do containers own disposal? The client did not create the dependency and may share it, so it cannot safely dispose it. "Whoever creates it disposes it" puts disposal on the injector, and that rule is what makes scopes necessary.
  • Why the move toward compile-time wiring? Reflection costs startup time and conflicts with AOT ahead-of-time compilation to native code, which strips types it cannot see being used and tree-shaking. Dagger made this trade on Android, where cold start and R8 matter. Spring Boot 3 AOT and .NET Native AOT apply the same pressure on the server.

Why it matters now

In 2026, DI is stable and built in on the JVM and .NET, and the default in Angular and NestJS. You rarely choose whether to use it; you choose how much container automation to accept. The live changes are at the edges:

  • Compile-time and AOT: serverless cold starts and native images favour generated wiring over reflection.
  • TypeScript: the standard decorators in TS 5.0 support neither parameter decorators nor emitDecoratorMetadata. Reflection-based TS containers (NestJS, InversifyJS) still depend on the legacy experimentalDecorators mode, and Angular has moved toward the inject() function.
  • Go: Wire's archival reinforces the idiom of hand-wiring in main.
  • LLM-backed systems: model clients, vector stores and tool executors are exactly the slow, non-deterministic dependencies DI was built to isolate. Injecting them is what makes deterministic fakes possible in evals and tests.

Open questions to verify in practice

  • Does my production build validate the container graph at startup? In .NET, ValidateOnBuild is off outside Development by default. What does a missing registration look like under load?
  • When the same service is registered twice (by me, a library, and a test override), which one wins, and do I get a warning?
  • Can I write a test that fails if any singleton transitively depends on a scoped service?
  • What do container build and first-resolve cost in cold-start time, compared with a Pure DI composition root?
  • Does my container survive trimming, Native AOT, GraalVM native image, or R8 without manual keep-rules?
  • At what constructor-parameter count does my team agree a class needs splitting, and can a linter enforce it?
