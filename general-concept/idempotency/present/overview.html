Overview

◔ ~3 min read ✎ intuition-first

Networks lie. Clients retry. Queues redeliver the same message more than once. If a "charge $50" call runs three times because of one flaky connection, the customer just lost $150, not $50.

ⓘ

In 30 seconds

Idempotency is the discipline of designing an operation so repeating it is safe: the second and third calls act as a no-op, not a second charge. It touches HTTP API design, message queues, payment systems, and database migrations all at once — which is why almost every senior engineer ends up learning it the hard way.

The mental model

Picture a light switch with two positions: up and down. Flick it up once and the light is on. Flick it up four more times and the light is still just on — nothing new happens. The action describes a destination, not a step.

Now picture a turnstile counter. Push it once and the count is 1. Push it four more times and the count is 5. Every push adds a new mark — the action describes a step, not a destination.

A real example: PUT /users/123 {"name": "Alice"} says "make user 123's name be Alice." Run it once or a thousand times — same end state. But POST /payments {"amount": 50} says "create a new payment of $50." Run it twice and there are two payments. That is why payment APIs hand you an idempotency key a unique token the client attaches to a request so the server can recognize a repeat instead of doing the work again: a token the client generates once so the server can say "I have seen this exact request before — here is the answer I gave last time" instead of charging the card again.

What it is not

⚠

Common mix-ups

  • Not the same as stateless. An idempotent operation can absolutely change server state — it just has to converge to the same state on retry.
  • Not the same as pure. A pure function has no side effects. Idempotent operations are allowed side effects; they just must not pile up more of them on repeat.
  • Not the same as safe. Safe methods don't touch state. Idempotent methods can — they just do so in a repeat-tolerant way.
  • Not automatic. Calling something PUT does not make it idempotent. Someone has to design the handler that way.

When to reach for it — and when not to

✓ Reach for it when

  • Any API endpoint a client might retry after a timeout or a 5xx.
  • Payment, billing, or "send email" operations where double-execution is user-visible damage.
  • Message-queue consumers, where duplicates are guaranteed eventually.
  • Database migrations and infra scripts you want to run repeatedly without breaking.
  • Webhook receivers — the sender retries until it gets a 2xx.

✕ Skip it when

  • Pure read endpoints — GET is already idempotent by definition.
  • One-off scripts a human runs and watches complete.
  • Append-only event logs where every call is meant to be a new entry (analytics events, for instance).
  • Internal trusted callers where retries can't happen and the extra machinery buys nothing.

Key vocabulary

Idempotent operation
Repeating it yields the same end state as running it once.
Idempotency key
A unique, client-supplied token used to deduplicate retried requests.
At-least-once delivery
A messaging guarantee where duplicates are expected; idempotent consumers are the fix.
Exactly-once semantics
The illusion of one-time processing — usually at-least-once delivery plus idempotency.
Safe method
An HTTP method that doesn't modify state at all: GET, HEAD, OPTIONS.
Side effect
Any change to state outside the function: a DB row, an email, a charge, a log entry.
Replay
Re-running the same request, intentionally or otherwise.
Deduplication window
The time span the server remembers a key has already been seen.
