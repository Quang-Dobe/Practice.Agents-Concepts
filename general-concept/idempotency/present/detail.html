Detail — the deep dive

◑ ~9 min read ✎ What · Where · When · How · Why

What it is

A function f is idempotent when f(f(x)) = f(x) for every x in its domain. Applied to a system: running an operation n times, for any n ≥ 1, leaves the system in the same observable state as running it once. The first call may still cause a real side effect — what idempotency forbids is piling up more state change on the calls after that.

Three near-neighbor ideas get confused with it:

Pure / referentially transparent
No side effects at all, and trivially idempotent. Idempotent operations are a bigger set: they may write to a database, send a webhook, or charge a card — as long as repeats converge to the same end state.
Stateless
A property of the handler, not the operation. A stateless server forgets between requests; an idempotent operation can still change persistent state.
Commutative
f(g(x)) = g(f(x)) — about reordering different operations. Idempotency is about repeating the same one. The two are independent; neither implies the other.

Operations split into two practical groups:

  • Naturally idempotent. The semantics carry the property on their own: PUT /users/123 ("make the user be this"), DELETE /users/123 ("ensure absent"), SET counter = 5, INSERT ... ON CONFLICT DO NOTHING, kubectl apply. These describe a target state, not a delta.
  • Made idempotent with a key. Delta-shaped operations — POST /payments, INSERT INTO orders, INCREMENT balance — need an outside mechanism to catch duplicates: a client-supplied idempotency key checked against a server-side idempotency store.

Idempotency belongs to the family of reliability primitives that exist because networks time out and partition. Its siblings: retries with backoff (the cause of duplicate requests), deduplication (the fix on the receiving side), conditional writes / optimistic concurrency (a tighter guarantee for concurrent edits), and transactions (an alternative for atomic multi-step writes inside one trust boundary). Serious production systems layer several of these together; idempotency is the one that crosses trust boundaries.

Where it lives

Idempotency is enforced at the application layer — whichever component owns the side effect. It can't be solved at the transport layer: TCP prevents duplicates only within one connection, and the moment a client retries on a fresh connection (a timeout, a load-balancer reset, a process restart), TCP has nothing left to say. That's also why messaging systems land on at-least-once delivery the realistic guarantee messaging systems give: duplicates happen, and the consumer must handle them: a broker cannot tell "ack lost" from "message lost," so it redelivers, and dedup gets pushed up to the consumer.

You'll run into it in these places:

HTTP APIs (RFC 9110)

PUT, DELETE, GET, HEAD, OPTIONS, TRACE are defined idempotent; POST and PATCH are not. The spec is about the server's intended effect, not the response — a retried request may legitimately get a different status code back (say, 200 then 204).

Payment APIs

Stripe, Adyen, Square, and Braintree all expose an Idempotency-Key header on create-charge endpoints. Stripe stores the response under that key and replays it for at least 24 hours.

Message brokers

Kafka's enable.idempotence=true (default since 3.0) dedups per-partition on the producer side; consumer-side dedup is still the application's job. SQS, RabbitMQ, NATS, and Pub/Sub all document at-least-once as the real guarantee.

Database upserts

INSERT ... ON CONFLICT, MERGE, REPLACE INTO, and Redis SETNX turn "create or no-op" into one atomic statement.

Kubernetes controllers

Every Reconcile() must be idempotent — controllers loop and re-run on every event. A non-idempotent reconciler produces drift, duplicate resources, or thrash.

Terraform / Pulumi / CloudFormation

plan and apply run repeatedly against the same desired state. Providers that get idempotency wrong throw "resource already exists" on retry.

When to use it

✓ Reach for it when

  • A client may retry across a network boundary you don't control — browser, mobile app, partner integration.
  • You consume from an at-least-once queue: Kafka, SQS, Pub/Sub, RabbitMQ — essentially all of them.
  • The side effect is user- or money-visible: a charge, refund, email, SMS, inventory change, account creation.
  • You build a webhook receiver — senders retry until they get a 2xx, so duplicates are guaranteed.
  • You run a reconciler against a desired-state model: operators, IaC, GitOps.
  • A human can double-click a submit button.

✕ Skip it when

  • The operation is already naturally idempotent — adding a key to a true GET or PUT rarely earns its keep.
  • The endpoint is append-only by design (analytics events, audit logs) where every call is supposed to be a new entry.
  • Calls are internal, trusted, synchronous, and bounded — a retry budget and a metric can be cheaper than a dedup store.
  • The dedup window you'd need (months, indefinitely) makes storage cost unreasonable.

How it works

For naturally idempotent operations the mechanism is state convergence the handler reads the current state, diffs it against the requested state, and applies only the difference: the handler reads the current state, diffs it against the requested state, and applies just the difference — on the second call the diff is empty. kubectl apply, PUT /users/123, and Terraform all work this way.

For the keyed pattern — POST plus an Idempotency-Key — the lifecycle is a small state machine:

  1. Client generates the key. A UUIDv4 or ULID, created once and reused byte-for-byte on every retry.
  2. Request arrives. POST /resource with header Idempotency-Key: K and body B.
  3. Atomic acquisition. INSERT INTO idempotency (key, fingerprint, status='in_flight') ON CONFLICT (key) DO NOTHING — one round trip, one winner. The row now sits in-flight.
  4. Insert won. Execute the handler. On success, update the row to succeeded with the response cached. On failure, update to failed, also cached.
  5. Insert conflicted — row already exists. Three outcomes: a fingerprint mismatch returns 422 Unprocessable; a still-in-flight row returns 409 Conflict; a terminal row replays the cached response.

Key design points:

  • Client generates the key. A server-generated key defeats the purpose — the client needs a stable identifier to resend.
  • Atomic acquisition. The ON CONFLICT DO NOTHING upsert (or Redis SET key value NX EX ttl) is what stops two concurrent retries from both executing the handler.
  • Request fingerprint a SHA-256 hash of the canonicalized request body, used to catch a key reused with a different payload. A hash over the canonicalized body (and sometimes method + path) catches "same key, different payload" before it silently replays the wrong result.
  • Persist the response, not just the fact of execution. A replay must return the byte-identical status and body — including 4xx/5xx — so the client sees the same outcome every time.
  • TTL. 24 hours is the Stripe default and a reasonable start: long enough to outlast a retry storm, short enough to cap storage. Past the TTL, a retry with the same key is treated as brand new.

Conditional writes — If-Match: "<etag>" per RFC 9110 §13, or WHERE version = ? in SQL — are a related but distinct guarantee. They make an update idempotent against a concurrent modification rather than against retried delivery: two retries of the same If-Match request either both succeed (the ETag still matches) or both fail with a repeatable 412 Precondition Failed.

Common failure modes

✕

Non-atomic acquisition

Two retries both see "key absent" from a separate SELECT then INSERT, both pass, both execute — a classic check-then-act race.

✕

Storing the request before executing

A crash between the insert and the handler call leaves a permanent in_flight row; later retries get 409 forever. Cause: no recovery path for stuck records.

✕

Forgetting to persist 4xx/5xx

Replays of a request that originally failed validation execute the handler again. Cause: confusing "idempotent" with "successful."

⚠

TTL shorter than the longest plausible retry

A cron-driven retry after the window closes sees a fresh key and double-processes. Cause: TTL picked by storage cost, not by modeling retry behavior.

⚠

Mutable request bodies

The client adds a timestamp on retry, the fingerprint mismatches, the server returns 422 and the operation is now stuck. Cause: not freezing the payload at first attempt.

✕

Idempotent at the API edge but not the worker

The API dedups, then enqueues; the queue redelivers; the worker double-executes. Cause: treating "the API is idempotent" as enough when the real side effect happens downstream.

✕

Side effects outside the dedup transaction

The handler writes to the database inside a transaction but sends an email separately; the transaction retries and the email sends twice. Cause: no transactional outbox.

Why it exists

A network request has three possible outcomes, not two: success, failure, and unknown. A timeout is the third case — the client can't tell "server received and processed it, the ack got lost" from "server never got it at all." The only safe response to "unknown" is to retry; the only safe way to retry a side-effectful operation is to make it tolerant of duplicates. Idempotency is what turns an inherently three-valued outcome into a two-valued one: it worked, or it didn't, and asking again is free.

This connects to the Two Generals Problem and the FLP impossibility result: no asynchronous protocol can guarantee both delivery and non-duplication at the same time. Given that limit, a system either loses messages (at-most-once) or duplicates them (at-least-once). For anything that matters, the industry picks at-least-once and pushes deduplication up to the application — which is exactly what idempotency provides.

Why it looks the way it does

The obvious alternative to a client-supplied key is server-side fingerprinting — hash the body and dedup on that. It fails in two real cases:

  • A client may legitimately want to send the same payload twice — two identical refunds to the same customer for two real purchases — and the server can't tell them apart by content alone.
  • An idle retry with a mutated field (a fresh timestamp header) gets a different fingerprint and executes twice anyway.

A client-generated key sidesteps both problems: it hands the "is this a retry?" decision to the only party that actually knows the answer.

The other obvious alternative is a distributed transaction (two-phase commit) between client and server. That works inside one coordinated cluster, but breaks down across organizational and network trust boundaries — it needs both ends to join a coordinator's protocol, holds locks across round-trips, and degrades badly under a partition. An idempotency key is a cheaper, one-sided protocol: only the server holds state, the client just resends.

Why it matters now

  • Event-driven and serverless architectures. Lambda retries, SQS redeliveries, EventBridge replays, and Step Functions all assume the handler is idempotent — the default invocation model is at-least-once.
  • LLM-agent orchestration. Agents retry tool calls, fan out parallel attempts, and replay traces during evaluation. Tools without idempotency keys produce double-bookings and double-emails in agent demos with embarrassing regularity.
  • AI-assisted code generation. Generated handlers tend to look correct on the happy path and fail open under retries — one of the few correctness properties a human reviewer still has to hold in their head.

The concept itself isn't changing; the surface area where it bites is only getting bigger.
