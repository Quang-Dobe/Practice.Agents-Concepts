Practice — how it plays out for real

● ~10 min read ✎ best practices · anti-patterns · checklist

Where you'll meet it

In a typical SaaS backend, idempotency sits between the public API and the side-effect layer — the charge, the email send, the row insert. The reverse proxy retries on 502, the mobile client retries on timeout, the partner integration retries on a stale connection, and every one of those retries lands on the handler with the original key. In an event-driven system, it's non-optional: at-least-once delivery is the realistic guarantee on every major broker, "exactly-once" claims included — the consumer will see duplicates, and the only question is whether anyone noticed.

SaaS backend

Between the HTTP client and every third party you can't fully trust: payment gateway, SMS provider, identity provider, LLM endpoint.

Event-driven consumer

Kafka, SQS, EventBridge, or a Lambda trigger — at-least-once is the default invocation model, duplicates are guaranteed.

Infrastructure code

Terraform, Pulumi, Kubernetes operators, Ansible. Reconcile() runs on every event, sometimes hundreds of times per deploy.

Webhook receiver

The partner keeps retrying until it sees a 2xx — duplicates are guaranteed by design, not by accident.

Best practices

1

Make the client generate the key, and freeze it at first attempt

Do

Generate a UUIDv4 or ULID client-side before the first request, and reuse it byte-for-byte across every retry of that logical operation. Persist it locally if the operation might outlive a process restart.

Why

Server-generated keys are useless — the server can't recognize a retry it never saw. Regenerating per attempt defeats the whole mechanism.

Avoid

Letting an SDK auto-generate a fresh key on each retry, or deriving the key from fields that legitimately change (timestamps, nonces).

2

Acquire the key atomically — never check-then-act

Do

Use INSERT ... ON CONFLICT DO NOTHING (Postgres), SET NX EX <ttl> (Redis), or PutItem with attribute_not_exists (DynamoDB) — one round trip, one winner.

Why

Two concurrent retries during a network blip both see "key absent" from a separate SELECT then INSERT, both pass, both execute. This is the single most common cause of "we have an idempotency table and still double-charged."

Avoid

A SELECT followed by an INSERT in the same handler — even inside a transaction at READ COMMITTED. The gap is the bug.

3

Store a request fingerprint, not just the key

Do

Hash the canonicalized body (and ideally method + path) with SHA-256 and store it beside the key. On replay, compare fingerprints and reject a mismatch with 422 (IETF draft) or 400 (Stripe).

Why

Without this, a client bug that reuses a key with a different payload silently returns the wrong cached response — invisible until a customer notices they got someone else's refund.

Avoid

Using the body hash as the key itself — that breaks legitimate retries that carry a fresh timestamp or trace id.

4

Persist the full response, including failures

Do

Cache status code, headers, and body on success and on 4xx. Replay byte-identically.

Why

Clients tell "permanently rejected" apart from "transient, retry" by status code. If a replayed validation failure suddenly returns 201 because the handler ran again, the client can't reason about anything.

Avoid

Caching only on 2xx. A retry loop on a 422 will hammer the handler repeatedly and can eventually succeed against a transient condition that should have stayed rejected.

5

Pick a TTL longer than the slowest legitimate retry source

Do

Default to 24 hours (Stripe's well-tested choice). Stretch to 7 days for cron-driven replays or human-operated retry tools. Index the TTL column and sweep it with a background job.

Why

Too short and a delayed retry re-executes; too long and the dedup table grows unbounded, hurting insert latency on a hot index.

Avoid

5-minute TTLs (catch a websocket blip, miss everything else) and "forever" — a Postgres table nobody prunes for two years that ends up blocking every deploy.

6

Make the dedup write transactional with the business write

Do

For a database side effect, insert the idempotency row and the business row in the same transaction. For an external side effect (email, payment, webhook), use a transactional outbox write the idempotency row and an outbox row atomically, then let a separate publisher deliver the outbox row with its own dedup.

Why

A handler that commits the business row, then crashes before writing the idempotency row, double-executes on retry. The outbox is the only sane way to keep "we did it" and "we told the world" in sync.

Avoid

"Best-effort" dedup writes after the side effect — they lose exactly the race that matters.

7

Model the key as a state machine, not a boolean

Do

Track in_flight, succeeded, failed explicitly with timestamps. Return 409 while in_flight; replay the cached response on terminal states; sweep in_flight rows older than a safety window (e.g. 2× the handler timeout) back into a recoverable state.

Why

A handler crash mid-execution leaves an in_flight row forever. Without a sweeper that key is permanently bricked and the client gets 409 until the heat death of the universe.

Avoid

A single "exists" boolean — it can't tell "still running" apart from "finished" apart from "crashed."

8

Prefer naturally idempotent operations when you can choose

Do

Model APIs as PUT /resources/{client-supplied-id} instead of POST /resources. Use INSERT ... ON CONFLICT DO NOTHING for "create or no-op." Use kubectl apply-style reconciliation for infrastructure.

Why

No dedup store, no fingerprinting, no TTL — the data model itself absorbs the duplicate. Less code, fewer failure modes.

Avoid

Bolting an idempotency-key system onto an endpoint that should have been a PUT in the first place. The complexity compounds.

9

Use conditional writes for entity-level idempotency

Do

For updates, use If-Match: "<etag>" (HTTP) or WHERE version = ? (SQL) to make the update idempotent against a concurrent modification.

Why

Two retries of the same If-Match request either both match (succeed identically) or both miss (fail with a repeatable 412 Precondition Failed) — meaningful without a dedup table.

Avoid

Last-write-wins on retries — the second attempt clobbering an unrelated concurrent edit is silent data loss.

10

Dedup on the consumer, not just the producer

Do

In a Kafka/SQS consumer, derive a dedup key from the message (event id, business primary key, offset + partition) and check it against an idempotency store before applying side effects. Commit the offset only after the side effect is recorded.

Why

Kafka's idempotent producer stops duplicates from one producer session into one partition — it does not stop consumer-side duplicates from rebalances, replays, or an offset reset. SQS FIFO dedup windows are 5 minutes — nothing for a slow consumer.

Avoid

Trusting "exactly-once" claims at the broker layer and skipping consumer-side dedup entirely.

Anti-patterns to recognize

✕

"Every POST is idempotent because we use UUIDs"

A UUID in the body isn't an idempotency key unless the server actively dedups on it. Fix: an explicit Idempotency-Key header with server-side enforcement.

✕

Hashing the body as the dedup key

Breaks retries that mutate auxiliary fields (timestamps, trace headers) and conflates two legitimately identical requests into one. Fix: a client-supplied opaque key, plus a body fingerprint used only for validation.

✕

Different status code on replay

Returning 201 then 409 because "this already exists" makes the client treat a normal replay as an error. Fix: replay the exact original response.

✕

Idempotency at the edge, not the worker

The API dedups, enqueues a job, the queue redelivers, and the worker executes twice. Fix: dedup at the layer that owns the side effect — usually the worker, sometimes both.

✕

The Stripe-style key-reuse trap

Same key, different params — the server returns the cached original response. A customer meant to wire $500, was charged $50, and never knew. Fix: store a fingerprint, reject mismatches with 422/400.

✕

Bricked in-flight rows

The handler crashes mid-execution, the row is stuck in_flight, and every retry gets 409 forever. Fix: a sweeper that resets rows older than max_handler_runtime × 2.

✕

Side effects outside the dedup transaction

The transaction retries and an email sends twice. Fix: the transactional outbox pattern, or move the side effect inside the transaction where possible.

✕

TTL too short for the retry source

A cron retries 26 hours later, sees a fresh key, and double-processes. Fix: model the retry distribution and set the TTL to the 99.9th percentile.

Real-world usage patterns

Payment processors (Stripe, Adyen, Square)

A merchant calls POST /v1/charges with Idempotency-Key: <client-uuid>. The server stores the key with the response under a 24-hour TTL; replays return the exact same response, failures included. Reusing the key with different params returns 400 — protecting the client from its own bugs. Lesson: the cached response is part of the contract. Redesign the response shape without rotating keys, and you can replay a stale schema to a client that no longer understands it.

Kafka consumers in a financial ledger

A consumer reads payment.requested events, writes to a ledger, and commits the offset. Duplicates arrive on rebalance. The handler computes a dedup key as event.id and does INSERT INTO ledger (event_id, ...) ON CONFLICT (event_id) DO NOTHING RETURNING *; no returned row means skip the downstream side effects. Lesson: the dedup is the business write — a separate check-then-insert is the same race in a different costume.

Kubernetes controller reconciling external resources

A controller watches a DatabaseInstance CRD and provisions an RDS database. Reconcile() runs on every event — possibly hundreds of times during a deploy. It always checks RDS for an instance tagged k8s-uid=<crd-uid> before creating one. Lesson: the cloud provider's tag is the idempotency store — no separate database needed.

Webhook receiver for a payments partner

The partner retries until it sees 2xx. The receiver dedups on (partner_id, webhook_event_id) in Postgres with a 30-day TTL, and returns 200 immediately after persisting the event to an inbox table — actual processing happens async. Lesson: the inbox pattern decouples "did we receive it" from "did we process it."

Operational checklist

✓

Before you call it done

  • Monitoring: a dashboard for idempotency_hit_rate (replays / total requests), in_flight_age_seconds (p99), fingerprint_mismatch_count (should sit near zero), and dedup table row-count growth.
  • Failure handling: is there a sweeper for in_flight rows older than 2× the handler timeout, tested by killing a handler mid-execution in staging?
  • Failure handling: when the dedup store is down, does the API fail closed (reject) or fail open (process without dedup)? Document the choice — both are defensible, silence isn't.
  • Security: are keys opaque and unguessable across trust boundaries, and are lookups scoped by tenant so one tenant can't replay another's response?
  • Cost: dedup-table size × storage cost + index maintenance. A 1KB row × 10M requests/day × a 7-day TTL is 70 GB of hot data — plan the index and sweeper for it.
  • Onboarding: can a new engineer point to the exact line that performs the atomic acquisition?
  • Testing: is there an integration test that fires two concurrent requests with the same key and asserts exactly one side effect occurred?
  • Schema evolution: is the cached response schema versioned, so a replay after a deploy doesn't return a shape the client no longer parses?

How it evolves in a codebase

  1. Zero idempotency, then the first incident. A few POST handlers, no dedup, "we'll add it when it's a problem." It becomes a problem the first time a payment double-charges, a welcome email fires three times, or a partner's webhook fires a duplicate downstream.
  2. Per-endpoint, in-memory dedup. A Redis SETNX with a short TTL wired into a single handler. Works until a second handler needs it, the logic gets copy-pasted, and the in-memory store loses keys on restart.
  3. Migration to a shared, durable layer. Extract a middleware, pick a real store (Postgres for transactional co-location, Redis with a Postgres backstop for the hot path), define the state machine, build the sweeper. A multi-week project — it touches every write endpoint and every cached-response schema.
  4. End state. A shared library (or sidecar/middleware) enforces the contract uniformly, consumer-side dedup runs in every queue worker, and new endpoints default to naturally idempotent shapes — PUT with client-supplied ids. Idempotency is cheaper to design in than to retrofit; the retrofit cost grows faster than the endpoint count.

Further reading

  • Stripe — Designing predictable APIs with idempotency — the canonical engineering blog post; the lifecycle, the response cache, and the conflict semantics with production scars showing.
  • Stripe API Reference — Idempotent requests — the exact wire format and error behavior, useful as a spec when building your own.
  • IETF draft-ietf-httpapi-idempotency-key-header-07 — the current standardization effort; defines 422 for a fingerprint mismatch and 409 for an in-flight conflict.
  • RFC 9110 §9.2.2 — Idempotent Methods — the authoritative HTTP definition; clarifies that idempotency is about server-side effect, not the response.
  • Microservices.io — Transactional Outbox pattern — the standard fix for "side effect outside the dedup transaction."
  • Confluent — Exactly-Once Semantics in Kafka — what Kafka's transactional API actually guarantees, and what it doesn't (consumer-side dedup is still your job).
