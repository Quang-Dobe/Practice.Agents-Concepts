Overview

◔ ~3 min read ✎ intuition-first

Distributed databases copy data across many machines. When the network between those machines breaks — a partition a network split that stops some nodes from reaching others — you cannot give every client the newest correct data and keep every node answering. You have to pick one.

ⓘ

In 30 seconds

CAP Theorem says that during a partition, a distributed system must choose between staying correct (reject some requests) or staying up (answer every request, even with stale data). Partitions are not rare — they happen on real networks all the time — so every distributed system is making this choice, whether the team names it or not.

The mental model

Picture a bank with two branches, Hanoi and Saigon, sharing one account ledger by phoning each other after every transaction. Now the phone line cuts out.

A customer walks into the Saigon branch and asks to withdraw $500. The teller has two options:

  • Refuse the withdrawal until the line is back. The ledger stays correct everywhere — no risk of the same $500 leaving twice — but the customer leaves angry. This is CP.
  • Allow the withdrawal and write it down locally, planning to sync later. The customer is happy, but the two branches now disagree about the balance until they reconnect — and might find an overdraft when they do. This is AP.

There is no third door where the Saigon teller magically knows the Hanoi balance without a working phone line. That third door doesn't exist once you accept that phone lines — and networks — can drop.

What it is not

⚠

Common mix-ups

  • Not a permanent pick-two rule. The trade-off only bites during a partition. In normal operation you usually get all three properties at once.
  • Not the same as ACID. ACID is about transactions on one database. CAP is about behavior across many nodes when the network misbehaves.
  • Not the whole picture. PACELC extends it to cover latency-vs-consistency choices even when the network is healthy — that's a Detail-page topic.

When to reach for it — and when not to

✓ Reach for it when

  • You're choosing a database for a multi-region service and need to reason about isolated regions.
  • Stale reads are dangerous — payments, inventory, leader election — and you need to argue for CP behavior.
  • Downtime is unacceptable — shopping carts, social feeds, DNS — and you need to argue for AP behavior.

✕ Skip it when

  • You're running a single-node Postgres on one machine. No partitions, no CAP.
  • You're picking between SQL and NoSQL. CAP doesn't map cleanly onto that axis — plenty of NoSQL is CP and some SQL is AP-tuned.
  • You want a precise consistency model for one operation. CAP is too coarse; you want linearizability, causal consistency, or eventual consistency instead.

Key vocabulary

Consistency (C)
Every read returns the most recent write — formally, linearizability.
Availability (A)
Every non-failing node returns a non-error response to every request.
Partition tolerance (P)
The system keeps operating even when messages between nodes are dropped or delayed.
Partition
A network split that prevents some nodes from reaching others.
CP system
Sacrifices availability during a partition to stay consistent (e.g. ZooKeeper, etcd).
AP system
Sacrifices consistency during a partition to stay available (e.g. Cassandra, DynamoDB in default mode).
Tunable consistency
Real systems often let you pick C-vs-A per request, not once at install time.
